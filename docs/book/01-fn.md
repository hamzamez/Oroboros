# 1. `fn`

Everything in Oroboros is built from six things. This chapter is about one of them.

Every reduction shown below was produced by running the example. You can run them too:

```bash
go run ./cmd/oro -target=tutorial FILE.oro
```

`tutorial` is a target that exists to teach ([targets/tutorial.oro](../../targets/tutorial.oro)).
It spells arithmetic `+ - * /` so a chapter about `fn` is not also a chapter about module paths,
and it declares `f`, `g`, `h`, `x`, `y`, `z` as **primitives** — stand-ins for "something we know
nothing about", so reduction halts on them and an example can show a *shape* without showing an
implementation. A target is just a set of names, so a teaching target is a legitimate one.

---

## 1.1 A function is a value

```lisp
(fn (n) (* n n))
```

Read it as *"given `n`, produce `n * n`"*. `n` is a **parameter**; `(* n n)` is the **body**.

Nothing happens yet. On its own, a function reduces to itself:

```lisp
(fn (n) (* n n))            ⟶   (fn (n) (* n n))
```

## 1.2 Applying it

Put a function first in a list and give it arguments:

```lisp
((fn (n) (* n n)) 7)        ⟶   (* 7 7)
```

That step is called **β**. The parameter is replaced by the argument, everywhere it appears.

Notice what did *not* happen: `(* 7 7)` did not become `49`. **No primitive is ever evaluated.**
`*` is a name the target provides, so reduction stops there and `(* 7 7)` is the answer — it is
what gets emitted.

Several parameters work the same way:

```lisp
((fn (a b) (+ a b)) 2 3)    ⟶   (+ 2 3)
```

And none at all:

```lisp
((fn () (+ 1 2)))           ⟶   (+ 1 2)
```

`(fn () …)` is unusual-looking but it is the shape a program's entry point must have — a `main`
takes no arguments.

## 1.3 What can be a parameter

A parameter is a **name**. Names are generous:

```lisp
(fn (sub-total) (+ sub-total 1))    ⟶   (fn (sub-total) (+ sub-total 1))
(fn (ok?) (h ok? 1))                ⟶   (fn (ok?) (h ok? 1))
(fn (Δ) (* Δ 2))                    ⟶   (fn (Δ) (* Δ 2))
```

Hyphens are ordinary letters here, `?` and `!` are ordinary letters, and source is UTF-8 so `Δ` is
a name like any other. `+`, `<` and `empty?` are names too — there is no separate class of
"operators".

Three things a parameter may **not** be.

**A number.** `1` is a literal, not a name:

```lisp
(fn (1) (+ 1 1))
;; line 1: fn parameter must be a name, got 1
```

**The same name twice.**

```lisp
(fn (x x) x)
;; line 1: fn binds x twice; a parameter list may not repeat a name,
;;         because the second would silently shadow the first
```

**A qualified name.** `.` separates a module from a member, and a function cannot bind into a
module:

```lisp
(fn (a.b) (+ a.b 1))
;; line 1: a.b cannot be a parameter; a binder is a simple name,
;;         and `.` qualifies a module member
```

> Both of the last two were **accepted** until the day this chapter was written. `(fn (x x) x)`
> applied to `1` and `2` gave `2` and silently lost the `1`. Binding `f64.add` let a parameter
> shadow a module primitive, after which `((fn (f64.add) (f64.add 1.0 2.0)) 9.0)` reduced to
> `(9.0 1.0 2.0)` — applying a number to two arguments. Writing the tutorial found both, which is a
> reasonable argument for writing tutorials.

## 1.4 Bound and free

A name inside a body is **bound** if a `fn` around it binds that name, and **free** otherwise.

```lisp
(fn (n) (+ n (y)))          ⟶   (fn (n) (+ n (y)))
```

`n` is bound. `y` is free — and that is fine, because `y` is a primitive this target provides. A
free name is legal exactly when something can supply it: a primitive, or a definition.

When nothing can:

```lisp
(fn (n) (+ n q))
;; at the top level: q is not bound — it is not a parameter,
;;                   not a definition, and not a primitive on this target
```

That message is worth reading closely. It lists the three ways a name *could* have been fine. Most
of the time the answer is a typo; sometimes it is a missing `(use …)`; occasionally it is a name
this target genuinely does not have, which is the language telling you the program is not portable
to it.

## 1.5 Shadowing

An inner `fn` may reuse an outer name. The inner one wins, from there inward:

```lisp
(fn (n) (fn (n) (* n 2)))   ⟶   (fn (n) (fn (n) (* n 2)))
```

The `n` in `(* n 2)` is the **inner** one. The outer `n` still exists — it is simply unreachable
from in there, because the name is taken.

This is legal and occasionally useful, but if you are shadowing by accident it is a bug that reads
as correct code. Prefer distinct names.

## 1.6 The one that used to be hard

Here is a shape that breaks naive implementations of β:

```lisp
((fn (n) ((fn (m) (fn (n) (h m n))) n)) (x))
```

Read it slowly. The outer `n` is bound to `(x)`. That `n` is passed as `m`. And `m` is used inside
a `fn` that binds **another** `n`.

A careless substitution puts the outer `n` inside the inner binder, where it silently becomes the
*inner* `n` — two different variables merged because they share a spelling. That is called
**capture**, and it produces a wrong answer that looks plausible.

```lisp
⟶   (fn (n) (h (x) n))
```

Correct: `(x)` sits beside the binder as itself, and `n` still refers to the inner parameter.

You do not have to think about this. Underneath, a bound variable is not stored as a name at all —
it is stored as *"the parameter of the binder N levels out"*. Two variables cannot be confused by
sharing a spelling, because the spelling is not what identifies them. The names you write are kept
only so the emitted code reads nicely.

## 1.7 Arity is exact

```lisp
((fn (a b) (+ a b)) 1)
;; arity: (fn (a b) (+ a b)) expects 2 argument(s), given 1
```

There is no partial application. `(fn (a b) …)` is a function of two arguments, not a function of
one that returns a function of one. If you want that, write it:

```lisp
(fn (a) (fn (b) (+ a b)))
```

Those are different functions, and the difference is visible in what gets emitted.

## 1.8 Reduction happens inside functions too

Most languages leave a function body alone until it is called. Here, reduction goes **under** the
binder:

```lisp
(fn (n) ((fn (m) (* m m)) n))   ⟶   (fn (n) (* n n))
```

The inner application was reduced even though `n` is still unknown. This is the single most
important thing to understand about the language: **reduction is compilation.** Whatever is left
when reduction stops is the program that runs. Anything that reduces away has no runtime existence
at all.

That is why abstraction is free here. A helper function you define and use once does not appear in
the output — not because an optimiser removed it, but because reduction consumed it.

## 1.9 Functions as arguments

A function is a value, so it can be an argument:

```lisp
((fn (k n) (k (k n))) f 3)      ⟶   (f (f 3))
```

`k` was replaced by `f`, twice, and the result mentions no `k` at all. The higher-order function
vanished; only the work remains.

A function can also be a **result**:

```lisp
(fn (k) (fn (v) (* v k)))       ⟶   (fn (k) (fn (v) (* v k)))
```

This one reduces to itself, and the inner `fn` **survives into the output**. A surviving `fn` is an
*escaping closure* — it must exist at runtime, capturing `k`. The three real backends currently
refuse to emit one and tell you so. It is a limit worth knowing about: functions that vanish are
free, and functions that survive are not yet supported.

## 1.10 Legal, and still a mistake

These all reduce. None of them is what you meant.

**Shadowing a primitive.**

```lisp
(fn (+) (+ 1 2))            ⟶   (fn (+) (+ 1 2))
```

`+` is an ordinary name, so it can be a parameter — and now the `+` in the body is that parameter,
not addition. The result applies an unknown value to `1` and `2`. Legal; almost never intended.

**An unused parameter.**

```lisp
(fn (a b) a)                ⟶   (fn (a b) a)
```

Fine if deliberate. If `b` was supposed to be used, nothing will tell you.

**Assuming your work is duplicated.**

```lisp
((fn (n) (+ n n)) (h 1 2))  ⟶   (let (h 1 2) (fn (n) (+ n n)))
```

`n` appears twice, so a naive β would compute `(h 1 2)` twice. It does not: the argument is bound
once and shared. You did not ask for that and you cannot turn it off — the compiler decides,
because [it measured](../../gauntlet/results/wordcount-2026-08-14.md) that guessing wrong costs
615×.

**Assuming an effect can be moved.**

```lisp
((fn (n) (+ 1 2)) (shout 9))    ⟶   (let (shout 9) (fn (n) (+ 1 2)))
```

`n` is used **zero** times, so `(shout 9)` could have been dropped entirely — and it was not,
because `shout` has an effect. An impure argument is kept, exactly once, where it was written.
Pure arguments get dropped in the same position:

```lisp
((fn (n) (+ 1 2)) (f 9))    ⟶   (+ 1 2)
```

The difference between those two lines is the whole of the effect discipline.

## 1.11 `let` is `fn`

There is no separate binding form. `let` is spelled differently and means an application:

```lisp
(let (f 2) (fn (n) (+ n n)))
```

is the same term as

```lisp
((fn (n) (+ n n)) (f 2))
```

which is why the compiler's own output above is printed with `let`. One construct, two spellings —
and only one thing to learn.

---

## What to remember

- **A function is a value.** It reduces to itself until it is applied.
- **β replaces parameters with arguments**, and reduction continues *inside* function bodies.
- **Reduction is compilation.** What is left is the program; what vanishes never existed.
- **A parameter is a simple name** — not a number, not repeated, not qualified.
- **Free names must be supplied** by a primitive or a definition, or you get an error naming all
  three possibilities.
- **Arity is exact.** No partial application.
- **A function that survives reduction is a closure**, and closures are the current frontier.
