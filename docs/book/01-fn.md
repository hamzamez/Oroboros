# 1. `fn`

The book builds the language one brick at a time, and this is the first. A program is made of seven
kinds of thing ([spec/state.md §1](../spec/state.md)): a name, an integer, a numeral, a string,
`true` or `false`, a function, and an application of one thing to others. Five of those are
leaves. **`fn` makes a function, and application uses one; everything the language does, it does
with those two.** A block, a `loop`, a `case` and a module's definition are all, underneath, a `fn`
and an application, and later chapters show each being taken apart into them.

So this chapter is small in vocabulary and long in examples: one form, and every corner of it.

## How to read the examples

Each example is a file in [code/fn/](code/fn/), and what is printed under it is what the compiler
gave. Most are run with `oro`, which reduces a file's `export`s and prints what is left, in the
language's own notation:

```bash
go run ./cmd/oro -j -target=tutorial docs/book/code/fn/apply.oro
```

Three things about that line.

- **`export fn name() { … }`** is only scaffolding here. A file holds named things, `oro` prints
  the exported ones, and naming is [chapter 2](02-def.md). `export fn one() { e }` is a function of
  nothing whose body is `e`, so its output reads `fn() { … }` with what `e` became inside.
- **`tutorial` is a target that exists to teach**
  ([targets/tutorial.oro](../../targets/tutorial.oro)). It supplies arithmetic, and six names we
  know nothing about: `f` and `g` take one argument, `h` takes two, and `x()`, `y()`, `z()` stand
  for a value from outside. Reduction cannot look inside them, so they stay in the output and show
  its *shape*. It also has `shout`, which has a side effect, for §1.11.
- **A file whose name begins `no-` is meant to be refused**, and its refusal is printed. One the
  *reader* refuses, before any meaning is involved, ends in `.oro.txt`.

`go run docs/book/check.go docs/book/01-fn.md` re-runs every block in this chapter and compares.
Checked 2026-11-10.

## 1.1 A function is a value

```go
fn(n) { n * n }
```

Read it *given n, the value of n × n*. `n` is the **parameter**, the braces hold the **body**, and
the body's value is its last expression. There is no `return`.

<!-- file docs/book/code/fn/value.oro -->
```go
export fn square(n) { n * n }

export cube = fn(n) { n * n * n }

export fn make() { fn(n) { n * n } }
```

<!-- oro tutorial docs/book/code/fn/value.oro -->
```go
square =
fn(n) { n * n }
cube =
fn(n) { n * n * n }
make =
fn() { fn(n) { n * n } }
```

Nothing happened, and that is the point: **a function on its own is already a value**, like `7`.
It reduces to itself. Two things to notice.

- `fn square(n) { … }` and `square = fn(n) { … }` are the same declaration in two spellings. A
  named function is a name and a function; the function has no name of its own.
- `make` is a function whose value is a function. Functions can be made, passed and returned like
  any value, which is §1.8 and §1.9.

This is the λ of Church's λ-calculus (1936), `λn. n × n`, with the binder spelled `fn` and the body
in braces.

## 1.2 Applying it

Put arguments in parentheses after a function:

<!-- file docs/book/code/fn/apply.oro -->
```go
export fn one() { fn(n) { h(n, n) }(7) }

export fn two() { fn(a, b) { h(a, b) }(2, 3) }

export fn nullary() { fn() { h(1, 2) }() }

fn pair(a, b) { h(a, b) }

export fn named() { pair(2, 3) }
```

<!-- oro tutorial docs/book/code/fn/apply.oro -->
```go
one =
fn() { h(7, 7) }
two =
fn() { h(2, 3) }
nullary =
fn() { h(1, 2) }
named =
fn() { h(2, 3) }
```

That step has a name, **β**: the parameter is replaced by the argument everywhere it occurs in the
body, and the body is what remains.

```
fn(x) { B }(a)   ⟶   B with a for x
```

It is the only thing a function is for. In `one`, the function and its application are both gone
and `h(7, 7)` is left; `h` is the target's, so reduction stops there, and that is what would be
emitted.

- The thing applied need not be a name. `fn(n) { h(n, n) }(7)` applies a function written on the
  spot, as JavaScript's `(n => h(n, n))(7)` does.
- A function of no parameters is applied to no arguments, `fn() { … }()`. A program's `main` is
  one.
- `pair(2, 3)` reduced the same way: the name was replaced by its function first, then β.
  **Calling a function you defined leaves no call.**

## 1.3 What is computed, and what waits

<!-- file docs/book/code/fn/fold.oro -->
```go
export fn literal() { fn(n) { n * n }(7) }

export fn unknown() { fn(n) { n * n }(x()) }

export fn by_zero() { 7 / 0 }

export fn too_big() { 2^62 * 4 }
```

<!-- oro tutorial docs/book/code/fn/fold.oro -->
```go
literal =
fn() { 49 }
unknown =
fn() { n = x(); n * n }
by_zero =
fn() { 7 / 0 }
too_big =
fn() { 18446744073709551616 }
```

- **Integer arithmetic on literals is done now.** `7 * 7` is `49`, and `2^62 * 4` is
  `18446744073709551616`, past the machine's 64-bit word: an integer is an integer at any size,
  so `2^62 · 4 = 2^64` is as true as `7 · 7 = 49`, and the program would compute the same
  integer ([ADR 0156](../decisions/0156-an-integer-constant-is-an-element-of-z.md)).
- **Nothing else is.** `x()` is the target's, so `n * n` waits for run time. `f`, `g`, `h` and
  every host function wait the same way: only the host knows what they do.
- **A fold never changes an answer** ([ADR 0009](../decisions/0009-staging-preserves-results.md)),
  and `7 / 0` has none, so it is not folded. What reduction shows here is not what runs: compiled
  for a target, `7 / 0` is refused, since dividing by zero is not defined (chapter 6, §6.7).

`unknown` did something worth a second look. The argument `x()` was not copied into both places
`n` stands; it was bound once, as `n = x()`. §1.11 is about exactly when that happens.

## 1.4 Parameters

A parameter is a **name**: a letter or `_`, then letters, digits and `_`, with an optional final
`?`. Letters are Unicode's, and case distinguishes names without meaning anything.

<!-- file docs/book/code/fn/names.oro -->
```go
export fn greek() { fn(Δ) { Δ * 2 } }

export fn predicate() { fn(ok?) { h(ok?, 1) } }

export fn snake() { fn(sub_total) { sub_total + 1 } }

export fn cased() { fn(x1, X1) { h(x1, X1) } }

export fn ignored() { fn(_, b) { b } }

export fn both_ignored() { fn(_, _) { 7 }(1, 2) }

export fn spread_out() {
    fn(
        first,
        second,
    ) { h(first, second) }
}
```

<!-- oro tutorial docs/book/code/fn/names.oro -->
```go
greek =
fn() { fn(Δ) { Δ * 2 } }
predicate =
fn() { fn(ok?) { h(ok?, 1) } }
snake =
fn() { fn(sub_total) { sub_total + 1 } }
cased =
fn() { fn(x1, X1) { h(x1, X1) } }
ignored =
fn() { fn(_, b) { b } }
both_ignored =
fn() { 7 }
spread_out =
fn() { fn(first, second) { h(first, second) } }
```

- `_` is the parameter you do not intend to use, and it may appear more than once.
- A parameter list may run over several lines and end in a comma.

What a parameter may not be, each refused by the reader:

**A literal.**

**The same name twice.** Which argument would `x` be?

<!-- file docs/book/code/fn/no-twice.oro.txt -->
```go

```


**A qualified name.** `a.b` is member `b` of module `a`, and a function cannot bind into a module.

<!-- file docs/book/code/fn/no-qualified.oro.txt -->
```go

```

<!-- oro tutorial docs/book/code/fn/no-qualified.oro.txt -->
```

```

What a parameter may carry is **a set**, after `∈`: the parameter says which values it accepts,
and a result in parentheses after the parameters says which values the function gives. A function
written without a name carries them as one written with a name does, since the two differ only by
the name ([chapter 2](02-def.md)):

<!-- file docs/book/code/fn/claimed.oro -->
```go
export fn run() { fn(n ∈ Int) { n }(1) }

export fn digit_twice() { fn(d ∈ 0..9) (0..18) { d * 2 }(4) }
```

<!-- oro tutorial docs/book/code/fn/claimed.oro -->
```go
run =
fn() { 1 }
digit_twice =
fn() { 8 }
```

`Int` is the integers and `0..9` the integers from 0 to 9. A set is a **claim**: the compiler checks
that each argument is in its parameter's set and that the body gives a result in the result's set,
for every argument the parameter accepts, and refuses the program where it cannot. The tutorial
target shows the reduction alone; what a set is, and how a claim is checked on a real target, is
[chapter 6](06-integers.md)'s (§6.12).

And the body is always in braces. There is no `fn(n) n * n` and no arrow form:

<!-- oro tutorial docs/book/code/fn/no-body.oro.txt -->
```
oro: docs/book/code/fn/no-body.oro.txt: line 1: "n" where "{" was expected
```

An empty body is allowed, and its value is `()`, the empty tuple, which is what "nothing" is here:

<!-- file docs/book/code/fn/empty.oro -->
```go
export fn nothing() { }

export fn nothing_of(n) { }
```

<!-- oro tutorial docs/book/code/fn/empty.oro -->
```go
nothing =
fn() { () }
nothing_of =
fn(n) { () }
```

## 1.5 Bound and free

Inside a body, a name is **bound** if a `fn` around it has it as a parameter, and **free**
otherwise.

<!-- file docs/book/code/fn/free.oro -->
```go
export fn run() { fn(n) { n + y() } }
```

<!-- oro tutorial docs/book/code/fn/free.oro -->
```go
run =
fn() { fn(n) { n + y() } }
```

`n` is bound. `y` is free, and that is fine, because the target supplies it. A free name is legal
exactly when something supplies it. When nothing does:

<!-- file docs/book/code/fn/no-unbound.oro -->
```go
export fn run() { fn(n) { n + q } }
```

<!-- oro tutorial docs/book/code/fn/no-unbound.oro -->
```
oro: docs/book/code/fn/no-unbound.oro: in run: q is not bound — it is not a parameter, not a definition, and not a primitive on this target
```

The message lists the three things a name can be. Usually the answer is a typo; sometimes a
missing `use`; and sometimes the name is one this target does not have, which is the compiler
telling you the program does not run there.

Every name is checked, in code that is never called too:

<!-- file docs/book/code/fn/no-typo.oro -->
```go
fn never_called(n) { n + totl }

export fn run() { 7 }
```

<!-- oro tutorial docs/book/code/fn/no-typo.oro -->
```

```

## 1.6 Shadowing, and what a name really is

An inner `fn` may use a name an outer one already uses. From there inward, the inner one is meant.

<!-- file docs/book/code/fn/shadow.oro -->
```go
export fn twice() { fn(n) { fn(n) { n * 2 } } }

export fn thrice() { fn(a) { fn(a) { fn(a) { h(a, a) } } } }

export fn inner_wins() { fn(a) { fn(a) { a } }(1)(2) }

export fn a_primitive() { fn(h) { h(1, 2) } }
```

<!-- oro tutorial docs/book/code/fn/shadow.oro -->
```go
twice =
fn() { fn(n) { fn(n1) { n1 * 2 } } }
thrice =
fn() { fn(a) { fn(a1) { fn(a2) { h(a2, a2) } } } }
inner_wins =
fn() { 2 }
a_primitive =
fn() { fn(h) { h(1, 2) } }
```

- **The compiler renamed the inner parameters**, `n1`, `a1`, `a2`. The function you wrote and the
  one printed are the same function: which name a parameter has does not matter, only where it is
  bound and where it is used. That is **α-equivalence**, and it is why a name is called a *hint*.
  What comes out of reduction has its binders named apart along each chain of scopes, so that
  every later pass may identify a variable by its name
  ([ADR 0036](../decisions/0036-a-residuals-binders-are-named-apart.md)).
- `inner_wins` applies to `1`, then to `2`, and the answer is `2`: the inner `a`.
- **A parameter may shadow a name**, the target's `h` included. In `a_primitive` the body's `h`
  is the parameter, an unknown value applied to `1` and `2`.

**Not a name of the language's own.** `1 + 2` is an application of the name `+`, which J writes in
backquotes, `` `+` ``, like any name that is not an identifier. A parameter named `+` would make the
`1 + 2` in its body an application of the parameter, so `+` would no longer mean addition there, and
`if c { a } else { b }` would no longer be a choice under a parameter named `if`. A binder
introduces a fresh name, and renaming it with its uses changes nothing (α-equivalence); `1 + 2` is
no use of a variable, so a binder of `+` is refused, as a definition of one is:

<!-- file docs/book/code/fn/no-operator.oro.txt -->
```go
export fn an_operator() { fn(`+`) { 1 + 2 } }
```

<!-- oro tutorial docs/book/code/fn/no-operator.oro.txt -->
```
oro: docs/book/code/fn/no-operator.oro.txt: a binder in an_operator names `+`, which is the language's own: J's reader writes its constructs with these names (`a + b` is `+`, `if c { a } else { b }` is `if`), so the binder would capture each of them in its scope. A binder introduces a fresh name; choose another
```

The names the language owns are its operators, `if`, `len`, `array` and a few more that its
constructs are written with. A function to pass in place of an operator is a parameter with a name of its own, and `+` keeps its meaning beside it:

<!-- file docs/book/code/fn/operator.oro -->
```go
export fn a_function() { fn(plus) { plus(1, 2) } }

export fn addition() { fn(plus) { 1 + 2 } }
```

<!-- oro tutorial docs/book/code/fn/operator.oro -->
```go
a_function =
fn() { fn(plus) { plus(1, 2) } }
addition =
fn() { fn(plus) { 3 } }
```

Shadowing is legal in source and occasionally reads well. If you did it by accident, it is a bug
that reads as correct code; prefer distinct names.

## 1.7 Substitution cannot capture

Here is the shape that breaks a careless implementation of β:

<!-- file docs/book/code/fn/capture.oro -->
```go
export fn run() {
    fn(n) {
        fn(m) { fn(n) { h(m, n) } }(n)
    }(x())
}
```

Read it slowly. The outer `n` is `x()`. It is passed as `m`. And `m` is used inside a function
whose own parameter is *also* called `n`. Replace `m` by the text `n` and the outer `n` lands
inside the inner binder, where it would be read as the inner one: `h(n, n)`, two different
variables merged because they share a spelling. That is **capture**, and it gives a wrong answer
that looks plausible.

<!-- oro tutorial docs/book/code/fn/capture.oro -->
```go
run =
fn() { n = x(); fn(n1) { h(n, n1) } }
```

Correct: `h`'s first argument is the outer `n`, which is `x()`, and its second is the inner
parameter, renamed apart.

You do not have to think about this when writing programs. Inside the compiler a bound variable is
not a name at all: it is *the parameter of the binder so many levels out* (de Bruijn 1972; the
*locally nameless* representation, Charguéraud 2012), so two variables cannot be confused by their
spelling. Names are kept so that what is emitted reads well.

## 1.8 Arity is exact

<!-- file docs/book/code/fn/no-few.oro -->
```go
export fn run() { fn(a, b) { h(a, b) }(1) }
```

<!-- oro tutorial docs/book/code/fn/no-few.oro -->
```

```

<!-- oro tutorial docs/book/code/fn/no-many.oro -->
```
oro: arity: expects 2 argument(s), given 3, in: fn() { fn(a, b) { h(a, b) } }
```

A function of two parameters takes two arguments: not one, with the second `undefined` as in
JavaScript, and not one, giving back a function of the other as in Haskell. There are no optional
parameters, no defaults, and no arguments passed by name:

<!-- file docs/book/code/fn/no-keyword.oro.txt -->
```go
export fn run() { h(a = 1, 2) }
```

<!-- oro tutorial docs/book/code/fn/no-keyword.oro.txt -->
```
oro: docs/book/code/fn/no-keyword.oro.txt: line 1: "=" where ")" was expected
```

If you want a function that takes its arguments one at a time, write that function. It is a
different one:

<!-- file docs/book/code/fn/curry.oro -->
```go
export fn both() { fn(a) { fn(b) { h(a, b) } }(1)(2) }

export fn first_only() { fn(a) { fn(b) { h(a, b) } }(1) }
```

<!-- oro tutorial docs/book/code/fn/curry.oro -->
```go
both =
fn() { h(1, 2) }
first_only =
fn() { fn(b) { h(1, b) } }
```

`f(1)(2)` applies `f` to `1` and the result to `2`. Given only the first argument, a function is
left that remembers it.

## 1.9 Reduction goes inside

Most languages leave a function's body alone until the function is called. Here reduction goes
*under* the `fn`:

<!-- file docs/book/code/fn/under.oro -->
```go
export fn run(n) { fn(m) { m * m }(n) }

fn square(v) { v * v }

export fn fourth(n) { square(square(n)) }
```

<!-- oro tutorial docs/book/code/fn/under.oro -->
```go
run =
fn(n) { n * n }
fourth =
fn(n) { v = n * n; v * v }
```

The inner application was reduced although `n` is not known yet. This is the most important thing
to understand about the language:

> **Reduction is compilation.** What is left when reduction stops is the program that runs. What
> reduced away has no existence at run time.

`fourth` calls `square` twice and no `square` is left, not because an optimizer inlined it but
because that is what a definition *is*. On a real target the same thing, compiled:

<!-- file docs/book/code/fn/helper.oro -->
```go
fn square(v) { v * v }

fn twice(k, v) { k(k(v)) }

export fn fourth(n ∈ 0..100) (Int) { twice(square, n) }
```

```bash
go run ./cmd/gen -name fn docs/book/code/fn/helper.oro go helper.go
```

<!-- gen go docs/book/code/fn/helper.oro -->
```go
func FnFourth(v0 int) int {
    v9 := (v0 * v0)
    v10 := (v9 * v9)
    return v10
}
```

Three functions in the source, two multiplications in the output. Abstraction is free here, and
that is what the next section spends.

A function is **not** simplified to something merely equal to it, though. `fn(n) { f(n) }` behaves
exactly as `f` does, and stays as written; the rule that would rewrite it, η, is not one of the
language's:

<!-- file docs/book/code/fn/not-eta.oro -->
```go
export fn wrapped() { fn(n) { f(n) } }

export fn applied() { fn(n) { f(n) }(3) }
```

<!-- oro tutorial docs/book/code/fn/not-eta.oro -->
```go
wrapped =
fn() { fn(n) { f(n) } }
applied =
fn() { f(3) }
```

## 1.10 Functions as arguments, and as results

A function is a value, so it can be an argument. Every example below is a small higher-order
function, used, and gone.

<!-- file docs/book/code/fn/hof.oro -->
```go
fn twice(k, v) { k(k(v)) }

export fn with_a_name() { twice(f, 3) }

export fn with_a_fn() { twice(fn(v) { h(v, 1) }, 3) }

fn compose(p, q) { fn(v) { p(q(v)) } }

export fn composed() { compose(f, g)(1) }

export fn composed_twice() { compose(compose(f, g), f)(z()) }

fn flip(k) { fn(a, b) { k(b, a) } }

export fn flipped() { flip(h)(1, 2) }

fn id(v) { v }

export fn identity() { id(id)(id)(7) }

fn pick(c, a, b) { if c { a } else { b } }

export fn picked() { pick(true, f, g)(1) }

export fn picked_later(c) { pick(c, f, g)(1) }

export fn used_twice() { fn(k) { h(k(1), k(2)) }(fn(v) { shout(v) }) }
```

<!-- oro tutorial docs/book/code/fn/hof.oro -->
```go
with_a_name =
fn() { f(f(3)) }
with_a_fn =
fn() { h(h(3, 1), 1) }
composed =
fn() { f(g(1)) }
composed_twice =
fn() { f(g(f(z()))) }
flipped =
fn() { h(2, 1) }
identity =
fn() { 7 }
picked =
fn() { f(1) }
picked_later =
fn(c) { if c { f(1) } else { g(1) } }
used_twice =
fn() { h(shout(1), shout(2)) }
```

- `twice` takes a function `k` and applies it twice. In the output there is no `k` and no `twice`;
  only the work is left.
- `compose` *returns* a function. Applied at once, as in `composed`, that function is used up too.
  Composing three functions leaves three nested calls and nothing else.
- `id(id)(id)(7)` applies a function to itself, twice, and is `7`.
- `pick` chooses between two functions. With the choice known, one is left. With the choice a
  run-time value `c`, the *application* moves into the two branches: `if c { f(1) } else { g(1) }`.
  No function is ever a run-time value, even when which one is called is decided at run time.
- `used_twice` applies its argument twice. The function was copied, which is always safe: a
  function is a value, and copying one runs nothing. Each `shout` stands where a call was written.

None of these says anything about types. `twice`, `compose` and `id` work at whatever they are
given, because each use is reduced separately; that is all of generic programming here, and it has
no syntax.

### A function that would survive

When a returned function is *not* applied, it is still there when reduction stops:

<!-- file docs/book/code/fn/survive.oro -->
```go
fn compose(p, q) { fn(v) { p(q(v)) } }

export fn unapplied() { compose(f, g) }

export fn half_applied() { fn(a) { fn(b) { h(a, b) } }(x()) }
```

<!-- oro tutorial docs/book/code/fn/survive.oro -->
```go
unapplied =
fn() { fn(v) { f(g(v)) } }
half_applied =
fn() { a = x(); fn(b) { h(a, b) } }
```

`oro` only reduces, so it shows them. `half_applied` is the telling one: a function that must
remember `a`, a value computed at run time. A real target would have to *build* that, a **closure**:
an allocation and an indirect call that the source never wrote. So a real target refuses it:

<!-- file docs/book/code/fn/no-closure.oro -->
```go
fn scale(k) { fn(v) { v * k } }

export fn make(k ∈ 0..10) { scale(k) }
```

<!-- gen go docs/book/code/fn/no-closure.oro -->
```
gen: fn-make: lowering: a λ in value position is a closure (callbacks.md): fn(v) { v * k }
```

The same holds
in the other direction. An entry point is called by the host, and the host cannot hand it one of
this language's functions:

<!-- file docs/book/code/fn/no-callback.oro -->
```go
export fn apply(k, n ∈ 0..9) (Int) { k(n) }
```

<!-- gen go docs/book/code/fn/no-callback.oro -->
```
  k is a parameter no header gives a set, so applied to one argument it is read as a
  table (tables.md §3.2). If k is a function, this definition takes one and cannot be
  compiled alone: a function does not cross an entry point (closures-direction.md), and the
  definition is used where it is inlined. If it is a table, declare its set, k ∈ Array(…).
```

So the language has **two levels** ([closures-direction.md](../closures-direction.md)). At compile
time functions are unrestricted: higher-order, nested, passed and returned freely, and free. At run
time there are none of yours, only the host's. **A function may do anything except outlive
reduction.** One kind of callback is built: a window procedure, which Windows calls with each
message, the λ lifted to a function of its own (chapter 18). Passing a function to a host API that
calls it only during the call, as a sort calls its comparator, is specified
([spec/callbacks.md](../spec/callbacks.md)) and not built.

## 1.11 How often is an argument evaluated?

β says *replace the parameter by the argument*. If the parameter occurs twice, is the argument
computed twice? If it does not occur, is it computed at all? The answer depends on one thing: **can
the argument be observed being evaluated?** `f` here is declared `pure`, having no effect; `shout`
is not.

<!-- file docs/book/code/fn/work.oro -->
```go
export fn once() { fn(n) { h(n, 2) }(f(9)) }

export fn twice() { fn(n) { h(n, n) }(f(9)) }

export fn never() { fn(n) { h(1, 2) }(f(9)) }

export fn a_value(a) { fn(n) { h(n, n) }(a) }

export fn in_a_branch(c) { fn(n) { if c { n } else { 0 } }(f(1)) }
```

<!-- oro tutorial docs/book/code/fn/work.oro -->
```go
once =
fn() { h(f(9), 2) }
twice =
fn() { n = f(9); h(n, n) }
never =
fn() { h(1, 2) }
a_value =
fn(a) { h(a, a) }
in_a_branch =
fn(c) { if c { f(1) } else { 0 } }
```

For a **pure** argument:

| the parameter is used | the argument is | |
|---|---|---|
| once | put where the parameter was | `once` |
| more than once | computed once and shared, as `n = f(9)` | `twice` |
| never | dropped | `never` |
| any number of times, and it is already a value | copied | `a_value` |

`in_a_branch` uses its parameter once, on one path only, so `f(1)` moved into that branch and the
other path never computes it. **Work is never duplicated and never done early**
([ADR 0071](../decisions/0071-work-stays-where-it-was-written.md)); this is *call-by-need*
(Wadsworth 1971), decided at compile time.

Now the same five shapes with an argument that has an effect:

<!-- file docs/book/code/fn/effects.oro -->
```go
export fn never() { fn(n) { h(1, 2) }(shout(9)) }

export fn once() { fn(n) { h(n, 2) }(shout(9)) }

export fn twice() { fn(n) { h(n, n) }(shout(9)) }

export fn in_order() { fn(a, b) { h(b, a) }(shout(1), shout(2)) }

fn pick(c, a, b) { if c { a } else { b } }

export fn not_lazy() { pick(true, 1, shout(2)) }
```

<!-- oro tutorial docs/book/code/fn/effects.oro -->
```go
never =
fn() { n = shout(9); h(1, 2) }
once =
fn() { n = shout(9); h(n, 2) }
twice =
fn() { n = shout(9); h(n, n) }
in_order =
fn() { a = shout(1); b = shout(2); h(b, a) }
not_lazy =
fn() { b = shout(2); 1 }
```

**An argument with an effect is evaluated exactly once, where it was written, in the order it was
written.** Not dropped when unused (`never`), not moved to where it is used (`once`), not
duplicated (`twice`), and not reordered though the body uses `b` before `a` (`in_order`).

`not_lazy` is the one to remember. `pick(true, 1, shout(2))` chooses `1`, and `shout(2)` still
runs, because it was written as an argument and arguments are evaluated. An `if` does not evaluate
the branch it does not take; a function you wrote to stand for an `if` evaluates all of its
arguments' effects. Purity is one declared bit on each of the target's operations, and
[chapter 5](05-effects.md) is about it.

## 1.12 A block is a function, applied

Chapter 0 showed blocks binding names, `n = e`, with no keyword. Here is what that is:

<!-- file docs/book/code/fn/block.oro -->
```go
export fn as_a_block() { n = f(2); h(n, n) }

export fn as_a_fn() { fn(n) { h(n, n) }(f(2)) }

export fn in_sequence() { a = f(1); b = h(a, a); h(b, b) }

export fn rebound() { a = f(1); a = g(a); a }

export fn a_statement() { shout(1); 2 }

export fn a_pair() { (q, r) = (f(1), g(2)); h(q, r) }

export fn a_local_fn() { sq = fn(n) { h(n, n) }; sq(sq(3)) }
```

<!-- oro tutorial docs/book/code/fn/block.oro -->
```go
as_a_block =
fn() { n = f(2); h(n, n) }
as_a_fn =
fn() { n = f(2); h(n, n) }
in_sequence =
fn() { a = f(1); b = h(a, a); h(b, b) }
rebound =
fn() { g(f(1)) }
a_statement =
fn() { #_ = shout(1); 2 }
a_pair =
fn() { h(f(1), g(2)) }
a_local_fn =
fn() { n = h(3, 3); h(n, n) }
```

**`{ n = e; body }` is `fn(n) { body }(e)`.** The first two are the same term, and print the same.
A block is not a second binding construct; it is how an applied function is written when you want
the name first. Everything §1.11 said about arguments is therefore true of bindings.

- `in_sequence`: each binding sees the ones before it, because each is a function applied inside
  the one before.
- `rebound`: `a = g(a)` does not change `a`. It is a new, inner `a`, shadowing the outer one as in
  §1.6; and since each is used once, both bindings dissolved into `g(f(1))`.
- `a_statement`: an expression on a line of its own is a binding whose name nobody reads. That is
  all of sequencing; there is no `;` operator with a meaning of its own. The compiler prints the
  unread name as `#_`. `shout(1)` stays because it has an effect; a pure statement would vanish.
- `a_pair`: a tuple on the left takes a tuple apart.
- `a_local_fn`: a function bound in a block is a local function. It was used twice and is gone.

A semicolon and a newline are the same separator. The *named* form of a local function is not
built; bind an anonymous one, as above.

```go
export fn run() {
    fn sq(n) { h(n, n) }
    sq(3)
}
```

```

```

### Where a newline falls

Because a newline ends a statement, an application's parenthesis must open on the line its
function ends on:

<!-- file docs/book/code/fn/newline.oro -->
```go
export fn one_line() { f (1) }

export fn two_lines() {
    f
    (1)
}

export fn arguments_wrap() {
    h(1,
      2)
}
```

<!-- oro tutorial docs/book/code/fn/newline.oro -->
```go
one_line =
fn() { f(1) }
two_lines =
oro: a statement's value is a function, f, which does nothing until it is applied: call it, `f(…)`, or discard it on purpose with ignore(…) (ADR 0116)
```

`two_lines` is two statements: the value `f`, read by nobody, then `(1)`. A function has no
effect until it is applied, so a statement whose value is one can only be a mistake, and it is
refused where it was written ([ADR 0116](../decisions/0116-a-statement-whose-value-is-a-function-is-refused.md)).
Inside parentheses a newline is only space, so arguments wrap freely, as `arguments_wrap` does.

## 1.13 A function cannot call itself

A `fn` has no name inside its own body, so it has no way to mention itself. The classical way
round that is to pass a function to itself:

<!-- file docs/book/code/fn/no-omega.oro -->
```go
export fn run() { fn(k) { k(k) }(fn(k) { k(k) }) }
```

<!-- oro tutorial docs/book/code/fn/no-omega.oro -->
```
oro: reduction did not terminate within the step limit; last term head: fn() { fn(k) { k } }
```

That term is Ω, the smallest program with no value: β turns it into itself, forever. Since
reduction is compilation, a term with no end to its reduction is a program that cannot be compiled,
and the compiler stops after a fixed number of steps and says so. A *named* function that mentions
its own name is refused before reduction starts ([chapter 2](02-def.md)). Repetition is `loop`, not
self-reference.

---

## What to remember

- **`fn(x) { body }` is a value.** It reduces to itself until it is applied.
- **β: `fn(x) { B }(a)` becomes `B` with `a` for `x`.** That is all a function does.
- **Reduction is compilation**, and it goes inside function bodies. What is left is the program;
  a function you defined and called leaves no call.
- **A parameter is a name**, not a literal, not repeated, not qualified, with an optional set
  after `∈`. `_` is one you will not use. The body is always in braces.
- **A name is free or bound**, and a free one must be a definition or the target's. A parameter
  shadows any name but the language's own: `+`, `if`, `len` and the rest are refused as binders.
- **Names are hints.** The compiler renames binders apart, and substitution cannot capture.
- **Arity is exact.** No defaults, no named arguments, no partial application; curry by hand.
- **Functions are passed and returned freely at compile time, and none survives it.** A closure, or
  a function crossing an entry point, is refused.
- **A pure argument is evaluated at most once and only if needed; one with an effect exactly once,
  where it was written.**
- **A block is a function applied**: `{ n = e; body }` is `fn(n) { body }(e)`. A statement is a
  binding nobody reads.
- **A function, named or not, may carry a header**, saying what its parameters and result are.
  That is [chapter 6](06-integers.md)'s.
- **Integer arithmetic on literals is computed at compile time**, exactly, at any size; `7 / 0`,
  which has no answer, is left, and refused when compiled.
