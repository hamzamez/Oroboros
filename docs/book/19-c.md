# 19. Calling C

Chapter 18 declared a host's function by writing the host's own text: `host expr "strings.Index(${s},
${t})"`, Go source with holes. That works for Go, JavaScript and Java, which have source to write.
Windows has none. Its operating system is a few thousand functions in DLLs, each described by a
C prototype in a header file:

```c
BOOL WriteFile(HANDLE hFile, LPCVOID lpBuffer, DWORD nNumberOfBytesToWrite,
               LPDWORD lpNumberOfBytesWritten, LPOVERLAPPED lpOverlapped);
```

So the question of this chapter is: **how does a program call a function that exists only as a C
prototype, and keep every promise this book has made: no unchecked index, no string that is not
text, no memory written behind its back?**

The answer is three sentences.

> **A C function is declared by its prototype**, and the call is written as C writes it:
> `call WriteFile(h, s, len(s), &put, NULL)`. How the arguments travel is derived from the
> processor's calling convention, not written.
>
> **Every pointer C passes is one of a few shapes**, and each is something this book already has:
> a table and its length, a string, a record, a cell for an answer, nothing.
>
> **A C struct is a record**, laid out as the C compiler lays it out, and checked against it.

The examples run on Windows, and need the Windows target (chapter 18). They are in
[code/c/](code/c/). `go run docs/book/check.go docs/book/19-c.md` re-runs every block. Checked
2026-11-21.

## 19.1 Writing to the console, the way C does

<!-- file docs/book/code/c/write.oro -->
```go
use win/print
use windows/processenv
use windows/fileapi

export fn main() {
    out = processenv.GetStdHandle(4294967285)
    hello = array { 104, 101, 108, 108, 111, 10 }
    (put, ok) = fileapi.WriteFile(out, hello)
    print.print_int(put)
    (put2, ok2) = fileapi.WriteFile(out, hello[4:6])
    print.print_int(put2)
}
```

<!-- run windows docs/book/code/c/write.oro -->
```
hello
6
o
2
```

`GetStdHandle(4294967285)` asks Windows for the console's output. (The number is C's
`STD_OUTPUT_HANDLE`, which is `(DWORD)-11`: −11 read as a 32-bit unsigned integer, 2³² − 11.) Then
`WriteFile` writes the six bytes of `hello`, the letters and a line break, and answers how many it
wrote, 6. The second call writes `hello[4:6]`, chapter 14's part of a table, positions 4 and 5:
`o` and a line break, 2 bytes.

Look at what the program did *not* pass. C's `WriteFile` takes five arguments: the handle, a
pointer to the bytes, how many bytes, a pointer to where it should store the count it wrote, and a
pointer that is usually `NULL`. The program passed two, a handle and a table, and got two answers
back, the count and whether it succeeded. Where did the rest go? Into the declaration.

## 19.2 The declaration

<!-- part targets/win32/fileapi.oro -->
```go
    fn WriteFile(h ∈ winnt.HANDLE, s ∈ Array(0..255)) (put ∈ minwindef.DWORD, r ∈ minwindef.BOOL) where len(s) <= 2^32-1 {
        host expr call WriteFile(h, s, len(s), &put, NULL) stdcall lib "kernel32"
    }
```

**`call WriteFile(h, s, len(s), &put, NULL)` is the C call, written as C writes it.** Each argument
is one of a few shapes:

| written | is | C sees |
|---|---|---|
| `h` | a parameter | its value |
| `s` | a table of bytes | a pointer to its first byte |
| `len(s)` | the table's length | a number |
| `&put` | a result of the declaration | the address of a cell, which the callee fills |
| `NULL` | nothing | the null pointer |

Read the header with that table. `s` and `len(s)` are one table: C's habit of passing a pointer and
a count separately, which is how a C function reads past an array's end when the two disagree, is
here one value whose length cannot be wrong. `&put` is C's *out-parameter*, the callee writing its
answer through a pointer, and here it is simply a result: `(put, ok) = WriteFile(…)`. And the
`where` bounds the length by the 32 bits C's `DWORD` holds.

**`stdcall lib "kernel32"`** says the function is in `kernel32.dll`, using Windows' standard calling
convention. *How* five arguments reach `WriteFile` (which go in which registers, which on the stack,
how a struct is copied) is the processor's rule, and the compiler derives it. Nobody wrote it here,
and nobody can write it wrong.

**The declaration is read against Microsoft's own.** The target file is grouped by C header, as
the Windows documentation is: `WriteFile` is in `fileapi.oro` because it is in `fileapi.h`. And a
test reads every declaration against the prototype in the Windows SDK, position by position, so a
`DWORD` declared where the SDK has a pointer fails before any program meets it. Chapter 18 said a
declaration is believed. Here it is believed *and* checked, because the SDK states the types in
a form a program can read.

A part can be passed where a table is, as `hello[4:6]` was, and its bounds are an obligation like
any index:

<!-- file docs/book/code/c/no-past.oro -->
```go
use win/print
use windows/processenv
use windows/fileapi

export fn main() {
    out = processenv.GetStdHandle(4294967285)
    hello = array { 104, 105, 10 }
    (put, ok) = fileapi.WriteFile(out, hello[1:5])
    print.print_int(put)
}
```

<!-- build windows docs/book/code/c/no-past.oro -->
```
build: main: `windows/fileapi`.`WriteFile#seg` requires (0 <= 1 && 1 <= 5 && 5 <= len(`array`(104, 105, 10))) && 5 - 1 <= 4294967295, which is false at this call
```

`hello` has three bytes and the part asks for positions 1 to 4. In C, `WriteFile(h, hello + 1, 4,
…)` compiles and writes one byte nobody owns. (The refusal names `WriteFile#seg`, the form of the
declaration that takes a part.)

## 19.3 A string for C

C has no strings. It has a pointer to bytes, and the string ends at the first byte that is 0. So a
string with a 0 inside, U+0000, is cut short by every C function that reads it, and a file name
`"notes\0.exe"` opens `notes`. Chapter 10 called a string with no U+0000 in it `nulfree`, and a C
string parameter says so:

<!-- part targets/win32/libloaderapi.oro -->
```go
    fn GetModuleHandleA(p ∈ String) (r ∈ Option(minwindef.HMODULE)) where nulfree(p) { host expr call GetModuleHandleA stdcall lib "kernel32" niche NULL }
```

Its answer, `Option(minwindef.HMODULE)` and `niche NULL`, is 18.4's. A literal is decided at once:

<!-- file docs/book/code/c/no-nul.oro -->
```go
use win/print
use windows/libloaderapi

export fn main() {
    m = libloaderapi.GetModuleHandleA("kernel32\u{0}.dll")
    print.print_str("loaded")
}
```

<!-- build windows docs/book/code/c/no-nul.oro -->
```
build: main: `windows/libloaderapi`.GetModuleHandleA requires nulfree("kernel32\u{0}.dll"), which is false at this call: the string holds U+0000 after 8 byte(s), and a C string ends at its first NUL (ADR 0091)
```

And a string from anywhere else passes through a test, which is the proof:

<!-- file docs/book/code/c/cstring.oro -->
```go
use win/print
use windows/libloaderapi

fn loaded(name ∈ String) (String) {
    if nulfree(name) {
        case libloaderapi.GetModuleHandleA(name) {
            'some(m) -> "yes"
            'none -> "no"
        }
    } else {
        "a NUL in the name"
    }
}

export fn main() {
    print.print_str(loaded("kernel32.dll"))
    print.print_str(loaded("nosuch.dll"))
    print.print_str(loaded("kernel32" ++ string_of(0) ++ ".dll"))
}
```

<!-- run windows docs/book/code/c/cstring.oro -->
```
yes
no
a NUL in the name
```

`GetModuleHandleA` answers whether a library is loaded: `kernel32.dll` always is, `nosuch.dll`
never, and the third name never reaches Windows. Inside `if nulfree(name)` the call is proven, by
chapter 17's rule: a condition is a fact in its branch. The string itself is passed as it is, with
no copy: this language's strings are UTF-8 bytes, and a string with no 0 in it already *is* a C
string.

`GetModuleHandleA` answers an `Option` (chapter 16): `'some(m)`, the library's handle, or `'none`,
which is how Windows says "no such library", its C `NULL`. The next section is why.

## 19.4 A handle is a type of its own

Windows gives a program **handles**: a window, a file, a device context, a menu. A handle is a name
for something Windows holds, and the program never sees the thing itself, only the name. C writes
each kind as a pointer to a struct of its own, which no program ever defines, `struct HWND__ *` for
a window, so that C refuses a window where a device context is wanted. The declarations say the
same, with C's own spelling:

<!-- part targets/win32/windef.oro -->
```go
    set HWND = host "HWND__*"           // DECLARE_HANDLE(HWND), struct HWND__ * (ADR 0146)
    set HDC = host "HDC__*"             // DECLARE_HANDLE(HDC)
```

`host "…"` is chapter 18's: a type the host defines, named as the host names it. Two kinds are one
type exactly when their spellings are, so a device context is no window:

<!-- file docs/book/code/c/no-kind.oro -->
```go
use win/print
use windows/winuser
use windows/windef

fn close(d ∈ windef.HDC) (Int) { winuser.DestroyWindow(d) }

export fn main() { print.print_int(0) }
```

<!-- build windows docs/book/code/c/no-kind.oro -->
```
build: close: in argument 1 of `windows/winuser`.DestroyWindow: d is `windows/windef`.HDC, but `windows/windef`.HWND is required here
```

**A failed call answers no handle.** `CreateFileA` opens a file and answers its handle, or, when it
cannot, a value that is no handle: `INVALID_HANDLE_VALUE`, all bits 1. That value is the call's
failure, so the declaration says its answer is an `Option`, and which value is the `'none`:

<!-- part targets/win32/fileapi.oro -->
```go
    fn CreateFileA(p ∈ String, a ∈ minwindef.DWORD, s ∈ minwindef.DWORD, sa ∈ ptr, d ∈ minwindef.DWORD, f ∈ minwindef.DWORD, t ∈ Option(winnt.HANDLE)) (r ∈ Option(winnt.HANDLE)) where nulfree(p) {
        host expr call CreateFileA stdcall lib "kernel32" niche -1
    }
```

`niche -1` names the failure, and `niche NULL` does for a function that fails with `NULL`, as
`CreateWindowExA` does. The program meets it as chapter 16's `case`, and so cannot forget it:

<!-- file docs/book/code/c/missing.oro -->
```go
use win/print
use windows/fileapi
use windows/handleapi
use llvm

export fn main() {
    case fileapi.CreateFileA("no-such-file.txt", 2^31, 1, llvm.null(), 3, 128, 'none) {
        'some(h) -> {
            ignore(handleapi.CloseHandle(h))
            print.print_str("opened")
        }
        'none -> print.print_str("no such file")
    }
}
```

<!-- run windows docs/book/code/c/missing.oro -->
```
no such file
```

What runs is the comparison a C programmer writes by hand, `h == INVALID_HANDLE_VALUE`, made by the
declaration instead of remembered by each caller.

**A handle that may be absent is an `Option` too.** CreateFileA's last argument is a template file,
which may be `NULL`: the SDK marks it `_In_opt_`, so its set is `Option(winnt.HANDLE)`, and `'none`
is passed as `NULL`. A pointer is no option:

<!-- file docs/book/code/c/no-optional.oro -->
```go
use win/print
use windows/fileapi
use windows/handleapi
use llvm

export fn main() {
    case fileapi.CreateFileA("no-such-file.txt", 2^31, 1, llvm.null(), 3, 128, llvm.null()) {
        'some(h) -> {
            ignore(handleapi.CloseHandle(h))
            print.print_str("opened")
        }
        'none -> print.print_str("no such file")
    }
}
```

<!-- build windows docs/book/code/c/no-optional.oro -->
```
build: main: in argument 7 of `windows/fileapi`.CreateFileA: a `case` reads a variant's tag and its payload, and llvm.null() is ptr, which is no variant: a value of `Option(T)` is 'some(x) or 'none, written as such (ADR 0040, 0146)
```

Every handle parameter the SDK marks `_In_opt_` is an `Option` in its declaration, and none other
is: a test reads the SDK's annotations and holds every declaration to them.

**A handle's one operation is `==`, with a handle of its own kind.** Chapter 7's `==` is integer
equality; between two windows it is the windows' own, and between a window and a device context it
is refused:

<!-- file docs/book/code/c/same.oro -->
```go

            ignore(print.print_int(same(w, w)))
            ignore(print.print_int(same(w, v)))

    }
}
```


A window is equal to itself, and not to another window.

## 19.5 A struct is a record

Much of Windows takes structs. A rectangle is four `LONG`s, a point two:

<!-- part targets/win32/windef.oro -->
```go
    set RECT = record { left ∈ winnt.LONG, top ∈ winnt.LONG, right ∈ winnt.LONG, bottom ∈ winnt.LONG }
    repr RECT c(left, top, right, bottom)
…
    set POINT = record { x ∈ winnt.LONG, y ∈ winnt.LONG }
    repr POINT c(x, y)
```

**`set RECT = record { … }` is chapter 12's record**, nothing more. **`repr RECT c(left, top, right,
bottom)`** says how C lays it out: those fields, in that order, each where C's rules put it. A
record has no order (§12.4); a C struct has one, and this line is where it is stated. The compiler
computes each field's offset and the struct's size from the processor's data model, and a test
asks a C compiler, clang, for the same numbers on the same processor and compares.

`PtInRect` asks whether a point is inside a rectangle:

<!-- file docs/book/code/c/inside.oro -->
```go
use win/print
use windows/winuser
use windows/windef

export fn main() {
    box ∈ windef.RECT = record { left : 0, top : 0, right : 10, bottom : 5 }
    print.print_int(winuser.PtInRect(box, record { x : 3, y : 4 }))
    print.print_int(winuser.PtInRect(box, record { x : 10, y : 4 }))
    print.print_int(winuser.PtInRect(box, record { x : -1, y : 0 }))
}
```

<!-- run windows docs/book/code/c/inside.oro -->
```
1
0
0
```

(3, 4) is inside. (10, 4) is not: Windows' rectangles include their left and top edges and exclude
their right and bottom, chapter 14's half-open ranges again. (−1, 0) is outside on the left.

C's prototype is `BOOL PtInRect(const RECT *lprc, POINT pt)`: the rectangle by its address, the
point *by value*, copied into the call. The declaration writes exactly that:

<!-- part targets/win32/winuser.oro -->
```go
    fn PtInRect(rc ∈ windef.RECT, pt ∈ windef.POINT) (r ∈ minwindef.BOOL) { host expr call PtInRect(&rc, pt) stdcall lib "user32" }
```

`&rc`, the address of a fresh copy of the record, laid out as a `RECT`; `pt`, the value itself.
What each becomes is the processor's business:

<!-- gen windows docs/book/code/c/inside.oro -->
```
…
declare dllimport i32 @PtInRect(ptr, i64)
…
```

<!-- gen windows32 docs/book/code/c/inside.oro -->
```
…
declare dllimport x86_stdcallcc i32 @PtInRect(ptr, ptr byval([8 x i8]) align 4)
…
```

On 64-bit Windows an 8-byte struct by value travels in one register, so the `POINT` is an `i64`.
On 32-bit Windows it is copied onto the stack (`byval`). The same source runs on both:

<!-- run windows32 docs/book/code/c/inside.oro -->
```
1
0
0
```

That is the point of deriving the call. Written by hand, the second form is the one people get
wrong, and the program then reads garbage from the stack.

## 19.6 One function, many messages

A window control is talked to through one function, `SendMessageA(window, message, w, l)`: the
message is a number, and what `w` and `l` mean depends on it. For the message 1076, `EM_EXGETSEL`,
`l` is the address of a `CHARRANGE`, which the control fills with the selection. For 186,
`EM_GETLINECOUNT`, both are 0 and the answer is the result. One C function, a different signature
for every message, all erased to integers.

So each message is a declaration of its own, named for the message, calling `SendMessageA` at a
constant:

<!-- part targets/win32/richedit.oro -->
```go
    fn ExGetSel(w ∈ windef.HWND) (cr ∈ CHARRANGE, r ∈ minwindef.LRESULT) {
        host expr call SendMessageA(w, 1076, 0, &cr) stdcall lib "user32"
    }
```

The constant 1076 is checked against C's type at that position, a `UINT`, and `&cr`, a `CHARRANGE`
the control fills, is converted to the integer C's `LPARAM` is. Every message prints the same
`SendMessageA`, so the program links against one function however many messages it sends. Here is
a text editor's status line, "Ln 2, Col 5", worked out as
[TinyRetroPad](https://github.com/plummersSoftwareLLC/TinyRetroPad), a Notepad-style editor written
in assembly, works it out:

<!-- file docs/book/code/c/status.oro -->
```go
use win/print
use windows/winuser
use windows/windef
use windows/libloaderapi
use windows/richedit
use llvm

fn digits(n ∈ 0..2^31-1) (String) {
    loop i = 0, v = n, s = "" {
        i < 10 && (i < 1 || v > 0) -> again(i + 1, v / 10, string_of(48 + v % 10) ++ s)
        else -> s
    }
}

fn status(h ∈ windef.HWND) (Bool) {
    (cr, r) = richedit.ExGetSel(h)
    ignore(r)
    line = richedit.ExLineFromChar(h, cr.cpMax)
    case {
        line >= 0 && line < 2^31 - 1 -> {
            start = richedit.LineIndex(h, line)
            case {
                start >= 0 && start < 2^31 && cr.cpMax >= start && cr.cpMax - start < 2^31 - 1 ->
                    print.print_str("Ln " ++ digits(line + 1) ++ ", Col " ++ digits(cr.cpMax - start + 1))
                else -> print.print_str("no column")
            }
        }
        else -> print.print_str("no line")
    }
}

export fn main() {
    ignore(libloaderapi.LoadLibraryA("Msftedit.dll"))
    case winuser.CreateWindowExA(0, "RICHEDIT50W", "", 4, 0, 0, 200, 100, 'none, 'none, 'none, llvm.null()) {
        'some(h) -> {
            ignore(winuser.SetWindowTextA(h, "first line\nsecond line"))
            ignore(richedit.ExSetSel(h, record { cpMin : 15, cpMax : 15 }))
            ignore(status(h))
            ignore(print.print_int(richedit.GetLineCount(h)))
            ignore(richedit.ReplaceSel(h, 1, "X"))
            status(h)
        }
        'none -> print.print_str("no control")
    }
}
```

<!-- run windows docs/book/code/c/status.oro -->
```
Ln 2, Col 5
2
Ln 2, Col 6
```

The program creates a Rich Edit control (the one WordPad was built on), puts two lines of text in
it, and places the caret at character 15: the fifth character of the second line, since the first
line and its line break are 11. Then it asks three questions, each a message: where is the
selection (`ExGetSel`), which line holds that character (`ExLineFromChar`), where does that line
start (`LineIndex`). The column is the difference. Inserting an `X` there moves the caret one
right.

The guards around each answer are the price of C's types. An `LRESULT` is a full 64-bit integer,
so `line + 1` could leave the word, and the control in fact counts in 32-bit `LONG`s. The guards say
so, once, and then the arithmetic is proven.

## 19.7 A function Windows calls

A window receives its messages by calling a function the program gives it: the *window
procedure*. Every Windows program with a window has one. It is the one place in this book where a
function survives to run time (chapter 2 said a function may not outlive reduction), and the
exception is narrow:

<!-- file docs/book/code/c/window.oro -->
```go
use win/print
use windows/winuser
use windows/windef
use windows/minwindef
use llvm

set S = record { clicks ∈ 0..1000 }

fn step(s ∈ S inout, h ∈ windef.HWND, m ∈ minwindef.UINT, w ∈ minwindef.WPARAM, l ∈ minwindef.LPARAM) (minwindef.LRESULT) {
    c = s.clicks
    case {
        m == 1025 && c < 1000 -> { s.clicks := c + 1; 0 }
        m == 1026 -> { winuser.PostQuitMessage(c); 0 }
        else -> winuser.DefWindowProcA(h, m, w, l)
    }
}

export fn main() {
    var s := record { clicks : 0 }
    wc = record { style : 0, lpfnWndProc : fn(h, m, w, l) { step(s, h, m, w, l) }, cbClsExtra : 0, cbWndExtra : 0,
        hInstance : llvm.null(), hIcon : llvm.null(), hCursor : llvm.null(), hbrBackground : llvm.null(), lpszClassName : "OroWndProc" }
    a = winuser.RegisterClassA(wc)
    case winuser.CreateWindowExA(0, "OroWndProc", "", 0, 0, 0, 0, 0, 'none, 'none, 'none, llvm.null()) {
        'some(h) -> {
            ignore(winuser.PostMessageA('some(h), 1025, 0, 0))
            ignore(winuser.PostMessageA('some(h), 1025, 0, 0))
            ignore(winuser.PostMessageA('some(h), 1025, 0, 0))
            ignore(winuser.PostMessageA('some(h), 1026, 0, 0))
            loop n = 0, quit = 0 - 1 {
                quit >= 0 -> { ignore(print.print_int(quit)); ignore(print.print_int(s.clicks)) }
                n > 1000 -> ()
                else -> {
                    (msg, r) = winuser.GetMessageA('none, 0, 0)
                    ignore(winuser.TranslateMessage(msg))
                    ignore(winuser.DispatchMessageA(msg))
                    again(n + 1, if r > 0 { 0 - 1 } else { if msg.wParam < 1000 { msg.wParam } else { 1000 } })
                }
            }
        }
        'none -> ignore(print.print_str("no window"))
    }
}
```

<!-- run windows docs/book/code/c/window.oro -->
```
3
3
```

The program registers a window class whose `lpfnWndProc` field is a `fn`, creates a window of that
class, and posts four messages to it: 1025 three times (a "click", a message number of its own) and
1026 once ("quit"). Then it runs the *message loop*, the heart of every Windows program:
`GetMessageA` takes the next message, `DispatchMessageA` calls the window procedure with it. Each
click adds one to `s.clicks`; quit posts the count, and the loop prints it twice, once as Windows
returned it and once from `s` itself.

What makes this possible, and safe:

- **The `fn` at `lpfnWndProc` becomes a function of its own**, compiled with the calling convention
  Windows uses for window procedures, which the target states as part of the field's set. It is
  the one place a λ is allowed to reach the host, because the field's set says it is a window
  procedure.
- **Its state is `var s` in `main`'s block**, and the `fn` reads and writes it through `step`'s
  `inout` (chapter 15). The cell lives as long as the block, and the block holds the message loop,
  so every message Windows delivers arrives while `s` exists. Windows may even call the procedure
  again from inside itself (some messages are sent, not posted), and each call reads the state the
  last one left.
- **`step` is an ordinary function**, checked as every other: `c < 1000` is what keeps `c + 1` in
  `clicks`'s set.

## 19.8 A function Windows calls during one call

`EnumWindows` passes each top-level window, in turn, to a function, and stops at the first that
answers 0; then it answers 0 itself. So for a function p that only computes, its answer is "p holds
for every window", ∀h ∈ W. p(h), and ∀ distributes over "and":
∀h. (p(h) ∧ q(h)) = (∀h. p(h)) ∧ (∀h. q(h)). This program checks it for every pair of constant
predicates, a and b each 0 or 1, printing 10 × the left side + the right side:

<!-- file docs/book/code/c/allwindows.oro -->
```go
use win/print
use windows/winuser

export fn main() {
    loop i = 0 {
        i < 4 -> {
            a = i % 2
            b = i / 2
            both = winuser.EnumWindows(fn(h) { if a == 1 && b == 1 { 1 } else { 0 } })
            pa = winuser.EnumWindows(fn(h) { a })
            pb = winuser.EnumWindows(fn(h) { b })
            lhs = if both != 0 { 1 } else { 0 }
            rhs = if pa != 0 && pb != 0 { 1 } else { 0 }
            print.print_int(10 * lhs + rhs)
            again(i + 1)
        }
        else -> print.print_int(i)
    }
}
```

```
4
```

```
4
```

It needs one window to exist, which a desktop has: over no windows at all, ∀ is 1 for every p.

The `fn` is chapter 18's callback during the call, with one more step, because a C function is
code alone, with nowhere to keep `a` and `b`. Its declaration says where Windows hands back a word
of the caller's choosing:

```go
set WNDENUMPROC = fn(h ∈ windef.HWND) (r ∈ minwindef.BOOL)
repr WNDENUMPROC c(h, ctx) stdcall
fn EnumWindows(f ∈ WNDENUMPROC) (r ∈ minwindef.BOOL) { host expr call EnumWindows(f, ctx(f)) stdcall lib "user32" }
```

`ctx` is that word, `LPARAM`: the compiler puts `a` and `b` in a record in `main`'s frame, passes
its address as `ctx(f)`, and the function it makes for the `fn` reads them back from there. A
program never writes `ctx`; it writes `EnumWindows(fn(h) { … })`. Windows promises each window
once and no order, so the `fn` may only compute, as under Go's `strings.Map`.

## 19.9 Text from Windows

Section 18.3 sent a string to C. The other way, Windows fills a buffer with a C string and says
how long it is. `GetWindowTextA` copies a window's text into a buffer, and its page says the count
it returns is "the length, in characters, of the copied string, not including the terminating null
character". A C string's length is the position of its first 0, so that sentence is a claim about
the buffer, and the declaration states it as chapter 17's `∀`:

<!-- part targets/win32/winuser.oro -->
```go
    fn GetWindowTextA(w ∈ windef.HWND, b ∈ Array(0..255) linear) (r ∈ minwindef.INT)
        where len(b) >= 1 && len(b) <= 2^31-1
        ensure 0 <= r && r <= len(b) - 1 && (∀ i ∈ 0..r-1 : b[i] != 0) && (r > 0 ⇒ b[r] == 0)
    {
        host expr call GetWindowTextA(w, b, len(b)) stdcall lib "user32"
    }
```

In the `ensure`, `b` is the buffer after the call, the text Windows wrote. When the call fails, r
is 0 and the page says nothing of the buffer, so its 0 is promised only for r > 0.

No compiler can check what Windows does. So this `ensure` is believed, as a host function's purity
is, and the sentence it rests on is kept beside it: `gauntlet/stdlib/host-ensures-evidence.txt`
gives each part of every such promise its page and sentence, and a test fails when a promise has no
sentence, or a sentence no promise.

What the promise buys. Here is C's `strnlen`, the position of the first 0, written in the
language, with the claim that it is r when the first r bytes hold no 0 and the next one is 0. A
table that is not such a string is refused at the call, its last byte 33 and not 0:

<!-- file docs/book/code/c/no-cstr.oro -->
```go
use win/print

fn cstrlen(b ∈ Array(0..255), r ∈ Int) (n ∈ Int)
    where 0 <= r && r < len(b) && (∀ i ∈ 0..r-1 : b[i] != 0) && b[r] == 0
    ensure n == r
{
    loop i = 0 invariant 0 <= i && i <= r {
        i < len(b) && b[i] != 0 -> again(i + 1)
        else -> i
    }
}

export fn main() {
    print.print_int(cstrlen(array { 72, 105, 33 }, 2))
}
```

<!-- build windows docs/book/code/c/no-cstr.oro -->
```

  A definition's declared parameter range and `where` are obligations at every call it is
  inlined into (ADR 0028). Prove the argument in range — narrow it, or declare the range of
  what it comes from — or widen the declaration if the definition is right outside it.
  (2 obligations at calls fail; this is the first.)
```

A window's text is such a string, by Windows' promise:

<!-- file docs/book/code/c/windowtext.oro -->
```go
use windows/winuser
use windows/windef
use windows/fileapi
use windows/processenv
use llvm as x
use win/print

fn cstrlen(b ∈ Array(0..255), r ∈ Int) (n ∈ Int)
    where 0 <= r && r < len(b) && (∀ i ∈ 0..r-1 : b[i] != 0) && b[r] == 0
    ensure n == r
{
    loop i = 0 invariant 0 <= i && i <= r {
        i < len(b) && b[i] != 0 -> again(i + 1)
        else -> i
    }
}

// the window's text: read inside the buffer's scope, whose value is its frozen
// table and the count (ADR 0031), the host's promise carried to both
fn show(w ∈ windef.HWND) {
    (b, r) = {
        var t := array { 0 : _ ∈ 0..63 }
        n = winuser.GetWindowTextA(w, t)
        (t, n)
    }
    case {
        r > 0 -> {
            print.print_int(r)
            print.print_int(cstrlen(b, r))
            (put, ok) = fileapi.WriteFile(processenv.GetStdHandle(4294967285), b[0:r])
            ignore(put)
            ignore(ok)
        }
        else -> ignore(print.print_int(0))
    }
    ignore(winuser.DestroyWindow(w))
}

// a window, or none: CreateWindowExA's failure is NULL, its result's niche
// (ADR 0146), and the parent, menu and instance are none, each its NULL
export fn main() {
    case winuser.CreateWindowExA(0, "STATIC", "TinyRetroPad", 2^31, 0, 0, 10, 10, 'none, 'none, 'none, x.null()) {
        'some(w) -> {
            ignore(print.print_int(1))
            show(w)
        }
        'none -> ignore(print.print_int(0))
    }
}
```

<!-- run windows docs/book/code/c/windowtext.oro -->
```

12

```

The window is never shown: its style is `WS_POPUP`, 2^31, without `WS_VISIBLE`, and its parent, menu and instance are `'none`. Both counts are 12, and they were known to be equal
before the program ran: the call to `cstrlen` owes its `where`, and the promise gives it. Its own
`ensure` is proven by the loop: a step from `b[i] != 0` keeps `i <= r`, because `b[r]` is 0 and
`b[i]` is not, so i is not r; and the loop ends at i = r, the first position the promise does not
cover. Then the bytes are written as Windows wrote them, `b[0:r]`.

The promise is used after the block where the buffer lives: what a block knows about the values it
hands out crosses it, so `b[0:r]` is proven inside `b` with no test. One thing in the program is
there for a reason of the compiler, not of the text: `cstrlen` tests `i < len(b)` as C's `strnlen`
does. The invariant already says i stays below the buffer's end, but the part of the compiler that
keeps each number inside its machine word reads tests, not invariants.

`examples/native/save-win.oro` is TinyRetroPad's save and load: a window's text written to a file
with `CreateFileA` and `WriteFile`, read back with `ReadFile`, and removed, each handle a type of
its own and each failure a `case`.

A call with a part of a buffer, `t[8:40]` (18.1), gets the promise about that part: its 0 at
`t[8 + n]`, which is proven, and not at `t[n]`, which is refused (`examples/logic/segment.oro`).

## 19.10 Your own functions, called from C

Everything so far in this chapter was this language calling C. The other direction is an `export`.
On Go, JavaScript and Java an export is a function of that host's, called by that host's code. On
Windows the compiler's output is a native program or library, so **an export is a C function**:
whatever calls it, C, C++, Rust, C#, does so by the C calling convention, and passes what C can
pass.

That decides what an export may take and return, because C's integers are its fixed widths,
`int64_t` and smaller, and C has no integer of any size. Inside a Windows program there is one: a
value past the word is a table of 64-bit digits with its sign and size in the last entry (chapter
7, §7.10). That table is the program's own arrangement of memory, not a type a C caller has.

**Inside a program, nothing changes.** A `main` takes nothing, so no caller passes it anything, and
it computes with integers of any size:

<!-- file docs/book/code/c/big-inside.oro -->
```go
use io

fn fact(n ∈ 0..1000) (Nat) {
    loop i = 1, acc = 1 {
        i <= n -> again(i + 1, acc * i)
        else   -> acc
    }
}

export fn main() {
    io.print_int(fact(30))
}
```

<!-- run windows docs/book/code/c/big-inside.oro -->
```
265252859812191058636308480000000
```

Reading a number of any size from a file or the console is the same: it arrives as bytes, and is
taken apart and computed with inside.

**An export whose integers are words is a plain C function**, `int64_t` in and out:

<!-- file docs/book/code/c/export-word.oro -->
```go
export fn square64(n ∈ -3037000499..3037000499) (-2^63..2^63-1) { n * n }
```

<!-- gen windows docs/book/code/c/export-word.oro -->
```llvm
define i64 @c_square64(i64 range(i64 -3037000499, 3037000500) %v0) #0 {
```

A C program declares it `int64_t c_square64(int64_t n);` and calls it.

**An export cannot take an integer of any size.** `Int` is every integer, and on Go this function
takes Go's `*big.Int`. On Windows there is no such C type to receive, so it is refused, saying how to
make it a word:

<!-- file docs/book/code/c/no-export-int.oro -->
```go
export fn square(n ∈ Int) (Int) { n * n }
```

<!-- gen windows docs/book/code/c/no-export-int.oro -->
```

```

<!-- gen go docs/book/code/c/no-export-int.oro -->
```go

```

**A result past the word is the program's own numeral.** Declare the result `Int`, `Nat` or any
range above the word, and the export compiles on Windows; on Go it returns a `*big.Int`:

<!-- file docs/book/code/c/export-int.oro -->
```go
export fn fact(n ∈ 0..30) (Int) {
    loop i = 1, acc = 1 {
        i <= n -> again(i + 1, acc * i)
        else   -> acc
    }
}
```

<!-- gen windows docs/book/code/c/export-int.oro -->
```llvm

```

<!-- file docs/book/code/c/export-nat.oro -->
```go
export fn fact(n ∈ 0..30) (Nat) {
    loop i = 1, acc = 1 {
        i <= n -> again(i + 1, acc * i)
        else   -> acc
    }
}
```

<!-- gen windows docs/book/code/c/export-nat.oro -->
```llvm
define nonnull dereferenceable(8) align 8 ptr @c_fact(i64 range(i64 0, 31) %v0) #0 {
```

Both return a pointer, `ptr`, to the program's own table of digits: `acc * i` passes the word and
the double word, and is held as the integer it is (chapter 7, §7.9). A C caller can call it, and then
holds memory in a format this book does not promise to keep: the digits' base, their order, where
the sign is and who frees the table are this compiler's choices today, written down nowhere a C
header could say. So treat it as not for C callers, the book's finding 113.

In one table:

| an export's integer | Go, JavaScript, Java | Windows |
|---|---|---|
| a range inside the word | the host's integer, `int`, `number`, `long` | `int64_t` |
| a parameter of any size, `Int`, `Nat`, `5..` | the host's big integer | refused |
| a result past the word, declared `Int`, `Nat` or a range | the host's big integer | a pointer to the program's own digits |

So on Windows you can write any program, and any library whose functions take and give words. What
you cannot write yet is a library that hands integers of any size to C callers, or takes them from
them. That needs a format agreed at the boundary, the number as a C struct of its digits and their
count, or as its decimal text, and it will be chosen when a program asks for one.

## 19.11 What is not here

**A struct's handle field is still a pointer.** `WNDCLASSA`'s instance, icon, cursor and brush, and
`MSG`'s window, are `ptr`: a field that may be `NULL` is an `Option` of its kind (ADR 0146), and an
optional field of a struct is not built. And Windows' pseudo-handles, `HWND_TOPMOST` and the like
passed where `SetWindowPos` takes a window, are not either.

**Text from Windows stays bytes.** A window's text comes back as a table of bytes proven to be a
C string (18.9), and is written out as it is. Taking it into a `String` needs its bytes read in
Windows' code page, and is not built.

**The `W` functions are not called.** Windows has two of most functions: `…A` takes 8-bit text,
`…W` takes 16-bit (UTF-16). This language's strings are UTF-8 and the program declares UTF-8 its
code page, so the `A` functions take them unchanged. The `W` functions need a conversion, not built.

**A function Windows calls during one call may only compute.** Windows' enumerators promise each
item once, in no stated order, so a count there is the commuting kind of write, which is decided
and waits on a program; no Win32 function found yet promises an order. And a struct whose address
Windows keeps after the call returns, as the Find dialog keeps its `FINDREPLACE`, is not built.

**An integer of any size at a Windows export.** A parameter of any size is refused, and a result
past the word is returned as the program's own table (18.10). A boundary format for C callers waits on a program that needs it.

**A function whose frame is larger than a page does not link.** Windows grows a thread's stack one
page at a time, and a function that needs more than 4096 bytes of it at once must touch each page
in order, through a small routine, `__chkstk`, that the C runtime provides. A program here links
without the C runtime, so that routine is missing.

## 19.12 What other languages do

| | a C function is declared | a struct | a pointer and a count | an out-parameter | a callback |
|---|---|---|---|---|---|
| C | by `#include`, the prototype | the struct | two arguments, unrelated | a pointer, by hand | a function pointer |
| Go | cgo, or `syscall` with every argument a `uintptr` | a Go struct, laid out by hand to match | `unsafe.Pointer(&b[0])`, `uintptr(len(b))` | `uintptr(unsafe.Pointer(&n))` | `syscall.NewCallback` |
| Rust | `extern "C"`, or generated from the SDK (`windows-sys`) | `#[repr(C)] struct` | `b.as_ptr(), b.len()` | `&mut n` | `extern "C" fn` |
| C# | `[DllImport]`, P/Invoke | `[StructLayout]` | an array, marshalled | `out int n` | a delegate, marshalled |
| Java | Panama's `Linker`, or JNI in C | a `MemoryLayout`, by hand | a `MemorySegment` | a segment for one value | an upcall stub |
| Python | `ctypes` | `ctypes.Structure` | `(c_char * n).from_buffer(b)` | `byref(n)` | `CFUNCTYPE` |
| here | by its prototype, in its header's module, checked against the SDK | a record and its C layout, checked against the C compiler | one table | a result | a `fn` at a field whose set is a callback's |

Rust's `windows-sys` is the nearest: it is generated from the same SDK metadata, so its prototypes
cannot drift from Microsoft's. The difference is what happens at the call. There, `b.as_ptr()` and
`b.len()` are two values that the programmer keeps in agreement, inside `unsafe`. Here they are one
value, and there is no `unsafe`: every shape a pointer may take is one the compiler can check.

## What to remember

- **A C function is declared by its prototype** and called as C writes it, `call F(x, s, len(s),
  &r, NULL)`; how the arguments travel is derived from the processor's convention.
- **A pointer and its count are one table**, or a part of one, `b[lo:hi]`, its bounds proven.
- **An out-parameter is a result**: `&r` in the call, `(r, ok) = F(…)` in the program.
- **A C string is a `String` proven `nulfree`**: a literal by its characters, anything else by a test.
- **A handle is a type of its own**, C's `HWND__*`, its one operation `==` within its kind; a failed
  call's handle is `'none`, the declaration's `niche`, and a handle that may be `NULL` is an `Option`.
- **A promise Windows makes about a buffer is an `ensure` with a `∀`**, believed with its page's
  sentence kept as evidence: `GetWindowTextA`'s text is a C string of r bytes.
- **A C struct is a record** with a C layout, `repr RECT c(left, top, right, bottom)`, passed by
  address `&rc` or by value, each as the processor requires: one source, 32- and 64-bit Windows.
- **One C function with many meanings is many declarations**, each at its constant.
- **A window procedure is a `fn` at a struct's field**, its state a `var` in the block that runs the
  message loop.
- **Your own export is a C function**: its integers are words, `int64_t`; an integer of any size
  works inside a program and does not cross to a C caller.
- **Declarations are read against the Windows SDK**, so a wrong type fails before any program.
