# 0030 — At a host boundary a string is the host's; ours is Σ*, entered by one total decode

Date: 2026-09-24
Status: Accepted. **Extends [ADR 0026](0026-an-int-is-an-integer.md)'s boundary rule** ("at a host
boundary an integer is the host's") to strings, and makes [strings.md](../spec/strings.md) §3's
definition, a sequence of Unicode scalar values, true of every value a program holds. **Closes the
divergence** recorded in hex-2026-09-14: `os.text-of` on bytes that are not UTF-8.

## Context

The language's `string` is a sequence of Unicode scalar values (strings.md §3), and the Go target
realizes it as a Go `string`: `(type string (host "string"))`. A Go `string` is any byte sequence.
So a declaration whose result is `string` claims that the host returns only valid UTF-8, and nothing
checked that claim. hamza asked whether the `string` in `(sig Quote ((s string)) string …)` is ours or
Go's; it is ours, and two measurements showed where the claim fails.

**One: a declared result that lies.** `strconv.Unquote` of `"\xff"` returns the single byte `0xFF`,
typed `string`. `utf8.ValidString` says false. Worse, `Unquote("\xe6")` and `Unquote("\x97\xa5")` are
each invalid, and their `concat` is `日`, which the program printed as bytes E6 97 A5. So `concat`,
specified as the free monoid over scalars, manufactured a scalar that neither operand contains.

**Two: three hosts, three decoders.** The portable `os.text-of` turns bytes into text on each host:

| bytes | Go (`string(b)`, then `range`) | JS (`TextDecoder`) | Java (`new String(b, UTF_8)`) |
|---|---|---|---|
| `E6 97 61` (a truncated 3-byte sequence) | the raw bytes kept; `range` reads FFFD FFFD 61 | FFFD 61 | FFFD 61 |
| `ED A0 80` (an encoded surrogate) | kept; FFFD ×3 | FFFD ×3 | **FFFD ×1** |
| `F0 9F 99 61` (a truncated 4-byte sequence) | kept; FFFD ×3, 61 | FFFD 61 | FFFD 61 |

JS agrees with the Unicode Standard's recommended practice on all 26 cases measured (§3.9, "U+FFFD
Substitution of Maximal Subparts"; the W3C/WHATWG Encoding Standard's UTF-8 decoder). Java deviates
only on encoded surrogates, and Go does not decode at all.

**How many declarations it touches.** All 57 hand-declared Go results mentioning `string`, read one
at a time against Go's source (the table in [strings.md §8](../spec/strings.md)):
- 5 are map types whose name contains the word;
- **41 provably return valid UTF-8 when given valid UTF-8**;
- **11 can return arbitrary bytes**.

## The algebra

    Σ = [0, 0xD7FF] ∪ [0xE000, 0x10FFFF], the Unicode scalar values      Str = Σ*, the free monoid
    B = [0, 255]                                                          GoStr = B*, the free monoid
    enc : Σ* → B*, the monoid homomorphism generated by UTF-8 on Σ        V = enc(Σ*) ⊆ B*

**enc is injective and V is a free submonoid.** UTF-8's codewords C = enc(Σ) form a prefix code: a
codeword's first byte fixes its length. A prefix code is uniquely decipherable, so enc is injective
and V = C* is free with basis C (Berstel & Perrin, *Theory of Codes*, ch. 2).

**Theorem 1 (synchronization).** If w ∈ V and w = x·u·y as bytes with u ∈ V∖{ε}, then x, y ∈ V.
*Proof.* B splits into continuation bytes K = [0x80, 0xBF] and the rest, and every codeword is one
non-K byte followed by K bytes. u begins with a non-K byte. In w, every non-K byte begins a codeword,
so x ends on a codeword boundary of w, and x ∈ V. Decoding u from that boundary follows w's own
parse, because the parse from a boundary is determined by the lead bytes, so u ends on a boundary
too, and y ∈ V. ∎

**Corollary.** On valid inputs, searching, splitting, replacing and trimming by a valid needle, and
concatenation, never leave V. That is why the `strings` package keeps `string` in its results.

**Theorem 2 (V is not factor-closed).** V·V ⊆ V, but x·y ∈ V does not imply x, y ∈ V: E6 · 97 A5 is
`日`. So invalid bytes cannot be admitted and repaired later, because a later concatenation can turn
them into a scalar. They must be excluded where they enter.

**The decode.** d : B* → Σ* is maximal-subpart substitution (Unicode §3.9, Table 3-7):
- read a well-formed sequence as its scalar;
- replace each maximal prefix of a well-formed sequence that cannot be completed, or each byte that
  begins none, with U+FFFD.

d is **total**, **d ∘ enc = id**, and **enc ∘ d = id on V**, so d is a left inverse of enc and the
identity on V. It is **not** a homomorphism: d(E6)·d(97 A5) is FFFD FFFD FFFD, and d(E6 97 A5) is
`日`. That is why it is applied once, to a whole value, at the boundary. **valid** = χ_V decides V.

**Subtyping.** Str ≤ GoStr by enc, and on Go enc is the identity on the representation: our string is
already stored as its UTF-8 encoding. So the coercion emits no code. The reverse is d, and it is not a
coercion.

## Decision

**1. The host's string is the host's type.** On Go it is `go.bytestring`, realized as Go `string`, and
**`string ≤ go.bytestring`**, declared `(implements string go.bytestring)`, never the reverse. A value of
the host's type enters `string` only through d.

**2. A result is `string` only where the host provably maps Σ* into V.** That can be by Theorem 1, by
output that is ASCII only, or by escaping every byte it cannot print. Otherwise the result is
`go.bytestring`. A parameter stays `string` (ours passes to Go by the coercion). A parameter the host
reads as bytes may be declared `go.bytestring`, the larger set, and ours still flows in:
- `unicode/utf8`'s five functions over a string, whose purpose is to decide and decode arbitrary bytes;
- `strconv.Quote`, `QuoteToASCII` and `QuoteToGraphic`, which escape what they cannot print, so their
  result is in V whatever they are given.

**The generator makes the claim only where it can justify it** (ADR 0023). It spells every Go `string`,
parameter or result, as `go.bytestring`. A person who reads a body may narrow a result to `string`
(ADR 0022). The tooling check accepts that narrowing, because both types realize Go's `string`, and
the claim is the declaration's own. A string *constant* is the exception: its value is known, so the
generator spells it `string` when that value is valid UTF-8.

**3. The way back is two primitives:**
- `go.text : bytestring → string`, which is d;
- `go.valid : bytestring → bool`, which is χ_V.

A checked conversion is `(if (go.valid s) (go.text s) …)`, because d is the identity on V. Nothing
else converts.

**4. The portable `os.text-of` is d on every host.**
- **JS:** `TextDecoder` is d, unchanged.
- **Go and Java:** implement d, since neither host's decoder is d (measured above). Each keeps the
  host's own decoder as a fast path wherever the input is valid, because there d is the identity:
  - on Go, `utf8.ValidString`;
  - on Java, the lenient decoder, whose answer is kept exactly when it holds no U+FFFD. It emits one
    for every ill-formed sequence and is d on valid input, so no U+FFFD means valid input and d's
    answer.
- **The portable `os.Args` and `os.Getenv` on Go** decode by d, which is what JS and the JVM already
  do to the command line.

**5. A language type is never identical to a host type by realization.** `Target.SameHostType`
identified two names that realize one host spelling, which is right for an opaque host type named
under two keys, and wrong for `string` and `go.bytestring`, one set inside another. A language type's
realization is its representation, not its identity (ADR 0003).

## Why not

- **Convert at every call.** It pays d's scan on the 41 results that cannot be invalid, and on every
  host string handed straight back to Go, where it gains nothing. A conversion belongs where the set
  changes, and only there.
- **One string type with Go's semantics.** The free monoid would stop being ours (Theorem 2), and the
  answer would stop being portable: JS and the JVM cannot hold a byte that is not a scalar's.
- **Check at every `concat`.** O(n) on the language's most common string operation, and it still
  admits the invalid operands whose concatenation is the problem.
- **Go's own decode, or `strings.ToValidUTF8`.** One U+FFFD per bad byte, or one per run of bad
  bytes. Neither is the standard, and neither agrees with JS, so `text-of` would stay a divergence.
- **Java's own decode.** It is the standard except on encoded surrogates, and matching it would make
  JS the odd one out.
- **Return bytes, `(array (int 0 255))`, from `Unquote`.** Exact about the set, but the value then
  stops being Go's string: handing it back to a Go API would need a conversion that Go does not.
- **Python's `surrogateescape` (PEP 383).** A lossless round trip, but it maps a bad byte to a lone
  surrogate, which is not in Σ, so it moves the problem inside the type.
- **This is Rust's `OsStr`/`str` split** (`std::ffi`), and it was chosen for that reason. The host's
  string is a type of its own, ours is validated, and the conversion is explicit, lossy (`to_string_lossy`)
  or checked (`to_str`). Here the lossy one is the standard's d.

## Consequences

- `concat` is the free monoid on every value a program can hold: a `go.bytestring` cannot reach it
  without d.
- **Two acceptance programs had relied on the old behaviour.** `encoding-hex` fed binary data to a hex
  encoder through the portable `text-of`, and `unicode-utf8` asked `ValidString` about invalid bytes
  made the same way. Both depended on a `string` that holds bytes that are not scalars. They now pass
  the host's string, `go/os`'s raw `text-of`, which is what they meant. The generated `tally` binding
  decodes each capture, line and number where it enters the portable core.
- **The 11 results become `go.bytestring`:**
  - `strconv.Unquote`;
  - `fmt.Sprint`, `Sprint2`, `Sprintln`, `Sprintf`, `Sprintf2` and `Sprintf3` (an `any` argument can
    carry host bytes);
  - `go/os`'s raw `text-of`, `Args` and `Getenv`;
  - the builtin `string-of-bytes`.

  No example uses them as ours, and the acceptance programs pass them only to `fmt.Println`.
- **Cost, measured on valid input:**
  - the coercion ours → Go emits nothing;
  - `text-of` on Go against the old `string(b)`: 1.09× on 1 KB of ASCII, 1.44× on 64 KB, and **4.65×
    on 1 KB of non-ASCII**, where the scan, about 0.65 ns per byte, dominates the copy;
  - on Java, 1.00× to 1.02× of the lenient decoder. The strict decoder, tried first, lacks the lenient
    one's ASCII intrinsic and cost 3.6×;
  - the replacement path runs only on invalid input.
- `text-of` now agrees on Go, JS and Java, **by construction on JS and by implementation on Go and
  Java**. It is pinned by a differential case over 18 ill-formed and edge sequences, whose expected
  answer comes from an implementation of d written from Table 3-7 and checked against `TextDecoder`.
- **The differential harness runs the JVM with UTF-8 output.** Its console encoding printed U+FFFD as
  `?`, which is a property of printing (strings.md §5). With it, `utf8-widths` runs on all four
  targets, where it had run on two.
- **Named, not built.** JS and Java strings are UTF-16 code-unit sequences, and a lone surrogate is
  their analogue of a stray byte. Their hand-declared string results are to be read against rule 2
  when a program first needs one. Windows strings are byte pointers and have no string results yet.
