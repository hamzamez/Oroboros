# abstract2 — usage on the trees, and a hole in the relevance check

2026-10-11. Step 2 of [spec/abstract.md](../../docs/spec/abstract.md) §13: usage (𝒰) and effects (𝓔)
on the trees, held against the checks the compiler has. hamza: *"go ahead with step 2"*.

## The finding first: a relevant value could be dropped at a back edge

abstract.md §8.1 says a back edge ends the path only of a name bound **outside** the loop it goes round.
The reducer's relevance check (`Env.usedOnEveryPath`, ADR 0043) made **every** `again` vacuous. So a
relevant value bound inside an iteration and never used before the jump was accepted:

```lisp
(loop ((i n)) (> i 3) 0 else (seq (write i) (again (- i 1))))      ; accepted: write's error dropped
(seq (write n) 1)                                                    ; refused, as it should be
```

A probe confirmed both readings, the second through `let r` as well. **Fixed**: `again` is vacuous only
for a variable bound outside the loop it goes round, tracked as the walk enters a loop's body
(`usedOn`'s `outer`), and is otherwise strict in its arguments. errors.md §7.1 and ADR 0043's status
line now say so.

| check | result |
|---|---|
| `TestAgainUsesOnlyWhatOutlivesTheJump` (new): inner binder dropped, passed, discarded with `ignore`, checked; outer binder used at the exit, and dropped | pass |
| planted fault: every `again` vacuous again | caught by that test |
| `cmd/check` emission | byte-identical: no exported program dropped a relevant value this way |
| the differential suite | pass: nor did any case's `run` |
| **`emit/tailctx_test.go`'s `TestAgainIsCheckedUnderEveryBinding`** | **failed**: its program, `(let (tuple v err) (sc.ParseInt "5" 10 64) (again "x"))`, drops a relevant error at the jump. The test is about the type checker seeing `again`'s argument, so its program now discards `err` with `ignore` |

So one test depended on the hole without knowing it, and none of the programs did.

## What was built

**`core/usage.go`, 𝒰 for relevance on trees.** The usage of a name is the hull of its counts over the
tree's paths (Cousot and Cousot 1977), or ∅ for a path that never reaches the end of the name's scope:
- sequence adds;
- the additive eliminators join their branches: `if`, `case`, the arms of `try` and `expect`, and a
  loop's clauses;
- `abandon` and a back edge of an outer loop end the path;
- a name handed on bare to a definition, or to a λ written in place, is used as that parameter is
  used in the receiver's body (usage inference).

"Used on every path that ends normally" is ∅ or a least count of at least 1.

**`emit/usage_agree_test.go`, the agreement on the corpus.** For every definition of every program
that loads on the Go target, and each of its parameters, the tree's usage is compared with the
reducer's usage inference (`Env.ParamUsed`, what the relevance check reads), field for field.

## What the build corrected in abstract.md §8

1. **A hand-off scales only a bare variable.** A compound argument is evaluated, so its uses count
   whatever the receiver does.
2. **A λ's body counts once, applied or not.** The draft's [0,∞] would refuse every use inside a λ
   passed to a host. errors.md §7.4 names the gap this leaves.
3. **`linear` is an ordering, not a count.** ADR 0018's buffer is read freely while live and moved at
   most once, with nothing read after the move but its length. That is Wadler's `let!` (1990). An
   interval forgets order, so usage is two judgements: a count semiring for relevance, and an ordering
   automaton for buffers, which is what `CheckLinear` already is.
4. **𝓔 is the core's effect judgement pulled back along D**, `impure(D(t))`. The bit depends on the
   target's purity and the definitions, which live where β reads them. A second rule, re-deriving on
   trees every shape D builds, would be a rule that can disagree with the first.

## Not built, and why

**The tree's linear check.** `CheckLinear` is seeded by type: a loop variable or a host call's result
is a buffer only by its type. On trees it would reach only the buffers a tree binds:

| buffers a tree binds | count |
|---|---:|
| `local` scopes in the corpus | 68 |
| `(buffer V)` parameters in program signatures | 2 |

The linearity tests mostly build residual terms of exactly the type-seeded shapes, so there is almost
nothing to hold a tree version against. It is built when the surface reports linearity at source
positions.
