# Where windows32's big-integer time goes: a zero fill and no reuse across the call

2026-11-17. Asked by hamza after [rangeload](rangeload-2026-11-17.md) ("Measure the allocation
first"), ahead of the plan's item 3. A measurement, with nothing built.

**On windows32, 20000! computed takes 132.5 ms, against Go's 15.7 ms on 386.** Allocation accounts
for about 43 ms of the 117 ms difference:
- every step's result is zero-filled, though it is born full;
- no step reuses the region the previous step freed, because the allocation and the death lie on
  two sides of a call.

Emulating both fixes makes the product 0.68×. On x86_64 the same allocations cost 4 ms of 31,
since its heap absorbs them. The other ~74 ms at 32 bits is compute and memory traffic, D5's.

## 1. The model

The loop is accᵢ = accᵢ₋₁ · i, for i ≤ 20000:
- log₂(20000!) ≈ 256,900 bits, so the final numeral has m ≈ 8,030 digits at w = 32 (4,015 at 64),
  each 8 bytes on both triples;
- each step runs `nat.mul_small`, which reads accᵢ₋₁ and makes a table of mᵢ + 2 words, and accᵢ₋₁
  dies there;
- by ADR 0100 and 0107, a dead region serves the next request of its capacity class, 2^⌈log₂ b⌉.

If reuse worked, the run would make about as many fresh allocations as classes it crosses, about
15, and otherwise one a step, 20,000. Σ mᵢ·8 is about 800 MB at w = 32 and 400 MB at 64.

## 2. The counts

A copy of each build's `main.ll` was instrumented (`scratchpad/alloc/instrument.py`; the compiler
unchanged). Every `HeapAlloc`, `HeapFree`, `VirtualAlloc`, `VirtualFree` and `RtlZeroMemory` call
is counted, its bytes summed and its time taken by `QueryPerformanceCounter`. Page faults come
from `K32GetProcessMemoryInfo` at exit. The program is 20000! with its remainder mod 10⁹ + 7
printed, and every run printed Go's answer.

| | windows32 | x86_64 |
|---|---|---|
| `HeapAlloc` with `HEAP_ZERO_MEMORY` | 20,000 calls, 800 MB, **69.9 ms**, 3.49 µs each | 20,000 calls, 400 MB, 3.0 ms, 0.15 µs each |
| `HeapFree` | 20,000 calls, 16.3 ms | 20,000 calls, 1.0 ms |
| page faults | **50,921** | 908 |
| in the allocator | **86 ms of 194** (instrumented) | 4 ms of 35 |

So the model's second case holds, with zeroing on top:
1. **One fresh allocation a step**, 20,000, where reuse would give about 15.
2. **Every allocation is zero-filled**, 800 MB of `memset` at about 11 GB/s, the 70 ms.
3. **Windows' 32-bit heap returns a freed large block as fresh pages**: 2.5 page faults a step. The
   x64 heap keeps the block warm, and the same pattern costs it 4 ms.

## 3. Why, and the algebra of each fix

### 3.1 The zero fill: the written prefix with a tail

ADR 0097's theorem proves a build born full when its loop writes b[i] at a counter from 0 and
leaves exactly on i ≥ n, n the build's count. `mul_small` leaves on i ≥ k, k = mᵢ, while its count
is n = k + 2, and its exit arm writes b[k] (the carry) and b[k + 1] (the header). So the theorem
does not apply, and the region is zeroed.

**The extension is an interval cover.** If the loop leaves on i ≥ k with n = k + c, c a constant,
and the exit arm stores b[k + j] for each j < c before any read of b, then

  W = [0, k) ∪ {k + j : j < c} = [0, k + c) = [0, n),

so every element is written before any is read, and the fill is dead.

It is a proof the analysis lacks, and its absence costs, never errs: a fill not proven dead is
kept. Measured by clearing the flag by hand (valid here, every zeroed allocation in the program is
`mul_small`'s), the product goes from 132.5 to **109.3 ms (0.825)**, the allocator from 86 to
19 ms.

### 3.2 Reuse across the call: a dead region as the callee's token

ADR 0100's equation is release(p) ; region(b) ≡ p (zeroed or not) when class(b) = class(p). R1b
and R1d apply it inside one function, across a region or a loop's back edge. Here:
- the fact loop's `acc` dies at each call `nat.mul_small(acc, i)`, released by the caller;
- the result is allocated inside the callee, where W13 requires it to be born (ADR 0101).

So the equation's two sides are in two functions, and nothing passes the token between them.

**The algebra.** In the loop, step i's call allocates while accᵢ₋₁ is live, and the region that died
last is accᵢ₋₂'s, released after step i − 1's call. The call commutes with the release: the callee
reads only its arguments, and none of them is p, which is dead. So

  release(p) ; f(x) = f′(x, p),

where f′ takes p as the token for its result's region, and ADR 0100's equation then holds inside f′.
That is destination-passing style (Shaikhha, Fitzgibbon, Peyton Jones and Vytiniotis, FHPC 2017),
and Perceus's reuse tokens passed to a callee (Reinking, Xie, de Moura and Leijen, PLDI 2021; Lean 4's
reset/reuse, Ullrich and de Moura, IFL 2019). In the steady state two regions alternate: Go's in
place z = z·x is the case of one.

**Measured by emulation**: a one-block cache in front of `HeapAlloc`/`HeapFree`, keeping a freed block
and its `HeapSize` for the next request it fits (`scratchpad/alloc/reuse.py`), on top of 3.1:

| windows32, 20000! product only, 9 interleaved rounds | median | vs the build |
|---|---|---|
| as built | 132.5 ms | 1 |
| no zero fill (3.1) | 109.3 ms | 0.825 |
| no zero fill, reuse across the call (3.2) | **89.6 ms** | **0.676** |
| Go `math/big`, 386 | 15.7 ms | |
| x86_64 as built / Go amd64 | 31.4 / 9.5 ms | 3.3× |

Page faults fall from 50,921 to 1,255, and the allocator's time from 86 ms to 3.

### 3.3 What is left: the digit's width

After both fixes the product is still 5.7× Go's on 386. Each step reads mᵢ words and writes mᵢ + 2,
8 bytes each, holding 32 bits: about 1.6 GB of traffic over the run, against Go's 640 MB in place at
4 bytes a digit. On top of that come the 64-bit index's `adc`/`sbb` and the spills that
`rangeload` read. A 4-byte digit with a 32-bit index is D5's representation (plan item 4), measured
there.

## Decisions this sets up

1. **The written prefix with a tail** (3.1): an extension of ADR 0097's proof, sound by the interval
   cover, with its planted fault. On windows32 it is worth 0.825 on this program. It needs no new
   surface.
2. **A dead region as a callee's token** (3.2): a change to ADR 0100's and 0101's design. An instance
   would take the caller's token for its result, and W12 and W13 be restated across the boundary.
   With 3.1 it is worth 0.676 here. It is significant enough for an ADR, and hamza's to decide.
3. **D5** (3.3), already in the plan, for the rest.
