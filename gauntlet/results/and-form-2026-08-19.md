# `p && q` versus `if p { q } else { false }`, 2026-08-19

The falsifier [booleans.md §6](../../docs/spec/booleans.md) asked for, run before writing any of
the proposal it tests.

## The question

[ADR 0012](../../docs/decisions/0012-portable-integer-range.md) rejected `(if a b false)` as the
meaning of `and`:

> All three hosts have short-circuiting `&&` natively; lowering to a conditional emits an
> if-statement and a temporary where the host has an operator.

That is CLAUDE.md's most-cited failure mode — *never lower further than the target requires* — so
it is the objection the proposal has to answer. **Is the nested form actually slower?**

There was also a reason to expect it might be *faster*. ADR 0015 measured that a compound loop
condition defeats Go's bounds-check elimination at 1.61×. A nested conditional is not a compound
condition.

Both forms are carried, per CLAUDE.md: `gauntlet/go/andform.go`, and a JS pair run one variant per
process (ADR 0015's rule — a shared call site measures V8's type feedback, not the code).

## Go — `go test -bench -benchtime=2s -count=5`

| | operator | nested | |
|---|---|---|---|
| value position, `p && q` | 1.42–1.56 ns | 1.50–1.66 ns | no difference |
| two-term guard, two arrays | 5617–6162 ns | 5613–6498 ns | no difference |
| three-term guard, 4096 elements | 10970–11038 ns | 9889–9970 ns | nested ahead, 1.11× |

The three-term row is the only separation, and the two sample sets do not overlap — every nested
run is faster than every operator run. **It is still 11%, which is below the ~15% noise floor this
machine is documented to have, so it cannot carry a decision.** It is recorded as "not slower",
not as "faster".

## Go — the compiler's decisions, not the clock

`go build -a -gcflags="-d=ssa/check_bce/debug=1"` reports **nothing** for `andform.go`. Every
bounds check is eliminated in *both* forms.

So the 1.11× is not bounds-check elimination, and **ADR 0015's 1.61× does not reproduce here**.
That result was an array index under a compound *bound*; this is a compound *predicate* over
already-loaded values. They are different shapes and only the first defeats BCE. Worth recording,
because the hypothesis was reasonable and wrong.

## JavaScript — V8 26.7, one variant per process

```
operator 12412 ns/call     nested  9091 ns/call     (first process: warm-up noise)
operator  4121 ns/call     nested  4144 ns/call
operator  4131 ns/call     nested  4094 ns/call
```

The first pair is JIT warm-up and is discarded; the two stable pairs are identical.

## Result

**The objection does not reproduce.** On Go the nested form is never slower and is marginally ahead
in one of three shapes; on JavaScript the two are indistinguishable. The premise ADR 0012 rejected
`(if a b false)` on — that lowering to a conditional costs something a host operator does not —
is not visible on either host at any of the shapes measured.

That clears the way for [booleans.md](../../docs/spec/booleans.md) candidate C, and it also lowers
the stakes on the peepholes that proposal describes: they are for **legibility** of the emitted
code, not for speed.

## Not measured

Java and windows. On windows the answer is structural rather than empirical — the host has no `&&`,
so there is no operator form to compare against — and Java is expected to track Go. Both should be
run before the proposal lands.
