# AoS against SoA: the access pattern chooses, not the host

2026-09-11. `gauntlet/go/aossoa.go`, `gauntlet/js/aossoa.mjs`,
`gauntlet/java/AosSoaBench.java`. [products.md §11](../../docs/products.md)
item 3, and the measurement [assessment-2026-09-09](../../docs/assessment-2026-09-09.md)
said *"could show part of what was built this week to be worth nothing. If every
host prefers the flat layout, the compiler's freedom to choose buys nothing and
the record is legibility alone."*

> **EVERY HOST DOES NOT PREFER FLAT, AND EVERY HOST AGREES ON WHICH LAYOUT WINS
> WHICH WORKLOAD.** SoA wins the column scan on all three hosts — **2.13x on Go,
> 1.69x on the JVM**, 1.12x on V8. Flat wins the random gather on all three —
> **SoA is 5.58x slower on Go, 3.94x on the JVM, 3.04x on V8**. The direction is
> the same everywhere; only the magnitude is a host property.
>
> **SO products.md §6 WAS RIGHT THAT THE CHOICE IS WORTH HAVING AND WRONG ABOUT
> WHO MAKES IT.** It said *"which one is emitted is a TARGET decision"*. Measured,
> it is a **PROGRAM** decision — the access pattern picks the layout and the host
> only scales the stakes. That is the opposite of `int-repr` and `big-repr`, where
> the host decides, and it means a per-target declaration is the wrong mechanism.
>
> **AND THE FLAT STRIDE THAT SHIPPED IS THE MINIMAX CHOICE.** Its worst case is
> 2.13x behind SoA on one scan; SoA's worst case is 5.58x behind flat. The product
> pass chose flat because the hand-written programs already had — and it turns out
> to be right for a reason nobody had stated.
>
> **AN ARRAY OF OBJECTS IS NEVER THE BEST LAYOUT, ON ANY HOST, FOR ANY WORKLOAD.**
> On Go the value struct IS the flat stride (identical on W1 and W3); on the JVM
> and V8 it is an array of references and loses everywhere but one cell. So "AoS"
> as a choice the compiler could make only ever means the flat stride.
>
> **AND THE FIRST VERSION OF THIS COMPARISON WAS MISSING ITS LOSING FORM.** Run
> with two workloads it said *SoA never loses* — because the one workload shaped
> for AoS ran on a table small enough for L1, where locality cannot matter. The
> third workload is what the rule *carry the form expected to lose* exists for,
> and it is the one that decided the result.
>
> **Cost: no compiler change.** Three new benchmark files; everything agrees on
> checksums pinned independently of all three layouts.

---

## 1. What the isomorphism says, and what it cannot

products.md §6:

```
    Π_{i∈I} (A × B)  ≅  (Π_{i∈I} A) × (Π_{i∈I} B)      array-of-structs ≅ struct-of-arrays
    Π_{(i,j)∈I×J} V  ≅  Π_{i∈I} Π_{j∈J} V              the flat stride
```

The three are the same object up to isomorphism, so the meaning of a program
cannot depend on which one is emitted. What the isomorphism cannot say is which is
*fast*, because that is a question about memory, and ADR 0008 says a host's
behaviour is measured rather than read off its documentation. This is that
measurement.

## 2. The design: one variable, three workloads

**The variable is the layout and nothing else.** The same algorithm, the same
element width on each host (`int` on Go, `int` on the JVM — rebench-2026-08-27
priced width at ~20% there, so it is held fixed — and plain `Array`s of Smis on
V8, which is what our emitter produces), no clamps:

| layout | Go | JVM | V8 |
|---|---|---|---|
| **flat** | `[]int`, `4*n+f` | `int[]`, `4*n+f` | `Array`, `4*n+f` |
| **SoA** | four `[]int` | four `int[]` | four `Array`s |
| **AoS** | `[]struct{tag,val,kid,sib int}` | `Node[]`, objects | `Array` of objects |

**Three workloads, because a layout wins or loses by access pattern:**

| | what it touches | size | expected winner |
|---|---|---|---|
| **W1** tree build and walk | all fields of one node, data-ordered | 443 nodes, **16 KB** | flat / AoS |
| **W2** column scan, `Σ val where tag = 2` | 2 of 4 fields of every node, in order | 65,536 nodes | SoA |
| **W3** random gather, all four fields | all fields of one node, random | 1,048,576 nodes, **32 MB** | flat / AoS |

W1 is the program products.md named — `tree.oro`'s node table. W2 and W3 are the
two access patterns a table has at a size where the layout can matter.

## 3. Measured

Median ns/op. Go: `-benchtime=3s -count=7`. V8: one `node` process per case,
median of 7, a sink the result escapes into. JVM: one JVM per case, median of 9.
In brackets, the ratio against flat on the same host.

| | **W1 tree** | **W2 scan** | **W3 gather** |
|---|---|---|---|
| Go flat | 4,371 | 32,368 | 206,360 |
| Go SoA | 4,095 (0.94) | **15,174 (0.47)** | **1,150,961 (5.58)** |
| Go AoS struct | 4,459 (1.02) | 38,635 (1.19) | 206,356 (1.00) |
| V8 flat | 10,377 | 58,072 | 300,215 |
| V8 SoA | 9,869 (0.95) | 51,663 (0.89) | **912,600 (3.04)** |
| V8 AoS objects | 12,283 (1.18) | 78,418 (1.35) | **986,820 (3.29)** |
| JVM flat | 5,227 | 32,720 | 159,665 |
| JVM SoA | 4,769 (0.91) | **19,337 (0.59)** | **629,500 (3.94)** |
| JVM AoS objects | 5,858 (1.12) | 35,290 (1.08) | 307,565 (1.93) |

The noise floor on this laptop is ~15%, so every W1 ratio and V8's W2 ratio are
inside it and are read as *no difference*.

## 4. What it says

### 4.1 The access pattern decides, and all three hosts agree on the direction

| workload | Go | JVM | V8 | winner everywhere |
|---|---|---|---|---|
| W1 (L1-resident) | ≈ | ≈ | ≈ | **none** |
| W2 scan | SoA 2.13x | SoA 1.69x | ≈ | **SoA** where it matters |
| W3 gather | flat 5.58x | flat 3.94x | flat 3.04x | **flat** |

No host prefers a layout for its own sake. **The answer's direction is a function
of the program; its magnitude is a function of the host.** A scan that reads two
of four fields streams half the bytes as SoA; a random visit that reads all four
costs one cache miss as flat and four as SoA. Neither fact is about Go, the JVM or
V8 — they are about memory, and all three hosts sit on the same memory hierarchy.

That inverts the shape of the decision products.md §6 proposed. `int-repr` and
`big-repr` are target declarations because the *host* decides what a 0..255 value
costs. Here the host does not decide anything — **the program's reads do**, and
whole-program reduction is what puts every read of a table in front of the
compiler at once. A per-target layout declaration would be the wrong mechanism,
and building one first would have repeated the `values` reversion.

### 4.2 The flat stride is the minimax choice, which is why shipping it was right

| | worst case against the best layout |
|---|---|
| **flat** | **2.13x** (Go, W2, behind SoA) |
| SoA | **5.58x** (Go, W3, behind flat) |
| AoS objects | 3.29x (V8, W3, behind flat) |

product-2026-09-09 §2.1 took flat *"because it is what `tree.oro`, `freq.oro` and
`kara/core.oro` already write by hand"*, and said that cannot cost speed. That was
true and incomplete. The stronger statement is that flat is the layout whose worst
case is least bad, so **a compiler that cannot see the access pattern should emit
flat** — which is what it does.

### 4.3 An array of objects is never the choice

On **Go**, `[]struct{…}` is the same bytes as the flat stride and measures the same
on W1 and W3 (206,356 against 206,360 ns). On the **JVM** and **V8** it is an array
of references, and it is the worst or near-worst layout in every column but one —
the JVM's W3, where it beats SoA by 2.05x and still loses to flat by 1.93x.

**That corrects g2-structs' Java figure in scope.** g2 measured `Point[]` at 1.05x
against parallel arrays, and explained it: *"HotSpot's bump allocator lays freshly
built objects out contiguously, so iterating `Point[]` is near-sequential despite
the indirection."* True, and it is the case of objects **visited in allocation
order**. Visited at random, the indirection is a second miss per node and costs
1.93x against flat. The allocator makes objects contiguous; it cannot make a random
access pattern sequential.

So the three layouts the compiler could choose between are really **two**: the flat
stride and SoA. "AoS" is the flat stride, wherever a host can express it.

### 4.4 The node table itself does not care

W1 is `tree.oro`'s real table, 443 nodes and 16 KB, and every host puts all three
layouts within the noise floor. **For the program products.md named, the freedom to
choose buys nothing** — and that is not a refutation, because the table is small by
construction (`build` fixes its capacity at 512). The layout matters past cache, and
nothing in this repository's corpus has a product table that large yet.

## 5. The first version missed its losing form

The comparison was designed with W1 and W2, and W1 was labelled *AoS's workload*
because it touches all four fields of a node. The first run said:

> SoA wins or ties everywhere; it is never worse.

That would have been written down as *emit SoA*, and it would have been wrong by
5.58x on the first large table accessed at random. **W1 has AoS's access pattern at
a size where locality cannot matter** — 16 KB sits in L1 whatever the layout — so
it measured address arithmetic (SoA's `tag[n]` has no `4*n+f`), not locality.

The rule gauntlet.md states — *carry the form expected to win AND the form expected
to lose* — was followed in letter and missed in substance: the losing form was
present, at a size where it could not lose. W3 is the same access pattern at a size
where it must, and it decided the result. **A workload is only the losing form if it
can actually lose.**

## 6. One thing measured and not explained

On Go's W2, the `[]struct` scan is **1.19x slower** than the flat scan, although the
two are the same bytes, 7 runs each with non-overlapping spreads (35,546–40,439 ns
against 30,111–33,493). The obvious explanation is bounds checks, and the compiler's
own output refutes it:

```
go build -gcflags='-d=ssa/check_bce/debug=1'
./aossoa.go:266:11: Found IsInBounds     ScanFlat, nodes[i]
./aossoa.go:267:14: Found IsInBounds     ScanFlat, nodes[i+1]
                                         ScanAoS: none
```

The flat scan keeps two bounds checks per iteration and the struct scan keeps none —
and the struct scan is the slower one. **Recorded as unexplained rather than given a
cause.** It is 1.19x, just past the noise floor, and it does not bear on any decision
here, because the struct form is never emitted: on Go it is the flat stride, and the
flat stride is what the product pass writes.

## 7. What it leaves

**A layout rule the compiler could apply, and should not yet.** The measurement
points at one: *a product table whose every read in the program is a sequential loop
touching a strict subset of its fields is SoA; anything else is flat.* Whole-program
reduction makes that decidable — the residual holds every read. But it rests on one
program and two synthetic workloads, the program's own table is too small to care,
and ADR 0008 says a rule built on that little is a principle waiting to be refuted.
**The trigger is a real program with a product table past cache**, and none exists.

**products.md §6's sentence needs correcting where it stands**, and is: the choice is
a program decision, not a target one.

**And the three numbers the assessment asked for exist now.** The answer to *does the
compiler's freedom to choose buy anything* is **yes, up to 5.6x — but the program
chooses, not the target, and the default the compiler already emits is the safe one.**
