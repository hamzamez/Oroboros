# A declaration is a directive, so it moves onto the term

2026-09-03. `core/reduce.go` (`AscribeName`, `ascribeResult`), `emit/target.go`,
`emit/bigrep.go` (`ascribedBig`, `eraseAscriptions`), `emit/interval.go`.

The build of [inlining-and-declarations.md](../../docs/inlining-and-declarations.md)'s
option (a), on hamza's *"a powerful type system should be able to prove or infer
everything about a function from its signature… that information will propagate
through the program safely and confidently, statically checked, using the best
representation at the end."*

**That model is right and is already the architecture** — `int-repr`, `big-repr`
and element widths all work exactly that way. What it needs is a *source* of
facts, and there are only two: derivation and declaration. This closes the case
where derivation provably cannot substitute for declaration.

## 1. The experiment that decided the design

Before building anything, the obvious cheaper answer was tested: **can the
analysis just derive the magnitude?** The loop has a constant trip count of six
and a constant multiplier, so a bound is computable in principle.

```
(* acc 999983)      →      [-inf, +inf]
```

It widens. And that is not a precision gap worth chasing, because the general
case is worse: a factorial's bound is `n!`, which is not expressible in an
interval domain at all.

**So derivation cannot replace the declaration here, and the declaration was
being erased.** That is the whole justification for what follows; without this
measurement the right answer would have been to improve the analysis.

## 2. What was broken

```
(sig scaled ((n (int 0 50))) (int 0 (pow 2 200)))
(def scaled (fn (n) (loop ((acc (+ n 7)) (i 0))
                      (>= i 6) acc else (again (* acc 999983) (+ i 1)))))
(sig run ((n (int 0 50))) int)
(def run (fn (n) … (scaled n) …))
```

`scaled` emitted alone is correct. Called from `run`, the program is **refused** —
reduction inlines `scaled`, the declaration was attached to a boundary, and
whole-program reduction removes every boundary that is not an entry point.

ADR 0019 has three escapes and this is the third — declare a range above the
window — which is **the only one that gives exactness** and the only one with
nowhere to live for a value that is neither a parameter nor a result.

## 3. Why the trichotomy did not apply, which is the finding

refinements.md §6b argues that dropping an internal `where` is a *strengthening*:
inlining lands the body's obligations on the caller's concrete values, which
beats checking a conservative summary. postconditions.md §3, indexnarrow and
scalarrange all repeat it. **Those four are about FACTS and the argument is
sound.**

A range above the window is a **directive**. It does not assert something the
compiler checks; it requests arbitrary precision. Inlining gives more information
about values and none at all about intent, so removing the boundary removes the
only record of the instruction.

> **The trichotomy holds for what a declaration ASSERTS and fails for what it
> REQUESTS.** Nothing here had separated those, because until arbitrary precision
> every declaration was an assertion.

A range's three effects split exactly on it: the **type** survives (the checker
re-derives it), the **premise** is correctly dropped, the **representation** is
destroyed.

## 4. What was built

`core.LoadWith` moves a declared result above the window onto the definition's
body:

```
(def scaled (fn (n) (the "int 0 1606938…" (loop …))))
```

- **No new term kind.** `the` is a structural name injected into every target the
  way `if`, `let` and `loop` are (`coreStructural` + `coreNames`), and a target
  may neither decline nor declare it.
- **No new type representation.** The payload is the canonical string
  `TypeName` already produces for a signature, so every consumer uses the same
  `ExceedsWindow` and `IntRangeBig` it uses on one. An endpoint may be an
  expression, and `TypeName` has already evaluated it at arbitrary precision.
- **No new surface.** The programmer already wrote the declaration; the compiler
  stops losing it.
- **Erased in one place** — `PromoteBig`, after the solver has read it and before
  the type checker runs. That is `LowerLimbs` removing `big-of-small`, and it is
  why no backend learns that ascriptions exist.

The solver needed almost nothing: an ascription is a **demand** in the same
`prim.Args[i] == big` sense every other position uses, and `bigTerm` answers from
the range it carries. The bidirectional solver was already right; it had lost its
seed.

## 5. Three bugs, and two were already there

**A widen inserted by the REPORTING pass.** `p.demandBig` was honoured whether or
not the pass was selecting a representation, so once the ascription was erased
the reporting pass could no longer tell a `let`-bound value was a bignum and
wrapped it again — `big-of(x)` on an `x` that is already a `*big.Int`, which Go
refuses. It appears only under `-checked`, whose emitted term is the reporting
pass's, and only in a `main` with no signature to seed from.

That is the **second** instance of exactly this: emit/interval.go's own comment
records `selectBig` firing during the reporting pass, and says *"a pass either
selects a representation or reports on one already selected, and the two are
exclusive."* Inserting a widen is a selection. It is gated now.

**`big%-small` had no transfer function**, so its result was ⊤ and every ordinary
word operation reading a digit group was unprovable — a program that renders a
bignum refused for arithmetic on values under 10⁸. `a % k` is bounded by `k`;
that is the whole reason the operation has an `int` result, and the analysis was
not told. Pre-existing, from earlier the same day, and invisible because the
differential harness builds with `-checked`.

**And the ascription had to be read before it was erased**, which is not a bug
but is the ordering the build got wrong first: wrapping without teaching
`bigTerm` broke the *working* path, because the marker sat between the signature's
demand and the loop.

## 6. Cost

- **No emitted file changes** — 70 programs × 4 targets byte-identical. Every
  definition in the corpus that declares a big result is an entry point, where
  the signature already reached the solver. **The corpus cannot exercise this**,
  which is a reason for the tests below rather than for confidence.
- `BenchmarkBigFactGen` 2,032 ns and `BigFactBounded` 2,256 — unmoved.
- Compiler suite, 25-case differential suite on four targets, gauntlet bignum
  tests green.

## 7. What checks it

`gauntlet/differential/cases/big-divmod.oro` is now written in the shape that was
refused — a non-exported helper declaring a big result, called from a `run` that
returns an ordinary `int` — and it runs on **six variants**:

```
ok  big-divmod  96453661 1000036777705  [go/host go/limbs js/host js/limbs java/host java/limbs]
```

so the promoted arithmetic is checked against `math/big`, `BigInt` and
`BigInteger`, in both storage choices, with the digits computed independently.

Three unit tests: the inlined accumulator is promoted and the marker does not
reach the backend; **the same loop without the declaration is refused with
`[-inf, +inf]`**, which is the §1 experiment pinned so that a future analysis
improvement is noticed rather than assumed; and no target declares `the`.

## 8. What this does not do

**It does not give a value with no helper anywhere a place to say this.** A big
accumulator inside `main` still has no declaration site. The mechanism is
general — `the` carries a range, not a flag — so exposing `(the TYPE e)` in the
reader is a small step, but it is a language construct and owes a spec, and it
should be motivated by a program rather than by symmetry.

**It does not enforce anything.** `the` carries a range and is erased; the
runtime enforcement of a declared bound is `big-fit` and the limb rung's `guard`,
which are a separate and already-built mechanism. A narrow ascription would need
one of them to be a *door* in hamza's sense — checked once, then trusted — and
that is the natural next use of the same construct.

**And it does not touch the four facts.** A `where`, an `ensures`, a narrowed
index and a declared scalar range are still dropped on an internal definition,
and that is still correct: inlining gives strictly more information about values.
Only intent had to move.
