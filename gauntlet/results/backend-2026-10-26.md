# backend-2026-10-26: MASM, C or LLVM IR for the native targets, measured

The 10-24 plan's item 6a (hamza, 2026-10-24): "for windows do we keep going with targeting masm, or do
we target llvm IR instead … llvm IR let us target every major architecture out of the box, on the other
hand, it could duplicate work and it may introduce checks that we dropped because of our type system.
we have to weigh our options and pick the best path forward." Decided by
[ADR 0080](../../docs/decisions/0080-the-native-targets-print-llvm-ir.md).

## 1. What a backend is

A backend is a map h_T : IR_P → L_T from the IR's text (ADR 0038) into a target language, and it is
correct when it preserves meaning: ⟦h_T(p)⟧_T = ⟦p⟧ for every p the IR accepts (semantic preservation,
Leroy's CompCert). Three languages were candidates for the native targets:

- **M, MASM**: x86-64 assembly, `ir/x86` (2,474 lines with its 398 lines of tests) and `targets/windows/x64.oro`'s
  instruction templates (264 lines). Exact machine semantics: wrapping words, and a hardware trap on `idiv`
  by zero.
- **C**: C11, compiled by MSVC's `cl` or clang. ADR 0004 deferred C "until iOS, embedded, or native
  desktop is actually wanted"; TinyRetroPad is a native desktop application, so the trigger is met.
- **L, LLVM IR**: the textual IR, compiled by clang or llc (Lattner and Adve, CGO 2004).

**The two questions hamza named, answered by the derivation:**

1. **"It may introduce checks that we dropped."** LLVM inserts no check. It has undefined behaviour,
   preconditions an operation's producer promises, and **each one the language can reach is an obligation
   the IR already discharges or refuses**: a signed operation's overflow (`nsw`) is ADR 0019's bounded by
   default; `sdiv`/`srem` by zero is a precondition (integers.md §5); INT_MIN / −1 lies outside the word; an
   out-of-bounds address (`inbounds`, a load) is an index obligation; shifts are not in the language. So
   h_L can state the proofs as LLVM's assertions, `exact` as `nsw` (and `nuw` when both operands are proven
   non-negative), an index as `inbounds`, and if every obligation is proven, h_L(p) has no undefined
   behaviour and preserves meaning (Lee et al., "Taming Undefined Behavior in LLVM", PLDI 2017, for poison's
   semantics). The direction is the reverse of the worry: **what the type system proves becomes facts the
   optimizer uses**, which MASM cannot use at all and C can only partly state (§3).
2. **"It could duplicate work."** The analyses are not duplicated: LLVM proves less than the IR (its range
   analyses do not reach ours) and receives the IR's proofs as flags. What LLVM replaces is the code
   generation `ir/x86` does by hand: instruction selection, register allocation (ours optimal by
   chordality, Hack, Grund and Goos 2006), the frame and the calling convention. That is a deletion, not a
   duplication, and the alternative is one such printer per instruction set.

## 2. The experiment

`experiments/backend/`, rebuilt from source by `build.bat LLVM_BIN_DIR`:
- two programs in the language's own operators, so one IR_P exists for every target: **`sieve.oro`** (100
  rounds of a 200,000 sieve, 1,798,400) and **`msort.oro`** (a bottom-up merge sort of a 100,000-element
  permutation, 20 rounds, the differential case `merge-sort` at size);
- **one IR_P each**, written by `cmd/gen -ir` for the windows target; **MASM** by `ir/x86`; **C and LLVM IR
  by a prototype printer** (`print/main.go`, 527 lines, the two printers' subset) that reads the IR's text
  with the IR's reader, the windows target's layout (an 8-byte length, then a byte per boolean and a qword
  per integer, allocated by `VirtualAlloc`), region parameters as slots that mem2reg makes φs;
- **one C driver** linked with each object, timing `gen_bench` in-process with the performance counter, so
  only the generated function differs; 11 interleaved rounds, one process at a time;
- the toolchains: MSVC 14.44 (`ml64`, `cl`, `link`); **LLVM 23.1.4, the official release**
  (clang+llvm-23.1.4-x86_64-pc-windows-msvc, downloaded 2026-10-26 with hamza's approval, kept in the
  session's scratchpad, not installed).

Every build of a program gives the same answer: 1,798,400 and 6,689,817,084.

## 3. Results

**Speed**, median ms and ratio to MASM's median (11 interleaved rounds; absolute times moved between
sessions with the machine's load, the ratios held across three sessions to ±0.03):

| | MASM | C, `cl -O2` | C, clang `-O2` | LLVM IR `-O2` | LLVM IR `-O2` + select | LLVM IR `minsize -Oz` |
|---|---|---|---|---|---|---|
| sieve | 113.2, 1.00 | 71.0, 0.63 | 116.2, 1.03 | 111.6, 0.99 | **71.8, 0.63** | **66.9, 0.59** |
| merge sort | 351.8, 1.00 | 154.3, 0.44 | 191.9, 0.55 | 122.6, 0.35 | **123.9, 0.35** | 346.4, 0.98 |

**Code size**, bytes of `gen_bench`:

| | MASM | C, `cl` | C, clang | LLVM IR `-O2` | + select | `minsize -Oz` |
|---|---|---|---|---|---|---|
| sieve | 236 | 201 | 252 | 338 | 528 | **182** |
| merge sort | 836 | 888 | 1,135 | 989 | 989 | **424** |

**Compile time** of the sort's file, median of 7: `ml64` 20 ms, clang on the `.ll` 97 ms, `cl` 135 ms,
clang on the `.c` 120 ms.

**Reach**: the sieve's printed `.ll`, its triple and its allocation's declaration changed and nothing else,
compiled for x86-64 and **i686 Windows** (COFF i386), ARM64 Windows, x86-64 and AArch64 Linux (ELF), ARM64
macOS (Mach-O) and wasm32: one printer, seven targets. One llc binary registers x86, x86-64, AArch64, ARM,
RISC-V, WebAssembly and NVPTX.

## 4. What made each number

Each surprising number was made to explain itself before it was recorded:

- **The sort's 2.9× is the division.** `key` is `(37 * (i + s) + 11) % 100003`; `ir/x86` emits `idiv` three
  times, clang none: a division by an invariant becomes a multiplication by its reciprocal (Granlund and
  Montgomery, PLDI 1994). Closing it in MASM is reimplementing that, and if-conversion, and the rest of an
  optimizer, per instruction set.
- **The sieve's 0.63 is a branch.** Counting the unmarked bytes, `if c[k] then k+1 else (acc+1, k+1)`, is a
  data-dependent branch that mispredicts on the primes' irregular pattern. `cl` if-converted it to `cmov`;
  clang on the same C did not (1.03). The IR knows both arms only go round the loop with pure arguments,
  so the printer can say so, one `continue` through `select`, sound under poison since `select` takes none
  from the operand it does not choose (LangRef). With that, LLVM IR equals `cl`'s 0.63 and does not depend
  on one C compiler's heuristic.
- **The same compiler, two inputs: 0.35 against 0.55.** clang on the printed LLVM IR beats clang on the
  printed C of the same IR_P by 1.6× on the sort. The difference is what each language can state: the IR's
  proofs as `nuw`/`nsw`/`inbounds`, where C can only say "signed". This is the information channel the
  derivation predicts, measured. The type system knows more that LLVM can take and MASM cannot (distinct
  buffers never alias, by R0–R4: `noalias`); not yet printed.
- **`-Os` changed nothing; `minsize` halved the sort.** A `.ll` input gets the size attributes only from its
  printer, not from the command line: the printer states `minsize optsize`, as it states `nounwind` (no
  function of ours unwinds, so no unwind tables). Size-first, the sort keeps its `idiv`s and runs at MASM's
  speed with half its code.

**So MASM is dominated on both programs**: LLVM `-O2` is faster (0.63 and 0.35), LLVM `minsize` is smaller
(0.77 and 0.51 of the code) at no worse speed (0.59 and 0.98). C is good under `cl` and depends on which C
compiler it meets (0.63 against 1.03 on one file), and it cannot carry the IR's facts (0.55 against 0.35
under one compiler).

## 5. What it costs

- **A toolchain**: clang and a linker. On Windows, Visual Studio's "C++ Clang Compiler for Windows"
  component, in the same workload as the MSVC this repository already requires, or LLVM's release. On
  macOS, Android's NDK and Linux, LLVM already is the native toolchain.
- **The text is not stable.** LLVM's developer policy: "The textual format is not backwards compatible. We
  don't change it too often, but there are no specific promises"; bitcode loads back to 3.0. The printed
  subset (integers, `ptr`, `getelementptr`, `load`, `store`, `icmp`, `select`, `br`, `call`, `alloca`) has
  had one syntax since opaque pointers (LLVM 15, 2022).
- **A wrong proof becomes a miscompilation rather than a wrong answer**: an `nsw` the IR did not earn is
  undefined behaviour. The proofs are theorems or refusals with planted faults (ADR 0019, 0038), and the
  flags are a function of them, so a build that prints none exists for diagnosis.
- **80 ms of compile per file.**

## 6. Not measured, and why

- **A whole program's size under Crinkler**: Crinkler packs COFF objects whatever produced them, and the
  PE overhead is the linker's, the same on every path; code size, measured, is what differs.
- **Calls, callbacks and records** (6b, 6c): the benchmarks call one Win32 function. LLVM states the
  calling conventions (`x86_stdcallcc`, Win64) and struct layout from the target's data layout, which is
  what 6c's walls need; that is a claim for 6c to measure.
- **An older LLVM**: only 23.1.4 was run. Visual Studio's clang component is an older release, at or above
  LLVM 15.
- **More programs**: two. Both kinds of cost a native backend has, memory in loops (the sieve) and
  arithmetic with data-dependent control (the sort), are covered; the differential suite's windows cases
  are the parity test when the printer is built.
