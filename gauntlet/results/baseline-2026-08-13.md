# Gauntlet baselines — 2026-08-13

Hand-written reference implementations, measured. These are the numbers any candidate core
must reach parity with, and the first check on claims the derivations made about host
compilers.

**Five claims confirmed. Five refuted. Five findings nobody predicted**, one of which
constrains the core's identity.

> **⚠ Read with [duplicate-read-2026-08-14](duplicate-read-2026-08-14.md).** That run found code
> alignment producing a **stable, reproducible 45% difference between byte-identical machine
> code**. The ~15% noise floor quoted below is therefore too small for comparisons between
> *similarly shaped* code. Large findings here are unaffected; anything resting on a margin under
> roughly 50% should be re-checked by diffing the machine code before it is relied on.

## Environment

| | |
|---|---|
| CPU | 12th Gen Intel Core i5-12500H (hybrid P/E cores) |
| OS | Windows 11 |
| Go | 1.26.5 windows/amd64 |
| Node | 26.7.0 (V8) |
| Java | OpenJDK 17.0.12, HotSpot 64-Bit Server VM |

**Measurement caveat.** This machine produced occasional ~3× fast outliers across unrelated
benchmarks — consistent with hybrid P/E-core scheduling. All figures below are **medians**,
with outliers visible in the raw output. Anything under ~15% should not be treated as a real
difference on this hardware.

Two sizes are reported where it matters. At n=65536 a `float64` slice is 512KB and the loops
are memory-bound, which hides everything the compiler does. n=1024 is 8KB and L1-resident.

## Confirmed

### C1 — Non-capturing closures are statically allocated (g6)

| Go | ns/op | B/op | allocs/op |
|---|---|---|---|
| `BuildOps` (3 non-capturing) | 18–27 | 24 | 1 |
| `MakeScaler` (captures `f`) | 14–15 | 16 | 1 |
| `RunOp` (indirect call) | 1.55 | 0 | 0 |

`BuildOps`'s single 24-byte allocation is the *slice* of three function pointers; the closures
themselves cost nothing. The capturing closure allocates its 16-byte environment. Indirect
dispatch is 1.55ns. **g6's cost model holds: escaping closures are affordable and cost what
hand-written costs.**

### C2 — `ys[:len(xs)]` hoists the bounds check (g1) — structurally

`go build -gcflags="-d=ssa/check_bce/debug=1"`:

```
gauntlet.go:27  Found IsInBounds        DotNaive     — ys[i] checked in the loop
gauntlet.go:34  Found IsSliceInBounds   DotHoisted   — one check, outside the loop
gauntlet.go:46  Found IsInBounds        DotRange     — ys[i] checked in the loop
```

The idiom works exactly as g1 described. See R2 for why it does not matter.

### C3 — Go's `m[k]++` beats get-then-set (g4) — but by 1.23×, not 2×

| Go, n=65536 | ns/op |
|---|---|
| `WordCountIncr` (`m[w]++`) | 1,959,729 |
| `WordCountReadWrite` (`m[w] = m[w]+1`) | 2,408,772 |
| `WordCountGetOr` (explicit get-or/set) | 2,404,768 |

**1.23×, where [g4 §7](../../docs/derivations/g4-word-count.md) claimed "roughly 2×."**
Directionally right, magnitude wrong — the loop also pays for `strings.Fields` and string
hashing, so the extra lookup is not the whole cost.

**Re-checked 2026-08-14** after the alignment finding put every sub-50% margin in doubt. The
timing is *not* the good evidence here; the machine code is:

| | map runtime calls |
|---|---|
| `WordCountIncr` (`m[w]++`) | **one** `mapassign_faststr` |
| `WordCountReadWrite` | `mapaccess` **plus** `mapassign` |

One hash lookup against two, structurally. **The capability-granularity finding stands on that,
not on the 1.23×** — which remains within the range alignment can distort and should not be
quoted as a magnitude.

### C4 — Array-of-objects loses on JS (g2)

| JS, n=65536 | ns/op |
|---|---|
| `centroidAoS` (array of `{x,y}`) | 96,807 |
| `centroidSoA` (parallel `Float64Array`) | 33,891 |

**2.86×.** [g2's](../../docs/derivations/g2-structs.md) central claim, confirmed on JS.
See R3 for Java, where it does not hold.

### C5 — Float formatting diverges (g5)

| Expression | Go | JS | Java |
|---|---|---|---|
| `1.0` | `1` | `1` | `1.0` |
| `1e8` | `1e+08` | `100000000` | `1.0E8` |
| `1e21` | `1e+21` | `1e+21` | `1.0E21` |
| `-0.0` (runtime) | `-0` | `-0` | `-0.0` |
| `1.0/3.0` | `0.3333333333333333` | same | same |

Confirmed. `print-line` cannot be Tier 1 without implementing formatting ourselves.

## Refuted

### R1 — Go *does* inline a generic fold with a func-value parameter

[g3 §8](../../docs/derivations/g3-generics.md) claimed Go would not remove the indirect call
"the callee being a parameter inside a loop." **False.**

```
gauntlet.go:133:13: inlining call to Fold[go.shape.float64,go.shape.float64]
gauntlet.go:133:13: inlining call to SumF64Generic.func1
```

| n=1024 | mono | generic + func value |
|---|---|---|
| Go sum | 1,339 ns | 1,324 ns |
| Go countPositive | 1,137 ns | 1,146 ns |
| JS sum | 456 ns | 453 ns |
| JS countPositive | 544 ns | 498 ns |
| Java sum | 1,362 ns | 1,440 ns |

All three hosts specialize a **literal** callback. **g3's counterexample to ADR 0002 survives
only in a narrower form:** where the function exceeds the host's inlining budget, or where the
callee is not statically known. Go's budget is visible and low — `Bounds` at cost 83 and
`WordCountReadWrite` at cost 82 were both rejected against a budget of 80.

The deeper correction: the hosts perform *the same specialization we do, under the same
condition* — the callee must be literal at the call site. We win only above their budget.

### R2 — Bounds-check elimination buys nothing measurable

| n=1024, Go | ns/op |
|---|---|
| `DotNaive` (ys[i] checked) | 1,383 |
| `DotHoisted` (check hoisted) | 1,389 |
| `DotRange` | 1,399 |

Identical, in L1, with the check verifiably present in one and absent in the other. The loop is
bottlenecked on the **serial dependency of `acc +=`** — 1.35ns/element is roughly 4–5 cycles,
which is the latency of a chained float64 add.

g1 §7's claim that range types let us "beat naive hand-written Go" **is not supported**. The
optimization is real and worth nothing here.

### R3 — Java's `Point[]` does *not* lose the way JS's array-of-objects does

| Java, n=65536 | ns/op |
|---|---|
| `centroidAoS` (`Point[]`) | 93,455 |
| `centroidSoA` (parallel `double[]`) | 88,924 |

**1.05×.** HotSpot's bump allocator lays the freshly-built objects out contiguously, so
iteration is near-sequential despite the indirection. g2 predicted Java and JS would fail the
same way. **Only JS does.**

### R4 — JS should emit a null-prototype Object, not `Map`

| JS, n=65536 | ns/op |
|---|---|
| `wordCountMap` (`new Map()`) | 20,546,287 |
| `wordCountObject` (`Object.create(null)`) | 6,320,347 |

**3.25× the other way.** [g4's](../../docs/derivations/g4-word-count.md) pass condition — that
JS output must contain `Map` — was written from assumption. For string-keyed counting the plain
object wins decisively.

### R5 — "Never split finer than the target's fused idiom" is target-dependent

> **DOES NOT REPRODUCE, 2026-08-25** —
> [native-java-2026-08-25](native-java-2026-08-25.md). Re-run on JDK 17.0.12 using the two
> functions below, unchanged: `merge` is **0.93×** of `getOrDefault`, and **0.84×** with `split`
> hoisted out of the timed region and one JVM per form. The unfused number reproduces; the fused
> one is 2.5× better than recorded, and the fused form is now the FASTER of the two.
>
> The reasoning below is left as written, per this repository's convention. What survives it is the
> conclusion — *which granularity wins is a per-target measurement, not a principle* — which a
> measurement moving under a five-month-old finding demonstrates rather than damages. What does not
> survive is the example.

| Java, n=65536 | ns/op |
|---|---|
| `wordCountMerge` (`merge(w, 1, Integer::sum)`) | 9,259,530 |
| `wordCountGetOr` (`put(w, getOrDefault(w,0)+1)`) | 3,577,103 |

On Java the **unfused** form wins by 2.6× — `merge` pays for boxing and a per-entry functional
call. Go's fused `m[k]++` wins; Java's fused `merge` loses.

The g4 law needs restating: the fused idiom is not reliably the fast one. **Which granularity
wins is a per-target measurement, not a principle.**

## Unpredicted

### U1 — Left-to-right summation costs 5–7× on Go

| n=1024 | strict L-to-R | 4 accumulators | ratio |
|---|---|---|---|
| Go dot | 1,389 ns | 267 ns | **5.2×** |
| Go sum | 1,360 ns | 189 ns | **7.2×** |
| JS dot | 473 ns | 301 ns | 1.6× |
| Java dot | 458 ns | 198 ns | 2.3× |

[g1 §8](../../docs/derivations/g1-dot-product.md) decided `sum` must be left-to-right, on the
principle that float addition is not associative and an unordered sum would differ per target.
That decision was made with no number attached. **The number is 5–7× on the primary target.**

This does not reverse the decision — determinism is worth paying for — but `sum-unordered`
stops being a footnote and becomes the form most numeric code will actually want.

### U2 — Java's JIT appears to already reassociate FP reductions

Java's `dot` at n=1024 runs at 458ns against Go's 1,389ns for the same source. 458ns over 1024
elements is ~0.45ns/element, **below the serial float-add latency floor**, which a strict
left-to-right reduction cannot reach. C2's SuperWord reductions are the likely cause.

If so, **hand-written Java is already not deterministic under reassociation**, and "parity with
hand-written Java" conflicts with "strict IEEE left-to-right" on that target. Worth confirming
with `-XX:-SuperWordReductions` before relying on it.

### U3 — Go's constant arithmetic is arbitrary-precision, and this breaks naive staging

```
const-folded  0.1+0.2 = 0.3
runtime       a+b     = 0.30000000000000004
const-folded  -0.0    = 0
runtime       -a*0    = -0
```

Go evaluates untyped float constants at **arbitrary precision**, rounding once at the end. The
same expression evaluated at runtime uses IEEE-754 binary64 throughout and gives a different
answer.

**This is the most important result in the run**, because it lands directly on
[g6's](../../docs/derivations/g6-escaping-closures.md) identity — *everything is a function,
evaluated at compile time*. If compile-time arithmetic differs from runtime arithmetic, then
**binding-time analysis changes the program's results**, and partial evaluation is unsound over
floats.

The constraint that follows is concrete and easy to get wrong, especially since the compiler is
itself written in Go:

> **Compile-time float arithmetic must use exactly IEEE-754 binary64, identical to runtime.
> No arbitrary-precision constant folding. Staging must never change an answer.**

### U4 — `Float64Array` is not obviously the right JS representation

| JS dot | ns/op |
|---|---|
| n=65536, `Float64Array` | 53,522 |
| n=65536, plain `Array` | 33,281 |
| n=1024, `Float64Array` | 474 |
| n=1024, plain `Array` | 486 |

At L1-resident size they are equal; at 512KB the **plain array is 1.6× faster**. Unexplained —
V8's `PACKED_DOUBLE_ELEMENTS` may get better locality than an `ArrayBuffer`. Flagged for
investigation, not concluded.

The lesson holds regardless: the obvious representation choice for a target needs measuring.

### U5 — Word count is the one program where targets differ by an order of magnitude

| n=65536 | ns/op |
|---|---|
| Go (`m[w]++`) | 1,959,729 |
| Java (`getOrDefault`) | 3,577,103 |
| JS (`Object.create(null)`) | 6,320,347 |
| JS (`Map`) | 20,546,287 |

A 10× spread between the best Go and the worst JS on the same program. Parity is per-target, so
this is not a failure — but it does mean the Parasite model's "use what the host is good at"
has real consequences for which target a workload belongs on.

## What this changes

1. **[g3's](../../docs/derivations/g3-generics.md) counterexample to ADR 0002 is much weaker
   than written.** All three hosts specialize literal callbacks. Rewrite the claim to cover
   only the above-budget and non-literal-callee cases.
2. **[g1's](../../docs/derivations/g1-dot-product.md) bounds-check win does not exist.** The
   `require` form is still justified — by correctness and by not rejecting valid programs — but
   not by performance.
3. **[g4's](../../docs/derivations/g4-word-count.md) pass condition is wrong for JS**, and its
   granularity law is target-dependent rather than universal.
4. **[g2's](../../docs/derivations/g2-structs.md) AoS penalty applies to JS only**, which
   shrinks the representation problem from "two of three targets" to one.
5. **[g6's](../../docs/derivations/g6-escaping-closures.md) identity gains a hard constraint**
   (U3): staging must not change results, so compile-time float arithmetic is IEEE-754
   binary64, exactly.
6. **`sum-unordered` is promoted** from a footnote to the form most numeric code wants (U1).
