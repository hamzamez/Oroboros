# Bounds-check elimination as an emitter pattern

**Result: the pattern provably removes the per-iteration check on every generated program, is
free, and is worth 1.96× on compute-bound loops and *nothing* on memory-bound ones.**

That last clause corrects [types-direction §1](../../docs/types-direction.md), which cited 1.94×
as the largest lever this project has measured without saying what it was measured on.

---

## 1. The pattern

Our own proof buys nothing — Go's bounds-check elimination has never heard of us
([types-direction §2.1](../../docs/types-direction.md)) — so the only thing that works is
**emitting a shape the host re-proves for itself**:

```go
acc := 0.0
n1 := (len(p))
p = p[:n1]        // ← added
q = q[:n1]        // ← added
for i := 0; i < n1; i++ {
    acc = (acc + ((p[i]) * (q[i])))
}
```

It is expressed as **data, not backend knowledge**:

```lisp
(narrow "%s = %s[:%s]")                                  ; targets/go.oro, once
(prim aindex (vec-f64 int) f64 expr "%s[%s]" pure index) ; arg 0 is indexed by arg 1
```

A target that declares no `narrow` gets no transformation, which is right for JavaScript (no
bounds checks to remove) and Java (arrays cannot be narrowed).

**Conservative by construction.** A container is narrowed only if *every* occurrence of it in the
loop body is an index by the **bare** loop variable. `examples/stencil.oro` indexes `a` at `j`,
`j+1` and `j+2`, so `a` is left alone — correctly, since `a = a[:n]` would break `a[j+2]`.

**Legality.** Narrowing moves a panic earlier: `q = q[:n]` fails before the loop where `q[i]`
would have failed inside it. That is permitted because
[primitives.md §2](../../docs/spec/primitives.md) specifies `aindex` as **unspecified out of
bounds**. The specification licensed the optimisation, which is not the order these things usually
happen in.

## 2. What it did

`go build -gcflags="-d=ssa/check_bce/debug=1"` over all eight generated programs:

| | before | after |
|---|---|---|
| `generated_dot.go` | `IsInBounds` **inside the loop** | `IsSliceInBounds` **outside** |
| `generated_centroid.go` | `IsInBounds` inside | `IsSliceInBounds` outside |
| all others | — | — |

**No per-iteration bounds check survives in any generated program.** Six of eight loops narrow;
`stencil` is correctly skipped and `report` narrows its one array.

## 3. What it is worth — and when it is not

### Isolated, two 4096-element vectors

| | ns/op |
|---|---|
| checked | 1,050 |
| narrowed | **535** |

**1.96×**, and consistent across every size measured in isolation — 256, 1024, 4096, 16384,
65536, 262144 all sit between 1.94× and 1.97×.

### On the gauntlet's own inputs, 65536 elements

`GenDot` against `GenDotChecked` — the pre-pattern shape, kept in `bceref.go` so the two can be
measured with the same inputs, the same package and the same call shape:

| | min ns/op |
|---|---|
| `GenDotChecked` | 33,293 |
| `GenDot` | 33,470 |

**No difference.** At 0.5 ns/element this loop is memory-bound, and the removed instruction hides
behind the cache miss.

Minimums over nine runs, because the arithmetic means were unusable: four consecutive runs of the
*same* function gave 34,890 / 38,998 / 96,177 / 98,382 ns/op. The machine is shared with a browser
and video playback, and this is what the ~15% noise floor in CLAUDE.md is a polite version of.

## 4. The honest conclusion

> **Removing the check is free and provable. Whether it is *worth* anything depends on whether the
> loop is compute-bound.**

Both halves matter:

- The pattern **always** removes real work and **never** costs anything, so it should stay.
- The **1.96× does not transfer to every workload.** It appears when the data is cache-resident
  and the loop is arithmetic-bound; it disappears when the loop is waiting on memory.

The gauntlet's large programs are memory-bound, which is why the headline number does not show up
there. That is a fact about the benchmark, not about the transformation — but it means the number
should never be quoted without the condition attached.

## 5. What this does to the case for types

[types-direction](../../docs/types-direction.md) used this measurement as the strongest evidence
that a type system would pay for itself in performance. That case is now **weaker and better
understood**:

1. The win is **real** and now **collected**, at zero language cost — as
   [§2.2](../../docs/types-direction.md) predicted, an emitter pattern got the whole thing without
   a single type.
2. The win is **conditional on being compute-bound**, so "bounds checks are worth 1.94×" was an
   overstatement of what a type system could buy.
3. What remains for types is exactly what §2.2 said: the cases the emitter **cannot see** — an
   index computed by arithmetic (`stencil`, skipped here), a length carried across a function
   boundary, a bound established by a caller.

So the performance argument for types has not disappeared; it has shrunk to its honest size, and
the argument from [§3.1](../../docs/types-direction.md) — that a signature is a list of names
until types make it a claim — is now clearly the stronger one.
