# R3 measured: the host's bignum against one we could emit — 2026-08-28

hamza: *"even if we have to test different implementations, that is true whether we use the target's
bignum or provide our own. The decision should be on which is faster, and which fits better with the
language."*

So it was measured before anything was designed around it, which is
[ADR 0008](../../docs/decisions/0008-measurement-over-principle.md).

**On Go, a limb form we could emit beats `math/big` at every size measured, with zero allocations.**
And the measurement corrects a recommendation I made in
[precision-by-declaration.md](../../docs/precision-by-declaration.md) yesterday.

---

## 1. What was compared

`gauntlet/go/bigarith.go`. The existing `bignum.go` prices **detection** — what a checked multiply
costs while the value stays inside a word. This prices the other half: arithmetic once the value
genuinely does not fit.

**The two workloads are the two programs `examples/int/` refuses.** `power.oro`'s accumulator
overflows by multiplication, `fib.oro`'s by addition — which are also the two operation shapes, one
linear with a carry chain and one linear per small multiplier.

The limb form is written to the constraints Oroboros actually has, so that a good number is a number
we could reach: limbs in a table whose length is known **before** the loop, one buffer threaded
through and written in place, and `bits.Mul64`/`bits.Add64` standing in for target-declared
primitives.

`math/big` is the correctness oracle — every size is checked against it before it is timed.

## 2. Numbers

Go 1.26, `-benchtime=2s -count=3`, medians.

| | limbs | `math/big` naive | `math/big` reuse | **ours** | ours vs best |
|---|---|---|---|---|---|
| 50! | ~4 | 2,733 ns / 100 allocs | 538 ns / 4 allocs | **135 ns / 0 allocs** | **3.97×** |
| 200! | ~20 | 13,950 ns / 400 allocs | 2,647 ns / 7 allocs | **1,459 ns / 0 allocs** | **1.81×** |
| 2000! | ~1900 | — | ~255,000 ns / 63 allocs | ~271,000 ns / 0 allocs | **~parity** |
| fib(1000) | ~11 | — | 7,438 ns / 14 allocs | **6,719 ns / 0 allocs** | **1.11×** |

**The advantage is largest small and amortises away**, which is the expected shape and is the honest
way to read it: `math/big`'s inner loops are hand-written assembly and better than ours. What we
avoid is its *overhead* — an allocation per operation in the naive form, and even in the careful
form a receiver, a sign field, a length field and a bounds-checked slice per call. At four limbs that
overhead **is** the cost; at nineteen hundred it is noise.

**Naive `math/big` is 4–5× worse than careful `math/big`**, at 100 and 400 allocations respectively.
That gap is what a `bignum` type costs if it lowers without anyone thinking about allocation, and it
is the number to remember when someone proposes the easy version.

## 3. What the measurement changed

### 3a. A declared range is what makes the bignum cheap — and that corrects yesterday's recommendation

Our form preallocates. `FactLimbs` is handed a buffer of `FactLimbCount(n)` limbs, and every one of
the zero-allocation results above depends on that number being known before the loop.

[precision-by-declaration.md §5](../../docs/precision-by-declaration.md) recommended **not**
supporting finite-but-huge ranges at first — `(int 0 10³⁰)` — on the grounds that a 128-bit rung
exists on only two of four hosts and so could carry no portability claim. That reasoning was about
the *middle* of the ladder and it is still right about the middle. It is wrong about the top:

> **A finite wide range is what buys the 4×.** `(int 0 HUGE)` gives a limb count, which gives a
> `build` of known length, which gives zero allocations. An *unbounded* declaration gives none of
> that and lands back on allocate-per-operation, which is `math/big` naive.

So the two top rungs are not one rung. **Bounded-but-huge** and **unbounded** differ by a factor of
four on this workload, and the language should be able to say which it has. §5's recommendation is
withdrawn.

### 3b. A bignum needs no growable storage

Every result's size is computable from its operands' sizes: a product has at most `len(a)+len(b)`
limbs, a sum at most `max(len a, len b)+1`. So the "count, then build" discipline
[growth.md](../../docs/growth.md) describes covers bignums completely, and **R3 is expressible with
`build` today** — no new construct, no growable buffer.

That is growth.md's conclusion arriving from a second direction, and it is the stronger evidence
because it was not what this benchmark was written to find out.

### 3c. The significant length must be a loop variable, and leaving it out is a silent 1.21×

The first `FibLimbs` added over the whole fixed buffer every iteration and measured **1.21× slower**
than `math/big`. The buffer is sized for fib(1000) — twelve limbs — and the early iterations need
one, so it was doing twelve times the necessary work at the start. `math/big` tracks its length; the
first version did not.

Tracking it flipped the result to **1.11× faster**. The general form matters more than the fix:
`build` gives a buffer its **capacity**, and the significant **count** has to be carried as an
ordinary loop variable. That is expressible today — one more `again` argument — but it has to be
written, and a library that forgets it is 20% slow for a reason no profiler points at.

This is also why the result was not recorded before it was explained. A suspicious number here would
have been reported as *"addition is where the host wins"*, which is false.

## 4. What is NOT measured, and it matters

- **Big × big.** Both workloads multiply a big value by a *small* one, which is linear for everyone.
  Karatsuba and `math/big`'s hand-written assembly matter most on big × big, and that is exactly
  where it should be expected to win. Squaring or a matrix-power fibonacci would find it.
- **Java.** `BigInteger` is immutable and allocates per operation — the naive column by
  construction — and `Math.multiplyHigh` exists only since Java 9. Expected to favour ours more
  strongly than Go does, and unmeasured.
- **JavaScript, where the answer is expected to invert.** V8's `BigInt` is a builtin, and **JS has no
  64×64→128 multiply at all**, so our limbs would have to be 32-bit or smaller with doubles — a
  handicap no amount of care removes. If that holds, R3 is *the host's* on JavaScript and *ours*
  elsewhere, which is the parasite model working exactly as designed rather than a compromise.
- **windows**, which has no bignum and where ours is the only option regardless.

## 5. Where that leaves the decision

The question was *which is faster, and which fits the language better*. On Go the answer is the same
for both: **ours**, by 4× where it matters most, with zero allocations, expressible with constructs
that already exist, and needing a declared range to get there — which is
[option C](../../docs/precision-by-declaration.md)'s own mechanism paying for itself.

That is one host. The design should not be settled until JavaScript is measured, because that is the
host expected to give the opposite answer, and a rule that says *"ours, except where the host has a
builtin we cannot beat"* is a target declaration rather than a language decision — which is where
this belongs anyway.
