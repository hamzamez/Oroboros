# R3 measured: the host's bignum against one we could emit — 2026-08-28

hamza: *"even if we have to test different implementations, that is true whether we use the target's
bignum or provide our own. The decision should be on which is faster, and which fits better with the
language."*

So it was measured before anything was designed around it, which is
[ADR 0008](../../docs/decisions/0008-measurement-over-principle.md).

**A limb form we could emit beats the host's bignum at the sizes precision integers actually reach on
all three hosts measured** — 3.97× on Go, 5.8× on JavaScript, 6.2× on Java — and the hosts differ
only in where that stops being true. So the answer is a **threshold**, not a winner. The measurement also corrects a recommendation made in
[precision-by-declaration.md](../../docs/precision-by-declaration.md) the day before, and turns up two
V8 facts that are worth more than the headline (§5a, §5b).

---

## 1. What was compared

`gauntlet/go/bigarith.go`. The existing `bignum.go` prices **detection** — what a checked multiply
costs while the value stays inside a word. This prices the other half: arithmetic once the value
genuinely does not fit.

**The two workloads are the two programs `examples/int/` refuses.** `power.oro`'s accumulator
overflows by multiplication, `fib.oro`'s by addition — which are also the two operation shapes, one
linear with a carry chain and one linear per small multiplier.

The limb form is written to the constraints Oroboros actually has, so that a good number is a number
we could reach: limbs in a table whose length is known **before** the loop, one buffer threaded
through and written in place, and `bits.Mul64`/`bits.Add64` standing in for target-declared
primitives.

`math/big` is the correctness oracle — every size is checked against it before it is timed.

## 2. Numbers

Go 1.26, `-benchtime=2s -count=3`, medians.

| | limbs | `math/big` naive | `math/big` reuse | **ours** | ours vs best |
|---|---|---|---|---|---|
| 50! | ~4 | 2,733 ns / 100 allocs | 538 ns / 4 allocs | **135 ns / 0 allocs** | **3.97×** |
| 200! | ~20 | 13,950 ns / 400 allocs | 2,647 ns / 7 allocs | **1,459 ns / 0 allocs** | **1.81×** |
| 2000! | ~1900 | — | ~255,000 ns / 63 allocs | ~271,000 ns / 0 allocs | **~parity** |
| fib(1000) | ~11 | — | 7,438 ns / 14 allocs | **6,719 ns / 0 allocs** | **1.11×** |

**The advantage is largest small and amortises away**, which is the expected shape and is the honest
way to read it: `math/big`'s inner loops are hand-written assembly and better than ours. What we
avoid is its *overhead* — an allocation per operation in the naive form, and even in the careful
form a receiver, a sign field, a length field and a bounds-checked slice per call. At four limbs that
overhead **is** the cost; at nineteen hundred it is noise.

**Naive `math/big` is 4–5× worse than careful `math/big`**, at 100 and 400 allocations respectively.
That gap is what a `bignum` type costs if it lowers without anyone thinking about allocation, and it
is the number to remember when someone proposes the easy version.

## 3. What the measurement changed

### 3a. A declared range is what makes the bignum cheap — and that corrects yesterday's recommendation

Our form preallocates. `FactLimbs` is handed a buffer of `FactLimbCount(n)` limbs, and every one of
the zero-allocation results above depends on that number being known before the loop.

[precision-by-declaration.md §5](../../docs/precision-by-declaration.md) recommended **not**
supporting finite-but-huge ranges at first — `(int 0 10³⁰)` — on the grounds that a 128-bit rung
exists on only two of four hosts and so could carry no portability claim. That reasoning was about
the *middle* of the ladder and it is still right about the middle. It is wrong about the top:

> **A finite wide range is what buys the 4×.** `(int 0 HUGE)` gives a limb count, which gives a
> `build` of known length, which gives zero allocations. An *unbounded* declaration gives none of
> that and lands back on allocate-per-operation, which is `math/big` naive.

So the two top rungs are not one rung. **Bounded-but-huge** and **unbounded** differ by a factor of
four on this workload, and the language should be able to say which it has. §5's recommendation is
withdrawn.

### 3b. A bignum needs no growable storage

Every result's size is computable from its operands' sizes: a product has at most `len(a)+len(b)`
limbs, a sum at most `max(len a, len b)+1`. So the "count, then build" discipline
[growth.md](../../docs/growth.md) describes covers bignums completely, and **R3 is expressible with
`build` today** — no new construct, no growable buffer.

That is growth.md's conclusion arriving from a second direction, and it is the stronger evidence
because it was not what this benchmark was written to find out.

### 3c. The significant length must be a loop variable, and leaving it out is a silent 1.21×

The first `FibLimbs` added over the whole fixed buffer every iteration and measured **1.21× slower**
than `math/big`. The buffer is sized for fib(1000) — twelve limbs — and the early iterations need
one, so it was doing twelve times the necessary work at the start. `math/big` tracks its length; the
first version did not.

Tracking it flipped the result to **1.11× faster**. The general form matters more than the fix:
`build` gives a buffer its **capacity**, and the significant **count** has to be carried as an
ordinary loop variable. That is expressible today — one more `again` argument — but it has to be
written, and a library that forgets it is 20% slow for a reason no profiler points at.

This is also why the result was not recorded before it was explained. A suspicious number here would
have been reported as *"addition is where the host wins"*, which is false.

## 4. What is NOT measured, and it matters

- **Big × big.** Both workloads multiply a big value by a *small* one, which is linear for everyone.
  Karatsuba and `math/big`'s hand-written assembly matter most on big × big, and that is exactly
  where it should be expected to win. Squaring or a matrix-power fibonacci would find it.
- ~~**Java.**~~ **Measured — see §6.** The prediction held: ours wins at every size, by more than on
  Go, and `BigInteger`'s immutability is why.
- ~~**JavaScript, where the answer is expected to invert.**~~ **Measured — see §5.** The prediction was
  half right and the half it got wrong is the useful half: it inverts only past ~100 limbs, and ours
  still wins 5.8× at the sizes precision integers actually reach.
- ~~**windows**~~ **Measured — see §7.**

## 5. JavaScript, and it does not invert — it CROSSES OVER

`gauntlet/js/bigarith.mjs`, one variant per process, `BigInt` as the correctness oracle. §4 predicted
the answer would invert here. It does, but only past a size precision integers rarely reach, and the
route to that conclusion produced two host facts worth more than the headline.

**Our limbs cannot be 64 bits on this host.** A JS number is a double, the bitwise operators coerce
to **int32**, and `Math.imul` gives only the low half of a 32×32 product. So the limb base is forced
small, and *which* small is the design question.

| | limbs | `BigInt` | **ours (bitwise)** | |
|---|---|---|---|---|
| 50! | ~16 | 1,420 ns | **245 ns** | **5.8× ours** |
| 200! | ~78 | 6,973 ns | **5,273 ns** | **1.32× ours** |
| 2000! | ~1,200 | **317,664 ns** | 833,348 ns | **2.62× BigInt** |
| fib(1000) | ~24 | 15,920 ns | **15,107 ns** | 1.05× — parity |

**Ours wins small, and V8's `BigInt` wins large.** The crossover is around a hundred limbs, where Go's
was around nineteen hundred — and the reason is structural: V8's `BigInt` is C++ with real 64-bit
limbs, so at scale it does a quarter of the limb-operations we do and we cannot close that from
JavaScript.

But **the sizes precision integers actually reach are the small ones** — a value that has just left
the 2⁵³ window is two or three limbs, not twelve hundred. So the useful reading is not *"JavaScript
inverts"* but *"ours until about a hundred limbs, the host's after"*, which is a threshold a target
could declare.

### 5a. Staying inside int32 is worth 1.7×, and leaving it is a CLIFF

The first base-2²⁴ float form — the classic JS-bignum choice, and what jsbn and node-forge use —
blew up **75×** from 50! to 200! where the work grows about 19×. Made to explain itself rather than
recorded:

```
fact-f24-array  n=128   7,727 ns
fact-f24-array  n=130   8,015 ns
fact-f24-array  n=132  19,695 ns     <- 2.5x for 1.5% more work
```

`acc[i] * k` leaves int32 at `k = 2³¹/2²⁴ = 128`. Both forms stay far inside 2⁵³, so exactness is not
what changed. **The control settles it**: an identical base-2²⁰ form, chosen so the intermediate stays
under 2³¹ for every n here, has **no cliff at all** — 9,775 / 10,233 / 28,812 at n = 130 / 132 / 200,
scaling smoothly, and 1.7× faster than base-2²⁴ at 200 despite carrying *more* limbs.

> **On V8 the constraint is not "stay under 2⁵³", it is "stay under 2³¹".** Exactness is the folklore
> limit; the Smi boundary is the performance one, and it is seven bits of limb width lower than every
> JS bignum library assumes.

### 5b. Bitwise carry extraction is worth 3.9×, isolated

fib(1000), same algorithm, same storage, differing only in how the carry comes out — a shift and a
mask against a comparison and a subtraction:

| | plain `Array` | typed array |
|---|---|---|
| float, base 2²⁴ | 71,194 ns | 104,482 ns *(Float64Array)* |
| **bitwise, base 2³⁰** | **18,136 ns** | **15,107 ns** *(Int32Array)* |

**3.9× at equal storage**, 6.9× with each form's best storage. Base 2³⁰ is the widest bitwise addition
JavaScript allows — two limbs plus a carry is under 2³¹, exactly int32's range — so the bitwise form
also carries *fewer* limbs than the 2²⁴ float one, and both effects pull the same way.

And a storage rule falls out that is worth stating because it is the opposite of the usual advice in
both directions: **match the element kind to the arithmetic.** `Int32Array` beats a plain `Array` for
int32 limbs (1.20×); `Float64Array` **loses** to a plain `Array` for the very same values held as
floats (1.47×), because V8 keeps a packed `Array` of small integers as Smis and a `Float64Array`
forces every element through a double. That does not contradict
[jsontok-2026-08-26](jsontok-2026-08-26.md)'s plain-`Array`-beats-`Uint8Array`; it is a different
pairing, and the rule that covers both is the element-kind one.

## 6. Java, where ours wins everywhere — and the high multiply is not worth it

`gauntlet/java/BigArithBench.java`, JDK 17, `BigInteger` as the oracle. §4 predicted this host would
favour ours most strongly, for a reason about the API rather than the arithmetic: **`BigInteger` is
immutable**, so every operation allocates a fresh object and a fresh `int[]`. The JDK has a mutable
version it uses on itself — `java.math.MutableBigInteger` — and it is package-private, so a caller
cannot reach the thing the implementation reaches for.

| | 64-bit limbs | `BigInteger` | L64 `long[]` | **L32 `long[]`** | L32 `int[]` | best ours |
|---|---|---|---|---|---|---|
| 50! | 6 | 754.9 ns | 135.5 | **123.9** | 121.4 | **6.2×** |
| 200! | 24 | 4,835.9 ns | 1,556.5 | **1,404.9** | 1,465.6 | **3.4×** |
| 2000! | 314 | 485,304 ns | **263,712** | 268,904 | 285,848 | **1.84×** |
| fib(1000) | 13 | 13,813 ns | 5,895.7 | **5,171.2** | — | **2.67×** |

**Ours wins at every size, and by more than on Go.** There is no crossover in the measured range —
1.84× even at 314 limbs, where Go had already reached parity and V8 had lost.

### 6a. The high multiply is not worth it on this host

`Math.multiplyHigh` is a JDK 9 intrinsic and it is **signed**; JDK 17 has no
`unsignedMultiplyHigh` (that is JDK 18), so 64-bit limbs need a three-term correction per multiply
plus `Long.compareUnsigned` for the carry. **32-bit limbs need none of it** — a limb times a small
multiplier fits in a `long` with room to spare, and the carry is a shift and a mask.

Measured, the 32-bit form **wins at 50! and 200! despite carrying twice the limbs**, and loses by 2%
at 2000!, which is inside the noise. So the arithmetic that looks obviously better is not, and the
reason is the sign correction the JDK version forces.

That is worth carrying into the emitter as a rule rather than a Java note: **a high-multiply
primitive is worth declaring only where the host has an *unsigned* one.** Go does (`bits.Mul64`),
x86-64 does (`mul`), JDK 18+ does, JDK 17 does not, and JavaScript does not have a high multiply at
all.

### 6b. `int[]` buys nothing but memory, which is the answer the emitter needed

Our `int` is a `long` on this host, so a table of limbs emits as `long[]` unless the element-width
machinery narrows it. The `int[]` column exists to price that, and it is **within noise at every
size** — 121 vs 124, 1,466 vs 1,405, 286k vs 269k. So the narrowing is worth half the memory and no
time, and an emitter that does not narrow here loses nothing.

## 7. windows: no host bignum, so a different question — and `adc` is a bounded hole

`gauntlet/windows/bigarith.asm`, hand-written x86-64 under MASM, checksums verified against an
independent computation (2000!'s top limb is 34,873,293,757,821 and fib(1000)'s low limb is
817,770,325,994,397,771).

The other three hosts ship a bignum, so the question was *ours or theirs*. `targets/windows/` brings
`VirtualAlloc` and nothing else, so **ours is the only option** and the question becomes: *what must
the target declare for us to reach hand-written assembly?*

x86-64 has two things no other host in the set does. **`mul`** is a 64×64→128 multiply in one
instruction. **`adc`** carries in a **flag**, so a limb-vector add needs no carry variable at all —
which is why the reference loop bumps its index with `lea` and its counter with `dec`, the two
instructions that leave CF alone.

| | ns/round |
|---|---|
| 2000!, `adc` | **162,663** |
| 2000!, explicit carry | 340,658 |
| fib(1000), `adc` | **3,922** |
| fib(1000), **declared primitive** | **7,271** |
| fib(1000), explicit carry | 15,449 |

### 7a. The multiply case is fully recoverable; the carry chain is half

**`mul` is an ordinary declaration** — one more `(prim …)` in `targets/windows/x64.oro`. And it fits
better than it had any right to: [values.md](../../docs/spec/values.md)'s multiple return is built and
measured, and on x86 it passes two results in **rax/rdx** — which is exactly where `mul` puts its low
and high halves. So `(prim mulwide (int int) (int int) …)` needs no new machinery, and the emitted
sequence is `mul; add; adc`, which **is** the hand-written form. The 2.09× on factorial is not a gap
we would pay; it is the gap against *ordinary arithmetic*, which is not what we would emit.

**The addition chain is the real question**, and the middle row answers it. A declared two-result
`add-carry` primitive materialises the carry as a **value** — so nothing has to survive between
emitted statements — but produces it with `adc r,0` rather than a compare. That recovers **2.12× of
the 3.94×**, and leaves **1.85×** on the table.

> **So `adc` is a real hole and a bounded one: worth 1.85× on addition-heavy bignum code and nothing
> on multiplication.** What we cannot express is the carry flowing *implicitly across loop
> iterations*; what we can express gets half of it with one declaration.

That is a much better answer than "the carry flag is unreachable", and it is the kind of thing only
measurement settles — the first version of this file assumed `adc` was simply out of reach and did not
measure a middle form at all.

### 7b. The absolute floor

For reference, 2000! across all four hosts, best form each:

| | ns |
|---|---|
| **x86-64 hand-written** | **162,663** |
| Java, 64-bit limbs | 263,712 |
| Go, 64-bit limbs | ~271,000 |
| Java `BigInteger` | 485,304 |
| JavaScript, bitwise | 833,348 |

Read with care: the loop structures differ, Go and Java carry bounds checks, and the x86 fib does
**not** track the significant limb count while the others do — so it is doing *more* work than the Go
and Java figures and is still faster. The within-host comparisons above are the sound ones; this table
is a floor, not a ranking.

## 8. Where that leaves the decision

The question was *which is faster, and which fits the language better*.

**On both hosts measured, ours wins at the sizes precision integers actually reach** — 3.97× on Go at
four limbs, 5.8× on JavaScript at sixteen — with zero allocations, using constructs that already
exist, and needing a **declared range** to get there, which is
[option C](../../docs/precision-by-declaration.md)'s own mechanism paying for itself.

**On all three hosts measured, ours wins at the sizes precision integers actually reach:**

| host | small | medium | large | crossover |
|---|---|---|---|---|
| **Go** | 3.97× ours (4 limbs) | 1.81× ours (20) | parity (1,900) | ~1,900 limbs |
| **JavaScript** | 5.8× ours (16) | 1.32× ours (78) | **2.62× the host** (1,200) | ~100 limbs |
| **Java** | 6.2× ours (6) | 3.4× ours (24) | **1.84× ours** (314) | none found |

**The hosts differ only in where it stops being true.** That is not a reason to pick one
implementation globally; it is a **threshold**, and a threshold is exactly the kind of thing a target
declares. `int-repr` already says *what this host can hold*; the same file saying *and past N limbs,
use the host's own* is the parasite model working rather than a compromise.

**windows** has no bignum at all, so there is no choice to make there — and §7 measured what it would
take to reach hand-written assembly: **`mul` is one ordinary declaration** that fits the existing
multiple-return convention exactly, and **`adc` is a bounded hole worth 1.85×** on addition-heavy code
and nothing on multiplication.
