# The limb rung is wired, correct on four targets — and SLOWER than the rung above it

**2026-09-02.** ADR 0019's ladder has four rungs and this is the third: a range that is FINITE and
above the portable window gives a **limb count**, which gives a `build` of known length, which gives
zero allocations. Until today a declared endpoint was compared against the window and thrown away —
`(int 0 (pow 2 1000))` and `(int 0 +inf)` produced identical code, and having the spelling was
necessary and nowhere near sufficient.

It is wired now. The same source, two declarations, two representations, on all four targets:

```lisp
(sig fact ((n (int 0 200))) (int 0 (pow 2 1300)))   ; 55 base-2^24 limbs, traps at the bound
(sig fact ((n (int 0 200))) (int 0 +inf))           ; the host's own bignum, exact
```

**And it does not pay.** On Go the limb rung is **13,850 ns against our unbounded rung's 2,131** —
6.5× slower, even after loop-carried buffer reuse took it from 19,270 and from 200 allocations to 2
(§2a). On Java it is **13,250 against 4,928**, 2.7× slower, and that is the host bigarith predicted
it would win on by 6.2×.

**That correction is the result**, and §4 is what it costs to fix. What the rung buys
unconditionally is windows: that target ships no bignum at all, and arbitrary precision there was
ADR 0019's item 4.

---

## 1. What a program says, and what it gets

```go
func GenFact(n int) []int32 {
	b := make([]int32, 55)          // the width came from (pow 2 1300)
	…                               // 1 spread over the limbs
	acc := b2
	for i := 2; ; i = i + 1 {
		if i > n { break }
		clear(sp1)                      // §2a: the loop owns its storage
		o := sp1
		for i3, c := 0, 0; ; i3 = i3 + 1 {
			if i3 >= 55 {
				if trapIfNonzero(c) == 0 { break }   // the carry check
				break
			}
			t := acc[i3]*i + c
			o[i3] = int32(t % 16777216)
			c = t / 16777216
		}
		acc, sp1 = o, acc
	}
	return acc
}
```

Correct against `math/big`'s `MulRange` at 0, 1, 2, 20, 50, 100 and 200; identical on Go, JavaScript
and the JVM in the differential suite at five factorials up to 50!; and emitting on windows, which
has no bignum to fall back to.

## 2. A fixed width has to TRAP, or selecting a representation changes the answer

This is the rung's real difficulty and it is worth stating before the numbers.

The host's bignum is **exact whatever the declaration says**, so an under-declared bound costs
nothing on the unbounded rung. A fixed width **truncates** — and then choosing a representation
would change the program's answer, which is ADR 0009's rule at a different boundary and the one
thing this project refuses.

So every operation checks its final carry:

```
$ ./trap                     # (int 0 (pow 2 100)) declared for 100!, which needs 525 bits
panic: bignum overflow: the declared range is too small
```

**Every target can fail**, which is what makes this affordable: `panic` on Go, `throw` on JavaScript
and the JVM, `ud2` on x86 — the same three instructions ADR 0019's checked arithmetic already uses.
One comparison per **operation**, not per limb.

That makes the two upper rungs a genuine choice rather than an implementation detail:

| | |
|---|---|
| `(int 0 (pow 2 1300))` | fixed width, no per-operation allocation, **traps at the bound** |
| `(int 0 +inf)` | the host's own bignum, **exact**, allocates |

## 2a. LOOP-CARRIED BUFFER REUSE, added the same day — 1.39×, and 200 allocations to 2

§8 named this as the first thing to fix and it is done for Go. A `build` on a
back edge writes into storage the loop already owns:

```go
sp1 := make([]int32, 55)          // hoisted, once
for ; ; i = i + 1 {
	clear(sp1)
	o := sp1
	…
	acc, sp1 = o2, acc            // the swap
}
```

**The conditions are rule R's, one level up** — `emit/bigreuse.go` asks when a
bignum operation may write into a loop variable's object and this asks the same
of a table: the `again` argument for vⱼ is a `build` of constant length, vⱼ's
initialiser is a `build` of the same length, every occurrence of vⱼ in the whole
`again` is inside that argument, and the loop has one back edge.

**TWO BUFFERS AND A SWAP, NOT ONE BUFFER IN PLACE**, and that is not caution. In
place, the body would read vⱼ through the same storage it writes — and whether
that is safe depends on the ALGORITHM: `mul-small` writes `o[i]` after reading
`a[i]` and would survive, while `mul` writes `o[i+j]` and reads `a[i]` later and
would not. Alternating two buffers needs no aliasing argument at all: the body
always reads one and writes the other, and the one it writes was last read two
iterations ago. The spare is `clear`ed because `build` zero-fills (tables.md
§14.3) and `mul` accumulates into slots it never writes.

**Cost: exactly the limb programs change**, on every target. No other program in
the corpus has a loop-carried buffer of constant length, which is the honest
scope: this is the back-edge instance of the gap, and Karatsuba's workspace and
ADR 0013's stencil are the boundary instance, still open.

### 2a′. IT PAYS ON ONE HOST OF FOUR, AND THE REASON IS THE ALLOCATOR

Ported to all four and measured A/B — the same source, the rule on and off:

| | reuse | allocating | |
|---|---|---|---|
| Go | **13,850** | 19,270 | **1.39×** |
| JVM | 14,841 | 14,188 | 0.96× — neutral |
| V8 | 524,803 | 532,599 | 1.01× — neutral |
| windows | — | — | not a speed question, §2a″ |

**Go is the only host where a short-lived table is expensive.** The JVM
bump-allocates in a TLAB and its young collector pays only for survivors, and
every one of these buffers dies immediately; V8's young generation is the same
shape. On both, a fresh array arrives already zeroed and the `Arrays.fill` /
`.fill(0)` that a reused one needs costs about what the allocation did.
json-tree-bench-2026-08-26 recorded exactly this about the JVM for a different
program, and it reproduces here.

So this is ADR 0008 again: **the transformation is not a portable win, it is a
Go win**, and measuring one host would have made it a principle.

### 2a″. ON WINDOWS IT IS NOT A SPEED QUESTION AT ALL

That target's allocator is **one `VirtualAlloc` per `build`, never freed**
(wintables-2026-08-25). A loop that allocates per iteration therefore leaks a
page every time round — 199 of them for `fact(200)`, at page granularity. Reuse
takes that to two allocations for the whole call.

The clear is a counted loop rather than `rep stos`, because that instruction
needs three fixed registers the allocator is using.

### 2b. AND THE MEASUREMENT METHOD WAS WRONG, WHICH IS A THIRD KIND

The first attempt reported the reuse form at **39,000 ns against 18,150 for the
allocating one** — reuse making it twice as slow, at a hundredth of the
allocations. Both numbers were `-benchtime=Ns`, which lets Go choose N, and the
allocating form's 200 allocations per operation make its cost depend on how many
iterations the harness decides to run: the same binary gave 62,206, 19,464,
19,356 and 19,145 on four consecutive `-count` passes.

With a FIXED iteration count (`-benchtime=100000x`) every number is stable to
under 2%, and the answer inverts. This repository has recorded two measurement
errors of this family — process composition, in json-tree-bench and in
bigrep-2026-09-02 §3.2 — and this is a third and different one: **iteration
count**. A program whose cost is dominated by allocation cannot be timed by a
harness that chooses its own N.

So the rung is **2.7× to 6.5× slower than the rung above it**, and 9.5× short of the hand-written
limb form that motivated it — after the reuse of §2a, which is the one of §8's three that is done.

## 4. Why, and both reasons are portability prices

bigarith-2026-08-28 measured a limb form at **3.97× over `math/big`, 6.2× over `BigInteger` and 5.8×
over `BigInt`**, and this repository has carried those numbers as what the rung would be worth. They
were measured on **hand-written Go, Java and JavaScript**, and that reference uses three things a
portable library written in *this* language cannot:

**64-BIT LIMBS.** Ours are 24 bits, and the base is forced rather than chosen: a limb product plus
its carry must stay exact, ADR 0012 makes an `int` exact to ±(2⁵³−1), so 2W < 53 and W ≤ 26. That is
**55 limbs where `math/big` uses 20 words** — 2.75× the iterations before anything else.

**A SHIFT AND A MASK.** Ours splits a carry with `/` and `%`, because bitwise operators are
deliberately not in the language: V8 coerces both operands to int32, so `(2³²) & −1` is 0 there and
4294967296 on the other three — an observable disagreement *inside* the portable window, which is
what makes a construct Tier 2 (integers.md §0a). bigarith measured bitwise carry extraction at
**3.9× at equal storage**.

**ONE REUSED BUFFER.** The hand-written form allocates nothing; ours allocates a fresh `build` per
operation — **200 allocations** for a 199-step factorial. That is the same linear-buffer gap rule R
closed for `math/big` objects this morning (bigreuse-2026-09-02), arriving in a **fourth** place
after Karatsuba's workspace, the stencil, and the mutable bignum.

**So this is ADR 0008 landing on a measurement that had become an expectation.** bigarith's numbers
are true of hand-written host code and were never true of emitted portable code; nothing measured
the difference until something was emitted.

## 5. What it buys unconditionally

**windows gets arbitrary precision, and it had none.** Go has `math/big`, the JVM `BigInteger`, V8
`BigInt`; windows ships nothing, so before today a program declaring a range above the window was
refused there by name. ADR 0019 item 4 says that host "needs one written — in Oroboros, which is
also the test of whether the language can write its own libraries". It is written, it is 150 lines,
and it emits.

What windows still cannot do is **render** the result: turning a limb table into decimal needs
repeated division and then a string, and strings are the one thing this language has almost none of.
The arithmetic works there; the printing does not, and the refusal says so by name. Computing and
rendering are two capabilities and only one of them needs a host bignum.

## 6. How the library gets in, and why it is not `win/map`'s way

`lowerMaps` injects `win/map` into the program **before** reduction, because a map operation is
visible in the source. Which `+` is a bignum is not: it is decided by a solver that needs the
**residual**, so by the time the answer exists reduction is over.

So the library is **spliced and reduced at each site** — `core.Normalize` on an application of a
closed definition to residual arguments is exactly an inline — and the width goes in as a literal,
so every loop bound and every buffer length in the result is a constant.

Three things the build taught that the design had not.

**THE WIDTH HAS TO COME FROM THE WHOLE PROGRAM.** Reduction inlines every non-exported call, so a
helper's declared range is gone by the time the representation is selected — refinements.md §6b's
limit for a **fourth** time — and `main` has no signature at all. The first version took the width
from the entry's signature, and every whole program silently kept the host's bignum: the trap never
fired because the rung was never selected.

**A MULTIPLY BY A WIDENED WORD IS A DIFFERENT ALGORITHM**, and it has to be recognised *before* the
operand is spliced. `(big* acc (big-of i))` is one pass; once `(big-of i)` has become a `build`,
nothing distinguishes it from any other limb table and the same program does w passes. A factorial
is nothing but this operation, so getting it wrong is a correct program doing 55× the work.

**A LIMB VALUE IS A TABLE, AND THE SIGNATURE HAS TO SAY SO.** `LimbSig` maps every big type to
`array int` for the checker, or a body that produces limbs is refused against a declaration that
says `big` — true of the declaration and false of the code.

## 7. Two bugs, and one of them is the same one three times

**Java forbids a lambda parameter shadowing a local.** The carry trap has no throw *expression* on
that host, so it is a lambda applied at once — and its parameter was called `c`, which is what the
emitter usually calls the carry it is handed. Go and JavaScript both allow the shadow, so this is a
one-host rule and it fired on the first program with a carry.

**`Body()` REBUILDS, for the third time.** The Java method emitter called `t.Body()` twice — once to
emit and once to type the result — and `LoopOneJoin`'s answer is keyed by term pointers, so the
method built `int[]` and declared `byte[]`. The interval pass's rebuild, the Go emitter's four
passes, and now this. *A map keyed by a pointer into a term that a helper rebuilds is a map that
answers about a copy.*

## 8. What would close the gap, in order

1. ~~**Buffer reuse across the loop**~~ **DONE the same day, §2a** — 200 allocations to 2, on all
   four targets. It is not the dominant term after all: 1.39× on Go, neutral on the JVM and V8
   because their allocators are cheap and the clear is not, and on windows a leak rather than a
   cost. The remaining 6.5× on Go is the other two items below.
2. **A target-declared limb width and carry extraction.** 64-bit limbs with a high multiply on Go,
   the JVM and x86; 24 bits on V8, where bigarith measured the Smi boundary at 2³¹ rather than 2⁵³.
   That is `int-repr`'s shape one rung up and it is exactly the parasite model — the language writes
   the algorithm once and each host says how wide a limb is and how a carry comes out.
3. **Decimal rendering in Oroboros**, which is what windows needs to print and which needs a string
   surface.

Until (1) and (2), the honest advice is the one the measurement gives: **declare `+inf` unless the
target has no bignum.** The rung is correct, sound and portable; it is not yet fast.
