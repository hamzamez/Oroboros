# ADR 0019's third escape is real: a declared range above the window is a bignum

**2026-09-02.** ADR 0019 decided *bounded by default*: an integer operation the compiler cannot
prove stays inside the portable window is a compile error, cleared by saying one of three things —
narrow the range, ask for the trap, or **declare a range above the window, which promotes that value
to arbitrary precision**. The third one has been in `emit/bounded.go`'s own error message since the
day it was written, qualified with *"when it exists"*. It exists now.

**Go 1.01x / 0.99x / 0.97x, JavaScript 1.00x / 0.98x / 1.01x, Java 0.92x / 1.01x / 1.01x** against
hand-written bignum code on fib(1000), 200! and 999^64. windows declares no bignum and refuses,
which is the capability model answering.

**And building it found a hole in ADR 0019 itself: bounded-by-default was VACUOUS on JavaScript** —
the one host whose failure mode is silent precision loss. §5.

---

## 1. What a program says, and what it gets

```lisp
(sig fib ((n (int 0 1000))) (int 0 (pow 2 1000)))

(def fib (fn (n)
  (loop ((a 0) (b 1) (i 0))
    (>= i n)  a
    else      (again b (+ a b) (+ i 1)))))
```

Nothing else. No `bigint`, no import, no library call, no annotation on `a` or `b`. One endpoint
above the window, and:

```go
func GenFib(n int) *big.Int {
	a := big.NewInt(int64(0))
	b := big.NewInt(int64(1))
	var i int = 0
	for ; ; i = i + 1 {
		if i >= n { break }
		a, b = b, new(big.Int).Add(a, b)
	}
	return a
}
```

```js
export function genFib(n) {
  let a = BigInt(0), b = BigInt(1), i = 0;
  for (;; i = i + 1) { if (i >= n) return a; const u1 = b, u2 = a + b; a = u1; b = u2; }
}
```

```java
public static java.math.BigInteger genFib(long n) {
	java.math.BigInteger a = java.math.BigInteger.valueOf(0);
	java.math.BigInteger b = java.math.BigInteger.valueOf(1);
	int i = 0;
	for (;; i = i + 1) { if (i >= n) break; final var u1 = b; final var u2 = a.add(b); a = u1; b = u2; }
	return a;
}
```

`fib(100)` is **354224848179261915075** on all three. ADR 0019's refusal quotes that number as the
one *no target produced*: Go and the JVM both returned 3736710778780434371 (wrapped) and V8 returned
354224848179262000000 (precision lost).

## 2. The solver has to be bidirectional, and factorial is why

precision-by-declaration.md named this a year of decisions ago and it is the whole difficulty:

> `(fact (int 0 30))` has every input small and an accumulator reaching 30! ≈ 2.65×10³², so the
> pressure comes from the declared **result** and nothing forward makes `acc` big. A forward-only
> solver would pass the entire current corpus and fail on the first factorial.

So the representation is a least fixed point over three rules, on a two-point lattice `word ⊑ big`
with `big` absorbing — precision-by-declaration.md's own proposal, and the reason the interval
domain did **not** have to go arbitrary-precision: an operation on a value that is already exact
cannot overflow, so the analysis is never asked about it. `emit/interval.go`'s `int64` arithmetic is
untouched.

| | rule | witness |
|---|---|---|
| **(S)** supply | some expression assigned to a name is big | `let` bound to a big value |
| **(D)** demand | it is returned where a bignum is wanted, or assigned to a loop variable that is one | fib: the result promotes `a`, then `(again b …)` promotes `b` |
| **(P)** pressure | a big **arithmetic** operation reads it **and** it is not provably inside the window | power's `x` |

Monotone over a finite lattice, so iteration reaches the least fixed point and terminates.

### 2.1 Rule (P) is the one that has to be exactly right, in both directions

```lisp
(def fact (fn (n) (loop ((acc 1) (i 2)) (> i n) acc else (again (* acc i) (+ i 1)))))
```

`i` is **read by** the big multiply. A solver that promoted everything a bignum touches would give
this loop a bignum counter, a bignum compare and a bignum increment — three allocations an iteration
for a value that provably fits. The gate is provability: `i` is 2..31, so it stays a machine word
and is widened at the multiply, one conversion per iteration.

```go
acc := big.NewInt(int64(1))
var i int = 2
for ; ; i = i + 1 {
	if i > n { break }
	acc = new(big.Int).Mul(acc, big.NewInt(int64(i)))
}
```

The same rule, with the gate going the other way, is what makes `power` correct at all:

```lisp
(loop ((acc 1) (x b) (k e))
  (= k 0)        acc
  (= (% k 2) 1)  (again (* acc x) (* x x) (/ k 2))
  else           (again acc (* x x) (/ k 2)))
```

`x` is never returned and is never assigned a big value, so neither (S) nor (D) reaches it. It is
read by the big multiply and its own square leaves the window, so it is promoted. **Leaving `x` a
machine word would silently give the wrong answer while `acc` was scrupulously exact** — this is the
one rule here whose absence is a wrong answer rather than a slow one, and its gate is the one whose
absence is a slow answer rather than a wrong one. Both directions are pinned by tests, because a
version of the pass that gets either backwards still compiles and still runs.

`k` halves and is provably 0..64, so the guard, the remainder and the division are ordinary integer
arithmetic.

## 3. Measured

Three programs, three hosts, generated against hand-written. Correctness first, against an oracle
that is not the same loop under another name: `math/big`'s `MulRange` and `Exp`, `BigInteger.pow`,
and `BigInt`'s `**`.

| | Go gen | Go hand | | JS gen | JS hand | | Java gen | Java hand | |
|---|---|---|---|---|---|---|---|---|---|
| fib(1000) | 48,312 | 48,003 | **1.01x** | 13,717 | 13,732 | **1.00x** | 13,228 | 14,415 | **0.92x** |
| 200! | 11,117 | 11,181 | **0.99x** | 5,125 | 5,232 | **0.98x** | 4,720 | 4,697 | **1.01x** |
| 999^64 | 535 | 549 | **0.97x** | 273 | 271 | **1.01x** | 242 | 240 | **1.01x** |

ns/op, median of five (Go) or of seven (JS, Java). On Go the allocation counts are **identical** in
every row — 2003 allocs for fib, 400 for the factorial, 18 for the power — which is the stronger
statement, since these programs are allocation-bound and a difference there would show before a
difference in the arithmetic.

### 3.1 The reference is the NAIVE form, and saying so is the result

> **Superseded the same day for Go** by [bigreuse-2026-09-02](bigreuse-2026-09-02.md): the emitted
> code now beats the careful form. What survives is the framing — name the reference — and the
> numbers below, which are what the gap was.


The emitted code calls the host's bignum operation for operation, so the comparison is against the
way a programmer **first** writes it. The careful form — reusing a receiver so nothing is allocated
per step — is a different program, and on Go it is:

| | emitted | careful | |
|---|---|---|---|
| fib(1000) | 48,312 | 7,465 | **6.4x** |
| 200! | 11,117 | 2,699 | **4.1x** |
| 999^64 | 535 | 372 | **1.44x** |

which reproduces bigarith-2026-08-28's *"naive `math/big` is 4–5x worse than careful"* exactly. So
the honest claim is **parity with what a person writes, and a rung above it that is measured and not
built**. Reaching that rung needs the bignum to be a **mutable buffer threaded through the loop**,
which is ADR 0018's linear buffer at a type the language does not have — the same gap
arrays-revisited.md's trigger 2 names for Karatsuba's workspace and ADR 0013 names for the stencil.
**Three places, one gap**, and that is now the strongest form of the argument for uniqueness on
parameters.

And above *that* is bigarith's own finding: a **finite** range gives a limb count, which gives a
`build` of known length, which gives **zero** allocations — 3.97x on Go, 6.2x on Java, 5.8x on V8.
That is what makes bounded-but-huge and unbounded two different rungs. This build implements the
top one only.

### 3.2 A measurement-method note, which is json-tree-bench's finding reproducing

The first Go run measured fib at **141,693 ns** and the factorial at **35,954**. Measured alone they
are **48,312** and **11,117** — a 2.9x and 3.2x difference on identical code, from nothing but being
benchmarked in the same process as other allocating benchmarks.

That is exactly what json-tree-bench-2026-08-26 recorded: *"measured alone the recursive Go version
is stable at 11,370 ns; measured in one process with the others it ran 19,168 to 36,495 — a 1.9x
spread on identical work, because 443 allocations put it at the mercy of the rest of the heap."*
Here it is 400 and 2003 allocations. The **ratio** was stable across both runs, because both sides
move together — which is the only reason the first numbers were not wrong as well as inflated.

## 4. windows declares none, and that is the model working

Go has `math/big`, the JVM has `BigInteger`, V8 has `BigInt` in the language. Three of the four
hosts already have the capability, so general-purpose.md's bar — *"beyond the window they cost what
they would cost if we implemented them on the target"* — is met by construction there. windows ships
none and declares none:

```
fib: a needs arbitrary precision — int 0 1.071e301 (302 digits) is above the portable
window ±(2^53−1) — and target windows declares none.
  Go has math/big, the JVM has BigInteger and V8 has BigInt, so those three parasitize
  the host's own. A target without one needs a bignum WRITTEN, in Oroboros, the way
  win/map is (ADR 0019, docs/unbounded-rung.md).
```

This is not the exception to CLAUDE.md's rule that a target may not decline a language construct.
`int` is ADR 0012's window and every target provides it; **above the window there is no portability
claim to keep**, so a missing bignum is the capability model answering — the same answer JavaScript
already gives for the `checked` primitive it does not declare, which
overflow-2026-08-19 recorded as a price list showing up as a capability. ADR 0019 already names what
is owed: a bignum written in Oroboros, the way `win/map` is, and bigarith-2026-08-28 and
karatsuba-2026-08-30 have already written and measured the algorithms.

The differential case says `; skip: windows` with the reason in the file, which the harness has
required since it was written: a target may be excluded, but it has to be **said**.

## 5. And it found ADR 0019's enforcement to be VACUOUS ON JAVASCRIPT

This is the more important half of the day.

The JavaScript emitter produced a **BigInt loop counter** — `let i = BigInt(2)`,
`i = i + BigInt(1)`, `i > BigInt(n)` — where Go and Java produced a machine word. Rule (P) promotes
a name a big operation reads unless it is *provably* inside the window, and on JavaScript nothing
was provable.

The cause: `targets/js` declares everything `any`, deliberately, because JavaScript has one number
type. `addCore` copies the host's operator when it promotes `+` to the language, and it copied the
**result type** too — so the language's `+` returned `any` on that host, and `emit/interval.go`'s
transfer function ignores any operation whose result is not `int`.

So the interval analysis counted **zero integer operations on JavaScript**, and `Unbounded` returns
success when there is nothing to prove:

```
$ go run ./cmd/gen fib.oro <target>          # fib WITHOUT a declaration
go      REFUSED: 1 of 2 integer operation(s) cannot be proven …
java    REFUSED: 1 of 2 …
windows REFUSED: 1 of 2 …
js      wrote /tmp/p.out
```

**Bounded by default was enforced on three targets and vacuous on the fourth**, and the fourth is
the one whose failure mode is silent precision loss — which is the case ADR 0019's own headline
example is about. The refusal fired everywhere except where it mattered most.

The fix is one line and it is a correction of principle rather than a patch: **the result type of a
language operator is the language's, not the host's.** `addCore` already declares their arguments
`(int int)`, and integers.md measured all four hosts agreeing on their meaning inside the window;
only the result had been left to whatever the host happened to say.

Afterwards all four refuse, and JavaScript emits `let i = 2`.

**Cost: no emitted file changes.** All 41 pre-existing programs are byte-identical on all four
targets — no existing example had arithmetic that JavaScript alone could not prove. So this is a
soundness hole closed with no code motion, which is the cleanest way it could have gone and also the
reason it survived: nothing was visibly wrong.

## 6. What was built, and where the seams are

| | |
|---|---|
| `emit/bigrep.go` | the three rules, the rewrite, and the widening |
| `emit/interval.go` | the rules are hooked into the pass that already opens the binders — see below |
| `targets/{go,js,java}/bigint.oro` | the declarations; 13 primitives each, no compiler code |
| `emit/check.go` | promote before checking, and two refusal messages |
| `core/read.go` | `ValueType` of a range above the window is `big`; `ShowType` abbreviates a 302-digit range |
| `examples/big/` | fib, fact, power — the three witnesses |
| `gauntlet/{go,js,java}` | hand-written references and the parity harness |

**The pass lives inside the interval analysis rather than beside it**, and that is a decision with a
scar behind it. `p.big` is keyed by the fresh names the pass itself hands out, so a separate walk
would have to reproduce `openFresh`'s naming exactly — and *"the obvious design has no key"* is
already recorded in this repository as a thing that was built, measured, and found to record nothing
the emitter could find (rebench-2026-08-27). Demand and supply are therefore not two walks: they are
one walk iterated to a fixed point, with the loop's own `step` doing the propagation.

**Three seams found while building, each of which compiled and ran:**

**`again` is a jump, not a value** (ADR 0015). The representation join at an `if` widens whichever
arm disagrees with the other, and a clause chain is an `if` whose one arm returns the accumulator
and whose other arm iterates — so the first version emitted `big-of(goto)`. The same mistake in the
demand direction promoted every bignum loop's counter, because `(+ i 1)` is arithmetic sitting in a
position that demands a bignum and there is nothing locally wrong with that reading. The back edge
takes its demand from its **loop variable** and from nothing else.

**A `let` and a `loop` have to report their own representation.** Neither can be read off its shape
from outside — one has a binder this pass may not open a second time, the other's value is spread
over its exit clauses — so each is recorded by the method that rebuilds it, keyed by the rebuilt
term. It has to be **exact** rather than conservative, which is the opposite of the usual direction
here: a term wrongly called word gets wrapped in `big-of`, which is a type error rather than a
missed optimisation.

**A flag whose meaning changed under a rename.** `p.tail` became `p.demandBig` when the demand
generalised from *the signature's result* to *any position declared `big`* — and the top-level seed
stayed `= true`, which had meant "this is a tail position" and now meant "this must be a bignum". It
promoted an arithmetic operation in a map benchmark, and a test that had nothing to do with any of
this caught it.

## 7. The declaration does not survive inlining, and the boundary is what does

Reduction inlines every non-exported call, so a helper's declared big result is **gone** by the time
the representation is selected — the same structural limit refinements.md §6b records for a `where`
on an internal definition and indexnarrow-2026-08-27 records for a narrowed parameter, arriving a
third time.

What survives inlining is the **boundary**, and for a bignum the boundary is `big-str`: no host
prints a value past 2^53 as an `int`, so a program has to name arbitrary precision there anyway.
That is where a whole program's demand comes from, and it is the reason a `main` with no signature
works:

```lisp
(def main (fn () (fmt.Println (big-str (fib 100)))))
```

The general rule is that **an argument position whose declared type is `big` demands a bignum**, and
the signature's result is the outermost instance of it rather than a special case.
