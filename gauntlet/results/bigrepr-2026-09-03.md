# A range is semantics; the target picks the representation

2026-09-03. `emit/biglimb.go` (`BigBound`, `BigRepr`), `targets/*/bigint.oro`,
`targets/windows/x64.oro`, `emit/bignum.oro`, `emit/bigrep.go` (`fitBig`).

On hamza's *"I thought our intervals are semantics, it says something about the
program. The compiler's job is to pick the fastest and best performing
representation or algorithm per target using that information. They are two
separate worlds."*

That is [ADR 0003](../../docs/decisions/0003-range-typed-integers.md) —
*mathematical semantics, machine representation* — and the bottom of the ladder
has always worked that way: `(array (int 0 255))` is a `[]byte` on Go, a
`short[]` on the JVM because the JVM's `byte` is signed, and a plain packed
`Array` on JavaScript, which declares no widths at all. Nobody writes `byte`.

**The top of the ladder did not.** A FINITE range selected fixed limbs and
`(int 0 +inf)` selected the host's own bignum, so the SHAPE of a declaration
chose a representation. This corrects that, and the correction is worth a factor
of 75 on one host.

## 1. What it cost, measured on the same program

`examples/big/fact-limbs.oro`, 200!, declared `(int 0 (pow 2 1300))`. Three
columns: our fixed-limb rung, the host's own bignum with the declared bound
enforced, and the host's own bignum with nothing to enforce — which is
`examples/big/fact.oro`, the identical loop declared `+inf`.

| | limbs | host + bound | host | policy is worth | the bound costs |
|---|---:|---:|---:|---:|---:|
| Go | 13,730 ns | **2,347** | 2,075 | **5.85x** | 1.13x |
| JavaScript | 528,137 | **7,050** | 5,360 | **74.9x** | 1.32x |
| Java | 15,164 | **5,379** | 5,143 | **2.82x** | 1.05x |
| windows | limbs only | — | — | — | free |

Go: 2 allocations for limbs against 6 for `math/big`, and the ALLOCATING rung
still wins by 5.85x — the reverse of what a reader of
[bigarith-2026-08-28](bigarith-2026-08-28.md) would predict, for the reason
[biglimb-2026-09-02](biglimb-2026-09-02.md) §4 gives: bigarith measured
HAND-WRITTEN host code with 64-bit limbs and a shift-and-mask carry, and a
library written in this language can have neither.

**windows has no column because it has no choice**: that host ships no bignum, so
fixed limbs are the only representation available. Declaring `(big-repr limbs)`
there is saying so rather than choosing.

### 1a. A number that did not reproduce

biglimb-2026-09-02 recorded Java's limb factorial at **7,948 ns**. It measures
**15,164** today, and the tightened bound check of §3 is not the cause — the
PREVIOUS guard measures **14,842** on the same JVM, a 2% difference. The
structure is unchanged (three loops, so still the one-pass `mul-small` and not
the 55-pass `mul`), and this work is not the cause either: the A/B run in the
buffer-reuse port already saw 14,841 against 14,188. So today's number stands
and the older one is withdrawn, unexplained. The direction on that host is
unchanged — 2.82x either way.

## 2. What a range MEANS, and what it does not

`(int 0 (pow 2 1300))` says the value is a mathematical integer in that
interval. That is a fact about the program: true on every target, checkable, and
teachable without naming a host. `(int 0 +inf)` says something different and
weaker — non-negative, no upper bound.

Neither says anything about storage. `BigBound` reads the first; `BigRepr` asks
the target, and the target's answer is a MEASUREMENT it declares:

```
(big-repr host)    ; targets/go, targets/js, targets/java
(big-repr limbs)   ; targets/windows — the only representation it has
```

**There is no total order to select from the way `int-repr` has one**, which is
why this cannot be derived the way an element width is. Widths nest, so
*narrowest containing* is a complete rule. Above the word, bigarith-2026-08-28
measured ours winning where the operation is LINEAR and the host winning where
it is QUADRATIC — two orders, no meet. So a target declares what somebody
measured, and **when the limb library gets 64-bit limbs and a bitwise carry, the
thing that changes is a target file and no program moves.**

## 3. The bound has to be enforced on BOTH, or it is not a bound

This is the part the framing forces, and the part that was missing.

A fixed width TRAPS when a value passes it — it has no choice, because the
alternative is truncation. The host's bignum is exact whatever the declaration
says, so left alone it would silently ACCEPT what the limb rung refuses. Then
`(big-repr host)` would not be a change of storage but a change of **which
programs are legal**, which is ADR 0009's rule at the representation boundary.

So the same bound is enforced on both.

- **The limb rung** already had the carry check, and it enforced `< 2^(24w)` —
  up to 23 bits MORE than was declared. `guard` now also checks the top limb
  against a ceiling the compiler computes, closing exactly that gap. When the
  bound is a whole number of limbs the ceiling is 2^24, and a limb is under 2^24
  by construction, so the check is present, free, and never fires.
- **The host rung** gets a new declared primitive, `(big-fit x k)`, wrapping
  every operation that can grow a value: `BitLen() > k` on Go, `bitLength() > k`
  on Java, `(x >> kn) !== 0n` on V8.

**`big-of` is not wrapped, and that is a proof rather than an omission**: a range
reaches this rung only by being ABOVE the portable window, so the declared bound
is at least 54 bits, and a machine word is under 2^53. Widening one can never
exceed the bound it is widened into.

### 3a. The bound is enforced at its BIT LENGTH

A value is refused when it needs more bits than the declared maximum does, so
`(int 0 (pow 2 1300))` admits everything under 2^1301 — slack of less than a
factor of two. Taking that slack is what makes the check O(1) on all three hosts
that have a bignum and free on the limb rung. Enforcing the endpoint exactly
would cost a full-width comparison per operation, which is what the operation
itself costs.

What matters is not the tightness but that both representations enforce the SAME
thing, and that is a theorem rather than a hope:

> the limb rung admits `x < limbLimit(bits,w) · 2^(24(w−1))`, the host rung
> admits `x < 2^bits`, and with `w = ceil(bits/24)` and
> `limbLimit = 2^(bits − 24(w−1))` these are equal.

Checked for every bound from 49 to 2,400 bits in
`TestBothRepresentationsAdmitTheSameValues`, and demonstrated at the boundary at
run time: with `(int 0 (pow 2 100))` declared, `2^100` prints on both and
`2^101` panics on both.

## 4. The suite gained an axis, because the old coverage evaporated

The moment three of the four targets declared `(big-repr host)`, the fixed-limb
rung lost its cross-target differential coverage — the code was still emitted
and nothing ran it. That is a coverage failure a green suite would have hidden.

`gauntlet/differential/run.go` now reads `; big-repr: both` on a case and builds
it BOTH ways on every target that can render the result, so the question becomes
*four hosts and two storage choices agree*:

```
ok  big-mul     [go/host go/limbs js/host js/limbs java/host java/limbs]
ok  big-select  [go/host go/limbs js/host js/limbs java/host java/limbs]
```

Six variants, byte-identical digits. That is a stronger test than the one it
replaced, and it is exactly the property §3 claims.

`cmd/build` and `cmd/gen` take `-big-repr=limbs|host` to override the target's
declaration — an override for MEASURING the alternative, not a decision. It is
how the numbers in §1 were taken from one source file, and it is how the next
target-file change will be justified.

## 5. Cost

- **One program changes**, on all four targets: `examples/big/fact-limbs.oro`,
  the only one in the corpus declaring a finite range above the window. The
  other 69 × 4 emitted files are **byte-identical**.
- The compiler test suite, the 21-case differential suite on four targets, and
  the gauntlet's bignum correctness tests are green.

## 6. What this does not settle

The limb rung is now chosen by exactly one target, and it is 2.8x–75x behind the
host's bignum on the other three. **What would change that is a target-declared
limb width and carry extraction** — 64-bit limbs where the host has a wide
multiply, and a shift and a mask instead of `/` and `%`. bigarith measured those
separately at 2.75x (limb count) and 3.9x (bitwise carry), which is about the
factor we are short on Go.

The value of doing the policy FIRST is that when that lands, no program changes.
A target file does.
