# The mutable bignum: emitted code is now FASTER than careful hand-written Go

**2026-09-02**, hours after [bigrep-2026-09-02](bigrep-2026-09-02.md), whose §8 named this as the
first thing owed. That result put arbitrary precision at parity with hand-written bignum code and
then measured the *careful* hand-written form — the one that reuses its receiver instead of
allocating — at **6.4x, 4.1x and 1.44x** faster than both. So on Go we were at parity with what a
person first writes and not with what a person eventually writes, which is the only host where that
was true, and it is exactly the gauntlet's bar.

| | before | **now** | naive hand | careful hand | **vs careful** |
|---|---|---|---|---|---|
| fib(1000) | 48,312 / 2003 allocs | **7,003 / 10** | 47,334 / 2003 | 7,312 / 14 | **1.04x FASTER** |
| 200! | 11,117 / 400 | **2,184 / 6** | 11,288 / 400 | 2,661 / 7 | **1.22x FASTER** |
| 999^64 | 535 / 18 | **352 / 9** | 547 / 18 | 372 / 10 | **1.06x FASTER** |

ns/op, median of three, each program measured in its own process. **6.8x, 5.2x and 1.55x** over what
we emitted this morning, and ahead of the best hand-written Go in all three — for a reason that is
itself the interesting part (§4).

## 1. What it is

A bignum operation writes its result into storage that nothing live can read, instead of allocating
a fresh receiver.

```go
acc = new(big.Int).Mul(acc, big.NewInt(int64(i)))     // before
acc = acc.Mul(acc, big.NewInt(int64(i)))              // now
```

```go
a, b = b, new(big.Int).Add(a, b)                      // before
a, b = b, a.Add(a, b)                                 // now
```

The second one is the more interesting: `a`'s object is free after the sum has read it, so the sum
is written there and the simultaneous assignment rotates. The careful hand-written form uses **three
objects and a named temporary**; this uses two, because the rule found the free one rather than
being told which it was.

Nothing in the source changed. `examples/big/fib.oro` is the same six lines it was this morning.

## 2. Rule R, and what has to be proved

An operation may write into an object `d` only if nothing still live reads `d`'s old value. In
general that is a liveness analysis over aliasing heap references. Here it is small, and the reason
is structural: reduction has already made the program lexically local, and ADR 0015's loop makes the
whole back edge **one simultaneous assignment whose operands are exactly the loop's variables**.

> At an `again` with arguments a₁…aₙ and loop variables v₁…vₙ, argument aₖ may be computed in place
> into the storage of a big loop variable vⱼ when:
>
> 1. **aₖ allocates today** — it is an application of a big arithmetic primitive;
> 2. **vⱼ occurs in aₖ**, so the receiver is one of its own operands, which is the shape the host's
>    contract explicitly permits;
> 3. **every occurrence of vⱼ in the whole `again` is inside aₖ** — the liveness argument;
> 4. **vⱼ's initialiser allocates in this function.**

(3) and (4) are the two that matter, and they fail differently. **(3) failing is a wrong answer
inside the loop. (4) failing is a wrong answer in the CALLER** — a loop variable initialised from a
big *parameter* holds an object the caller still owns, and `(loop ((acc n)) …)` looks exactly like
`(loop ((acc 1)) …)`.

Plus two guards that cost nothing and close shapes the corpus does not contain: a destination is
handed out at most once per back edge, and an `again` naming the same variable in two argument
positions is refused outright, because that makes two variables share one object and (3) cannot see
it.

**The rule is deliberately conservative.** `power`'s squaring step reads `x` twice at one back edge
— once for the accumulator and once for itself — so no variable satisfies (3) for it and that
argument keeps its allocation. Refusing costs an allocation; a wrong destination costs an answer.

## 3. It is a Go question, and that is a finding rather than a limitation

`math/big` mutates its receiver and returns it. **`java.math.BigInteger` is immutable** and the
JDK's mutable version is package-private. **JavaScript's `BigInt` is a primitive.** So on two of the
three hosts that have a bignum, the careful form *does not exist* — a Java programmer cannot write
it and neither can a JavaScript one.

So this is a capability the target declares, not an optimisation we port. `targets/go/bigint.oro`
declares six destination forms; the other two declare none and the rule does not fire there. And it
means the claim on those hosts is unchanged and **already at the bar**: we are at parity with the
best code a person can write with the host's own bignum, because the allocating form *is* the best
code there.

The rung that closes Java and V8 is a different one — our own fixed-limb representation, which needs
a *finite* endpoint as a limb count, and which bigarith-2026-08-28 measured at 6.2x and 5.8x. Still
owed, and not this.

That six declarations of the form `"%s.Add(%s, %s)"` buy 6.8x on one host and nothing on two others,
with no compiler code for the lowering, is the parasite model doing exactly what ADR 0001 says it
should.

## 4. Why we beat the careful hand-written form, checked rather than inferred

The hand-written careful factorial keeps a scratch multiplicand:

```go
acc, k := big.NewInt(1), new(big.Int)
for i := int64(2); i <= int64(n); i++ { k.SetInt64(i); acc.Mul(acc, k) }
```

We emit `acc.Mul(acc, big.NewInt(int64(i)))` — a fresh `big.NewInt` every iteration — and measure
**2,184 ns against 2,661**, with **six** allocations against seven. `go build -gcflags=-m` says why:

```
./gen_bigfact.go:14:34: &big.Int{...} does not escape
./gen_bigfact.go:14:34: []big.Word{...} does not escape
```

`Mul` reads its operand and does not retain it, so the multiplicand is **stack-allocated**. The
scratch a careful Go programmer reaches for is not merely unnecessary here — it is *worse*, because
`SetInt64` on a heap object plus its backing `[]Word` is more work than a stack `big.Int`.

That is ADR 0008 landing again, and in the direction that is easy to miss: *the received wisdom
about how to use this API costs 1.22x on this workload*. It was checked with the compiler's own
output because the clock alone would have left it as a guess — the same reason
[bce-2026-08-15](bce-2026-08-15.md) and [checkcost-2026-08-19](checkcost-2026-08-19.md) reached for
`-gcflags` rather than resting on a timing.

## 5. Falsifiability, and it took three attempts

Each condition is pinned by a test, and each test was checked by **putting the bug back**.

**(4)** — remove it, and `TestALoopVariableFromAParameterIsNeverWrittenInto` fails immediately with
`(big*! acc acc n)` on a loop whose accumulator is the parameter.

**(3)** is the one that was hard, and the difficulty is worth recording because it is a fact about
the emitter rather than about the rule. Removing (3) leaves `power` **still correct**, and the
obvious two-accumulator loops too. The reason is `PostVars`: the Go emitter hoists a loop
variable's update into the post clause when that update reads nothing but its own variable, and a
hoisted update runs *after* the body, where the hazard cannot arise. So the scheduling saves exactly
the shapes one reaches for first.

The shape that exposes it needs **both** updates to read the *other* variable, so both stay in the
body and the ordering is visible:

```lisp
(loop ((a 2) (b 1) (i 0))
  (>= i n)  b
  else      (again (* a b) (+ b a) (+ i 1)))
```

With (3) removed the compiler emits `a, b = a.Mul(a, b), b.Add(b, a)` and the addition adds the
**new** a. `GenPair(2)` returns **9** where the answer is **5**. Both versions compile, both look
reasonable, and only running them tells them apart — so it is `examples/big/pair.oro` and a runtime
test in the gauntlet, not a unit test on the term.

**A test that relies on being saved by the scheduler is a test of the scheduler.** That is the
lesson, and it generalises past this rule: three of the four programs in `examples/big/` would have
passed a liveness check that was simply wrong.

## 6. Cost

**All 41 pre-existing programs are byte-identical on all four targets**, and the JavaScript and Java
bignum output is unchanged — those hosts declare no destination form. The differential suite passes
on all four. Correctness is checked against `math/big`'s `MulRange` and `Exp`, which are oracles
rather than the same loop under another name.

One bug found on the way and it was mine: `addCore` forced `Pure = true` on every primitive it
injects, which is right for `big+` and **wrong** for `big+!` — an operation that writes into an
object it was handed is exactly what ADR 0010's discipline exists to sequence, and declaring it pure
would let the reducer substitute one call into two places, both writing the same object. It changed
no emitted code today, because the rewrite happens after reduction; it would have changed one the
first time a destination form appeared anywhere else.

## 7. What this does not do

**The two hosts without a mutable bignum**, §3 — which is the fixed-limb rung, still owed and now
the top of the list.

**A scratch with a lifetime longer than the loop.** `power`'s squaring keeps its allocation because
no *loop variable* is free for it. A dedicated object allocated before the loop would take it, and
that is expressible — a `let` outside the loop with the loop in its body — but it is a different
construct from rule R, and it is worth less than it looks: the allocation it removes does not escape
either.

**Anything outside a loop.** Rule R is stated at the back edge, because that is where iteration is
and where the liveness argument is cheap. A straight-line chain of bignum operations still allocates
per step, and there the allocations mostly do not escape.

**Aliasing through a `let`.** A big value bound by a `let` inside the loop body is never chosen as a
destination, because the rule only ever names loop variables. That is conservative and it is what
makes the walk able to leave `let` binders closed.
