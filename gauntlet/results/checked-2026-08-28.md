# What turning the checks on costs now — 2026-08-28

[precision-integers.md](../../docs/precision-integers.md) asked how much the compiler can prove,
because that number decides whether exact integers are affordable. A week of analysis work later, the
question is worth re-asking against the code rather than the notes.

**Answer: on 30 of 39 programs, `-checked` emits a byte-identical file.** The proof rate is now high
enough that representation selection is a no-op almost everywhere.

**And the path was broken.** `-checked` emitted Go that would not compile, on the one program in the
corpus with two live buffers.

---

## 1. The bug

`emit/interval.go`'s `evalR` walks a lambda by opening its body — `Body()` turns this binder's
KBound indices into KNames — and rewrapped it with **`FnClosed`**, which takes an *already-closed*
body and does not close. So every parameter occurrence came back a **free name** and the binder
stopped binding.

```go
v, b := p.evalR(t.Body())
return v, core.FnClosed(t.Params, b)     // wrong: Body() opened it
```

The rebuilt term is what `-checked` emits from, and the default path throws it away — so the bug was
invisible for as long as nobody turned checking on. `examples/json/tree.oro` compiled to Go
containing

```go
nodes6 := make([]int, (4 * 512))
nodes7 := nodes          // `nodes` belongs to a DIFFERENT function
```

and `go build` refused the file. `p.let` has the same shape and gets it right, with a comment saying
`core.Fn` closes an open body; the generic lambda case did not.

**Printing hides it**, which is why the test for it has two halves. An opened body prints its
parameters by the same names it was opened with, so `out.String() == in.String()` **passes against
the bug**. The structural check — after `Fn`, a lambda's stored body holds its own parameters as
indices, never as names — is what fails, and it names the variable:

```
"b" occurs as a free NAME inside the lambda that binds it; the rebuilt body was never closed
```

`TestIntervalsRebuildsTheSameTerm` pins both halves, and `TestIntervalsSelectsOnlyTheUnprovable` is
its companion: a rebuild that changed nothing would pass the first and be useless, so the second
requires the checked primitive to appear on an unbounded accumulator **and** the provable counter to
keep `go.+`.

## 2. The cost, measured

Every program, its own target, emitted twice and diffed.

| | checks inserted |
|---|---|
| **30 of 39 programs** | **none — byte-identical** |
| `tree.oro` | 42 |
| `smooth-java` | 2 |
| `divmod-go`, `divmod-java` | 1 each |
| `wordcount-go`, `wordcount-java` | 1 each |
| `collatz`, `power`, `fib` | 3, 2, 1 |

The last row is the proof system working: those three are in `examples/int/` **to be refused** —
Collatz because the conjecture is open, Fibonacci past 2⁵³, and exponentiation whose accumulator
genuinely overflows. The other six are the gaps already named elsewhere: `divmod`'s parameters carry
no `where` (the author's job), `wordcount` needs a map's value range
([growth.md](../../docs/growth.md)), and `tree.oro`'s 42 all chain off a depth read back out of the
worklist that stores it ([frozen-2026-08-28](frozen-2026-08-28.md) §6).

`tokenize.oro` is byte-identical, where before the fix it showed six lines of spurious name churn —
that churn *was* the binder bug.

### The one program that pays

`examples/json/tree.oro` on Go, `go test -bench -benchtime=2s -count=3`:

| | ns/op |
|---|---|
| unchecked | 5345, 5379, 5300 |
| **42 checks** | 5604, 6095, 5609 |

**1.05×, which is inside the 15% noise floor** and therefore not a number to lean on beyond "small".
That is consistent with [checkcost-2026-08-19](checkcost-2026-08-19.md), which measured **4.54× on
Go arithmetic-bound** and **1.23× memory-bound** and said the shape decides. A tree walk chasing
links is the second regime.

## 3. What this means for precision integers, and what it does not

**The affordability blocker has cleared.** precision-integers.md's central worry was that declaring
ranges *"changes NOTHING on the two parsers"* — which [fixpoint-2026-08-27](fixpoint-2026-08-27.md)
showed was a soundness bug, not a limit. With that fixed and a week of work since, selection is a
no-op on 30 of 39 programs and costs ~1.05× on the single program where it is not.

**But `-checked` is DETECTION, not precision.** It panics. Exact integers as asked for mean the value
stays exact past the window — promote, not trap — and that is R3, which is not built. The two are
different features and the measurement above is only about the first.

**And promotion is a representation change, which is the constraint that matters.** A value that may
exceed the window is no longer a machine word; it is a boxed `big.Int` / `BigInteger` / `BigInt`. The
repository's hardest rule is *never introduce boxing or hidden allocation into the core* — the
predecessor's cause of death. So the proof rate is not a performance question at all: **it decides
whether a boxed value can appear in an emitted program**, and at the sites where the proof fails
there are exactly three policies:

- **box there** — hidden allocation, refused by the rule above;
- **trap there** — what `-checked` does today, and honest, but it is not exactness;
- **refuse to compile** — make an unprovable operation an error and require the programmer to declare
  a range or ask for the trap. That is Low\*'s *"the restriction IS the mechanism"*
  ([lowstar-lessons.md](../../docs/lowstar-lessons.md)), and `examples/int/` already demonstrates it
  with three programs written to be refused.

Choosing among those is an ADR, not a build, and it is the next thing this line of work needs.

**Turning `-checked` on by default is still not a free call.** It reverses
[ADR 0012](../../docs/decisions/0012-portable-integer-range.md) without an ADR and makes cross-target
divergence *worse* — three targets trap, JavaScript declares no checked form at all and silently
loses precision. [assessment-2026-08-20 §2](../../docs/assessment-2026-08-20.md) recorded that once
already: *a demonstration wired into the default path is a decision, whether or not anyone made one.*

## 4. What is still owed

- **R3 on four targets.** Go `math/big`, Java `BigInteger`, JavaScript `BigInt` — three of four hosts
  have it in the language, so *"costs what it would cost if we implemented it on that target"* is met
  by construction there. windows needs one written.
- **JavaScript declares no checked primitive**, so representation selection there is currently a
  refusal rather than a rewrite. That is the honest answer and it is also a hole.
- **The policy ADR** of §3.
- Element narrowing is lost under `-checked` (`tree.oro`'s node table comes back `[]int` rather than
  `[]int16`), because a selected operation's name is not one `arithOp` knows. Not chased; it is
  self-consistent rather than clearly wrong, and it costs nothing on Go by
  [rebench-2026-08-27](rebench-2026-08-27.md).
