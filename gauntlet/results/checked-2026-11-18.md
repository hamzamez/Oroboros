# -checked traps on every target, or refuses (the book's finding 93)

2026-11-18. The book's finding 93: `-checked` did not trap on JavaScript. Under the rule that a
wrong answer goes ahead of the plan (assessment-2026-11-16 §3.4), it went first.

## 1. What was measured first

`no-grow.oro` squares 3 seven times. Built `-checked -target=js`, it printed
`1.1790184577738583e+61`, as the finding says. The IR shows why: the multiplication reached the
printer as `mul exact`, not `mul trap`. `ir.Decide` makes an unproven operation a trap only when
the target's operation declares a checked form (`checked add_exact`), and JavaScript declared none.
Without one, the operation kept the mode a proven operation has. The build then reported it as a
trap: its note counted Ops − Proven as traps, and under `-checked` it never asked for a refusal.
So the operation was neither refused nor checked.

**The fault is wider than JavaScript.** Go and the JVM declare checked forms for `+ − × /` only, and
the decision also counts `<<`. `3 << 69`, built `-checked`:

| target | before | after |
|---|---|---|
| Go | prints `0` | stops (`panic: int overflow`) |
| JavaScript | prints `3.541774862152234e+21` | stops (`RangeError`) |
| the JVM | prints a wrapped value | stops (`ArithmeticException`) |
| windows | stops (illegal instruction) | stops |

windows was already right: the LLVM layer states a checked realization for each operation
(`targets/llvm/lang.oro`'s `add_checked` … `shl_checked`).

## 2. What was built

**The rule** (`ir.CheckedRefusal`, `ir.RefusalUnder`). Under `-checked`, every counted operation
must be proven, trapped or closed on the word (below); otherwise the program is refused, naming
the operations and the target with no checked form for them. The three call sites that skipped the
refusal under `-checked` call it: `cmd/build` twice and `cmd/gen` once. An unproven operation in
the double word, or a `u64` word call, is untrapped too, and is now refused under `-checked` where
it was printed unchecked.

**Lemma C, an operation closed on the word.** By induction on the program, when every counted
operation is proven or trapped, every value held in the word W is in W at run time. So an
operation mapping Wⁿ into W needs no trap.
- **Which operations are closed.** On a two's-complement word: `~`, `&`, `|`, `⊕`, `>>` and `mod`.
  On JavaScript's symmetric ±(2⁵³−1): negation, `/`, `>>` and `mod`, but not the Boolean
  operations, since −(2⁵³−1) & −2 = −2⁵³.
- **Where it was found.** The rule alone refused `~p` on Go and the JVM after a loop of trapped
  operations, because p's interval was [0, +∞]: the interval does not narrow a trap's result to W.
- **How it is counted.** Such an operation is counted apart (`Legality.Closed`), not as a proof, so
  the pinned provability count stays 8,852 of 8,906. A first version counted it as proven and
  raised the count to 8,854, which would have claimed a proof the program does not have. The
  build's note says "N more closed on the word under them (Lemma C)" when there are any.
- **An operand held in U** (Go's `uint64`, a fact inside U beyond W) is not a W operand, and the
  lemma does not apply to it.

**The checked forms**, each with its reason in the target file:
- **JavaScript** `+ − ×`: by **Lemma S**, for safe integers a and b, fl(a ∘ b) is safe iff a ∘ b
  is, and then it is exact. If |a ∘ b| < 2⁵³ the integer is a double. If not, rounding is
  monotone and 2⁵³ is a double, so |fl| ≥ 2⁵³. So `Number.isSafeInteger` of the host's own result
  decides it, with each operand evaluated once.
- **JavaScript** `~`: −a − 1, decided by Lemma S.
- **JavaScript** `<<`: a·2ᵇ is exact where finite, since a power of two scales exactly. Past
  b = 1023, 2 ** b is Infinity and 0 · Infinity is NaN, so a = 0 answers 0.
- **Go** `<<`: a·2ᵇ ∈ W iff (a << b) >> b = a. For b ≥ 64, a << b is 0. For b < 64, t ≡ a·2ᵇ
  (mod 2⁶⁴) and t >> b = a put t within 2ᵇ of a·2ᵇ, so they are equal.
- **The JVM** `<<`: Java masks a count by 63, so b ≤ 62 is `Math.multiplyExact(a, 1L << b)`, and
  b ≥ 63 is in W only for a = 0, or a = −1 at b = 63.
- **The JVM**'s host `neg`: `Math.negateExact`. The language's −p is 0 − p, a subtraction, so a
  negation is reached only by a program naming `java.neg`.

## 3. The tests

`cmd/build/checked_test.go`, on four targets:
- **`TestCheckedStopsOnEveryTarget`**: nine programs, each operation one step inside a word and one
  past it (3³², 3⁶⁴, 3·2⁵¹, 3·2⁶¹, 3·2⁶², ~(2⁵²−1), ~(2⁵³−1), −(−2⁶²), −(−2⁶³)), where the words
  differ (3·2⁶¹ and −2⁵³ are in S₆₄ and outside JavaScript's word). Plus `java.neg` at −2⁶² and
  −2⁶³. 38 runs, each ℤ's answer or a stop.
- **`TestAnUntrappedOperationIsRefused`**: `PlantNoCheckedForm`, every target read as declaring no
  checked form, must be refused, naming `p * p`. With `PlantUntrappedAccepted` too, the bug as it
  shipped must build and print a number, so the case can fail.
- **Lemma C's fault, `PlantNegClosed`**: negation claimed closed on S₆₄. The JVM's −(−2⁶³) must
  then print instead of stopping.
- **Each checked form's fault** is the form being wrong. A missing check makes the step past the
  word print a number, and a check too strict makes the step inside it stop. Either fails the case.

## 4. Not built, and found

- **`0 << b` for b ≥ 1024 on JavaScript without `-checked`.** `js.shl` is `a * 2 ** b`, NaN there.
  Not reproduced: a loop's count did not discharge the shift's `b >= 0` obligation, so the program
  was refused first. Owed: whether any program reaches it.
- **Narrowing a trap's result to W in the interval analysis**, which would prove some of Lemma C's
  operations instead of counting them closed. Not needed for soundness.
