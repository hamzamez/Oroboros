# What a process costs on each host: the ring, natively and as a step function

2026-10-04. The first measurement of [concurrency-research.md](../../docs/concurrency-research.md)
(§6, M1). Erlang's design rests on a premise: processes are cheap enough to create one per activity,
so that one can be let to crash. This measures what that premise costs on each host, in two
lowerings of the same process:

- **native**: the host's own unit of concurrency, with a stack per process. A goroutine and a buffered
  channel on Go; an async function on a promise mailbox on JavaScript; a platform thread and an
  `ArrayBlockingQueue` on Java (JDK 17, which has no virtual threads); and a BEAM process, the
  reference.
- **stackless**: a step function per process, run by one scheduler over a run queue, each mailbox a
  fixed ring of 16. This is research §2.2's state-machine form: what a process with blocking receive
  compiles to in a language with no recursion. It is written the same way on Go, JavaScript and Java.

Sources: `experiments/concurrency/` (`ring.go`, `ring.mjs`, `Ring.java`, `ring.erl`, `mem.*`).

## 1. The ring

N = 1000 processes in a ring. T tokens are each passed M = 1000 times round it, so there are N·T·M
hops. Each process receives an integer and sends it on, and the head decrements it. Figures are the
median of 7 runs after a warm-up, in ns per hop. Each case ran in its own process, two passes
interleaved; the passes agree within 3%, except JavaScript stackless at T = 100 (7.9 and 5.4).

| host | lowering | T = 1 (latency) | T = 100 (throughput) |
|---|---|---:|---:|
| BEAM (OTP 29, 16 schedulers) | native | 428 | 70 |
| BEAM, one scheduler (`+S 1`) | native | 358 | 90 |
| Go 1.27, GOMAXPROCS = 16 | goroutine + channel | 275 | 9.3 |
| Go, GOMAXPROCS = 1 | goroutine + channel | 180 | 39 |
| Go | **stackless, one thread** | **5.7** | **2.0** |
| Node 26 | async function + promise | 53 | 48 |
| Node | **stackless** | **13** | **5–8** |
| JDK 17 | platform thread + queue (M = 100) | 4,220 | — |
| JDK 17 | **stackless** | **7.0** | **3.6** |

## 2. Memory per idle process

100,000 processes, each blocked receiving:

| host | lowering | bytes per process |
|---|---|---:|
| Go | goroutine + channel | 9,306 (stack 8,192) |
| BEAM | native | 2,673 |
| Node | async function awaiting a promise | 729 |
| any | stackless: a 16-slot mailbox, its head and size, a run-queue slot | 76 (int32), 152 (int64), by layout |

The JVM's platform threads were not measured at 100,000: each reserves a stack of about a megabyte.

## 3. What it says, and what it does not

- **A process need not have a stack, and without one each hop is cheaper than the host's own unit of
  concurrency on every host.** At T = 1 every hop is a context switch; for the stackless lowering it
  is an array write and a run-queue push. Per hop it is:
  - 4× cheaper than JavaScript's async functions, which are state machines already;
  - 48× cheaper than Go's goroutines;
  - 600× cheaper than JDK 17's threads;
  - 75× cheaper than BEAM's processes, comparing Go's stackless figure with BEAM's.
- **The comparison is not like for like, and the differences are the research's questions.**
  - BEAM preempts by reductions, collects garbage per process, copies every message between heaps,
    and accounts for each process. The stackless scheduler does none of these. A step that loops
    forever starves every process on its scheduler (research §5, C2(b)).
  - Go's goroutines at T = 100 use 16 cores (9.3 ns per hop, wall); the stackless scheduler uses
    one (2.0). Each hop does no work, so this measures scheduling, not the parallelism a real step
    would use.
  - A stackless scheduler stalls on a **blocking host call**. A goroutine does not, because Go's
    runtime parks it (research §4, Go).
- **JavaScript's native form is already a state machine.** An async function is compiled to one, so it
  is cheap in memory (729 B). Its cost per hop (53 ns) is the promise machinery, not a stack switch.
- **JDK 17's thread is an OS thread**, 4.2 µs per handoff. Virtual threads (JDK 21, JEP 444) are the
  JVM's own answer, and no JDK 21 was installed to measure them.

## 4. Method, and what went wrong first

- **The first JavaScript memory figure was 0 bytes.** Nothing read the mailbox array after the
  measurement, so V8 collected it before the heap was read. That is "V8 eliminating unused work" from
  CLAUDE.md's list. The array is now read after the measurement, giving 729.
- **The installed `erl` would not boot**: "corrupt atom table" for every module, and it wrote a crash
  dump into the working directory. `bin/erl.ini` points at runtime 15.2.5 while the libraries are
  OTP 29. The runtime that matches them, `erts-17.1`, was run directly.
- Processes were listed before the runs, and no other benchmark was running. Every case ran in its own
  process, and the passes were interleaved, not consecutive.
