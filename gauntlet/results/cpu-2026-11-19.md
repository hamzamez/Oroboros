# cpu — ADR 0085's forms on LLVM, and a target's CPU (ADR 0142), 2026-11-19

hamza, 2026-11-19: "Build everything that is decided and wait for a program." Two decisions
waited:
- ADR 0085 (2026-10-30), vectors as a representation of a table: "Accepted; not built (its main
  consumer is `ir/llvm`)";
- kernels-research §6 Q2 (2026-11-15), "a target may name its CPU and features … baseline stays
  the default".

The program for both is the integer dot product, `examples/table/idot.oro`: Σ a[i]·b[i] over two
tables of 65,536 entries in 0..65535, taken 2,000 times. It prints Python's 244038704.

## What was measured first: ADR 0085's forms already vectorize on LLVM

ADR 0085 item 2 says "on LLVM the facts are stated and its vectorizers act". Each of its three
forms, compiled by the build's own `clang -O2` at the baseline:

| form | program | loop body |
|---|---|---|
| a fold by `+` | `acc + a[i] * b[i]` | `movdqu`, `pmuludq`, `paddq`: two i64 lanes, unrolled twice |
| a rule | `array { a[k] * 3 : k }` | `paddq` (3x as x + x + x) |
| a loop of stores | `b[i] := a[i] + 1` | `psubq` of −1, `movdqu` stored |

So nothing is built for item 2 on LLVM: its vectorizer acts on what we print. Item 4 (explicit SIMD
on Go and the JVM only where a measurement shows it pays) has no measurement asking yet.

## What was built: a target's CPU

ADR 0142:
- `cpu "NAME"` is target data beside `triple`, combined by agreement;
- the printer writes it as every function's `"target-cpu"`, so the module states what it is
  compiled for;
- the member `windows-v3` glues `windows` and states `cpu "x86-64-v3"`;
- a windows member's program layout is read off its triple's OS, where it was a list of names.

`windows-v3`'s module differs from `windows`' by its attribute line alone.

## The measurement

`idot.exe`, median of 12 runs each, interleaved, the same window:

| | ms | against Go |
|---|---:|---:|
| Go (scalar; Go does not vectorize) | 54.0 | 1 |
| windows, baseline (SSE2) | 65.7 | 1.22× |
| windows-v3 (AVX2) | 41.7 | 0.77× |

The baseline against x86-64-v3 measured 67.1 / 40.3 and 67.2 / 46.4 ms in two other windows:
0.60–0.69×.

**Against hand-written C** ([`cpu-2026-11-19/dotc.c`](cpu-2026-11-19/dotc.c), the same clang at the baseline, a compiler barrier in the
round loop so the read-only call is not hoisted out of it):

| | ms |
|---|---:|
| C, `int64_t` elements | 63.4 |
| ours, windows baseline | 63.1 |
| C, `uint16_t` elements | 47.2 |

At i64 elements ours is C's. Go's scalar loop beats both: LLVM's two-lane i64 vectorization loses
to one scalar `imul` here. Elements of 16 bits, what the values need, are 0.74× in C.

## What failed first

1. **The baseline loses to Go's scalar loop, and C at i64 loses with it.** SSE2 has no 64-bit
   lane multiply, so LLVM's two-lane i64 product is three `pmuludq` and shifts, slower than one
   scalar `imul`. Its cost model took a vectorization that loses, for C as for us. The values are
   below 2^16 and the tables hold them in i64 elements (llvm.md §4: "every other integer element
   is an i64"), so the lanes are four times wider than the values need.
2. **C's first time, 12 ms, was eliminated work.** `dot` is read-only over unchanged tables, so
   clang hoisted its 2,000 calls into one. A memory barrier in the round loop restored them.
3. **`windows-v3` had no program layout**: `WriteProgram` chose it by the names `windows` and
   `windows32`. The family's layout is its triple's OS, so it is read from the triple now.

## The tests

`TestATargetsCPUIsInItsModule` (`ir/llvm/cpu_test.go`): `windows-v3` has `windows`' triple at
x86-64-v3, and its module states it; `windows`' states no CPU. The fault `PlantCPUUnprinted` prints
none, and the test sees the module silent.

## Owed

- **A table's element by its set on LLVM** (i16, i32 beside today's i8): a change to llvm.md §4's
  layout, so a decision for hamza. The measurement for it is C's 0.74× at 16-bit elements.
- **A feature beside the CPU** (ADX for the adder, kernels-research R2), when a program needs one
  feature alone.
- **`windows-v3` in `cmd/check`'s sweep**: only its test and its program run it.
