# D2: K(ℕ\*)'s base is the triple's native word

2026-11-17. Item 4 of [assessment-2026-11-16](../../docs/assessment-2026-11-16.md) §5, step 4 of
[ADR 0122](../../docs/decisions/0122-the-windows-family-is-a-fibration-and-a-triple-is-a-model.md)
(D2), after [D6](d6-2026-11-17.md). Decided by
[ADR 0124](../../docs/decisions/0124-k-n-stars-base-is-the-triples-native-word.md), amending ADR 0106.

**windows32 computes in base B = 2³²**, x86_64 still in 2⁶⁴, from one library whose base is a
parameter block. Every K(ℕ\*) case of the suite passes on windows32 (15, four of them refused
before), so 72 of 74 cases pass there. x86_64's emission is byte-identical. The cost is measured:
20000! printed takes 7.9× Go's `math/big` on 386, against 3.7× on x86_64. The cause, read off the
machine code (§4), is the digit step's 64-bit arithmetic on a 32-bit machine, not the division.

## 1. The algebra

- **The base, by ADR 0106's theorem.** B = 2^w for the largest w whose B² − 1 the native double
  word holds, and whose multiply-accumulate and division by a digit the machine does natively.
  That is i128 on x86_64 (`mulq`, `divq`) and i64 on i686 (`mul r/m32` into EDX:EAX, `divl`). So w
  is the ISA's word, a function of the triple (`Target.DigitBits`), and nothing restates it.
- **The library is a theory with a parameter** (ADR 0035, 0101). Every line reads B through one
  block: dbits, dm = B − 1, bq = B/4, bh1 = B/2 − 1, β = 10^kd, kdd. Each instance is decided under
  the block of its triple. The block's own algebra is checked from dbits alone:
  - B = bq·4;
  - β, the largest power of 10 below min(B, 2⁶²): 10¹⁸ at 64 bits, 10⁹ at 32;
  - kdd = ⌊w·log₁₀ 2⌋ + 1: 20 at 64, 10 at 32.

  `kdigits`' bound on the base-β digits, m + m/14 + 1, holds at both bases, since log_β B is 1.0704
  at 64 bits and 1.0703 at 32, both below 1 + 1/14.
- **A word is ⌈64/w⌉ digits.** `of` writes |v| as one digit at 64 bits and as two at 32, |v| mod B
  and ⌊|v|/B⌋ < B, since |v| ≤ 2⁶³ < B². `word` reads back d₀ + d₁·B. The choice is on a constant,
  folded by the reducer, so each base sees only its own form.
- **The two-digit lemma on the unsigned word.** At B = 2³², q̂ = ⌊(u·B + w)/d⌋ with u < d is
  computed in the word: `u64/` of `u64+` of `u64*`, the operands converted by `u64-of`. Those are
  ℤ's operations on the integers they hold, and `u64-of` is the identity wherever wordsel places it.
  So the lemma, ⌊t/d⌋ ≤ C − 1, applies through them unchanged. Without it, q̂ ∈ [0, 2⁶⁴), and its
  signed reading [−2⁶³, 2⁶³) made Algorithm D's correction `q − b` unprovable.

## 2. The witnesses

- **`TestKNStarIsInTheTriplesDigit`** (cmd/build, windows32): a program computes and prints 300!,
  the 500th Fibonacci number, and quotients and remainders of them by numerals of 6 to 10 digits,
  each line checked against Go's `math/big`. 300! has 65 digits at 32 bits, past the 32-digit
  threshold, so it is printed by the tree of divisions. **The planted fault** (`PlantNatBase64`)
  keeps the 64-bit block on the triple, and the program is refused as before, "no realization
  holds both".
- **`TestTheTwoDigitLemmaReadsTheUnsignedWord`** (ir): windows32's `div` and `render` instances are
  decided under their parameters' sets. **The planted fault** (`PlantQuotientWordOnly`) reads the
  lemma on ℤ's operations alone, and `div` is not decided.
- **`TestTheBaseBlockIsItsBase`** (emit): each triple's block is the function of dbits it claims.
  **The planted fault** is a 32-bit block with β = 10¹⁸, past its digit, and it is reported.
- **The suite on the triple** (`run32.go`): all 15 `big-*` cases pass, `big-fib`, `big-nat-div`,
  `big-nat-ops` and `big-render` among them. 72 of 74 cases pass, the two left the harness's
  (`u128`, Go-only).
- **x86_64**: the emission sweep is byte-identical, 660 runs, with the proof counts unchanged.

## 3. What failed first

1. **The constant `w` was captured by locals.** The first rename wrote the base as `w`, and
   `natnum.oro` binds `w` in `kup`, `kun`, `kslot` and `numeral`, so `t >> w` there would have
   shifted by the local. It is `dbits`, a name no line used. A context keyed by name is captured
   by the name alone (CLAUDE.md's lessons). Here the capture was caught by reading the library,
   not by a test.
2. **Two K(ℕ\*) compiles ran for over 20 minutes** (`big-nat-div`, `big-nat-ops` on windows32), and
   were stopped. An instance its contract does not prove is inlined (P4), and Algorithm D inlined
   into a program did not finish compiling. The cause was `div` and `render` undecided at 32 bits
   (item 4). With them decided the cases compile in seconds. **A compile that does not end is not
   refused**: that is owed, below.
3. **14 allocations were unproven inside max_len** (`big-fib`): `kdigits`' 2·kj digits and
   `kdlevel`'s n + 1 words had relied on room's 2³¹ being far below 2⁴⁷. On i686 max_len is
   2³¹ − 9, so each size goes through `room`. On x86_64 the decision proves those guards dead.
4. **The lemma did not fire, three times.** I extended it to the `u64` calls (no change), then masked
   q̂'s reads (no change), then let it see through conversions (no change). Each time I had guessed
   at the premise. Instrumented, `numeralQuotient` showed `scaled` returning C = 4: the inner product
   u·2³⁰ was a signed-word `mul` behind a `u64-of`, so the recursion stopped at the conversion.
   `scaled` now reads through conversions too. The masks were reverted, since they were not needed
   and would have changed x86_64's emission.
5. **The test's divisors.** `fib(500) + 1` is not proven nonzero by the refinement layer, since a
   definition's result above the word is no fact there. The test divides by constants of 6 to 10
   digits, as `big-nat-div` does.
6. **A Python heredoc corrupted non-ASCII text** (read in the console's code page). The script was
   rewritten with the Write tool before it touched the library; the library was checked for U+FFFD.

  | windows (x86_64), B = 2⁶⁴ | 45.4 (42.9) ms | 12.3 (11.9) ms | 3.68 |

## What was not built

- **The 2-by-1 division at 32 bits for q̂** (the rest of D4's `x86.oro`). The lemma proves the
  quotient below 2³², so q̂ is one `divl`, where it now calls `__aulldiv`. It is a small part of the
  7.9×, at most a few percent (§4).
- **`adc` at 32 bits**: LLVM expands the i64 adds, and nothing is measured yet.
- **The Karatsuba threshold at 32-bit digits**: kt = 64 was measured at 64-bit digits.
- **A refusal for a compile that does not end**: an undecided instance inlined into a program
  compiled for over 20 minutes. A bound on the reducer's or the decision's work per program, or a
  refusal when an instance a program needs is not decided, is the missing rule.
- **windows32 in `cmd/check`**: hamza's (d6-2026-11-17).

## 4. Where windows32's time goes (read after the step)

The 20000! program's machine code, compiled as the build compiles it:
- **Only three calls to `__aulldiv` survive**, all in `nat.render`, LLVM having folded each
  remainder into its quotient's call. They run about once per quotient digit of the tree of
  divisions, of the order of 10⁵ times, a few milliseconds of the 208.
- **The product's inner loop is the cost.** The step t = a_i·k + c is a full 64×64 multiply, one
  `mull` and two `imull`. Each digit is loaded as two words from an 8-byte element whose high half
  is always 0, the loop index is 64-bit (an `adcl` and an `sbbl` a step), and the loop spills.
  Go's 386 kernel is one `mull` and an `adc` per 4-byte digit.

So the 32-bit gap is owed to two facts the decision has and LLVM does not see:
- **a digit's range**, [0, 2³²), which `!range` on a load states: φ's next kind, item 5 of the
  plan;
- **its width**: a 4-byte element and a 32-bit index, ADR 0083 item 2's 32-bit scalars, D5.

The division is not the first cause; the result as first written said it was.
