# D6: i686's 64-bit division is the language's, at the symbols LLVM calls

2026-11-17. Item 4 of [assessment-2026-11-16](../../docs/assessment-2026-11-16.md) §5, step 3 of
[ADR 0122](../../docs/decisions/0122-the-windows-family-is-a-fibration-and-a-triple-is-a-model.md)
(D6), after [windows32](windows32-2026-11-17.md). Decided by
[ADR 0123](../../docs/decisions/0123-a-triples-runtime-is-a-library-in-the-language.md).

**windows32 links its own 64-bit division**: `lib/rt/i686.oro`, Warren's divDu over `divl`, linked as
the triple's runtime. Every operation in it is decided, and it runs at 0.87× the time of MSVC's
libcmt helpers. 68 of the 74 differential cases pass on the triple (66 before); the six left are
D2's four and the harness's two.

## 1. The algebra

- **What the triple leaves free.** LLVM 23 at -O2 on i686-pc-windows-msvc expands every 64-bit
  instruction Σ_LLVM offers inline, except division at a divisor it does not see through. For those
  it calls `__aulldiv`, `__aullrem`, `__alldiv` and `__allrem`, stdcall (probe: 20 functions, every
  instruction family of `instructions.oro`):
  - unsigned by any constant: inline;
  - signed by a constant: a call;
  - both operands known in 32 bits: `divl` or `idivl`;
  - i128 `mul` and `udiv`: inline.

  On x86_64 nothing is called. So Σ_LLVM is one signature on both triples, closed on i686 only
  together with Σ_RT = {those four}, a parameter of the triple's model as Σ_OS is of T_LLVM.
- **The primitive.** `divl` is D(n, d) = (⌊n/d⌋, n mod d) on its domain ⌊n/2³²⌋ < d < 2³². Off it,
  the instruction raises #DE, which is the process's trap. So D is total with ⊥ off its domain, and
  never answers wrongly. It is declared i64 throughout: n is the pair EDX:EAX (`A`), and d is a
  memory operand whose low dword, little endian, is d.
- **The quotient** (Warren, Hacker's Delight 2nd ed. §9-5; Knuth TAOCP 2 §4.3.1), for x < 2⁶⁴ and
  0 < y < 2⁶⁴:
  1. If y < 2³² and x₁ = ⌊x/2³²⌋ < y, then q = D(x, y), one digit.
  2. If y < 2³² and x₁ ≥ y, it is short division in base 2³²: (q₁, k) = D(x₁, y), then
     (q₀, r) = D(k·2³² + x mod 2³², y). The second is in domain since k < y.
  3. If y ≥ 2³², then q < 2³². Let s = clz(y) ∈ [0, 31] and v₁ = ⌊y·2ˢ/2³²⌋ ∈ [2³¹, 2³²). Then
     q₁ = D(⌊x/2⌋, v₁) is in domain, since ⌊x/2⌋ < 2⁶³ ≤ v₁·2³². Warren's theorem gives
     q ≤ q₀ = ⌊q₁·2ˢ/2³¹⌋ ≤ q + 1, so q₀ − 1 (or 0) is q or q − 1, and one comparison of
     x − q₀·y with y fixes it.

  Every product there is at most x, so each C `uint64_t` step is its residue mod 2⁶⁴ in ℤ (ADR
  0082), exact. The remainder is x − q·y < y, a residue too.
- **The signed ones.** |q| = ⌊|a|/|b|⌋ carries the sign of a·b, and r = a − q·b carries a's
  (truncation, integers.md §3). |q| ≤ 2⁶³, with equality only at −2⁶³/−1, off LLVM's domain; there
  the function traps, as x86's `idiv` does. A negation −m is written −1 − (m − 1), so no value at
  2⁶³ is ever read as a signed word.
- **Well-founded.** A division by a word inside the runtime would be a call to itself. The runtime,
  compiled, calls none of its four symbols.

## 2. The witnesses

- **`TestTheTriplesRuntimeDivides`** (cmd/build, windows32), a program dividing words the facts
  cannot narrow, checked against Go's answers:
  - every pair of 20 unsigned edge classes (0, 1, 2³² ± 1, 2⁶³ ± 1, 2⁶⁴ − 1, …);
  - every pair of 15 signed ones (−2⁶³, −1, 0, ±(2³² − 1), …), skipping LLVM's excluded points;
  - 300,000 generated pairs, the divisor shifted through all 64 widths, so all three of the
    quotient's cases are reached.

  **The planted fault** (`PlantRuntimeUnlinked`) builds without the runtime, and the link must
  refuse.
- **`TestTheRuntimeCallsNoHelper`**: `lib/rt/i686.ll`, compiled for its triple, calls none of its
  symbols. **The planted fault**, through `plantOnce`, is a runtime whose `__aulldiv` is the
  language's own `x / y`, which is found calling `__aulldiv`.
- **`TestAHostResultBoundsAWhere`**: `1 << (clz_low(v) − 32)` builds and prints the right powers.
  **The planted fault** (`PlantHostResultUnassumed`) seeds no result set, and the shift is refused
  under `<<`'s requirement.
- **The suite on the triple**: `bits-edges` (`__allrem`) and `word-wide` (`__alldiv`) pass, so 68 of
  74 cases pass.
- **The runtime is regenerated and compared**: `gauntlet/regen.txt` lists it (with `gen`'s flags,
  which the list now carries), so `cmd/check`'s gauntlet step requires it byte-identical.

## 3. What failed first

1. **A host result's set was no fact for the refinement layer.** The normalization shift `1 << s`,
   with s from `clz`, was refused, because `<<`'s count is a `where`, which only the refinement
   layer decides, and that layer did not read `clz`'s declared result. The IR's intervals did, so
   the two routes had decided on different premises. Now both do (ADR 0123 item 5).
2. **A value at 2⁶³ read as a signed word.** `0 − m` on a guarded m ∈ [0, 2⁶³] converts m to the
   signed word first, where 2⁶³ reads as −2⁶³. That is sound, since the conversion's interval is the
   bit reading, but it is refused. I first took the reported interval [−2⁶³ + 1, 2⁶³] for an
   unsound fact and stopped D6 to look. The IR shows `u64>` and the conversion are right. The
   negation is now −1 − (m − 1).
3. **The signed residue does not lower.** `((v + 2⁶³) mod 2⁶⁴) − 2⁶³` needs `mod` on a value in
   the unsigned word, which no realization holds. The sign step is a guarded case instead.
4. **A helper inlined into a claim lost its π.** `pos(x)`, whose own claim passes, did not pass as
   the body of an export's claim: the inlined arm yields the parameter itself, unrefined. The
   signs are written in the exports instead. This is owed, below.
5. **The test drivers met three of the analysis's known gaps:**
   - a literal table indexed inside a contract mark does not lower;
   - `y != 0` from `if y == 0` is a hole an interval cannot hold;
   - `mod 2⁶⁴ − 1` puts its operand in the unsigned word.

   Each driver was written around them: guards `y >= 1`, case chains, and `>>`.
6. **Heredocs ate backslashes four times** (CLAUDE.md's warning): in `"\\01"`, in `"\n"` twice, and
   in a Python script. Those edits were redone with the Edit tool.

## Paid and bought

- **Run time**: the same `main.obj`, a mix of 10⁷ unsigned and signed divisions of every divisor
  width, linked once with `rt.obj` and once with `libcmt.lib`, nine interleaved rounds, medians
  (minima): ours 374.2 (370.1) ms, libcmt's 432.3 (427.9) ms, a ratio of **0.866** (0.865). The
  fallback ADR 0122 kept, libcmt, is not needed.
- **Code size**: `rt.obj` (3,338 bytes) is linked whole into every windows32 program.
  - The benchmark is 8,192 bytes with our runtime and 5,632 with libcmt's, which links only the
    helpers called.
  - `hello-win`, which divides nothing, grows from 4,096 bytes to 6,656 (+2,560).

  The remedy is owed (below).
- **Compile time**: 1.05× the baseline in the accepting run (the median of 58 compiles over
  300 ms). The second sweep kept one suspect, `utf8-widths` on windows, cleared at 1.00× when paired
  serially against `gen` built at `0b3fdc4`. The first run was 1.04×.
- **The suite's files**: `gauntlet/regen.txt` lists 34, the harnesses' 33 and the runtime.
  `TestTheRegenListNamesItsSources` now says so, and CLAUDE.md and `gauntlet/check/README.md` quote
  the 34.
- **Emitted text**: unchanged on every target. The baseline gains one source, `lib/rt/i686.oro`,
  refused on the sweep's four targets, since none of them is windows32. The refinement layer's new
  fact changed no other outcome.
- **Proofs and refusals**: unchanged, 8,852 of 8,906 integer operations and 924 of 962 loops.
- **Compiler lines**:
  - `emit/target.go` +57 (the `runtime` form, its file, the link line, the plant);
  - `emit/refine.go` +48 and `requires.go` +1 (`seedResultSets`, the plant);
  - `ir/llvm/llvm.go` +41 (`RuntimeEntry`);
  - `cmd/gen` +23 (`-runtime`), `cmd/check/gauntlet.go` +12 (gen's flags in `regen.txt`) and its
    test, `core/jreadtarget.go` +1;
  - `experiments/i686/run32.go` +6 (`$I686_TARGET`, from step 2);
  - tests: `cmd/build/runtime_test.go` 230.
- **Language and target lines**:
  - `lib/rt/i686.oro` 93, generating `lib/rt/i686.ll` (385);
  - `targets/windows32/x86.oro` 24 (`divl` and a restricted `ctlz`);
  - `windows32.oro` +7.
- **Rules made less general**: none. The refinement layer assumes one fact more, and it is the
  IR's own.

## What was not built

- **D2**, K(ℕ\*) on base 2³² (the four `big-*` cases), and with it the rest of D4's `x86.oro`.
- **The runtime only where it is called.** `rt.obj` is linked into every windows32 program. A
  section per function (`-ffunction-sections`) with `/OPT:REF` would drop what is not called.
- **A per-site realization of `/` chosen by the facts**, a divisor proven below 2³² taking one
  `divl` inline: an optimization over this, to be measured.
- **windows32 in `cmd/check`'s differential step** and in the emission sweep: the suite runs through
  `experiments/i686/run32.go`.
- **The inlined helper's π** (§3 item 4) and **the signed residue's lowering** (§3 item 3), each a
  missing proof a program named, left as written around.
