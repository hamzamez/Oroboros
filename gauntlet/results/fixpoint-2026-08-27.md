# A latent fault in the interval fixpoint — 2026-08-27

> **Fixed the same day. §7 onward is the fix, the proof, and what it costs.**

**No feature shipped from the first attempt.** Two small gaps were meant to be closed; the second one
found something that has to be fixed before either is worth having, so this records what was found,
what was measured, and what was reverted.

---

## 1. What was being attempted

[monotone-2026-08-27](monotone-2026-08-27.md) derived a lower bound on a loop's value and used it to
prove the JSON tokeniser's loops terminate. `examples/json/tree.oro` did not benefit, and the reason
was mechanical rather than deep: [ADR 0015](../../docs/decisions/0015-loop-and-again.md) permits
`again` under a `let`, and the tree uses it, so the argument advancing the index is the **name** `ni`
rather than the scanner's loop term:

```lisp
(let (if (= (src i) 34) (scan-string src i)
      (if (numeric? (src i)) (scan-run src (go.+ i 1) numeric?)
                             (scan-run src (go.+ i 1) alpha?))) (fn (ni)
  (again … ni …)))
```

Two things were needed and both were built:

- **Look through a `let`.** The pass records a name's interval; it now also had to record the *term*,
  because monotonicity works on the term.
- **Look through an `if`.** `ni` is bound to a choice of **three** scanners, so neither a loop nor a
  `self ± c` shape is visible. The derived step is the **minimum** over the branches — either may be
  the one evaluated.

That worked: `examples/json/tree.oro` went from **20 of 25 loops proven terminating to 25 of 25**,
with no regression on the tokeniser or the sieve.

## 2. And it produced a silent wrong answer

The differential suite refused it:

```
FAIL json-tree — targets disagree
  go       3030081 3030111 4040171 7070331
  js       3030081 3030111 4040171 7070331
  java     3030081 3030111 4040171 7070331
  windows  3030081 3030111 4030140 7050270
```

The same two wrong values as [the first-store bug](elemwidth-2026-08-27.md), and the same mechanism:
the node table's inferred element range collapsed from `int 0 512` to **`int 0 5`**, so every link
index above 255 truncated.

## 3. The cause is NOT the change, and that is the finding

Proving the loop terminating is what enabled `tripCount` — it runs only when size change succeeds:

```go
ok, witness := SizeChangeTerminates(p.scEdges, wf)
if ok { trip, haveTrip = p.tripCount(cur) }
```

So a code path that had never executed on this program executed, and it read a value that was
already wrong.

**The fixpoint settles two loop variables at their initial values.** Traced round by round on the
parse loop, `raw = [nodes stk i nn sp ok]`:

```
widen  r0  cur[i]=[0,0]  next[i]=[0,2]
widen  r1  cur[i]=[0,2]  next[i]=[0,0]     ← next SHRANK below what was established
widen  r2  cur[i]=[0,2]  next[i]=[0,0]
narrow r0  cur[i]=[0,2]  next[i]=[0,0]     ← contained, so narrowing accepts it
           cur[i]=[0,0]
```

`sp` never leaves `[0,0]` either. **The identical trace is produced by the code with the change
reverted** — checked by stashing — so this predates today and is not caused by looking through a
`let`.

Two consequences follow from `cur[sp] = [0,0]`, and both are wrong:

- `(go.< sp 1)` is decided **always true**, so the `else` branch of `link` — which is where every
  parent-to-child and sibling-to-sibling store lives — is treated as unreachable and its stores are
  never recorded. The range then sees only the tag stores, which are 1..5.
- `cur[i] = [0,0]` gives `span = 0`, so `tripCount` computes **1**: the analysis believes the parse
  loop runs at most once.

## 4. What was reverted, and why not just guard it

Two guards were tried and neither is the right fix.

**A derived step yields no trip measure.** Returning `down, descent{}` gives the descent arc and
withholds the measure, so the variable cannot be a witness. It did not help: `i` still gets
`kind{1,1}` from the *other* clauses, whose argument is a plain `(go.+ i 1)`.

**A position advanced through an inlined loop is excluded from `tripCount` entirely.** Also did not
help, for the same reason and because the damage comes through `sp`, not through the witness.

Guarding the symptom was the wrong instinct anyway. `cur[i] = [0,0]` for a variable that plainly
grows is unsound on its own terms, and the buffer narrowing that already ships
([elemwidth §5d](elemwidth-2026-08-27.md)) reads `cur` to decide how many **bits** a value gets. The
right order is to fix the fixpoint and then re-land the two gaps against an analysis that can be
trusted.

So the change is reverted. `tree.oro` is back to 20 of 25 loops, all ten differential cases agree on
four targets, and nothing narrows on a value the fixpoint got wrong.

## 5. What is left in place

`TestNodeTableRangeHoldsEveryIndex` — a tripwire in `emit/`, asserting that the node table's inferred
range contains 0..511. It passes today. It is there because it *broke*, from a change that touched
nothing about buffers, and it fails loudly where the damage shows rather than three layers away.

## 6. Where to look

Two candidates, neither confirmed:

- **`next` is allowed to shrink and the narrowing phase accepts it.** A post-fixpoint step should be
  a *descending* sequence from a sound over-approximation; a `next` below an established `cur` means
  the step function is not monotone in `cur`, which is the property widening/narrowing rests on.
- **`snapshot`/`restore` around a conditional leaks.** `restore(saved)` installs the snapshot *by
  reference* and the following `refine(cond, false)` then mutates it, so the second `restore(saved)`
  cannot undo anything. For a clause chain the accumulated negation happens to be what is wanted;
  whether it stays correct through nested conditionals and a `let` is exactly the question, and this
  program is the first with both.

The second is the more likely and the cheaper to test.


---

## 7. The fault, found

`restore` installed the snapshot **by reference**:

```go
func (p *intervalPass) restore(m map[string]ival) { p.env = m }
```

and what follows a restore is `refine`, which narrows the environment **in place**. So:

```go
saved := p.snapshot()          // C, a copy of the entry environment
p.refine(c, true);  eval(then) // ✓
p.restore(saved)               // p.env = C  — by reference
p.refine(c, false); eval(else) // ✓, but this MUTATES C
p.restore(saved)               // no-op: C already carries ¬c
```

The environment leaving an `if` carried `¬c` — a fact true on only one of the two paths.

### Why that is the bug, stated as the property it breaks

The abstract step for a loop is

> `F(c⃗) = z⃗ ⊔ ⨆{ ⟦a⃗⟧# (R_branch(c⃗)) : each `again` }`

and the whole apparatus rests on **monotonicity**: `c⃗ ⊑ d⃗ ⟹ F(c⃗) ⊑ F(d⃗)`. It is what makes the
widening sequence converge to a *post-fixpoint*, and it is what makes the narrowing phase's
`within(next, cur)` test legitimate — narrowing descends *within* the post-fixpoints rather than
leaving them.

**Lemma (refine is monotone).** `intersect` is monotone in its first argument, and the bound `R`
derives from the environment is monotone in the environment. So `σ ⊑ σ′ ⟹ R(σ) ⊑ R(σ′)`.

**Theorem.** If each branch is evaluated in `R_branch(c⃗)` and the entry environment is restored
exactly, `F` is monotone — a join of compositions of monotone maps. ∎

The leak breaks the hypothesis: a later branch is evaluated in `R` applied to an already-narrowed
state, and the state after the `if` is not `c⃗`. Measured, it is not monotone:
`[0,0] ⊑ [0,2]` and yet `F([0,0])[i] = [0,2]` while `F([0,2])[i] = [0,0]`.

**The fix is that `restore` installs a copy.** One edit, both sites, and the discipline cannot be
got wrong again. The trace becomes monotone: `i` goes `[0,0] → [0,+∞)` and stays; `sp` reaches
`[0,32]`; nothing shrinks.

## 8. And the numbers were inflated

This is the uncomfortable half. The unsound intervals were *narrow*, so they made operations look
**bounded** that were not.

| | before the fix | after, nothing declared | after, one range declared |
|---|---|---|---|
| `tokenize.oro` | 100%, 20/20 loops | 86.7%, 16/20 | **100%, 20/20** |
| `tree.oro` | 91.3%, 20/25 | 88.9%, 17/25 | 91.3%, 20/25 |

**And it corrects the central finding of the research.**
[precision-integers.md §2](../../docs/precision-integers.md) recorded that declaring ranges
*"changes NOTHING"* on the two parsers, and called that "a qualitatively different failure from not
enough is declared". **That was the bug.** With a sound fixpoint, declaring one range takes the
tokeniser from 86.7% to **100%** — which is exactly what
[intervals-2026-08-19](intervals-2026-08-19.md) predicted and what the whole precision-integer plan
assumes.

**And `elemwidth-2026-08-27 §5d`'s interval-derived buffer narrowing is withdrawn.** `tree.oro`'s
node table is `[]int` again, not `[]uint16`, because in the `build` lambda alone `src` is free and
the stores genuinely cannot be bounded. The old `int 0 512` was a *sound range reached unsoundly* —
it contained 511, so no wrong answer shipped, but that was luck. The **syntactic** narrowing is
untouched: the tokeniser's stack is still `[]byte`, because literals never needed the fixpoint.

## 9. Two more gaps, found by re-measuring

Neither is subtle and both were costing more than the fault itself.

**`len` was not recognised.** The refinement and interval layers knew `alen` and `slen` — the
**retired portable layer's** names — and not tables.md's structural `len`, which is what every
program written since says. So `(go.>= i (len src))` bounded nothing and a `where` on `(len src)`
propagated nothing. Both layers now share one `isLenOp`, and the key is normalised so `alen(a)` and
`len(a)` are the same variable.

**An exactly-known length was thrown away.** A table given by its graph has as many elements as it
was written with; `alloc` and `build` have the length they were asked for. All three are in the
term. It matters because **reduction inlines**: `run` passes four literal documents to the
tokeniser, and call-by-need *let-binds* each one rather than substituting it — `src` occurs many
times — so the length is exactly known at the binding and was lost one line later.

Carrying it through the binding is what took the tokeniser from 33.3% to **86.7%** and the tree from
79.1% to **88.9%**.

## 10. Both gaps, closed against the fixed analysis

**Gap 2 — the derived step through a `let` and an `if`** — re-applied, and correct this time.
`tree.oro` goes from **17 of 25 loops proven terminating to 21 of 25**, and to **25 of 25** with one
range declared. The differential suite passes, and nothing narrows on a bad value because there is
no longer a bad value.

It lands as a strict **fallback**. `DerivedStep` is a *lower* bound, so using it where an exact step
exists turns `[1,1]` into `[1,+inf)` and costs every trip count that depended on it. And it gives the
descent arc while **withholding the measure** — `descent{}` keeps the position out of `tripCount`,
because `span / delta + 1` also needs `cur[src]`, and that value comes out of the same opaque loop
the bound came from.

**Gap 1 — a read carries its element range.**

> **Theorem.** If `t` has element type `(int lo hi)` then the value of `t[i]` is in `[lo,hi]`.
> *Proof.* The range over-approximates every stored value, and `0` is in it because `build`
> zero-fills (tables.md 14.3). A read returns a stored value or the zero fill. QED

**Non-circular by construction**, which is the design constraint: only two sources are used and
neither is this analysis — a range **declared** on a signature, which is a premise, and the
**syntactic** range of a buffer's stores, which never consults an interval. `BufferRange`, which does
consult one, is deliberately *not* a source; using its answer here would be a fixpoint feeding
itself. An `(array ...)` literal's hull is added for the same reason: exact, and what reduction
actually produces.

**And it buys nothing measurable on this corpus** — an honest negative, the second this week after
index narrowing changed nothing on the Java gauntlet. It demonstrably works:

| a squared byte over a declared `(array (int 0 255))` | ops proven |
|---|---|
| element range declared | **3 of 3** |
| element range absent | 1 of 3 |

It does not bind on the parsers because their reads feed comparisons and literal stores rather than
counted arithmetic. It is the mechanism the precision-integer plan needs, in place and tested, and
waiting for a program that leans on it.

## 11. And one more bug, caught the same way

With the analysis finally good enough to narrow a loop that reads a table, index narrowing fired on
the `array-literal` differential case for the first time — and javac refused the file:

```
Main.java:15: error: incompatible types: possible lossy conversion from long to int
                        acc = (acc + a[i]);
```

The value fits — the whole-method gate says every integer operation stays inside a 32-bit index — but
Java **types** the expression, and reading a `long[]` element makes the arithmetic `long` whatever
its range. A narrowed variable needs a cast on assignment. The post-clause path does not: `PostVars`
already refuses any update that reads another loop variable, so a hoisted update is `v ± c` and is
`int` whenever `v` is.

## 12. Where it ends up

| | nothing declared | one range declared |
|---|---|---|
| `tokenize.oro` | 86.7%, 16 of 20 loops | **100%, 20 of 20** |
| `tree.oro` | 88.9%, 21 of 25 | 91.3%, **25 of 25** |

Every loop in both parsers is proven terminating once a range is declared, and these are numbers the
analysis has earned rather than ones a broken fixpoint handed it.
