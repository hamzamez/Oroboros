# A word-frequency report, and the merge sort is a loop over levels

2026-09-08. [examples/io/freq.oro](../../examples/io/freq.oro) — `sort | uniq -c
| sort -rn`, in Oroboros. The second tool written in this language and, at **158
lines of code**, the largest program in it by 1.4× (jsonfmt 95, `tree.oro` 112).

The assessment's standing criticism is that the corpus is not evidence for the
claim being made, and jsonfmt is the one data point answering it: 95 lines that
found four bugs, two of them silent wrong answers. This is the second.

> **It agrees byte for byte with `sort | uniq -c | sort -rn`** on seven real
> files, and builds with **951 of 951 integer operations bounded** and no
> `-checked`.
>
> **Four bugs, two of them in the compiler and both pre-existing.** A program
> that COMPUTES a byte could not get a byte buffer; and **a `let` inside a loop
> guard emitted dead statements that Go refuses** — nine lines reproduce it, and
> no program had ever put a `let` in a loop guard.
>
> **And the termination finding is the one worth keeping.** The four loops that
> are not proven are the merge sort's, and they are unprovable for one reason:
> size-change termination handles a counter that steps by a CONSTANT and not one
> that DOUBLES. karatsuba-2026-08-30's rule for turning recursion into
> iteration — *a balanced, data-independent recursion is a loop over levels* —
> produces exactly the loop shape this analysis cannot prove.

---

## 1. What it does, and that it is right

```
$ freq README.md
433 The
318 A
280 is
...
```

Reads a file, counts how often each distinct word occurs, prints the commonest
first. Checked against the tool it is named after:

```
diff <(freq F) <(tr -cs 'A-Za-z' '\n' <F | tr 'A-Z' 'a-z' |
                 sort | uniq -c | sort -k1,1nr -k2,2 | head -20)
```

**Identical on seven files** — this repository's README, `tables.md`,
`uniqueness.md`, `jsonfmt.oro`, `core/read.go`, `emit/interval.go`, ADR 0018 and
gauntlet-2026-09-07 — plus an empty file, a file with no letters in it, a
missing file and no argument at all.

## 2. THE LANGUAGE'S OWN MAP CANNOT COUNT WORDS

Not a gap — a derivation. `(map K V)` is well formed exactly where the
language's `=` is defined, and that is **integer equality only**
([maps.md §3](../../docs/spec/maps.md)): floats are out because NaN is not an
equivalence relation, strings because no two targets agree. **So a word cannot
be a key**, and what replaces the map is `sort | uniq -c`.

That is not a workaround, and the reason is the tie-break. A report has to
order words with equal counts, and a hash map has no order to offer, so a
deterministic report over four hosts would have to invent one. **Sorting has
already established it**: the counting pass runs over lexicographically sorted
words, so the second sort — stable, by count — leaves equal counts in
alphabetical order for free.

Stability buys a second thing that is easy to miss. The report prints each word
**as written**, taken from the first member of its case-folded group; a stable
sort makes "first" mean *first in the file*, so the printed spelling is a
function of the input and not of the host.

## 3. A TEXT PROGRAM STILL DOES NOT INDEX A STRING

[overloading.md §5](../../docs/overloading.md) named one measurement as the thing
that decides how a string is represented — *does a real text program index a
string, or only fold it?* — and this is its third and last data point.

| | what it needed |
|---|---|
| `render.oro` — **produces** text | `concat`, `""`, η. No `length`, no `(s i)`, no `=` |
| `jsonfmt.oro` — **transforms** text | bytes throughout, converted once at the boundary |
| `freq.oro` — **consumes** text | byte ranges, and one byte comparison |

This was written to be the awkward case: it **compares words to each other**,
which is the operation neither of the others needed, and it is the operation a
string representation would exist to support. It still does not index a string.
A word is a **pair of offsets into the file's bytes**, so the whole program
sorts and counts small integers and touches text exactly twice — once to compare
bytes, and once at the very end to hand the report to the host.

**Three programs, three shapes, and none of them wants `length`, `(s i)` or
string `=`.** That is a reason to keep deferring a concept name and `alloc` on a
string, which is what overloading.md recommends and what this now supports from
the direction it said would be hardest.

## 4. A MERGE SORT WITHOUT RECURSION — AND THE TERMINATION FINDING

karatsuba-2026-08-30 states the general rule and names mergesort first:

> **A balanced, data-independent recursion is a loop over levels.**

Written out, that is bottom-up merge sort: width 1, 2, 4, …, and at each width
every adjacent pair of runs is merged from one buffer into the other, then the
two swap. No recursion, no stack, and the shape is a function of the length
alone. It works, on three targets (§7), and it sorts a **permutation** so that
nothing large moves.

**And it is where the termination analysis stops.** 33 of 37 loops are proven;
the four that are not are the sort's two, once per comparator:

```
loop(a,b,w): (nothing known)      w = 1, 2, 4, …
loop(b,lo):  (nothing known)      lo += 2w
```

Both terminate, obviously. Neither is a size-change. sct-2026-08-19 handles an
ascending counter **by orientation** — μ = −v, a ranking function as a change of
variable — and that works because the step is a CONSTANT. `w *= 2` needs μ =
⌈log₂(n/w)⌉, which is not a linear measure and not a size-change; `lo += 2w`
needs a step that is itself a variable.

> **The general rule for eliminating recursion produces the one loop shape the
> termination checker cannot prove.** ADR 0015 makes termination a computed
> property rather than a guarantee, so the program compiles and the report is
> honest — but every future FFT, binary search and Karatsuba level-walk will
> land here for the same reason. This is the first time it has been isolated.

Not fixed, deliberately: it wants its own measurement and probably a ranking
function over a derived quantity (`n / w` descends), which is a real extension
to the framework rather than a missing case.

## 5. TWO COMPILER BUGS, BOTH PRE-EXISTING

### 5.1 A program that COMPUTES a byte could not get a byte buffer

The report is built as bytes and handed to `os.text-of`, which takes
`(array (int 0 255))` — jsonfmt's discipline, and the only one available, since
`string-of` is η over SCALARS and pushing a raw UTF-8 byte through it turns 0xC3
into U+00C3. The buffer came out `[]int`, and the program would not compile.

**NEITHER OF THE TWO EXISTING PATHS DECIDES IT, AND THAT IS THE PRECISE
STATEMENT.** A report line is a word copied out of the file and a count rendered
into digits, so the buffer holds one of each:

- the **syntactic** rule knows the COPY — a read from an already-narrowed table —
  and its rules are *closed under nothing*: a literal, an `if` over literals, a
  narrowed read, and `(+ 48 (% (/ x p) 10))` is none of those although every
  operand is exact;
- the **interval** rule knows the ARITHMETIC, because `remI` already contracts to
  the divisor — and cannot see the copy, because `BufferRange` runs on the
  `build` lambda ALONE (frozen-2026-08-28), where `src` is free and therefore ⊤.

So each path can decide a buffer of one kind and the buffer of both is refused.
jsonfmt only ever COPIED; nothing had computed a byte before, and nothing had
done both.

The fix is on the syntactic side, since it is the one that can be made exact:
`storedRange` recurses through arithmetic, plus one rule that needs no fact about
its operand at all:

> **|a % d| < |d| whatever a is.** The remainder takes the dividend's sign and
> its magnitude is under the divisor's, on all four targets inside the portable
> window (integers.md §5). So a literal divisor bounds the result with nothing
> known about the dividend — which is exactly what makes a digit exact, since
> nothing bounds `x / p`.

**This is still not the interval analysis**, and the distinction is the one
`storedRange`'s own header makes. Interval *arithmetic* is exact on exact
endpoints; what fixpoint-2026-08-27 withdrew is the interval **fixpoint**, whose
endpoints come from widening a loop. There is no fixpoint here, and no loop
variable can enter, because a loop variable is a bare name and a bare name is
decided by `typeOf` alone.

**And the anti-circularity guard had to move.** *A buffer may not narrow on its
own contents* was written for a BARE read and sat at the top level; arithmetic
can bury one, and `freq`'s run-length counter is `(+ (b s) 1)` — an increment of
a slot, inside the `build` that fills it. The guard is now `storedRange`'s own
`self` argument, refusing at any depth. `buffer-swap` is the case that found the
first version and still covers it.

### 5.2 A `let` inside a loop guard emitted dead code, and Go refuses it

Nine lines:

```lisp
(def lim (fn (n) (let (- n 1) (fn (d) (if (< d 0) 0 d)))))
(def run (fn (n)
  (loop ((s 0) (k 0))
    (>= k (lim n))  s
    else            (again (+ s k) (+ k 1)))))
```

```
main.go:13:6: declared and not used: t1
```

The bounds-check elimination pass asks `countedGuard` for the loop's bound and
then decides whether there is anything to narrow:

```go
if idx, bound, ok := countedGuard(e, body, raw); ok {
    if bv, err := e.emit(bound); err == nil && len(e.narrowTargets(idx, body)) > 0 {
```

**`e.emit` is not a query.** A bound containing a `let` emits STATEMENTS into the
enclosing block, and when the narrowing is then declined they stay — after the
loop's initialisers, dead. The fix is to check the targets first.

It survived because **no program had a `let` in a loop guard**, which means no
guard had ever called a definition that binds anything. `(>= k (slen sp w))` is
the first, and `slen` binds because a span's length is a difference of two table
reads that has to be clamped.

## 6. TWO PROGRAM BUGS, AND WHAT THEY SAY ABOUT CAPACITIES

**`a a` reported 1.** The run-length pass had the capacity guard as its own
clause:

```lisp
(>= k nw)   dt
(>= d nd)   dt        ; <- exits as soon as the LAST group is opened
```

so every repetition after the final distinct word was dropped. **The capacity
constrains opening a group, not counting one**, and the guard belongs inside the
new-group clause. Caught by the smallest input that can show it, which is why
the small cases were run before the large ones.

**`the` came out 433 against 440.** The word cap was 8192 and this repository's
README has more, so `nwords` stopped counting and the tail of the file was
dropped **with no diagnostic**. jsonfmt refuses a file over its cap; this one
truncated.

> A capacity that TRUNCATES is worse than one that refuses, and better than
> either is **one that cannot be reached**.

Words are maximal runs of letters, so two of them are separated by at least one
non-letter byte: k words need at least 2k−1 bytes. `main` refuses a file of
65536 bytes or more, so k ≤ 32768. The cap is now that, the guard stays because
the *analysis* needs it, and no input reaches it. That is a derivation where
`tree.oro`'s node cap and jsonfmt's file cap are declarations — the same move
made one step further.

## 7. THE SORT ON THREE TARGETS, AND THE THIRD x86 CEILING

`freq.oro` is Go-only because its file I/O is — `targets/go/os.oro` is the only
host binding for `ReadFile` — but the sort is portable and is the part with
something to get wrong. It is now the differential case **`merge-sort`**: 16
elements, a computed key, and a position-weighted checksum, so a sort that
merely permuted would not pass. Expected values computed by hand before running.
**Verified to fail against two bugs**: the buffer swap removed, and the
comparator reversed.

**windows is skipped, for a compiler ceiling and not a capability**:

```
build: x64.movb has more spilled operands than there are scratch registers:
       mov byte ptr [r10+r11], qword ptr [rsp+104]
```

A store needs three registers when the address's base, its index and the value
are all spilled, and a template may not touch anything but r10 and r11
(ADR 0016). **Third program to hit this** — after `big-divmod` and
`limb-subdiv` — and the first that is nothing but a sort, so the shape is now
isolated rather than incidental to a large program. The case says so exactly and
says how to reproduce it, because winstrings-2026-09-07 lost weeks to a `skip`
whose reason was true when written and had quietly stopped being true.

The first version sorted a **permutation** and was refused; sorting values fits.
The difference is one live value — a comparator reading a key through an index —
which is a useful measure of how close the allocator is to the line.

## 8. A NUMBER I RECORDED YESTERDAY IS CORRECTED

§5.1's fix narrows any buffer whose stores are computed from exact operands —
and `examples/kara/workspace.oro`, ADR 0020's demonstration, stores a product of
two bytes. Its workspace went from `[]int` to `[]uint16`, so the two forms
stopped being comparable: the file's own comment says a comparison that changes
two things measures neither.

Both sides now declare `(int 0 65535)`, and the measurement is re-taken:

| | ns/op | B/op | allocs/op |
|---|---:|---:|---:|
| `GenMacInto` — the buffer is a parameter | **18,973** | **0** | **0** |
| `GenMacFresh` — `build` inside | 34,927 | 131,072 | 1 |

**1.84×, where [uniqueness-2026-09-07](uniqueness-2026-09-07.md) recorded 4.5×.**
The work is identical and the workspace is a quarter of the size, so the
allocation costs a quarter — which is that document's own framing landing on its
own number one day later: *the cost grows with the size of the workspace
relative to the work.* **The unconditional half survives unchanged — 0
allocations against 1** — and 1.84× is much closer to arrays-revisited's
1.07×–1.66× on Karatsuba, so the corrected number supports the decision better
than the original did.

## 9. AND G5's PORTABLE-LAYER DEBT IS CLOSED

gauntlet-2026-09-07 said three gauntlet programs were still benchmarked on the
retired portable layer. **Checked: it was one.** `search` has
`BenchmarkSearchNative` over `NativeFindFirst` and `wordcount` has
`BenchmarkG3WordTallyNative` over `NativeTally`; only `report` had no native
benchmark. That result is corrected here.

It was not a one-line fix, as that result said: the native source exports `main`,
which takes nothing and **builds** its data, where the portable one takes an
array and a label — so the hand-written reference had to be rewritten to
construct too, which is the honest comparison. **1,717 ns against 1,731,
0.99×**, identical allocations, and the pure part still fuses into one pass.

**A ranking function for a geometric step.** §4. It is the first termination gap
