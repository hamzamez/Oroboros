# The gauntlet, on the IR's printers

2026-09-29. Item 1 of [assessment-2026-09-28](../../docs/assessment-2026-09-28.md): one run of every
program on Go, JavaScript and Java against the hand-written references. The last full run
([gauntlet-2026-09-07](gauntlet-2026-09-07.md)) predates every IR printer.

> **All seven programs are at parity on all three targets.**
> - **Geometric mean of generated over hand-written:** Go **0.990**, JavaScript **0.977**, Java
>   **0.987**.
> - **The IR's printers against the term backends they replaced:** 1.006, 0.988, 0.971. The
>   migration cost nothing, and Java's JSON tree got 1.28× faster.
> - Three residues above 1.10× remain. Each one explained itself: identical machine code, a module
>   boundary, and a trap the source asked for (§4).

## 1. What was being measured, until today

The gauntlet benchmarks **committed copies** of generated code. Of the 26 files the three harnesses
call, 24 were last written between 2026-08-20 and 2026-08-28. The other two were written on 09-08,
and at 12:31 on 09-25, hours before IR step 2 made the Go printer the IR's. **All 26 came from the
term backends.**
Every migration step since irstep2 measured its own change against the term backend in scratch, and
left the committed copies alone. So the gauntlet as committed was measuring a compiler that no longer
exists: a path nothing ran.

**`gauntlet/regen.sh` is now the one list.** For each file it names the target, source, `-name` and
output, and it regenerates all 26 with the compiler at HEAD.
- A source whose first line says ``BUILT WITH `-checked` `` is compiled with it, the rule
  `cmd/check`'s sweep uses.
- The JSON programs' JavaScript and Java versions substitute the host prefix in the Go source, as
  jsontok-2026-08-26 §6 recorded.

Every regenerated file exports the functions its harness calls. The one exception is Java, whose
methods are now lower camel case (`natDotDot`); that was a pure rename in the harness. Every file
agrees with its hand-written reference before it is timed: the Go tests, `native.mjs --check`,
`jsontok.mjs` and `jsontree.mjs --check`, and each Java harness's own agreement step.

## 2. Method

**Three numbers per program:**
- the hand-written reference;
- the **old** generated code (the committed copies, in a git worktree at `b4e02c8`);
- the **new** generated code (regenerated in the main tree).

The same harness and hand-written code run in both trees. So each reference is measured twice, which
**measures the machine's drift** instead of assuming it is small. Every ratio is taken against the
pooled reference. The trees alternate, and the order is swapped each round.

| host | one process per | rounds | a sample is |
|---|---|---:|---|
| Go 1.27.0 | **benchmark** (the test binary built once per tree) | 5 | `-benchtime=2s` ns/op |
| node v26.7.0 | case (V8 carries state across benchmarks) | 3 | the median of the process's 7 runs |
| Java 17.0.12 | **case** (a new filter, §5) | 3 | NativeBench: median of 9; the others: best of 9 |

The table shows medians, with the range of the new code's samples in parentheses. Ratios compose
multiplicatively, so the summary is their **geometric** mean (Fleming and Wallace, 1986). An
arithmetic mean of ratios depends on which side is the numerator. The raw samples, the runners and the
analysis are in [gauntlet-2026-09-29/](gauntlet-2026-09-29/).

**Drift control.** Every hand-written reference measured the same in the two trees within 0.99–1.04
on Go, 0.97–1.05 on JavaScript and 0.95–1.02 on Java. A difference between the trees smaller than
that is not a difference.

## 4. The residues, each made to explain itself

**(a) Go, search with early exit, 1.10×: identical machine code.** 2.9 against 2.6 ns. Each tree's
`gen_search_native.go` was compiled alone with `-gcflags=-S`, and the two functions are the same 19
instructions in the same order. The Go differs only in where the increment is written (the `for`
post-statement, against the body). So the 0.3 ns is where the function lands in the binary, not what
it does. That is measurement bias from layout, which Mytkowicz et al. (ASPLOS 2009, "Producing wrong
data without doing anything obviously wrong!") showed moves results by more than this at this scale.
It is below what the gauntlet resolves.

**(b) JavaScript, search with early exit, 1.21×: a module boundary.** 7.7 against 6.4 ns, and the
term backend's code was 1.28×, so it predates the IR. The two functions are the same loop. The
reference is defined in the benchmark's own module, and the generated one is imported. A controlled
run, each case in its own process five times:

| | median | range |
|---|---:|---|
| reference, local | 6.81 ns | 6.67–7.09 |
| generated, **imported** | 7.71 | 7.29–8.69 |
| generated, the same text copied into the benchmark's module | 7.13 | 6.41–8.12 |

Most of the gap is the import. What remains lies within the local copy's own range. That is the
placement effect `native.mjs` records in its header (a property load that blocks inlining), met
again, at about 1 ns.

**(c) Java, word count, 1.06× unfused and 1.25× fused: a trap the source asks for.**
- `examples/native/wordcount-java.oro` is ``BUILT WITH `-checked` ``, so the IR's code increments with
  `Math.addExact(v15, 1)`. The term backend's August copy had a plain `+ 1`, from before the source
  asked for the check. So 1.06× is the price of the trap.
- 1.25× compares the generated **unfused** get-then-put with the hand-written **fused** `merge`, a
  different shape. The source's own fused variant, `natWcTallyMerge`, is generated, but the harness
  only checks it and does not time it. Not measured here.

**The trap is there only for want of a proof, and the proof is elementary.** Each iteration increments
one cell by 1. So after t iterations every cell is at most t, and t ≤ `len ws` ≤ max-len_T (2³¹ − 1
on the JVM). So `count + 1` stays inside the word. This is Theorem 3, bounded increments into a buffer
(irstep4d). The IR proves it for a table, and for the language's `(map int V)` through its cell fact
(irstep4j). It does not prove it for a host map keyed by strings, whose cells the IR does not model.
**Gauntlet program 4, the parasite test, is naming that gap**: on Go its read/write form pays 1.02×,
on Java 1.06×. By plan item 4 that makes it a candidate, since a program names it.

## 5. Method errors: two of mine, and a hazard fixed before it bit

**(i) Pairs in one Go process.** The first runner ran a comparison's two benchmarks in one process.
`go test` runs them in file order, so the hand-written map benchmark ran first and left its heap and
GC state to the generated one.

| G4, identical code and allocations (18, 1.1 MB) | ns/op |
|---|---:|
| hand-written `m[k]++`, alone | 1,804,138 |
| generated `m[k]++`, alone | 1,782,592 |
| the same two in one process, the generated second | 1,881,176 → **2,741,001** (1.46×) |

"Benchmarks sharing one process, including allocating ones" is already on the list of method
errors. It happened again because the rule named JavaScript's and Java's harnesses, and I wrote a new
Go runner without applying it. Every benchmark now has its own process.

**(ii) A stopped run that kept running.** A new species. Twice I stopped a run and started a
corrected one. The stop ended the outer shell, not the script's loop, so both earlier runs went on
timing benchmarks next to the new one. It was found because their rows interleaved in one file, and
two cases held 8 samples where the runner writes 5. That run read the tokeniser at **1.14×** and dot
at 1.07×. After every leftover process was killed, the same runner read **1.04×** and **0.97×**. The
contaminated data is kept as `go-contaminated.csv`, and nothing above comes from it. **Before a
measurement, list the processes, and do not trust that a stopped job has stopped.**

**(iii) One call site for every Java case.** Each Java harness timed all its cases in one JVM through
one `Runnable`/`Supplier` call site. After a few lambdas that site is megamorphic, so HotSpot stops
inlining through it, and a later case pays for the earlier ones. Each harness now takes an optional
case name and times only that case, and every case above ran in its own JVM. How much this biased
earlier Java numbers was not measured.

## 6. What this settles, and what it does not

**The commitment holds on the IR.** Seven programs, three targets, parity, with the migration measured
directly rather than inferred: every analysis and every representation choice moved to the IR, and
the gauntlet did not notice, except that Java's JSON tree got faster.

**Not settled:**
- **The committed generated files can drift again.** `regen.sh` makes regenerating one command, but
  nothing runs it. A step in `cmd/check` that regenerates into a temporary directory and diffs would
  make drift a review item, as emission already is. Not built.
- Java's fused word count (`natWcTallyMerge`) is generated and checked, not timed.
- Output size, the method's third criterion, was not re-measured.
