## 1. What was measured

Each host's harness runs the hand-written reference and the generated code, one process per case.
**Two trees** alternate, the order swapped each round. On Go, JavaScript and Java the old tree is
09-29's (a worktree at `525ab98`), and the new tree is HEAD with this step's changes; every
reference runs in both, so the machine's drift is measured, not assumed. On windows the old tree
is `e07ffc9`'s compiler on the same ported sources, so new/old there isolates the release fix.

|---|---|---|---:|---|

| JavaScript | node v26.8.1 (09-29: v26.7.0) | case | 3 | the median of the process's 7 runs |
| Java | 17.0.12 | case | 3 | NativeBench: median of 9; the others: best of 9 |
| windows | clang 23.1.4 `-O2`, both sides | case | 5 | the median of 9 batches of at least 20 ms, and the peak working set |

The runners, the raw samples, the analysis and a log of other processes are in
[gauntlet-2026-11-16/](gauntlet-2026-11-16/). The 09-29 runners were reused unchanged except for
their paths. Every generated function agreed with its reference before anything was timed: the
Go tests, `native.mjs --check`, `jsontree.mjs --check`, each Java harness's own step, and on
windows every case against Go's own answers, bit for bit.

**The windows reference** ([gauntlet/windows/](../windows/README.md)) is the Go references written
as a person writes C:
- a pointer and a length, `int` indices;
- stack arrays where a size is fixed (the tokenizer's stack, the tree's tables), and `calloc` as a
  second form of the tree;
- `malloc` where Go allocates;
- `restrict` as a second form of the stencil. C can say that the buffers are disjoint, which Go,
  JavaScript and Java cannot.

Go's `math/rand` draws the inputs, so `gauntlet/go/wininputs` writes them and Go's answers to
files. Every timed function is called through a volatile pointer and is not inlined into the
timing loop, so the two sides pay the same call.

**Drift control.** On Go, JavaScript and windows, every hand-written reference measured the same
in the two trees within 0.98–1.02, with one exception each: Go's `StencilFreshRef` (1.07) and
Java's early search (1.08 at 4 ns). Java's references were otherwise within 0.98–1.03. A
difference between the trees smaller than that is not a difference.

**Contamination.** Another session's book checker ran from 01:16:23 to 01:17:09 (`procs.log`),
the first 46 seconds of Go's round 1, which timed dot and centroid. Those round-1 samples read
0.996–1.071 of their rows' medians (the generated dot's 470.7 ns against 439.5 is the largest).
Every Go row is the median of five rounds, so one high sample does not move it. The Java run had
no other compiler beside it (`procs-java.log`).

## 4. What the gauntlet found on windows: a buffer frozen into nothing was never released

**The finding.** The generated JSON tree was 2.5× the C on windows, while it is at parity on Go.
Its optimized IR showed the cause:
- three allocations a call, zero-filled from the heap's classes: 32 KiB, 1 KiB and 16 KiB;
- one release, of the node table.

The stack and the worklist were never freed, and `bench.exe`'s peak working set was 786 MB after
41,000 calls. A controlled run explains the time. Given the generated code's storage (i64
elements, the same `HeapAlloc` sizes and flag), the C runs at 3.9 µs, so storage costs 0.45 of the
5.2 µs gap. The rest is the leak's cost: fresh, zeroed memory every call, never reused.

**Why.** A table is released at its death (ADR 0096), and R1a follows a table *value* from its
birth. A build's value is a product of frozen buffers and values (ADR 0031). A buffer frozen into
the product is a table, followed and released. One frozen into nothing has no table value at all:
a stack whose scope's value is an integer, or an inner build whose value is the outer buffer
frozen. Worse, that inner build's table result was counted as born from the inner storage (the
stack's), so the stack's storage had no death anywhere.

**The rule** ([release.go](../../ir/release.go)). A build's region holds its buffer's full view, and
the region's yield is the build's value. Define **own(b)** as the least set that holds the region's
buffer parameter and is closed under:
- every statement result that is a buffer or a table and has an argument in own(b);
- by position, a loop's body parameter whose initial or continuing value is in own(b);
- by position, a loop's, an `if`'s or a nested build's result whose breaking or yielded value is
  in own(b);
- a π of a member.

An integer read from the buffer is not a member. If no value the region yields is in own(b), the
buffer's view comes back at the region's end and nothing outside names it, so the storage is dead
right after the build: `release(p, n, w)`, with p, n and w its allocation's own.

own(b) may over-approximate b's descendants, never under-approximate them. One member too many
only keeps a storage alive (a leak, as before), and one too few would free a live one. That is the
direction the closure errs in.

**Its checks.**
- **W11** re-derives own(b) apart from the pass. It requires the release's (n, w) to be p's
  allocation's, and p to be named by nothing but its build and its release.
- **W12** accepts such a region as a token when it is handed to the next allocation of its size,
  locally or across a back edge. That region may have been answered by a `reuse` for the build, so
  (n, w) are the last two arguments of any of the region operations. W12 requires it to be named
  by nothing but its build and the point that hands it on. The witness
  (`TestADeadBuildsRegionIsAToken`) first failed exactly there: the next iteration's allocation had
  become `reuse`, which W12 did not yet read as a region.

**The planted faults.**
- `PlantReleaseFrozenBuild` releases every build's storage, the node table's too, which is frozen
  and read after. W11 refuses it (`TestABuildsBufferNotFrozenOutIsReleased`).
- `PlantReuseKeepRelease` on a dead build's token: freed, then written. W12 refuses it.

**Measured.** The tree went from 8,896 to 3,239 ns (0.36× its time, 2.69× → 0.98× the C), and its
peak from 767 MB to the C's 7.6 MB. The tokenizer, which leaked its 32-entry stack, stays within
the noise (1.04 new/old), and its peak fell from 30.0 MB to 7.6 MB.

## 5. The port: the JSON programs in the language's operators

`tokenize.oro` and `tree.oro` were written in August against Go's names (`go.\`+\``, `go.\`>=\``),
and the JavaScript and Java lines of `regen.txt` substituted the prefix, `js:PATH`. Since the
operators are the language's (integers.md §0a), that was a port nothing needed. Each
`go.\`op\`(a, b)` became `a op b`, with parentheses only where j.md §3's precedence needs them,
and `use go` went. ι maps each operator back to the host's own on every target, so on the
tokenizer the emitted text is **byte-identical** on Go, JavaScript and Java.

On the tree the language's `*` folds constants inside the word, which `go.*` did not: `4 * 512`
is `2048`. On JavaScript, a stack whose length is now a literal is a `Uint16Array` where it was
`new Array(1024).fill(0)`. Every other line is the same modulo renumbering. Measured new/old:
0.91 on JavaScript, 1.00 on Go, 1.01 on the JVM. So the change is kept.

With nothing substituted, `cmd/check`'s `port` and its test went, and every line of `regen.txt`
is its source as it is.

## Paid and bought

- **Compile time**: 1.03× the baseline by the median of 46 compiles. Nine suspects were paired
  serially against `fe38917`'s `gen`, and six confirmed. All six are the JSON programs on
  JavaScript, Java and windows, which `gen` refused in 15–31 ms for an unbound `go.` name and now
  compiles in full, 0.64–1.11 s paired: a refusal become an emission, not the same work slower.
- **Run time**: the tables above. On windows the tree's time is 0.36× its old, the tokenizer's
  1.04 (inside the noise). On JavaScript the ported tree is 0.91× its old, and 1.00 and 1.01 on
  Go and the JVM.

  calls and branches. Their `.ll` grew 7% (235 → 251 KB, 119 → 127 KB), mostly `release`'s `class`
  dispatch inlined at each. The tree's text shrank on Go (46,308 → 45,888 bytes), JavaScript
  (29,207 → 29,090) and Java (60,500 → 59,860).
- **Peak memory**: the tree's 767 MB and the tokenizer's 30 MB on windows are the C's 7.6 MB.
- **Proofs**: 8,881 of 8,935 operations and 886 of 924 loops, against 6,977 of 7,031 and 747 of 785.
  The new runs added 1,904 operations and 139 loops, every one proven. Those are the JSON programs
  emitting on JavaScript, Java and windows, and `generic-win.oro` on four targets. The 54 and 38
  left are unchanged.
