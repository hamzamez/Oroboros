# Gauntlet program 3 — generics, on both targets

[g3](../../docs/derivations/g3-generics.md) made the strongest positive claim in the project:

> A non-recursive function definition **is** a rewrite rule. Type parameters never appear —
> term matching is untyped, so instantiation is a side effect of substitution rather than a pass.
> **No monomorphization pass exists.**

Every program built so far used each definition exactly once, so the claim had never been
exercised. This one uses a single definition at two element types and two accumulator types.

**Result: confirmed, and more strongly than expected. The generic definition has no runtime
existence, and one instantiation is byte-identical machine code to hand-written monomorphic Go
while the other is textually identical to the hand-specialized word count.**

---

## 1. The program

One definition. **No type annotations, no constraints, nowhere.**

```lisp
(def reduce-over (fn (n get combine init)
  (fold-range init n (fn (acc i) (combine acc (get i))))))

(def sum-floats  (fn (a)  (reduce-over (alen a) (fn (i) (aindex a i)) add 0.0)))
(def tally-words (fn (ws) (reduce-over (slen ws) (fn (i) (sat ws i)) dict-inc (dict-empty))))
```

The two instantiations differ in **element type** (`f64` vs `string`), **accumulator type**
(`f64` vs a dictionary), **accessor** (`aindex` vs `sat`), and **combiner** (`add` vs `dict-inc`).

## 2. Both residuals

```lisp
(fn (a)    (fold-range 0.0 (alen a) (fn (acc i) (add acc (aindex a i)))))
(fn (text) (let (split-words text)
             (fn (ws) (fold-range (dict-empty) (slen ws)
                        (fn (acc i) (dict-inc acc (sat ws i)))))))
```

**`reduce-over` appears in neither.** It is grade 0 — absent from the residual — which
[s2](../../docs/derivations/s2-multiplicity-inference.md) said is *observed*, and here it is
observed twice at two different types with no machinery in between.

Call-by-need also fired in the second, hoisting `split-words` out of the loop, which is
[the fix](callbyneed-2026-08-14.md) working inside a generic instantiation rather than beside one.

## 3. Emitted, with different types

**Go** — the backend worked out `float64` for one and `map[string]int` for the other, from the
same definition, with no type information in the source:

```go
func GenGeneric0(a []float64) float64 {
	acc := 0.0
	n1 := (len(a))
	for i := 0; i < n1; i++ {
		acc = (acc + (a[i]))
	}
	return acc
}

func GenGeneric1(text string) map[string]int {
	ws := (strings.Fields(text))
	acc := (make(map[string]int))
	n1 := (len(ws))
	for i := 0; i < n1; i++ {
		acc[(ws[i])]++
	}
	return acc
}
```

**JavaScript** needed no types at all, which is the same division
[the JS backend](js-2026-08-14.md) established: types are Go's problem, not the language's.

## 4. The evidence

**Instantiation 1 — byte-identical to hand-written monomorphic Go.** Against `SumF64`, a
hand-written `for i := 0; i < len(xs); i++ { acc += xs[i] }`:

```
diff BenchmarkSmallSumF64.n BenchmarkSmallGenGeneric0.n
36c36
< JMP oroboros/gauntlet.BenchmarkSmallSumF64(SB)
---
> JMP oroboros/gauntlet.BenchmarkSmallGenGeneric0(SB)
```

One line differs — each function's jump to its own name. **The generic instantiation compiles to
exactly the monomorphic loop.**

**Instantiation 2 — textually identical to the hand-specialized word count.** `GenGeneric1` and
`GenWordcount` are the same function, and `GenWordcount` came from a program written *without*
`reduce-over`. Going through a generic cost nothing at all.

Correctness asserted separately against `SumF64` and `WordCountIncr`.

Timings are reported for completeness and are **not** the evidence, per
[the alignment finding](duplicate-read-2026-08-14.md): 672 ns generic against 789 ns
hand-written, medians of five, on identical machine code — a 17% spread that is layout, not
substance, and a good illustration of why the diff is what settles it.

## 5. Why this is the strongest result the design has

Three things are absent that a conventional implementation would need:

| | |
|---|---|
| A **monomorphization pass** | none — instantiation is substitution |
| **Type parameters** in the source | none — matching is untyped, so `reduce-over` is polymorphic by construction |
| A **dictionary or vtable** | none — `get` and `combine` are substituted, not passed |

`get` and `combine` are *higher-order arguments*, and they vanish too. So
[g3](../../docs/derivations/g3-generics.md)'s second claim also holds:
**monomorphization and higher-order specialization are the same operation**, and it is the one
the reducer performs anyway.

The honest qualifier from that derivation still applies: this is free for **non-recursive**
definitions. A recursive generic cannot be δ-unfolded and would need real monomorphization —
name mangling, one copy per instantiation — and nothing here tests that.

## 6. What is still not tested

- **Recursive generics**, per above. The case where the claim is known *not* to hold.
- **A generic used at more than two types**, where code size would start to matter and
  [the outlining rule](size-2026-08-13.md) would apply.
- **Named output.** `cmd/gen` names multiple functions `gen-generic-0`, `gen-generic-1` by
  position. There is no way for a source file to name its exported functions, which is a module
  question and the same gap program 5 will hit.
