# unicode/utf8, the whole package — and the wall is the memory model

2026-09-13. `emit/golang.go`, `gauntlet/stdlib/survey.go`,
`gauntlet/stdlib/acceptance/unicode-utf8.oro`, `gauntlet/stdlib/tooling_test.go`,
`emit/receive_test.go`, `emit/discard_test.go`,
[target-files.md §3](../../docs/spec/target-files.md). The first package of the goal hamza set:
*support the entire Go standard library, one package at a time; when a wall needs language work,
stop and research.*

> **EVERY FUNCTION AND EVERY CONSTANT IN `unicode/utf8` IS DECLARED, GENERATED, AND CALLED FROM A
> PROGRAM WITH VALUES IT COMPUTED** — fifteen functions, four constants, output equal line for line
> to hand-written Go calling the real package. **And two of the fifteen are supported only in a
> weakened form, because the language cannot say what they do**: `EncodeRune` writes into a buffer
> and returns a count, and `AppendRune` may write into the spare capacity of a value this language
> says is immutable. That is the wall, and it is the memory model's, not the generator's.
>
> **EVERY EARLIER ACCEPTANCE PROGRAM PASSED LITERALS, SO NONE COULD HAVE FAILED.** A Go untyped
> constant converts silently, so `utf8.RuneLen(233)` compiles whatever the declaration says; a
> variable of our `int` handed to a `rune` parameter does not. The generated declarations were
> wrong for every narrow parameter in the survey, and a witness made of literals proved nothing —
> the containment harness's lesson, and win32enum's `MulDiv(7, 6, 2)`, a third time.
>
> **Constants are primitives now: 509 of 2,989 exported.** Two emitter bugs fell out, both pinned by
> tests that fail against HEAD.

## 1. The literal trap, and the two conversions

The survey spelled a Go `rune` as `(int -2147483648 2147483647)` and wrote the template
`utf8.RuneLen(%s)`. With a literal the host converts; with a variable of type `int` Go says
`cannot use r (variable of type int) as rune value`. ADR 0003 separates what a range MEANS from
how it is REPRESENTED, and the two directions of a call split exactly along that line:

- **An argument needs the host's type**, which only the template knows. The generator now writes
  `utf8.RuneLen(int32(%s))` for `int8`/`int16`/`int32`/`rune`/`uint8`/`byte`/`uint16`/`uint32`.
  `int64`, `uint` and `uint64` are left alone deliberately: the first is our `int`, and the other
  two carry values past ADR 0012's window, which is strconv's question and not this one.
- **A result is received into the language's integer**, which is the emitter's, because
  `int(x)` compiles from every Go integer type and so needs to know nothing about the host. A
  single range result is emitted `int(call)`; a multi-result call receives each range result into
  a temporary and converts it. target-files.md §3 now says so.

The second half is what printing could not find. `r, n := utf8.DecodeRuneInString(s)` followed by
printing `r` compiles either way; `(+ r n)` is `int32 + int` and does not. So the program prints
the sum of every decoded pair, and `TestSeveralRangeResultsAreReceivedAsInt` and
`TestASingleRangeResultIsReceivedAsInt` fail against HEAD with exactly that shape — with a control
that a plain `int` result is emitted as before.

**Cost: no emitted file moves** — the sweep in §3 covers both changes together.

## 2. Constants

A constant is a zero-argument pure primitive whose result is its own exact range:

```
(prim MaxRune (none) (int 1114111 1114111) expr "utf8.MaxRune" pure (import "unicode/utf8"))
```

Pure is justified here as it was not for functions (gomethods-2026-09-09): a constant has no
effect to discard. The exact range is what makes `(+ (u.MaxRune) 1)` provable under
bounded-by-default with no declaration.

```
CONSTANTS: 2989 exported, 509 declarable
  constant of a named type                      2425
  integer constant whose value is per-platform    50
  integer constant outside the portable window     5
```

**Named types are refused**, not spelled as their underlying integer: `os.O_RDONLY` is an `int`
and `time.Second` is a `Duration`, and passing a bare integer where Go wants the named type is the
literal trap again. **50 have a value only per platform** — `syscall.AF_INET6` and
`syscall.SOMAXCONN` are `ideal-int` in the manifest with a value only on lines qualified by an
OS and architecture, because the number differs between them. The first report called these *no
readable value*, and the first guess at why was issue numbers, which was wrong (`parseLine` already
strips ` #…`). **5 are past ±(2⁵³−1)**, which ADR 0012
says is not an `int`. A complex constant is refused as well; there are none in this count.

**Go emitted 4,773 primitives and emits 5,282**, and the tooling suite's arithmetic closes:
4,331 declarable − 20 voids + 462 constructors + 509 constants.

## 3. Two emitter bugs the program found

**A range result was bound at the host's width** — §1's receive side. Latent because no target file
declared a range result on Go.

**A loop whose value is discarded left an unused variable.** `(seq (loop …) rest)` is a β-redex with
an unused binder, and the emitter writes `_ = v` for a discarded value unless `v` is atomic — right
for a parameter or a literal, wrong for the `r9` a loop's result is assigned to, which Go refuses as
*declared and not used*. No program had put a loop before another statement. The rule is now that a
discarded name gets its `_ =` exactly when emitting the discarded term DECLARED it — the emitter's
set of bound names only grows, so that is *bound after and not before*;
`TestADiscardedLoopResultIsRead` fails against HEAD. **The first version of the rule was coarser and
the sweep caught it**: *any compound term emitting a bare name* also fired on the sieve, whose inner
loop hands back the buffer `c` it threaded — a name that already existed — and added a harmless
`_ = c` to a gauntlet program. Legal Go, and still a change to an emitted file with no reason to be
one. **With the rule as committed, 178 of 178 emitted files across examples, `lib/` and the
differential cases on all four targets are byte-identical to HEAD.**

And one limitation of the ACCEPTANCE program rather than the compiler: `(def runes (array …))` read
as `(runes i)` is refused as *an application of a non-name*, because δ substitutes the literal into
operator position. The table is `let`-bound, which is the `array-literal` differential case's shape.

## 4. THE WALL: a host call that writes into a buffer

### 4a. `EncodeRune(p []byte, r rune) int` — a write-borrow

The host writes into `p` and returns how many bytes it wrote. ADR 0018's buffer is linear: passing
it to a primitive CONSUMES it. So a program can have the count

```
(build 4 (fn (b) (u.EncodeRune b r)))   ; the count; the buffer is scratch
```

or the bytes, and never both — `the buffer b is used after it has already been handed on`. What the
host call actually does is BORROW the buffer for writing and hand it back, and the language has no
way to say *this call does not retain its argument*. The acceptance program prints the count only,
and says so.

This is the same shape as every Go API that fills a caller's slice — `io.Reader.Read`,
`binary.PutUvarint`, `hex.Encode`, `(*base64.Encoding).Encode` — so it is not a utf8 detail: it is
the next wall on the whole standard library. `os-methods.oro` (gomethods-2026-09-09) is already an
instance and nobody called it one: it reads 64 bytes of `go.mod` with `(*File).Read` and prints the
COUNT, because the bytes went into a buffer the call consumed.

### 4b. `AppendRune(p []byte, r rune) []byte` — aliasing an immutable value

`AppendRune` returns `append(p, …)`, which writes into `p`'s spare capacity when there is some. Our
arrays are immutable values, so two appends to ONE value must give two independent results. They do
not, in Oroboros and in plain Go identically:

```
(let (u.AppendRune h 233) (fn (base)
(let (u.AppendRune base 26085) (fn (x)
(let (u.AppendRune base 128578) (fn (y) …print base, x, y…)))))))
```

```
[104 195 169]
[104 195 169 240 159 153]          ← x, which was 日 when it was made
[104 195 169 240 159 153 130]
```

`x` changed when `y` was made. **That is a silent wrong answer reachable today through a generated
declaration**, and the acceptance program avoids it only by threading the accumulator linearly
through a loop, which is what an append-shaped API wants anyway. The declaration claims `AppendRune`
takes and returns an `(array …)`; the host's behaviour is a BUFFER's.

### 4c. Also found: an empty buffer's element type

`(build 0 (fn (b) b))` bound by a `let` and later handed to `AppendRune` comes out `[]int`, because
the rule that gives an unwritten buffer the element type of the host call it reaches (gomethods) looks
only inside its own `build`. The program starts from one stored byte instead, which the syntactic rule
types `[]byte`. A compiler gap, smaller than §4, recorded rather than fixed.

## 5. What is next, and what is not decided

The package is supported in the sense a program can call all of it and get the host's answers. It is
not supported in the sense the goal means, because two of its functions are declared as something
they are not. **Both are one question** — what a host call does to a buffer it is handed — with
two answers the language needs to be able to write:

1. **a non-retaining write**: the call writes into the buffer and returns it, plus results;
2. **a possibly-aliasing return**: the result may share storage with an argument, so the argument
   must be consumed (a buffer) rather than shared (an array).

ADR 0020 already has half the vocabulary — `(buffer V)` in a signature — and the declarations used
`(array …)` because the survey spells every slice that way. Whether the answer is a spelling in the
target format, a rule in `CheckLinear`, or something ADR 0018 does not yet allow is research, and per
the goal's own rule it stops here for design.
