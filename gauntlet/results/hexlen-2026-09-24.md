# A pure call's guarantee, where its term is read

2026-09-24. hamza's question: must `Encode`'s precondition be written `2·len src ≤ len dst`, or could
it say `EncodedLen(len src) ≤ len dst`, and is the difference a shortcoming? Spec first:
[postconditions.md §5](../../docs/spec/postconditions.md), [theories.md §7.9](../../docs/spec/theories.md).

## 1. What was measured

**The two spellings are one claim.** `EncodedLen` is the map n ↦ 2n, and the precondition's content
is the linear inequality, which is what the host code needs: it writes `dst[j]` and `dst[j+1]` for
every source byte. The declaration keeps the linear spelling. It is also the one that does not pull
`EncodedLen`'s own precondition into `Encode`'s contract.

**But the idiom Go's documentation uses was refused:**

```lisp
(build (hex.EncodedLen (len src)) (fn (b) ((hex.Encode b src) (fn (b2 n) b2))))
```

```
go/encoding/hex.Encode requires -len(b) + 2*len(src) <= 0, which does not follow
```

The same program sized `(* 2 (len src))` compiled. There were two gaps, and both had to close:

1. **The declaration did not state its law.** The comment said "the ℤ-linear map n ↦ 2n", but there
   was no `ensures`, and a comment carries no meaning (ADR 0024).
2. **The refinement layer did not read a `build`'s size for guarantees.** It recorded
   `len b = EncodedLen(len src)` with the call as an atom, but it collected pure calls' `ensures` only
   from the arguments of a primitive. A `build` is structural, so its size was never read.

## 2. What is built

- `EncodedLen` carries `(ensures (= result (* 2 n)))` and `DecodedLen` `(ensures (= result (/ x 2)))`.
  Both are the host's code exactly: `n * 2` and `x / 2`, with the same truncation.
- A `build` assumes the guarantees of the pure calls in its size before recording `len b = n`.
- **An instance makes its terms present.** DecodedLen's guarantee names the quotient `x/2`, which no
  program term contains, so the lang facts are instantiated on each instance as it is assumed. The
  floor facts, 2q ≤ x < 2q + 2, are what make `len src ≤ 2·len dst + 1` follow.
- `gauntlet/stdlib/acceptance/encoding-hex.oro` now sizes its buffers as Go's documentation does,
  with `EncodedLen` and `DecodedLen`, and still prints exactly what the real package prints.

## 3. What failed first

- **A rule for `let` was specified, built, and then deleted.** Its test passed with the rule removed.
  β substitutes a pure value, so no residual `let` has one. A pure call inside an impure value, such as
  an allocation's size, is a primitive's argument, and rule 1 had already assumed its guarantee. The
  spec now says a `let` needs no rule and why, rather than carrying code no program reaches.
- **DecodedLen's first test failed.** Its guarantee was assumed, but the quotient it named had no
  facts, which led to the instance rule above.

## 4. Checked, and how each check fails

`emit/hexlen_test.go` has five tests, and each rule was removed in turn:

| removed | caught by |
|---|---|
| the guarantee at a `build` | both `build` tests |
| facts on an instance | the DecodedLen `build` test |
| EncodedLen's law | the `build` test and the `let`-bound allocation test |
| DecodedLen's law | the DecodedLen `build` test |
| EncodedLen claiming 3n | the allocation test's exactness half (i < 3·len src must be refused) |
| DecodedLen claiming x | `TestDecodedLenIsHalfNotMore` |

`TestAShortBufferIsStillRefused` (a `DecodedLen`-sized buffer handed to `Encode`) and
`TestAGuaranteeNeedsItsPrecondition` (Lemma 1: with `src` unbounded, `EncodedLen`'s own `where` is
refused and nothing is concluded from its result) are the controls. **The acceptance program fails**
against the declaration without EncodedLen's law.

## 5. What it cost

- The full check passes, tooling included.
- Emission is byte-identical, and the proof counts are unchanged.
- Compile time is 1.09× median, within the rule.

## 6. Not built, from the same question

- **The wrapper `func(dst, src []byte) ([]byte, int) { return dst, hex.Encode(dst, src) }`** is the
  linear write-borrow `B ⊸ B ⊗ int` written as a template. Measured: Go inlines it. The machine code
  equals a direct call except for two no-op inlining marks (`XCHGL AX, AX` and `NOP`), with 74
  instructions either way for the allocating form. Its cost is legibility, and host-buffers.md's claim
  that the emitted Go "is what anyone would write" is false for this shape. A declared "result k is
  argument j" clause would fix it, and is not built.
- **`EncodedLen`'s own precondition for an arbitrary slice.** `len src ≤ 2⁶² − 1` is honest, because
  Go's `EncodedLen` wraps past it. But Go cannot allocate a slice near that size, and a declared
  practical maximum length for the Go target, from `maxAlloc` in its runtime, would discharge it.
- **A literal table's length after β binds it** is unknown to the refinement layer: a let-bound
  `(array 72 105 33)` is known only to be non-negative.
