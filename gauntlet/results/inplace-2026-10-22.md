# inplace-2026-10-22: the header is the caller's view of a borrow, and the wrapper is gone

ADR 0070, amending ADR 0052 item 4. hamza's questions: "hexencode is declared to return a product of two
values, but when used in the program `n = hex.Encode(buf, src)`?", "should we say so in the
declaration?", "should we drop the func wrapper too?"

## 1. What it is

A host call that borrows a buffer is one arrow in the core, B ⊸ B ⊗ R (the state translation S hands a
borrowed buffer back first, G7), and two arrows at the host, told apart by **representation**
(host-buffers.md §1):

- a **write-borrow** writes the argument's storage and returns R, so the buffer after the call is the
  argument (`hex.Encode`, `File.Read`, `binary.PutVarint`, `utf8.EncodeRune`);
- a **consume-and-return** returns the storage, possibly new (every `Append*`).

So the core's threaded result is a function of the header: each `linear` parameter in order, then the
declared results, B × 1 ≅ B dropping a unit. A primed result `p' ∈ buffer(V)` puts the host's returned
storage in p's position. Without one, p's component is the argument itself, `(inplace j i)`. The host's
own results are the threaded ones minus the in-place components (`emit.HostResults`). That is the list
the hand check compares with Go's manifest, now exactly.

The core, the type checker, the refinement layer and linearity see the threaded primitive they always
saw: integer operations 2,065 of 2,110 and loops 353 of 374, unchanged.

## 3. What changed in emission

One emitted file of 303, `examples/lines/shape.oro` on Go, the only program in `examples/` and `lib/`
that calls a write-borrow. Its read loop:

```go
// before
v343, v344h, v345 := func(p []byte) ([]byte, int, error) { n, err := v342.Read(p); return p, n, err }(v48)
...
v48, v49, v50, v51 = v343, 0, v344, v348
// after
v343h, v344 := v342.Read(v48)
...
v49, v50, v51 = 0, v343, v347
```

The closure is gone, and so is the back edge's copy of the buffer: the IR binds the handed-back
component to the argument, so the loop variable is its own value on every edge and the jump no longer
carries it. That is a consequence the ADR did not predict. Go inlined the closure before (Wrapped 115
bytes against Plain 112, measured while deciding), so no speed was expected and none claimed.

## 4. Planted faults

Each caught:

- the hand check (`gauntlet/stdlib/tooling_test.go`): `strconv.AppendInt` declared in place (the grown
  slice would be lost), `hex.Encode` declared as handing back storage (it returns only `int`),
  `utf8.AppendRune` declared in place; each refused on the result count against the manifest. The old
  allowance, "a write-borrow's results may begin with the buffer", is deleted, not kept beside it;
- the reader (`emit/hostdef_test.go`, `TestHostHeaderIsTheCallersView`): with the old spelling's
  refusal disabled, `(buffer(0..255) × Int)` on a `linear` header is accepted, and the test fails;
  a `q'` naming a non-`linear` parameter is refused with its reason.

## 5. What failed first

- The `inplace` clause was dropped in the round trip through the tree, because a declaration is read,
  made a definition and printed back (D3); `HostBody.InPlace` carries it.
- The old product spelling `(buffer(0..255) × Int × error)` came in as one part; the reader expands
  `×` into factors before naming them.
- An unused single result printed `int(hex.Encode(v8, v3)` with no closing parenthesis: the wrapping
  belonged to the binding, which a statement has none of.
- While planting the reader's fault, a backup restored from the wrong path brought back a week-old
  `core/jreadtarget.go`; `git diff --stat` caught it within seconds. A `cmd/check` already running
  built three differential cases in that window (`big-subdiv`, `buffer-swap`, `build-zero`), each
  failing to read `hex.oro`'s new header. Rerun after the restore, all three pass, and the accepting
  run is a fresh one.

## 6. Not built

- A `void` writer, a host that writes a buffer and returns nothing: no host primitive has zero results,
  and none of Go's thirty borrowing declarations needs one.
- The 21 closures left in `targets/go` are not borrows. They are representation conversions of a
  multi-result call (`bits.Add64`'s carry to `int`, `strconv.ParseInt`'s `int64`) and the overflow
  traps, out of this ADR.
- JavaScript, Java and Windows declare no borrowing host call; the first follows the same rule.
