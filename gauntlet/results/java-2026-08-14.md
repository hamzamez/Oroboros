# The Java backend — 2026-08-14

The third target [ADR 0004](../../docs/decisions/0004-first-targets.md) named, and the one that
settles whether the shape shared by the Go and JS emitters is a line or a coincidence.

**Result: all five programs emit, compile, and agree with hand-written Java. The core needed no
changes for a second time. And the dictionary idiom came out the *opposite* of Go's — which is
the Parasite thesis at its sharpest.**

**Measurement caveat, stated up front:** these numbers were taken on a machine that was
simultaneously browsing and playing video. Java parity is the **least confirmed** of the three
targets, for a structural reason given in §4, not just because of the load.

---

## 1. Correctness

All five programs — dot, filter, centroid, word count, generics — compile under `javac` and agree
with hand-written Java references, including both generic instantiations.

## 2. Java diverges from both predecessors

The point of a third target is to find out which of the first two backends' choices were general.

**Java has no free functions.** A file is a *class*, so `JavaFile` emits a wrapper. Neither Go
nor JS needed one — the first purely structural requirement any target has imposed.

**Types are needed by two targets of three.** Go needs them, Java needs them, JS needs none. The
type lattice is therefore not a Go quirk, and
[the decision to keep types in the backend](js-2026-08-14.md) rather than in the language looks
better with three data points than with two: JS would be carrying machinery it has no use for.

**ANF is required by exactly one target of three.** Java has a conditional expression, like JS and
unlike Go, so `(if c a b)` becomes `c ? a : b` when both branches are pure. [g3 §6](../../docs/derivations/g3-generics.md)
and [g5 §4](../../docs/derivations/g5-bindings.md) each derived ANF as necessary and the Go
emitter confirmed it a third time — and it turns out to be **Go's constraint alone**.

**Parallel-assignment temporaries are needed by two of three.** Go has tuple assignment
(`ax, ay = …, …`); JS and Java do not, so both need temporaries for `fold-range2`'s simultaneous
update. That is [g2 §6](../../docs/derivations/g2-structs.md)'s hazard, now confirmed as a
majority case rather than a JS quirk.

**Mangling is identical for the third time.** Hyphen to camelCase, `?` to `P`, `!` to `B`,
everything else escaped. Three targets, one transformation, three keyword sets. Three agreeing is
strong evidence it belongs to the **language** — a fact about what an Oroboros name is — with a
small per-target table of what the target forbids.

## 3. The dictionary goes the other way

This is the result worth keeping.

| target | emitted | why |
|---|---|---|
| Go | `acc[k]++` | **fused**; one `mapassign_faststr`, verified in [baseline C3](baseline-2026-08-13.md) |
| JS | `acc[k] = (acc[k] ?? 0) + 1` on a null-prototype object | `Map` is [3.25× slower](baseline-2026-08-13.md) for string keys |
| **Java** | `acc.put(k, acc.getOrDefault(k, 0) + 1)` | **unfused**; `merge(k,1,Integer::sum)` was [2.6× slower](baseline-2026-08-13.md) — [and is 1.19× FASTER on JDK 17](native-java-2026-08-25.md), so both forms are declared now |

**Go's fused idiom wins and Java's fused idiom loses.** One source, three targets, and the
*opposite* choice on two of them — decided by measurements taken months before either backend
existed, and living entirely in the primitive table.

[ADR 0008](../../docs/decisions/0008-measurement-over-principle.md) said parasite decisions are
per-target measurements rather than principles. This is what that looks like when it is real.

## 4. Why bytecode is not the evidence here

For Go, the compiler optimises before emitting machine code, so a machine-code diff proves
equivalence — that is how [the duplicate-read result](duplicate-read-2026-08-14.md) and
[structs](structs-2026-08-14.md) were settled.

**That technique does not transfer to Java.** `javac` barely optimises; it transcribes source
almost directly and leaves the work to HotSpot at runtime. So bytecode differences reflect
*source* differences that the JIT will erase, and bytecode identity is the wrong test.

Measured anyway, loop bodies only:

| | generated | hand-written |
|---|---|---|
| `dot` | **17** instrs | 18 |
| `filter` | 21 | 20 |
| `centroid` | 25 | 22 |

`dot`'s loop body is *smaller* because the emitter hoists `p.length` into a local and the
hand-written version re-reads `xs.length` each iteration. `centroid`'s is three larger: the
temporaries Java needs for the simultaneous update, all of which are copy-propagation candidates
HotSpot will remove.

So Java parity rests on timings, and timings are the thing this machine could not deliver
cleanly. Reported for completeness only:

| n=1024 | hand-written | generated |
|---|---|---|
| dot | 510.2 ns | 510.3 ns |
| filter | 457.8 ns | 465.0 ns |
| centroid | 528.5 ns | 504.8 ns |

Consistent with parity, and **not** evidence of it. Re-measuring on a quiet machine, or with JMH
and `-XX:+PrintCompilation`, is the honest way to close this.

## 5. What three backends share

| | Go | JS | Java |
|---|---|---|---|
| lines | 466 | 325 | 445 |

Present in all three: `emit`, `emitIf`, `emitFoldRange`, `emitFoldRange2`, `line`, `fresh`, and a
mangler. Present in two: `emitLet`, `typeOf`, `inferFrom`, `inferLet` — all absent from JS, all
for the same reason, that JS needs no types.

So the shape [ADR 0006](../../docs/decisions/0006-ir-file-format.md) asks for, now with three
points rather than two:

- **The term walk is common.** Duplicated three times.
- **The primitive table is the target.** Template, arity, result type, and a kind — expression,
  loop, two-accumulator loop, conditional, statement-returning-an-argument, or binding.
- **Types are an optional layer** that two targets need and one does not.
- **Mangling is language-level** with a per-target keyword set.
- **The file wrapper is per-target** — package clause, ES module, or class.

That is a concrete interface, and every part of it was discovered by writing three backends
rather than designed before writing one.

**It should still not be factored yet.** The next target — C, per
[ADR 0004](../../docs/decisions/0004-first-targets.md) — has manual memory, no garbage collector,
and no dictionary at all, and it is the one that would break any interface designed from these
three.

## 6. What is not done

- **Java parity is unconfirmed** (§4). The weakest claim in this document.
- **Word count on Java was not benchmarked**, only checked for correctness.
- **`split(" ")` versus `strings.Fields`** still diverges on whitespace runs, as
  [g4 §9](../../docs/derivations/g4-word-count.md) found. All three backends use a single-space
  split and the corpus hides it.
- **No Android/dex path.** ADR 0004 chose Java to reach Android via `javac → d8 → apk`, and only
  the first arrow has been walked.
