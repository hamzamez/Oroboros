# joinlet — an `again` after a join point, read as a `let` of several names (ADR 0139), 2026-11-19

hamza, 2026-11-19: "since it does not change the surface let's go with the recommendation, and
see where it lands performance wise". ADR 0134's B was not the core's term (joinjump-2026-11-19),
and this is its replacement.

## The result

**`wc` written nested, as Go writes it, runs at 1.013× Go's nested form, and 0.926× its own flat
form.** A 100,000,048-byte file of mixed ASCII and multibyte words, one process per run, the four
programs interleaved and their order rotated, 9 rounds, the file in the cache, every count equal:

So the 16% of wc-2026-10-24, the program's shape and not the printer, is gone: the nested J program
is within the noise floor of nested Go, as ADR 0134 item 3 required. The flat forms show the cost
of the shape on both sides, 1.07–1.09×. The Go references are rewritten for this step: the 10-24
ones were not kept. They have the same reads, decoding and saturating counts as the J programs.

## What it means

`(a, b) = loop … { … }; …; again(…)` in a tail is a `let` of two names: the loop P runs once, its
own `again`s its own, and the body once after it with P's components bound. ADR 0027 already reads
a host call's continuation that way, `(p a…) (λx̄. E)`, the fourth tail form. iteration.md §2's
tail grammar gains the production `P (λx̄. E)`, P a loop or a scope, which holds for the same
reason: the continuation runs once, immediately, and never escapes.

## What failed first, and what that showed

1. **With ADR 0134's refusal merely switched off, a program was mis-proven.** The nested programs
   were right, and so were two probes of an index the join body's back edge drives out of range.
   But a loop variable kept above 0 by one `again` and driven to −4 by the join body's was
   certified `0 <= k`, and the program panicked at run time: *index out of range [-4]*. The
   monotonicity proof (`emit/monotone.go`) reads a clause chain through `multiLet`, which knew a
   host call's continuation and not the pattern, so it never saw the edge. Its own comment had
   warned of exactly this.
2. **The fix is one predicate.** `continuation(tg, t)` is a host call's continuation or `joinLet`,
   a tuple pattern over a producer whose body jumps out. Every walker of a clause chain that read
   the fourth form reads it:
   - `projectTail`, `projectExits`, `eraseExits`, `badTail`, `etaTail` and `etaExits`;
   - the type checker's `unselected` and `loopBody`, which until now left the join body's `again`
     arguments unchecked;
   - `multiLet` (monotonicity);
   - the refinement layer's two tail walkers.

   The value-level walkers already handled the tuple pattern as a value: linearity, refine's
   binding of a call's results, the lowering's eliminator, and the IR's intervals and size-change
   termination, whose structured `continue` is the edge. Only a pattern whose body jumps out is
   read so, as ADR 0139 decision 1 says, so no other program's handling changed.
3. **ADR 0139 said "rewrite to a `let`", and it reads instead.** Rewriting the term into an
   m-name `let` would have made every value-level walker of `let` learn m names. 12 sites match a
   `let`, and the type checker's, linearity's, refine's and the lowering's assume one, some falling
   to a default that would skip a buffer. The walkers that needed the reading were the clause-chain
   walkers, and they already have the one-predicate shape for the host call. The meaning is the
   ADR's.
4. **The direct nested form met an older gap of the state translation.** A loop under a tuple
   pattern, inside a loop that carries a buffer, had its operands threaded as a call's, its body's
   λ passed as it stands. So the inner loop read the scope's first version of the buffer its
   enclosing loop had written. W7 refused it, *buffer %10 is used after it was consumed*, so no
   wrong code was printed. Translated as a loop, its value nests a tuple in the state tuple, which
   no join point binds (tables.md §2.5). It is older than ADR 0139: any such pattern meets it, with
   or without an `again`. **Owed**: the state flattened into the elimination, as spliceTails
   flattens a borrow's. The nested `wc` therefore writes the rune loop as a definition, `runes(b,
   k, n, …)`. A call's arguments are threaded, so b is its current version, and inlining gives
   the same nested loops in the residual. The compiler before this step refuses that program at
   the join point, so the pattern is the one ADR 0139 admits.
5. **A header cannot name a constant's set**: `k ∈ 0..size_buf` in `runes`' header was refused,
   *0..size_buf is not a type*, where a binder's claim takes it. Written `0..65536`. Owed.

## The tests

- `TestAnAgainAfterAJoinPointIsABackEdge` (`cmd/build/joinlet_test.go`):
  - the nested program right on Go and windows (165 0 15150);
  - the join body's edge driving the index below 0 refused naming `0 <= k`;
  - the fault `emit.PlantJoinLetUnread`, the pattern unread by the walkers, under which the
    program builds again: the mis-proof of point 1.
- `TestWcIsItsDefinitionWhateverTheReads` runs on both shapes, flat and nested: 33 inputs at the
  buffer's edges, as files and through a pipe, and several files with a missing one.
- `TestAJoinPointAndAScopeRefuseWhatIsNotBuilt` now pins that the pattern is accepted.
