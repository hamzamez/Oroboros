# A JSON tokeniser without recursion — 2026-08-26

[`examples/json/tokenize.oro`](../../examples/json/tokenize.oro),
[`gauntlet/differential/cases/json-tokenize.oro`](../differential/cases/json-tokenize.oro).

ADR 0014 says recursion is not in the language, and the standing counter-claim — written in
[data-structures.md](../../docs/data-structures.md) and repeated in
[sums-research.md](../../docs/sums-research.md) — is that **recursive data is a flat table plus
indices**. A JSON document is the case that claim has to survive: it nests to a depth the *input*
decides, and every textbook treatment of it is recursive descent.

So this is that claim, run. A tokeniser over a table of bytes, with an explicit stack in a `build`
buffer, `loop`/`again` for control, and nothing else.

```
ok   json-tokenize          13021 7031 4010 1000  [go js java windows]
```

Four documents, four targets, byte-identical output, and the answers are independently right:

| document | tokens | depth | valid | encoded |
|---|---|---|---|---|
| `{"a":[1,2],"b":true}` | 13 | 2 | yes | 13021 |
| `[[[1]]]` | 7 | 3 | yes | 7031 |
| `{"a":1` | 4 | 1 | **no** — unterminated | 4010 |
| `]` | 1 | 0 | **no** — unbalanced | 1000 |

x86-64 assembly under MASM is one of the four.

---

## 1. What it does and does not settle

**Settled: the control half.** Tokenising, character classification, string and number scanning,
bracket matching to an input-decided depth — the parts recursion is normally *for* — need no
recursion and no closures. Depth lives in a table, and `again` is the jump.

**Not settled: the value half.** This produces counts, not a tree. Building the document as a flat
table of nodes plus indices is the other half of the claim and is not written here. That is the
honest boundary: ADR 0014 survives the part that was tested, and the part that was not tested is
named rather than assumed.

---

## 2. The compiler made the parser state its depth limit

Three clauses in the program exist because the refinement layer demanded them, and each is marked
in the source. Two are analysis limitations. The third is the result.

`(set stk sp …)` carries `sp < cap` as an obligation, and nothing in the program can discharge it,
because `sp` grows with the input. So the program has to answer *"what happens when the nesting is
deeper than the stack"*:

```lisp
(go.>= sp (cap))  (go.* nt 1000)
```

**A recursive-descent parser has exactly the same limit — the C stack — and is never asked.** The
explicit stack does not create the limit; it makes it visible, and the refinement layer is what
forces it into the open. That is the strongest argument for ADR 0014 found so far, and it is not a
performance argument.

The other two are the analysis being non-relational, per
[decidability-map.md](../../docs/decidability-map.md):

- `(go.< j 0) j` in each scanner, because `j ≥ i + 1` is **relational** and intervals are not.
- `(go.< i 0) 0` in the main loop, because a scanner's result is a loop's value and therefore
  opaque.

Each costs one compare. Both are exactly the shape octagons would remove.

---

## 3. Four bugs, and what they have in common

None of these is a new construct. The differential suite has covered every construct here since
[yesterday](differential-2026-08-26.md), and all eight cases passed. **These four are about a
program being BIGGER, not about a construct being new** — which is the distinction between a
construct suite and a program, and the reason to have both.

### 3a. `typeOf` of a `build` assumed the body hands the buffer back

```
.\main.go:622:9: cannot use r28 (variable of type int) as []int value in return statement
```

Every `build` previously written in this repository returns its buffer — that is what a sieve does
and what ADR 0018 describes. **This is the first program whose buffer is SCRATCH**: a stack, written,
read back, and dead at the boundary, with a *count* returned. The Go and Java emitters declared
`[]int` / `long[]` and returned an `int`.

Fixed by binding the buffer's own type and asking the body, so a body that does return the buffer
still answers `array V`. Go and Java both.

### 3b. `any` demanded something, in two places

```
in again's argument 5: the branches of a conditional are any and int
a loop's exits are int and any
```

`emit/check.go` has a `compatible` helper whose comment says *"`any` and the unknown type agree with
anything"*, and the conditional and loop-exit checks did not use it. `targets/js/` declares
everything `any` **on purpose**, so `(if (js.> (js.+ sp 1) mx) (js.+ sp 1) mx)` — an ordinary
running maximum — was a type error on JavaScript and fine everywhere else.

The checker's own §3 test (`TestCheckerAcceptsAny`) states the rule; two sites had not been taught
it, because nothing had previously mixed a known type with an `any` inside one conditional.

### 3c. x86 emitted a memory-to-memory `mov`

```
mov qword ptr [rsp+56], qword ptr [rdi]
```

`(len src)` loading into a **spilled** destination. `move` already handles slot-to-slot; the two
*loads* — a table's length header and an element read — did not, because until now no program had
enough simultaneously live values for the destination of a `len` to be spilled. Six loop variables
and three nested loops did it.

The fix has to pick a register that is free *after* the address is formed. A scratch register the
address does not use is free by definition; failing that, one the address **does** use is free the
instant the load reads it, because a single instruction computes its memory operand before writing
its destination.

## 4. CLAUSE ORDER CHANGES WHAT CAN BE PROVED

The finding this program produced that argument had not.

Same guards, same clauses, same answers on all four documents — one clause moved:

| the depth-limit clause | integer ops bounded | loops proven terminating |
|---|---|---|
| **above** the end-of-input clause | 36 of 124 | **0 of 16** |
| **below** it (as committed) | 80 of 124 | **12 of 16** |

Reproduce it by moving `(go.>= sp (cap)) (go.* nt 1000)` back above
`(go.>= i (len src))` in `examples/json/tokenize.oro` and running

```bash
go run ./cmd/gen examples/json/tokenize.oro go /tmp/o.go
```

The four loops still unproven in the committed version are the scanners, and those are a **true**
negative: a scanner terminates because it makes progress, `j ≥ i + 1`, which is relational.

**The cause is not isolated.** `emit/interval.go`'s `collectAgain` refines through both branches of
every clause, so the negations of all preceding guards should reach every `again` in either order.
Four reduced versions of the shape — the `sp` guard first, moved, removed, and with the buffer
threaded through `set` — all prove at 1 of 1, so the reduction that would show it has not been
found. It is reproducible in the real program and nowhere smaller.

What it means in the meantime is worth saying plainly: **the analysis is order-sensitive in a way
the language is not**, so a program can lose its termination proof to an edit that preserves its
meaning. That is a stronger reason to want the relational layer than the two extra compares in §2
were, and it belongs with the octagon work
([decidability-map.md](../../docs/decidability-map.md) calls octagons the highest-value move
available).

---

## 5. What this cost

One `.oro` file, 120 lines with the comments. No new term kind, no new reduction rule, no new
primitive, and **no target declares anything** for it. Four compiler fixes, all of them in code that
was already wrong and had not been asked.
