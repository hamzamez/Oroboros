# A JSON tree without recursion — 2026-08-26

[`examples/json/tree.oro`](../../examples/json/tree.oro),
[`gauntlet/differential/cases/json-tree.oro`](../differential/cases/json-tree.oro).

[json-2026-08-26](json-2026-08-26.md) settled the **control** half of *"recursive data is a flat
table plus indices"* — nesting to an input-decided depth needs no recursion — and said plainly that
it produced counts, not a tree. This is the **value** half.

It parses four documents into a node table and then **walks** it, because building a tree and never
traversing it would prove nothing: the walk is where a tree normally recurses.

```
ok   json-tree              730461 440291 320150 530441  [go js java]
```

The four answers were computed by hand from the tree structure before the program was run, and the
program reproduced all four:

| document | nodes visited | max depth | checksum | valid |
|---|---|---|---|---|
| `{"a":[1,2],"b":true}` | 7 | 3 | 46 | yes |
| `[[[1]]]` | 4 | 4 | 29 | yes |
| `{"a":1` | 3 | 2 | 15 | **no** — unterminated |
| `[{"x":[]},7]` | 5 | 3 | 44 | yes |

The checksum is Σ(tag × depth) + Σ(val) over every node the walk reaches, so a wrong link is a
wrong number rather than a crash. **x86 is verified too, at one document** — it prints 730461 like
the other three; §5 is why it is not in the suite run.

---

## 1. The representation

One buffer, stride 4. Node *k* occupies `4k+0` tag, `4k+1` val, `4k+2` first child, `4k+3` next
sibling. **Node 0 is the `none` sentinel**, so its four slots are free and hold the header: the node
count and the valid bit.

Two things fell out of that which the design had not stated:

**Zero is `none`, and `build` zero-fills** ([tables.md §14.3](../../docs/spec/tables.md)). So `kid`
and `sib` never have to be initialised — the parser writes a tag and a value and links, and every
node is born childless and last. That is a small property doing a lot of work, and it is specified
in one line of a comparison table rather than anywhere a reader would look for it.

**The document is node 1, pushed before the loop starts.** With a real root on the stack, `sp` is
never 0 and every value has a parent, which deletes the special case from the link step entirely.

---

## 2. Linking is what a recursive parser gets for free

The one operation this needs that recursive descent does not have to write: a recursive parser
**returns** its subtree to its caller, and a flat one has to **point at it**.

```lisp
(let (stk (sx d1 1)) (fn (lc)
(let (if (= lc 0)
         (set nodes (nx (stk (sx d1 0)) 2) nn)      ; first child of the open container
         (set nodes (nx lc 3) nn)) (fn (linked)     ; next sibling of its last child
```

That is the whole of it — two writes and a saved "last child" per stack frame. It is not a
consolation prize for lacking recursion; it is the same work the call stack was doing, written down.

---

## 3. ADR 0015 chose the shape, and the shape it chose is better

`again` may sit under a `let` and **never** under an `if`. Five token classes therefore cannot be
five clauses each ending in its own `again` without repeating the link step four more times.

So they became **one `again`** whose arguments are computed by `let` — the end index, the tag and
the value each selected by a pure conditional, with the link shared. That is better code than the
five-clause version, and it was **not the first thing tried**. A restriction that forces a
factoring is the [Low\* lesson](../../docs/lowstar-lessons.md) arriving in miniature.

Three other things the language allowed without complaint, each of which was an open question
before this program: **two nested `build`s** (the parser holds a node table and a stack live at
once, the walk opens a third), **a buffer under both branches of an `if`** — the linearity checker
counts occurrences in evaluation order and one branch runs — and `again` under five stacked `let`s.

## 4. Five bugs, and the first two are silent wrong answers

The differential suite's construct cases all passed throughout. As in
[json-2026-08-26 §3](json-2026-08-26.md), what found these is that the **program was bigger**.

### 4a. A call-by-need binding took a definition's name

```lisp
(def d1 (array 7 8 9))
(def run (fn (k) ((fn (d1) (go.+ d1 d1)) (go.+ k 100))))
→ (let (go.+ k 100) (fn (d1) (go.+ (array 7 8 9) (array 7 8 9))))
```

**The worst kind of bug this project can have**: it compiles, it runs, and it returns the wrong
number.

The mechanism is exact. `core/reduce.go`'s comment on the `KFn` case states reduction's invariant —
*"The CLOSED body. Reduction never opens, so it never re-closes, so a colliding hint can never merge
two variables."* Call-by-need is the one place that breaks the invariant **on purpose**: when β
declines to substitute, it puts the parameter's own NAME back into the body and wraps a `let` around
it. That is safe only if δ will not unfold the name it puts back, which is true of every imported
name because `resolve` qualifies it with its module path — and false in the **main** module, where
`qualify("", n)` leaves definitions bare.

One occurrence substituted and compiled correctly; two reached this path and did not. Fixed by
choosing a binding name that is not a definition's. Regression test:
`core.TestCallByNeedDoesNotCaptureADefinition`.

### 4b. `PostVars` hoisted an update out of the `let` that bound it

[loopshape-2026-08-25](loopshape-2026-08-25.md) moves a uniformly-updated loop variable into the
`for` statement's post clause, worth 1.4× on the sieve. It had three conditions and needed a fourth:
the post clause is written **outside every binder the body opened**, so an update like
`(if (go.> dp mx) dp mx)` whose `dp` came from an enclosing `let` cannot go there.

ADR 0015 permits `again` under a `let`, and [match.md](../../docs/spec/match.md) leans on that — but
no program before had a *non-trivial* update under one. It surfaced as `unhandled term: #0.0`,
which is the good outcome; the bad one was one binder away. Regression test:
`emit.TestPostDoesNotHoistOutOfALet`.

### 4c. `any` demanded something, for the third time today

`run returns any, but its signature declares int` on JavaScript. `emit/check.go` has a `compatible`
helper meaning *"`any` and the unknown agree with anything"*, and today three separate sites turned
out not to call it: the conditional, the loop exit ([json-2026-08-26 §3b](json-2026-08-26.md)) and
now `CheckAgainstSig`. A host that declares everything `any` **on purpose** could not otherwise
carry a `sig` with a concrete result.

### 4d. x86 could not store when all three operands were spilled

A store wants three registers — base, index, value — and this host reserves two scratch. Forming
the address with `lea` first frees the index register before the value needs one. It costs an
instruction, so it is taken only when the one-instruction form cannot be built; the sieve's inner
loop that [wintables-2026-08-25](wintables-2026-08-25.md) measured is untouched.

### 4e. …and the template path was enforcing the wrong constraint entirely

```
x64.movb has more spilled operands than there are scratch registers
```

The rule x86 actually has is **one memory operand per instruction**, not two spilled operands per
template. Most templates only ever move an operand into a register, and `mov rcx, [rsp+56]` is a
legal instruction — so a fifth argument to `WriteFile` never needed a scratch register to get there.

The excess now stays in its frame slot and the **result** is checked: a filled line naming memory
twice is refused, and it names the line. That is both more permissive and more precise than the
budget it replaces, and the message above is what it produces when a template genuinely does need a
register.

## 5. The x86 ceiling, stated rather than hidden

The case carries `; skip: windows`, and the reason is register pressure in the **harness** rather
than in the program. x86 builds this and prints 730461 for **one** document. The harness inlines
`run` once per input, and two copies of three nested buffers plus eleven live values exhaust the
seven callee-saved registers the value pool has — and there is no eighth: `rbp` is the frame pointer
and the rest of the callee-saved set is already in the pool.

`gauntlet/differential/run.go` predicted this in a comment before the case existed. It is a real
limit that belongs to the backend, and provoking it from a test harness measures the harness.

## 6. Termination got worse, and that is consistent

| program | integer ops bounded | loops proven terminating |
|---|---|---|
| [tokenize](json-2026-08-26.md) | 80 of 124 | 12 of 16 |
| tree | 131 of 161 | **0 of 6** |

More operations are bounded — the clamped index helpers `nx` and `sx` are bounded by construction,
which is most of that. **No loop is proven to terminate.** The tokeniser's proven loops were the
ones whose counter walks the source; here every loop's progress depends on a link or an index read
out of a table, which is a value the interval analysis cannot bound and a relation it cannot state.

This is the same finding as [json-2026-08-26 §2 and §4](json-2026-08-26.md) arriving with more
force, and it is now the clearest argument on the board for the relational layer
([decidability-map.md](../../docs/decidability-map.md)'s octagons).

## 7. What it settles

**The claim holds.** Recursive data is a flat table plus indices — built, linked, traversed, on Go,
JavaScript and Java in the suite and on x86-64 assembly by hand. 215 lines. No new term kind, no new
reduction rule, no new primitive, and no target declares anything.

**So the superseding ADR that [general-purpose.md](../../docs/general-purpose.md) called owed is not
owed on the grounds it gave.** That argument was *"a JSON parser, a DOM walk and a
recursive-descent parser all recurse to a depth the input decides"*, and two of those three now run
here without recursion — the walk in §1 is a DOM walk in miniature.

**What is not settled is ergonomics, and that is a different argument.** This cost 215 lines, five
compiler bugs, and a factoring the author did not reach first. None of that is evidence about
speed or expressiveness, and none of it has been measured against anything. If recursion is wanted,
that is the case to make, and it has not been made.

One thing genuinely gained rather than merely survived, the same as the tokeniser's: the depth bound
is **visible**. `(set stk sp …)` carries `sp < cap`, so the program says what it does when the
nesting is deeper than the stack. A recursive-descent parser has the same limit and is never asked.
