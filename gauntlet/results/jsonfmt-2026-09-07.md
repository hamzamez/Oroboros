# A tool, and the four bugs it found

2026-09-07. [examples/io/jsonfmt.oro](../../examples/io/jsonfmt.oro),
[assessment-2026-09-06](../../docs/assessment-2026-09-06.md)'s item 4 — *write
something awkward*, named in four consecutive assessments and acted on in none.

```
$ jsonfmt doc.json
```

A JSON pretty-printer: reads a file named on the command line, reformats it with
two-space indentation, writes it to stdout. **95 lines**, the second largest
program ever written in this language and the first that is a *tool* rather than
something that computes a number.

> **It works, and that is the smaller half of the result.** Writing it found
> **four bugs, two of them silent wrong answers** — and one of the two was
> shipped the previous day, in the very feature that made this program possible.

---

## 1. It works

Validated against a real parser rather than by inspection:

```
$ jsonfmt n.json
{
  "a": [
    {
      "b": [ 1, 2, { "c": null } ],        ← (each on its own line; elided here)
      "d": "x\"y"
    },
    []
  ],
  "e": -1.5e3
}
```

- **valid JSON**, and `json.load` says the output is *semantically identical* to
  the input;
- **idempotent** — formatting the output again gives the same bytes, so layout is
  a fixed point;
- `{}` and `[]` stay compact, which is the whole job of the `fresh` bit;
- escapes survive (`"x\"y"`), because a string token is copied verbatim after
  `scan-string` finds its end;
- 300 records, 22.8 KB in and 49.2 KB out, round-trip identical;
- all three error paths — no argument, unreadable file, file too large.

**And it builds without `-checked`: 99 of 99 integer operations bounded, 13 of 13
loops proven terminating.** That is worth one line of the program, see §4.

## 2. Bug 1 — ADR 0019 was vacuous inside a multi-result continuation

**Mine, shipped the previous day** in
[multiresult-2026-09-06](multiresult-2026-09-06.md).

`evalR` reached an application whose operator is itself an application, did not
recognise it, and returned `top` **without walking the continuation's body**. So
the interval pass never entered any code written after a host call with several
results — which is how every program that opens a file is written.

The same unbounded multiplication, in two places:

```lisp
(def blow (fn (n) (loop ((a 1) (k 0)) (>= k 40) a else (again (* a n) (+ k 1)))))

(sig f ((n int)) int) (def f (fn (n) (blow n)))          ; REFUSED, correctly
((os.ReadFile p) (fn (src err) (blow (len src))))        ; ACCEPTED, silently
```

**Bounded-by-default was enforced everywhere except in the new code.** That is
the same failure mode [bigrep-2026-09-02](bigrep-2026-09-02.md) found on
JavaScript — *"enforced on three targets and vacuous on the fourth"* — arriving
at a construct instead of at a target.

The fix walks the continuation and binds each parameter to what the primitive
**declares** it gives back: a scalar range binds the interval, and an
`(array (int LO HI))` binds the element range. So the same repair that closes the
hole is what lets §5's byte copy narrow.

## 3. Bug 2 — the bounds-check narrowing truncated its own source

**Pre-existing since [bce-2026-08-15](bce-2026-08-15.md)**, and a silent wrong
answer.

```go
src = src[:n25]        // ← writes back to the container itself
```

`emitNarrow` implements bounds-check elimination by narrowing every container the
loop indexes to the loop's own bound. Its comment justifies this:

> *"narrowing moves the panic earlier, and no program with defined meaning can
> tell"*

which is **true of indexing** — primitives.md §2 leaves an out-of-range read
unspecified — and **was never true of `len`**, which is specified and which
nothing had asked about afterwards.

Invisible for three weeks because **every earlier narrow was to the container's
own length**, where `q[:len(q)]` is the identity. The formatter copies a *token*
out of a document, so the bound is that token's end: after the first string,
`src = src[:7]`, `len(src)` becomes 7, and the loop exited. The output was

```
{
  "name"
```

and then nothing — no diagnostic, no crash, just a truncated document.

**The fix narrows into a fresh name** and renames the container inside the loop
that narrowed it. **The optimisation is unaffected**: the emitted sieve has
**2 `IsInBounds` at the same two lines before and after**, checked by compiling
both forms in one package with `-d=ssa/check_bce/debug=1` rather than trusting
the timings.

## 4. Bug 3 — a copied byte could never be narrowed, and two rules had never met

The output is a byte buffer, so it should be `[]byte`. It was `[]int`, and
`string(…)` on it does not compile.

The cause is two rules that are exactly complementary and had never been in the
same program:

- [effects.md §7c](../../docs/spec/effects.md) **guarantees** a table read is
  *never* substituted into an impure body — a read moving across a store is a
  silent wrong answer, and a swap once became a copy. So a copied byte is
  **always** let-bound.
- The syntactic element inference resolved only the bare name, and `typeOf` on a
  table read calls `ValueType`, which **normalises a range to `int`** — correct
  for the value, since a local reading a byte array is an integer and cannot
  overflow at 255, and exactly what destroys the fact here.

So `(set out i (src k))` never survives as written, and what the inference saw
was a name whose range had already been normalised away. elemwidth-2026-08-27
states the rule — *"a read from an already-narrowed table carries one"* — and
this path could not reach it.

The fix makes the `let` **transparent** to the inference, and it re-opened a
circularity the project had already identified: a buffer must not narrow on its
own contents. `buffer-swap` is exactly that shape, and the differential suite
caught it on Java within a minute. The self-read is excluded explicitly, which is
the same policy the interval path already has.

## 5. Bug 4 — Java declared a local at the element's width

`final byte vx = (long) b[0];` — javac refuses it.

Go's `typeOf` normalises a table read with `ValueType` and Java's did not, so a
local bound to a read of a **narrowed** buffer was declared at the storage width
while the read itself emits a cast to the host's `long`. Latent until §4 made a
buffer narrow in a program that also binds a name to one of its reads.

## 6. What the program says about the design

**A text program that COPIES works in bytes, not in the free monoid.**
[render-2026-09-04](render-2026-09-04.md) answered the producing half of
[string-operations.md §8](../../docs/string-operations.md)'s question — decimal
rendering folds with `concat`. This is the other half, and the answer is
different: `string-of` is **η over scalars**, so pushing a raw UTF-8 byte through
it turns 0xC3 into U+00C3. A formatter cannot build its output as text at all.
It works in bytes throughout and converts **once**, which is that document's own
`alloc`-once advice arriving from the opposite direction.

> So the monoid is enough to *produce* text and not enough to *transform* it, and
> the operation a transforming program needs is bytes-to-text at the boundary —
> not `length`, not indexing, and not `=`.

**Count-then-build has a real ergonomic cost, and this is the first time anyone
has had to write it.** `build` fixes a length up front, so the output size must be
known before the output exists, and a `build` returns the buffer with nowhere to
put a second result. The state machine is therefore written **twice** and the two
copies must agree byte for byte. What makes that safe rather than a latent bug is
factoring the three length contributions — `pad-before`, `pad-close`,
`depth-out` — into definitions both passes call. maps-2026-08-30 measured this
pattern at 2.95× faster than growing `append`; this is what it costs to write.

**Stating the input limit is worth everything.** The output length accumulates
over the input, and a file is unbounded, so nothing can bound it — 33 operations
unprovable. One line —

```lisp
(if (>= (len src) (cap-in)) (fmt.Println "…too large") …)
```

— takes it to **99 of 99 and 13 of 13**, with no `-checked`. That is `tree.oro`'s
node cap again: *a capacity does not create the limit, it makes it visible*, and
here it is the difference between a proven program and a trapped one.

**And once the language pushed the program toward saying what it means.** The
formatter emits `(if (= (src i) 123) 123 91)` rather than echoing `(src i)`,
because a let-bound copy of a byte loses its range. That is friction, and it is
the good kind: a formatter *does* know which bracket it is writing.

## 7. Cost

| | |
|---|---|
| emitted files changed | **6 of 64**, all the narrowing rename |
| bounds checks in the sieve | **2 before, 2 after**, same lines |
| differential suite | 27 cases, four targets, green |
| unit tests, `go vet` | green |

The six changed files are `sieve`, `dot` and `centroid` on Go — every program
that narrows. Nothing else in the corpus moves.

**No benchmark.** There is no hand-written reference formatter to compare against
and inventing one to beat would be measuring the wrong thing; the claim here is
correctness and expressiveness, not speed. What *is* measured is that the
optimisation the narrowing exists for is unchanged.

## 8. What it did not need

Worth recording, because the list is short and was not obvious in advance: no
tree, no tokeniser table, no map, no sum, no recursion, no string operations
beyond one conversion, no new term kind, no new reduction rule, and **no target
declares anything for it** except the two `os` names and `text-of`.

It also did not need `-checked`, which `tree.oro` and both `wordcount`s do.
