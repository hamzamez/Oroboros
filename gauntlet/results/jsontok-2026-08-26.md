# The tokeniser against hand-written code — 2026-08-26

[`examples/json/tokenize.oro`](../../examples/json/tokenize.oro) against hand-written Go,
JavaScript and Java. References in [`gauntlet/go/jsontok.go`](../go/jsontok.go),
[`gauntlet/js/jsontok.mjs`](../js/jsontok.mjs),
[`gauntlet/java/JsonTokBench.java`](../java/JsonTokBench.java).

**The first branchy program in the gauntlet.** Everything measured here before — dot, centroid,
smooth, stencil, sieve, search, report, wordcount — is a numeric loop: countable, predictable,
array-walking, which is the shape every host optimises best and the shape the emitter has been
tuned against for five months. A tokeniser is a data-dependent switch per byte with unpredictable
branches and scanners whose trip count the input decides.

It was written and committed [yesterday](json-2026-08-26.md) with no number attached, which is a
breach of this project's own standard. This is that number.

---

## 1. The results

Same document on every host: 64 records of realistic JSON, ~7.6 KB, nested two deep, with escapes,
numbers and all three literals. Every form is checked against every other on four sizes and six
malformed inputs before anything is timed.

### Go — `go test -bench=Tok -benchtime=2s -count=5`, median

| | ns/op | vs like-for-like |
|---|---|---|
| hand-written `[]byte` | 9,658 | — |
| hand-written `[]int` | 10,164 | 1.00× |
| **generated** (`[]int`) | **9,715** | **0.96×** |

### JavaScript — one `node` process per case, median of 3

| | ns/op | vs like-for-like |
|---|---|---|
| hand-written `string` (`charCodeAt`) | 15,747 | 1.89× |
| hand-written `Uint8Array` | 9,577 | 1.15× |
| hand-written plain `Array` | 8,314 | 1.00× |
| **generated** (plain `Array`) | **8,451** | **1.02×** |

### Java — `java -cp out JsonTokBench`, best-of-9 inner, median of 3 processes

| | ns/op | vs like-for-like |
|---|---|---|
| hand-written `String` (`charAt`) | 8,586 | |
| hand-written `byte[]` | 7,702 | |
| hand-written `long[]`, `int` index | 7,817 | idiomatic |
| hand-written `long[]`, **`long` index** | 9,156 | **the shape we emit** |
| **generated** (`long[]`, `long` index) | **9,400** | **1.03× of our shape, 1.20× of idiomatic** |

**Parity holds on branchy code**, on Go and JavaScript, first time measured. Java misses by 1.20×
and §3 is what that is.

## 2. The compiler's own decisions, not just the clock

`go build -gcflags="-m -m"`:

```
./gen_jsontok.go:9:14: make([]int, 32) does not escape
```

**ADR 0018's buffer is stack-allocated** — the same as the hand-written `var stk [32]int`. Zero
allocations per call, confirmed with `-benchmem`, on both sides.

`-gcflags="-d=ssa/check_bce/debug=1"`: the generated tokeniser keeps **2** bounds checks where the
hand-written `[]int` version keeps **5**. That is the [bce-2026-08-15](bce-2026-08-15.md) emitter
pattern still holding on a shape it was not designed for.

---

## 3. Java's 1.20× is the index type, and that is isolated rather than assumed

[indextype-2026-08-25](indextype-2026-08-25.md) found that a Java array index is 32-bit while our
`int` is 64-bit (ADR 0012), so an emitted `long` counter carries an `(int)` cast per access and
costs 1.04× to 1.54×. The fix narrows a counter to the host's own `int` when it is **bounded by a
length** and **steps by +1**. That result explicitly named the sieve as *not* reaching the general
case, because its bound is `i*i >= n` and its step is `+i`.

**This is the case it named.** A tokeniser's `i` is assigned a *scanner's return value*, so neither
condition holds, the narrowing does not fire, and `GenTokens` carries 14 `(int)` casts.

Rather than assume that was the cause, the same program was hand-written a fourth time with a
`long` index and the casts written out:

| | ns/op |
|---|---|
| hand-written, `int` index | 7,817 |
| hand-written, `long` index | 9,156 |
| generated | 9,400 |

**The long index alone costs 1.17×, and the emitter is at 1.03× of the shape it emits.** So this is
not a code-generation gap; it is one missing narrowing, with a number on it.

What would close it is a **platform** fact rather than an inferred range, exactly as
indextype-2026-08-25 argued: a Java array holds at most 2^31-1 elements, so a value that is compared
against `src.length` and then used to index `src` is provably in `int`. The current condition is
written in terms of how the counter *steps*, and this program shows that is too narrow. That is a
named next task, not a mystery.

## 4. A benchmark-method error, caught — the third in this repository

The first JavaScript run had the generated code at **0.68×** hand-written, which would have been the
best result in the project's history. It was wrong.

The hand-written reference read each byte through a closure — one `tokenize(len, at)` called with
`(i) => s.charCodeAt(i)` — which is an **indirect call per byte**. Removing it took the hand-written
plain-`Array` form from 12,320 ns to 8,314 ns. The generated side did not move.

So the honest answer is 1.02×, and the closure was worth **1.5×** of pure measurement artifact. This
is the same class as native-js-2026-08-20's `g.dotTyped` (1.66× for a property load) and its
per-process V8 state. **Every JavaScript result in this repository that looked surprising has turned
out to be a benchmark-method error at least once**, and the rule that catches them is to make the
suspicious result explain itself before recording it.

## 5. Three things worth carrying

**The 64-bit `int` is nearly free on Go and costs nothing on JS.** ADR 0012 makes our input eight
times larger than a `[]byte`, and Go's `[]int` form is only 1.05× the `[]byte` one. The loop is
branch-bound, not memory-bound, so the wider element is hidden. That is the third regime — the
first two are [checkcost-2026-08-19](checkcost-2026-08-19.md)'s arithmetic-bound 4.54× and
memory-bound 1.23× — and the lesson repeats: **a cost behaves the way a saving does, and neither
survives being quoted without its condition.**

**The refinement layer's extra compares are not visible.** The program carries three it would not
otherwise have — `(go.< i 0)` per token and `(go.< j 0)` in each scanner — because `j >= i+1` is
relational and the interval analysis is not ([json-2026-08-26 §2](json-2026-08-26.md)). At 0.96× on
Go and 1.02× on JS they cost nothing measurable. The branch predictor gets them right every time,
which is exactly what a never-taken branch is cheap for.

**A string-based tokeniser is 1.89× slower than an array-based one on V8**, and 1.11× on the JVM.
That is a fact about the hosts, not about us, and it lands on the **strings** work
([general-purpose.md](../../docs/general-purpose.md) has strings as owed): a JSON API is handed a
string, and on V8 the right move is to convert once rather than index it repeatedly. Also
counterintuitive and below the noise floor, so recorded but not leaned on: a plain `Array` beat a
`Uint8Array` by 1.15x.

## 6. Method

Machine is the usual hybrid P/E-core laptop with a ~15% noise floor, so nothing here rests on a
margin smaller than that except where it is labelled as not resting on it. Java and JavaScript get
one process per comparison; Go uses `-count=5`.

The JavaScript and Java sources are derived from the one Go-flavoured `.oro` by substituting the
host prefix, which is what the differential suite does:

```
sed -e "s/(use go)/(use js)/" -e "s/go[.]/js./g" examples/json/tokenize.oro > tok-js.oro
go run ./cmd/gen -name=native tok-js.oro js gauntlet/js/gen_jsontok_native.mjs
```

x86-64 is not measured here. Its correctness is covered by the differential suite, and the bar this
program is being held to is the gauntlet's three targets.
