# The JVM's JSON tokenizer "slowing mid-run": the process's age, not the code

2026-11-19. The 10-24 plan's open item: "the JVM's generated JSON tokenizer slows from 8 to 22.5 µs
mid-run (bits-2026-10-27 §2): find the cause against hand-written code". Time-boxed to an hour.

## 1. Measured

`gauntlet/java`'s `JsonTokBench`, and a harness of my own (`TokOrder`, in the session's scratchpad)
that runs a chosen sequence of cases, each with `JsonTokBench`'s method: 50,000 warm calls, then the
best of 9 rounds of 2,000.

| sequence in one process | the last case |
|---|---:|
| the generated tokenizer alone | 7.9 µs |
| the hand-written `byte[]` tokenizer alone | 7.4 µs |
| one, two or three cases, then the generated | 7.6–8.0 µs |
| `JsonTokBench`'s five hand-written cases, then the generated | **22.3–22.9 µs** |
| the same five, then the **hand-written** `byte[]` again | **23.6 µs** |
| the same five, then the generated through its own copy of `run` | 22.5 µs |
| **3 s of spinning**, then the generated | **22.6 µs** |
| **3 s of sleeping**, then the generated | **22.8 µs** |
| 3 s of spinning, then the hand-written | 22.2 µs |

Round by round, in a process that runs only the generated tokenizer, 60 rounds stay between 7.9 and
11.2 µs, and the hand-written between 7.4 and 9.2. Pinned to logical CPUs 14–15 (`start /affinity
C000`), the generated tokenizer runs 15.1 µs from the start. Pinned to CPUs 0–1 and then slept for
3 s, it runs 11.3 µs, the JIT's threads sharing the two CPUs.

## 2. The cause

**The process's age.** About 3 s after a process starts, whatever it measures runs about three times
slower, hand-written code and generated code alike, whether the 3 s were spent spinning or sleeping.
The JIT is not the cause: sleeping compiles nothing, and the generated method reaches C2 (tier 4)
as usual (`-XX:+PrintCompilation`). Neither is the harness's megamorphic `Supplier` site: an own
call site is as slow. The pinning points at the laptop's hybrid cores. Placed on CPUs 14–15 the code
is slower from the first second, and placed on CPUs 0–1 it keeps most of its speed past 3 s. So the
scheduler moves an older thread to an efficiency core, or lowers its clock. Which mechanism Windows
uses (Thread Director, EcoQoS) is not measured here.

**So the "mid-run degradation" was a measurement artifact.** `JsonTokBench` runs the generated case
sixth, after about 2.5 s of the other five, and bits-2026-10-27 compared its steady state against
cases measured earlier in the process. Against the hand-written tokenizer measured at the same
moment the generated one is at parity: 22.5 against 23.6 µs late, 7.9 against 7.4 µs early.

## 3. What it means for other measurements

Every benchmark that runs several cases in one process and compares cases measured seconds apart can
measure this. The gauntlet's JVM harness, and any `cd gauntlet/go && go test -bench` run of many
benchmarks, are candidates. A comparison is sound when both forms are measured in the same window:
- each case in its own process, as the 'runs alone' measurements of bits-2026-10-27 were;
- the forms interleaved round by round;
- or the process pinned to the performance cores.

Whether the gauntlet's published ratios were taken that way is not re-measured here. That is owed,
and is the next step for any ratio near the noise floor.
