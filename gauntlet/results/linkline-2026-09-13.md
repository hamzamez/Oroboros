# The link line is computed from the declarations, and 666 callable Win32 names became 3,593

2026-09-13. `emit/target.go`, `emit/asm.go`, `targets/windows/windows.oro`,
[target-files.md §6a](../../docs/spec/target-files.md), `gauntlet/stdlib/win32.go`,
`gauntlet/stdlib/acceptance/link-line.oro`. The item structval-2026-09-12 left as
next: *the link line computed from the declarations.*

> **THE LINK LINE WAS A CONSTANT, AND NOW IT IS DATA PLUS WHAT THE PROGRAM
> CALLS.** `(link "…")` in `windows.oro` names what every program links; a
> primitive's `(lib "…")` names the import library that resolves its `import`,
> collected exactly as the import is — only from what the program uses. **One
> field, one list, one collection site; no backend learned anything new.**
>
> **CALLABLE AND IT LINKS: 666 → 3,593**, 5.8% → **31.0% of the flat API.** A
> program calling `IsCharAlphaA` from `user32` and `GetSidLengthRequired` from
> `advapi32` builds and prints what C prints — **1, 0, 12, 28** — and against the
> old line the linker names both symbols unresolved.
>
> **NAMING A LIBRARY CHOOSES A DLL, AND THE LIBRARY SAYS WHICH.** An import
> library is an archive of short import objects, each binding one symbol to one
> DLL. So *which DLL does this name mean* is read, not inferred — and **155
> callable names are bound to DIFFERENT DLLs by different libraries**:
> `AbortPrinter` to `winspool.drv` and to `spoolss.dll`, the print client and the
> spooler's own side. Those get no `lib`, and the linker refuses the call rather
> than binding it to the wrong code.
>
> **THE FIRST RULE WAS A HEURISTIC AND WAS WRONG TWICE, found before this was
> committed.** It counted each library's DLLs, called the split bimodal, and
> treated a library naming many as a different deployment target. **20 libraries
> sit between 2 and 428** — `vfw32` binds three — and **`onecore.lib` binds
> `MulDiv` to `kernel32.dll` exactly as `kernel32.lib` does.** It reported 3,622.
>
> **So yesterday's projection was 233 generous**: *"about 3,826"* is 3,593.
>
> **No emitted program moves**: a program that calls no `lib` gets its old build
> script byte for byte, pinned by a test against the literal line.

## 1. What was hard-coded, and what it cost

`emit/target.go` wrote every Windows build script with one line:

```
link … main.obj kernel32.lib msvcrt.lib ucrt.lib vcruntime.lib legacy_stdio_definitions.lib -out:main.exe
```

A Win32 call is four steps and three of them already worked: the declaration
loads and type-checks, the backend writes `extern IsCharAlphaA: proc` — only for
what the program calls — and `ml64` assembles it. The fourth, `link`, must be
handed a library that defines the symbol, and that came from the constant.
structval-2026-09-12 measured the gap — **666 of 4,093 callable names were in one
of those five libraries** — and demonstrated both halves on `GetDpiForSystem`:
`LNK2019`, then 96 with `user32.lib` added by hand.

So "callable" was a property of the declarations, and 16.3% of it was a property
of a program. A host fact was living in Go, which is this repository's own rule
broken in its own emitter.

## 2. The format: two declarations, and the collection that already existed

```lisp
(link "kernel32" "msvcrt" "ucrt" "vcruntime" "legacy_stdio_definitions")
(prim IsCharAlphaA (int) int expr "mov rcx, %1\ncall IsCharAlphaA\nmovsxd %r, eax"
      (import "IsCharAlphaA") (lib "user32"))
```

**`lib` is `import`'s other half on a host that resolves at link time.** The x86
backend already put an import into a set when it emitted the call; the `lib` goes
into a second set at the same two sites, so declaring thousands of libraries
costs a program that calls none of them nothing. The line is `link` in declared
order, then each used `lib` not already present, sorted — a function of the
program and the target, so a program that calls nothing new gets the line it
always had.

**Two small decisions, each a host fact.** Library names compare lowercase,
because Windows compares them that way. And a repeated library is not an error: a
library is a set member, which is also why layers append `link` the way they
append `implements` — a set cannot collide.

**Only the x86-64 backend reads either field.** Go, Java and JavaScript resolve
imports with the host's own compiler or loader and have no line to build; a `lib`
there is accepted and ignored, as JavaScript ignores `import`.

The spec came first — target-files.md §6a — and its paragraph on what `lib`
claims was rewritten once, by §3.

## 3. Which library a generated declaration may name

A symbol is typically listed by several import libraries. `MulDiv` is in
`kernel32` and in ten others — `onecore`, `onecoreuap`, `windowsapp`,
`windowscoreheadless`, and their `_downlevel` and `_apiset` variants.
structval-2026-09-12 ranked by the **shortest name**, which picks `onecore` (seven
letters) over `kernel32` (eight).

### 3.1 The first rule, and how it was wrong

The first build read something the library says about itself: one
`__IMPORT_DESCRIPTOR_<dll>` per DLL it binds to. 362 libraries bind exactly one,
and the rule was *name the single-DLL library; refuse a name only an "umbrella"
has.* It reported **3,622**, and the result document said the split was bimodal.

**It was not, and checking the claim before recording it is what found it:**

| DLLs a library binds to | libraries |
|---:|---|
| 1 | 362 |
| 2 – 34 | 11 — `appnotify` 2, `vfw32` 3, `shcore` 6, `runtimeobject` 8, `ucrt` 14, `nanosrv` 34, … |
| 129 – 428 | 9 — `onecore` 129, `mincore` 209, `windowsapp` 275, `onecoreuap_apiset` 428, … |

`vfw32` is the Video for Windows library and binds three real DLLs; a name only it
listed was refused as if it came from an API-set umbrella. And the umbrellas are
not what the rule assumed either, which is the larger error.

### 3.2 The rule that replaced it: read the binding

**An import library is an archive of short import objects**, each an
`IMPORT_OBJECT_HEADER` (`0x0000`, `0xFFFF`) followed by the symbol name and the
DLL name. So the library states, per symbol, which DLL it resolves to. Read for
all 461:

```
MulDiv            kernel32.dll   via kernel32, onecore, onecoreuap, … (every library agrees)
AVIFileOpenA      avifil32.dll   via vfw32, avifil32
AbortPrinter      winspool.drv   via winspool, …
                  spoolss.dll    via spoolss
CM_Get_Version    cfgmgr32.dll   via cfgmgr32
                  setupapi.dll   via setupapi, onecore, …
```

**`onecore.lib` binds `MulDiv` to `kernel32.dll`.** Naming either library puts
the same DLL behind the call, so an "umbrella" was never the question. The
question is whether the libraries **agree about the DLL**:

| | callable names | |
|---|---:|---|
| a library the target links anyway lists it | **666** | named; adds nothing to the line |
| every library binds it to ONE real DLL | **2,927** | `(lib "…")`, the library binding the fewest DLLs |
| libraries bind it to two or more DLLs | **155** | refused |
| reachable only through an API set | **61** | refused |
| listed, and bound to no DLL | **17** | refused — a static library |
| no import library lists it | **267** | refused |
| **callable and it links** | **3,593** | **31.0% of 11,575** |

**The baseline goes first, over any binding**, for a reason that is not
convenience: a program on this target already imports from those five libraries,
so naming one binds nothing new. It settles `AcquireSRWLockExclusive`, bound to
`kernel32.dll` by kernel32.lib and to `vertdll.dll` by vertdll.lib, without anyone
choosing — and keeps a CRT name in `ucrt`, which binds 14 DLLs, from being
refused.

**Among libraries that agree, the one binding the fewest DLLs is named** —
kernel32.lib over onecore.lib, avifil32.lib over vfw32.lib. The same DLL answers
at run time either way; the rule only keeps the narrower library on the line.

**An API set is refused, and it did not have to be.** 61 names are bound only to
`api-ms-win-…` or `ext-ms-win-…` contracts, which the loader maps to whatever
implements them on the machine that runs the program. That links and usually
works; whether a program may ask for it is a target decision, not a generator's
guess.

### 3.3 The ties

| DLLs the libraries disagree between | callable names |
|---|---:|
| `cfgmgr32.dll` + `setupapi.dll` | 80 |
| `spoolss.dll` + `winspool.drv` | 28 |
| `bluetoothapis.dll` + `bthprops.cpl` | 8 |
| `kernel32.dll` + `lz32.dll` | 8 |
| `logoncli.dll` + `netapi32.dll` | 7 |
| `dsparse.dll` + `ntdsapi.dll` | 6 |
| `bcrypt.dll` + `ncrypt.dll` | 5 |
| `chakra.dll` + `jscript9.dll` | 3 |
| `davclnt.dll` + `ntlanman.dll` | 3 |
| `secur32.dll` + `sspicli.dll` | 3 |
| `winsta.dll` + `wtsapi32.dll` | 2 |
| `advapi32.dll` + `wer.dll` | 1 |

**A tie is two DLLs, and some of them are two different programs.**
`winspool.drv` is the print client API and `spoolss.dll` the spooler's side;
`chakra.dll` and `jscript9.dll` are two JavaScript engines. Others may be one
implementation reached through two DLLs — `netapi32.dll` and `logoncli.dll` look
like that — and then either would work; that was not measured, because it needs
the DLLs' own export tables rather than the libraries. **Nothing in the libraries
distinguishes the two kinds**, and the SDK's documentation names the DLL in a *Requirements*
row that no header carries. **A generator does not make a claim it cannot
justify** (struct-literals.md's rule, and `pure`'s before it), so a tied
declaration is emitted with no `lib`: it loads and type-checks, and a program
calling it is refused by the linker instead of bound to the wrong code. Some of
those 155 are refused needlessly; none is bound wrongly.

The count went up under the better rule — 130 ties under the descriptor count,
155 under the binding — because the binding sees disagreements the count could
not: `lz32.lib` binds `LZOpenFileA` to `lz32.dll` while an umbrella binds it to
`kernel32.dll`, and the count saw only that `lz32` was a single-DLL library.

### 3.4 The correction to yesterday

structval-2026-09-12 §6 projected **666 → about 3,826**, which is 666 plus every
name listed by *some* other import library. **The measurement is 3,593, and the
233 are §3.2's refusals** outside the 267 that were already counted: 155 ties, 61
API-set-only, 17 static. The shape of structlit-2026-09-10's +486 that built as
+229 — a projection counts what exists and a build counts what can be named.

Its ranked table was wrong in two rows as well: **`onecore` 281 and `mincore` 197
are the shortest-name rule attributing `kernel32` and `user32` names to
umbrellas.** Ranked by the library a declaration now names, neither appears;
`setupapi` is 160 and `advapi32` 147. Both corrections are annotated where they
stand.

## 4. The witness

`gauntlet/stdlib/acceptance/link-line.oro`, the eleventh acceptance program:

```lisp
(seq (fmt.print-int (u.IsCharAlphaA 65))
     (fmt.print-int (u.IsCharAlphaA 49))
     (fmt.print-int (s.GetSidLengthRequired 1))
     (fmt.print-int (s.GetSidLengthRequired 5)))
```

| | host (C, this machine) | Oroboros, `lib` declared | Oroboros, no `lib` |
|---|---|---|---|
| `IsCharAlphaA('A')` | 1 | **1** | — |
| `IsCharAlphaA('1')` | 0 | **0** | — |
| `GetSidLengthRequired(1)` | 12 | **12** | — |
| `GetSidLengthRequired(5)` | 28 | **28** | — |
| build | | links | **`LNK2019` on both symbols** |

**Two libraries, four answers, two per declaration**, so neither call is right
by accident, and the failure against the old line is at LINK time with both
names — the failure the bug had. Each witness is bound to one DLL by every library
that lists it, and neither is in the baseline. `PathIsRelativeA` was the first
choice and is not in the generated set at all: `shlwapi.h` declares it through
`LWSTDAPI_(BOOL)`, which the survey's pattern does not read.

| | |
|---|---|
| compiler | `emit/target.go` +61/−4 (a field, a list, a parse case, the script), `emit/asm.go` +12/−3 (a set, two collection sites) |
| format | target-files.md §6a; `windows.oro` +7, the five libraries moved out of Go |
| emitted programs | **unchanged**: a program with no `lib` gets the old line byte for byte, pinned against the literal |

| Oroboros | 9 lines, one program |

**The survey stopped holding its own copy of the baseline.** It had a map of the
five libraries beside the constant in the emitter — a host fact written twice,
which is two facts that can disagree. It now reads `(link …)` out of
`targets/windows/windows.oro`, the one place the fact lives.

**And the balance, against the standing criticism**: 73 lines added to the
compiler, 260 to the survey and 9 of Oroboros. The compiler change is the one the
measurement pointed at, and it removed a host fact from Go; the tooling grew
again, and this time half of what it grew is a reader for a file format the host
defines, which is the kind of survey code that cannot disagree with the host.

## 6. What this leaves

**The 155 ties have a source of truth and it is prose.** The documentation's
*Requirements — DLL* row names the DLL for every one. Reading it would be a
fourth input after headers, import libraries and MSVC, and the only one that is
not machine-readable. Not attempted.

**The 267 no library lists are unexamined.** They are declared in `um/` headers
and bound by nothing under `Lib/`. The likely account is kernel-mode and driver
interfaces — `winddi.h`'s `Eng*` functions live in `win32k`, which no user-mode
program links — and that is a guess until someone counts it.

**An API set is a target decision nobody has made.** `(link "onecore")` in a
project layer would put every contract-bound name on the line today,
deliberately; the generator refusing them is the absence of that decision, not an
argument against it.

**What the acceptance suite still is: eleven programs against 47,000 generated
declarations.** The two checkable halves of a generated Win32 declaration are
now its TYPES (MSVC can compile a call from its signature) and its LIBRARY (the
linker can resolve it) — both questions the host answers in under a minute, and
neither is yet asked of all 10,479.
