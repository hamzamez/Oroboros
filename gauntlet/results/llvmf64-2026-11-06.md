# llvmf64-2026-11-06: the roundings onto F64 on the LLVM layer

6b′ step 3, its second part (hamza, 2026-11-06: "go ahead with f64-round. always mathematical and
algebraic"). `f64-round`, skipped on windows because no declaration there realized a rounding onto
F64, runs there and agrees with Go, JavaScript and the JVM on all seven roundings.

## The algebra

**A rounding is realized by a declaration's `ensure`** (ADR 0086, numbers.md §6.2):
`ensure r == round(F64, t)` is the equation round(F64, t) = f(x̄), read right to left, so wherever a
program writes round(F64, u) and u matches t, it is that call. The LLVM layer needs Σ_LLVM's
operations whose meaning is such a rounding. LangRef gives them. LLVM's default floating-point
environment rounds to nearest, ties to even, with traps disabled and the status flags unobserved.
There:
- `fadd`, `fsub`, `fmul` and `fdiv` on `double`, with no fast-math flag, are IEEE 754's correctly
  rounded operations (§4.3.1), so `fadd` realizes round(F64, a + b), and so on;
- without the `contract` flag no two fuse, so two roundings are two instructions, which a
  fused-multiply-add would not be: round(F64, round(F64, a·b) + c) ≠ round(F64, a·b + c) in general;
- `sitofp` of n ∈ ±2⁵³ is exact, since every such integer is a double: round(F64, n) = n.

The obligations (each rounding finite, each divisor not zero) are the rounding's own, decided where
the program writes it. So no instruction is ever asked for ±∞, NaN or −0, and the environment's flags
have nothing to record.

**A comparison is N's at a sort.** The language's `= < <= > >=` are N's, and a program uses them at
two sorts: the word, an integer, and F64, a double. Σ_L is a many-sorted signature, and an
interpretation ι : Σ_L → T(Σ_H) maps each operation at each sort, so `<` at F64 is a realization of its
own, `fcmp olt`. On the LLVM layer ADR 0088's chooser takes a later realization where the facts prove
its domain. A domain is a sort before it is a range: a parameter set F64 holds of exactly the operands
the IR types as doubles, and an integer set holds of none of them. So the chooser now tests the sort
(`sortsHold`), then the interval, then the `where`.
- **The first realization realizes its name at its own sort only.** A double compared through the
  word's `icmp` is a reading of its bits as an integer, which is not N's order (−0.0's bits are
  2⁶³ as an unsigned integer, and negative doubles order backwards as signed ones). An operation at a
  sort no realization takes is refused, naming the sort.
- **Which predicate.** IEEE compares finite values as reals (§5.11), and `fcmp oeq` reads −0 = +0,
  which is the identification d makes (d(−0) = d(+0) = 0). NaN is not in F64, so each ordered
  predicate agrees with its unordered twin on every pair the language can make. The ordered one is
  false on NaN, so it claims nothing about a value F64 lacks. `≠` is D's ¬∘=, `fcmp oeq` with its arms
  swapped.

## What was built

- **`targets/llvm/instructions.oro`**:
  - `fadd fsub fmul fdiv` (a, b ∈ F64), each `ensure r == round(F64, a ∘ b)`;
  - `fint(n ∈ -2^53..2^53)`, `sitofp`;
  - `f_eq f_lt f_le f_gt f_ge`, `fcmp` with the ordered predicates.
- **`targets/llvm/llvm.oro`**: `realize = = llvm.eq, llvm.f_eq` and likewise for `< <= > >=`.
- **`ir/realize.go`**:
  - `sortsHold`, the sort test, used by `narrowest` before the interval;
  - on the first realization, the refusal "OP on F64: no realization of target T takes operands of
    that sort";
  - `PlantSortFault`.
- **`ir/print.go`, `ir/read.go`**: a comparison carries its realization in IR_P's text,
  `(gt via llvm.f-gt %a %b)`, as an arithmetic operation does.
- **llvm.md §3b**, numbers.md §6.2, and the case's skip replaced by a note.

## Witnesses

- **`TestAComparisonIsRealizedAtItsSort`** (ir/llvm): one function compares two doubles with `<` and
  `=` and two integers with `<`, and prints `fcmp olt double`, `fcmp oeq double` and `icmp slt i64`,
  and no `icmp` of a double. Then:
  - with F64's realization of `<` taken from the target, the program is refused, naming F64;
  - **planted fault**: with the first realization's sort not tested, it prints `icmp slt double`,
    which is what the refusal prevents.
- **`f64-round`** on four targets: ties to even both ways (1 + 2⁻⁵³ and (1 + 2⁻⁵²) + 2⁻⁵³), ÷ off a
  tie on both signs, the literal 0.1 rounded once in the scope, 3 · 0.1 at a tie, and IEEE's
  0.30000000000000004 from three roundings. That last one is what a fused or reassociated sum would
  change.
- **And it is in the text** (ADR 0038): the same test prints IR_P, finds `via llvm.f-lt` in it, reads it
  back and prints the same function from it. With the reader's `via` planted out, it fails ("via is not
  a value"). A first version of this witness, `search` added to `ir`'s round-trip corpus, passed with
  the fault planted: that corpus is lowered and never realized, so its text has no `via` to lose. It
  was removed.
- **Probed** (not kept as tests): `≠`, a double carried through a loop's slots and rounded each
  iteration (`fmul double %x, 0x3FE0000000000000`), a branch selecting one of two doubles. All print as
  §3b says.

## What failed first

- **The probe compiled to nothing**: `run` is not an entry point, so `gen` emitted no function and
  no refusal. The differential wraps `run` in a `main`, and run there the case met the refusal it
  should have: "no declaration of target windows realizes it".
- **With the roundings declared, every obligation was proven (77 of 77 operations), and LLVM refused
  the text**: `icmp eq double %v50, 0x3FF0000000000000`. The comparison of a rounding with its
  expected double had been realized by `llvm.eq`, the word's, because the chooser read only integer
  intervals, and a double has none, so it fell through to the first realization. This was a soundness
  hole, not only a failure: on a host that does not type its instructions, the double would have been
  compared as an integer. Here LLVM's verifier was the only check, and it is not ours.

- **The printer did not factor through the text.** `cmd/check`'s IR step reprinted `search` from IR_P's
  text and got `icmp sgt double`: the IR's printer and reader carry `via` for the arithmetic operations
  only, and no comparison had had a later realization before. A comparison now prints and reads its
  `via` (`(gt via llvm.f-gt %12 %1)`); one without prints as before.
- **The baseline had shipped the bug.** `search` on windows was in the accepted emission printing
  `icmp sgt double %v12, %v1`, which clang refuses ("icmp requires integer operands"). The emission
  step compares text and never assembles it, and no differential case runs `search` on windows, so
  nothing had noticed. Assembling every emitted windows file is now in the plan, beside re-running
  skips (CLAUDE.md 6b′ step 3).

## What was measured

- `f64-round` agrees on go, js, java and windows.
- **The gauntlet's float programs emit on windows**: `dot`, `centroid` and `smooth-go`, refused before
  ("no declaration of target windows realizes it"), and `search`, now `fcmp ogt`. All four assemble
  with clang -O2.
- **Counts**: 5,009 of 5,063 operations proven (was 4,999 of 5,053), 497 of 521 loops (was 493 of
  517). The +10 operations and +4 loops are the three new programs' (dot 1 and 1, centroid 1 and 1,
  smooth 8 and 2), all proven.
- **Emission**: 4 changes, the four programs above. The gauntlet is byte-identical. Compile time is
  1.14× (gate 1.5×).
- **Not measured**: the float programs' speed on windows against hand-written code. That is this
  step's later part, with the rest of the gauntlet's programs.

## Not done here

- **Negation of a double** is refused before any target ("returns N, but its header declares F64"):
  the checker's N at its boundaries, a loose end of the numbers round (CLAUDE.md, waiting on a
  trigger). `round(F64) { -a }` is the spelling that works.
- **A host's double as a type**, `sqrt` and a fused multiply-add as realizations (`llvm.sqrt.f64` and
  `llvm.fma.f64` are intrinsics LLVM has), the directed modes. These wait on their triggers, as on the
  other targets.
- **A table of doubles** (`Array(F64)`), which waits on N's subsets, as everywhere.
