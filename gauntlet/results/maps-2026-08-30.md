# The three map measurements, re-taken — 2026-08-30

[growth.md §4](../../docs/growth.md) said three of the four numbers a map design would rest on are
stale and one is known-unstable, and that re-taking them comes first. Done. **All three moved, one of
them reversed, and one of growth.md's own predictions was wrong.**

Method throughout is the corrected one that
[karatsuba-2026-08-30 §3b](karatsuba-2026-08-30.md) forced: one variant per process on V8,
**time-budgeted** rather than count-budgeted, and the result escaping into a sink that is read
afterwards.

---

## 1. Java: `merge` against `getOrDefault`+`put`

`gauntlet/java/MergeCheck.java`, JDK 17, 65,536 words over 500 distinct keys.

| | ns |
|---|---|
| unfused `put(w, getOrDefault(w,0)+1)` | 1,546,223 |
| **fused `merge(w, 1, Integer::sum)`** | **1,261,935** |

**`merge` is 1.22× faster.** Baseline R5 recorded it **2.59× slower**. With R5's own functions —
which split the text *inside* the timed region — it is 0.95×, so merge still wins either way.

**Correction to this document as first written**: it said `targets/java/util.oro` declares the unfused
idiom because of R5. It does not — native-java-2026-08-25 already caught that and the file has
declared **both** forms since, with the reversal recorded in its comment. Nothing needs changing
there; what needed changing was this paragraph.

**This is the second independent re-take to disagree with R5**, after the 1.19× recorded in
CLAUDE.md. A number that has now failed to reproduce twice should stop being quoted: the honest
statement is that the two forms are within about 20% of each other on JDK 17 and the ordering has
flipped since R5.

It remains [ADR 0008](../../docs/decisions/0008-measurement-over-principle.md)'s best example, just
not in the direction it was recorded — *the rule survives its own example* by being applied to it.

## 2. JavaScript: `Map` against an object

`gauntlet/js/maps.mjs`, 65,536 words, 320 distinct.

| | ns | per word |
|---|---|---|
| `new Map()` | 1,158,288 | 17.7 |
| `Object.create(null)` | 740,865 | 11.3 |
| **plain `{}`** | **718,423** | **11.0** |

**The object still wins, by 1.56×.** The first baseline recorded **3.25×**, so the direction survives
and the magnitude has roughly halved — V8 has had years of `Map` work since.

**And a plain `{}` beats a null-prototype object**, by 3%. Small, but it is the opposite of the
folklore that `Object.create(null)` is the fast dictionary, and it means the target does not need to
reach for the unusual constructor.

### 2a. Integer keys are a different question, and a bigger gap

This is the case [growth.md §5](../../docs/growth.md) proposes building **first**, and it was not
measured before:

| | ns | per key |
|---|---|---|
| `Map` with number keys | 1,308,360 | 20.0 |
| **object with number keys** | **356,978** | **5.4** |

**3.67× — more than twice the string-key gap.** V8 stores integer-keyed properties in the *elements*
backing store, which is a dense or sparse array rather than a hash. So `(map int V)` on JavaScript
should lower to an object, and the margin for getting that right is larger than for strings.

## 3. Count-then-build against append — a growable array is not needed

The measurement that decides whether growth enters the language at all.

**Go**, 65,536 elements, half surviving:

| | ns | allocs |
|---|---|---|
| `append` onto nil (growing) | 208,013 | 17 |
| `append` with capacity | 101,655 | 1 |
| **count, then build** | **70,403** | 1 |

**2.95× faster than growing `append`, and 1.44× faster than `append` with the capacity already
right.** At 1,000 elements it is 1.67× and 1.49×. Two passes beat one pass plus growth, and not
narrowly: the counting pass is a branch-predictable scan with no stores, and the fill writes into an
exactly-sized allocation.

**JavaScript**, same shape:

| | ns |
|---|---|
| `push` onto `[]` | 136,357 |
| **count, then build into `new Array(n)`** | **129,135** |

**1.06× — parity, or slightly better.**

### growth.md predicted this would lose on JavaScript, and the first run agreed for the wrong reason

The prediction was *"two passes win on Go and windows for small elements and lose on JavaScript"*. The
first run appeared to confirm it — `push` at 136,110 against count-then-build at 207,827, a 1.53× win
for growth.

**That was a confound, not a result.** `filterPush` produces a plain `Array` and the count-then-build
form produced a `Float64Array`, so the comparison was array-kind against array-kind, not growth
against two passes — and V8 cares about that enormously, since a packed `Array` of small integers is
Smi-backed. Made like-for-like, both producing a plain `Array`, the ordering reverses.

Same lesson as §5b of the Karatsuba result, and the third time this session: **a comparison that
changes two things at once measures neither.**

---

## What this settles

**A growable array is not needed.** Count-then-build is *faster* on Go and at parity on JavaScript, so
the workaround growth.md called "parity-preserving" is better than that. Design option **D3 is
withdrawn** until a program appears that count-then-build genuinely cannot express — reading input to
EOF being the named candidate.

**The map is confirmed as the primary gap**, and it now has numbers to design against rather than
stale ones:

- JavaScript lowers `(map K V)` to a **plain object**, not `Map` — 1.56× on strings and **3.67× on
  integers**;
- Java should prefer **`merge`** — already declared beside the unfused pair, so this is a note for
  whatever selects between them, not a target-file change;
- Go's `map` was never in question.

**And `(map int V)` first is the better call than it looked.** It was chosen to dodge the string
question; it turns out to be the case where the host choice matters most.

## What is still not measured

Our own hash table against the host's, which is the parasite test: if ours came close on Go, that
would be evidence the rule is being applied to something the hosts are not actually good at. It needs
the map to exist first, so it is the measurement to take immediately *after* the build rather than
before it.
