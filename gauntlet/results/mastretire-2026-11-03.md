# mastretire-2026-11-03: MASM retired; the windows target prints LLVM IR

llvm.md §9 step 4, ADR 0080 item 5. Two printers, h_x86 and h_LLVM, each a map IR_P → programs
preserving meaning; parity was measured (llvm-2026-11-02), so h_x86 goes.

## The algebra

A program over Σ_x86 (`x64.add`, `x64.setl`) is ported by ι⁻¹. Where the target states
x64.add = ι(+), the name becomes `+`, which moves the program into Σ_L, where it means the same on
every target. A name with no preimage (`x64.movb` on a `VirtualAlloc` pointer) has its language form
in a buffer, `c[j] := true`, so the three Windows sieves became one, `examples/table/sieve-win.oro`.

**The Win32 survey's writer** (`gauntlet/stdlib/win32.go`, `llvmCall`) is the same map for Win32. A
function is `declare dllimport T @F(…)` and one `call`, and the calling convention is LLVM's to lower.
What remains is each value's set:

- an integer of w < 64 bits is its C range, passed by `trunc`, exact since trunc ∘ embed = id on it.
  MASM passed the low bits of any `Int`, a silent wrap;
- a narrow result is its C range, by `sext` or `zext`;
- pointers are `ptr`, and a 64-bit integer is the word.

**A string carries a NUL after its bytes** (llvm.md §4): (len, bytes, 0), whose abstraction function
ignores the sentinel. A literal, `string_of` and `++`, the only producers, write it. So s + 8 is the C
string `LPCSTR` reads, exactly on B*₀, the strings with no NUL.

## What was measured

- **The survey**: every pinned figure unchanged: 90.5% declarable, 35.4% callable, 31.0% callable and
  linked. The figures describe the API and the language, not the printer.
- **The Win32 acceptance programs**: all seven pass, and none needs `-checked` any more. Each result
  carries its C range, which the decision reads; on MASM every one needed it.
- **A new witness, `c-string`**: `lstrlenA` of a literal, a `string_of` and a `++` equals each one's
  length (5, 2, 5). **Planted fault**: without the sentinel it printed 14 for `string_of`. The `++`
  leg still printed 5, because fresh heap memory was zero, so that leg is weak.
- **The differential suite**: four targets agree on every case. `bits-edges` now runs on windows (`>>`
  past 63 is total there); its skip was MASM's.
- **The probe** of the 15 cases skipped on windows, run there alone:
  - 1 runs (`bits-edges`);
  - 4 need the unsigned word on windows (`codecs`, `fnv64`, `fnv64-fold`, `pairs`);
  - 7 need `big_str`;
  - 1 needs F64's roundings;
  - 2 need `os/host`.

  Each skip now states its own reason.
- **The Windows sieve**: 0.71 and 0.68 of hand-written MASM in two sweeps of 21 interleaved process
  runs, both printing 1798400.
- **Counts**, on the corpus without MASM's rows: 4,983 of 5,043 operations, 489 of 513 loops.
- **Emission**: the only windows text that changed is the sentinel. Compile time 1.05×.

## A wall, for hamza

A C string's domain is **B*₀**, the free submonoid generated by the non-NUL scalars. Membership is
closed under `++`, and `string_of(c)` is in it iff c ≠ 0, so it is a refinement sort (Freeman and
Pfenning 1991), decidable by evaluation for a literal. The language cannot state it.

Today a string holding a NUL reaches an `LPCSTR` parameter and C reads the prefix, as it did on MASM.
**Recommendation**: the set CStr = B*₀ as a refinement of String, derived through `++` and
`string_of` and proven for literals, refused otherwise, or checked under `-checked`, as integers are.
The same mechanism serves "Validity through functions that preserve it".

**And a second hole, measured** (2026-11-04): Win32's `A` functions read their bytes in the process's
ANSI code page, not UTF-8. `CreateFileA("tést.txt", …)` created a file named `tÃ©st.txt`: the UTF-8
bytes C3 A9 read in code page 1252. So the identity s ↦ s + 8 is the C string only on ASCII ∩ B*₀,
today as on MASM. It is the identity on all of B*₀ once the program's manifest declares
`<activeCodePage>UTF-8</activeCodePage>` (Windows 10 1903 and later), embedded at link. Otherwise a
non-ASCII string needs a codec, CP_ACP's or the `W` functions' UTF-16.

**The encodings between the language's strings and Win32's**, each a map of its own:

| direction | Win32's form | the map | total? |
|---|---|---|---|
| language → Win32 | `LPCSTR` | the identity on the representation, restricted to B*₀ (with a UTF-8 code page) | partial: its domain is the refinement |
| language → Win32 | `(LPCVOID, DWORD)`, WriteFile | a segment, as built | total |
| language → Win32 | `LPCWSTR` | UTF-8 → UTF-16, a copy | partial on B*₀, a codec |
| language → Win32 | a double-NUL list (`lpstrFilter`, `REG_MULTI_SZ`, an environment block) | (B*₀)* → bytes, s₁ 0 … sₙ 0 0 | total on its domain, a list of C strings |
| Win32 → language | a C string returned or filled | strlen, then a copy into a counted string | total, lands in B*₀ |

A string holding a NUL is a value the language needs (U+0000 is a scalar, and a format is free to hold
one). But it has no faithful C string: any map into C strings that accepts it loses information, by
truncation or by an escape that Win32 does not read. The Win32 calls that take NULs inside take a
different type, a list of NUL-free strings, and that is what a program should pass.

## Not built

- Floats in the survey: still refused, now because a host's double is not yet a type the language
  holds.
- Σ_LLVM's families (step 3), by demand.
