## 1. The theorem

For a reference variable `v` and a set `S` of names already known `≥ v`, define `e ⊒ S`:

| | |
|---|---|
| 1 | `x ⊒ S` if `x ∈ S` |
| 2 | `(+ a c) ⊒ S`, `(+ c a) ⊒ S` if `a ⊒ S` and `c` is a literal `≥ 0` |
| 3 | `(- a c) ⊒ S` if `a ⊒ S` and `c` is a literal `≤ 0` |
| 4 | `(if _ p q) ⊒ S` if `p ⊒ S` **and** `q ⊒ S` |
| 5 | `(let d (fn (x) b)) ⊒ S` if `b ⊒ S ∪ {x}` when `d ⊒ S`, else `b ⊒ S` |

**Lemma A.** If every `x ∈ S` has `⟦x⟧σ ≥ ⟦v⟧σ` and `e ⊒ S`, then `⟦e⟧σ ≥ ⟦v⟧σ`.
*Proof.* Structural induction. (1) immediate. (2) `⟦a⟧+c ≥ ⟦a⟧ ≥ ⟦v⟧` since `c ≥ 0`; symmetric case
likewise. (3) `⟦a⟧−c ≥ ⟦a⟧` since `c ≤ 0`. (4) whichever branch is evaluated satisfies it by the
hypothesis. (5) if `d ⊒ S` then `⟦x⟧ = ⟦d⟧ ≥ ⟦v⟧`, so `S ∪ {x}` meets the premise. ∎

**Theorem (loop monotonicity).** Let `L = (loop (fn (v₁…vₘ) B) z₁…zₘ)`. Position `k` is
*non-decreasing* if for every `again` in `B`, reached with let-environment `S ⊇ {vₖ}`, the argument
`aₖ ⊒ S`. Then at every iteration `⟦vₖ⟧ ≥ ⟦zₖ⟧`.
*Proof.* Induction on the iteration count. At `n = 0`, `vₖ` is `zₖ`. At `n → n+1` the next value is
`⟦aₖ⟧` for some `again`; by the induction hypothesis `⟦vₖ⟧ ≥ ⟦zₖ⟧`, so `{vₖ}` meets Lemma A's
premise and `⟦aₖ⟧ ≥ ⟦vₖ⟧ ≥ ⟦zₖ⟧`. ∎

**Corollary (exit bound).** If in addition every exit expression `e` of `L` satisfies `e ⊒ {vₖ}`,
then `⟦L⟧ ≥ ⟦zₖ⟧`.
*Proof.* An exit is evaluated at some iteration where `⟦vₖ⟧ ≥ ⟦zₖ⟧` by the theorem; Lemma A gives
`⟦e⟧ ≥ ⟦vₖ⟧`. ∎

The corollary is what is used. It turns a loop into a **lower bound on the value it produces**, which
is what a caller needs and what an interval cannot express when the bound mentions a variable.

**Caveat, stated not hidden.** Rules 2 and 3 use `a + c ≥ a`, arithmetic over ℤ. It is false under
wrapping. Our integers are exact inside [ADR 0012](../../docs/decisions/0012-portable-integer-range.md)'s
window and the target's outside it — the same caveat the rest of the interval layer carries.

## 2. The corollary needs BOTH halves, and a test for one would pass a wrong program

```lisp
(loop ((j i)) (go.>= j 10) 0 else (again (go.+ j 1)))
```

Every step increases `j`, so the theorem holds — and the loop returns **0**, which is not `≥ i`.
Checking the steps alone would accept it. `TestLoopLowerBound` carries this case for that reason,
alongside a decreasing step, a conditional with one bad branch, an opaque step, and `j + k` where
`k` is a variable rather than a literal.

`TestAtLeastIsTheRelationAndNothingMore` checks the relation directly — thirteen cases, including
that `(go.- 3 j)` is refused because subtraction is not commutative, and that a literal says nothing
about `j`.

## 3. Two places needed it, not one

`stepOf` reads a variable's per-iteration change, and `relate` builds the size-change arc. They
derive the same thing separately, and **both** had to learn the loop case — wiring only `stepOf`
moved nothing, and the diagnostic said so:

```
before   no descent on the cycle loop(stk,i,nt,sp,mx,ok): nt>nt
after    no descent on the cycle loop(...): stk>=stk i>=i nt>nt sp>=sp mx>=mx ok>=ok
```

`i` produced **no arc at all** before; it produces `i>=i` after. The arc is only sound for the
ascending measure: a lower bound says nothing about descent when the measure is `+v`, because
`v + c` with `c ≥ 0` is not smaller than `v`.

## 4. `i>=i` is the truth, and the fix was in the PROGRAM

`>=` rather than `>` is not a weakness in the derivation. `scan-run` starts at `i` and returns `i`
when the first byte fails its predicate, so `i' > i` is **false in general** — and the analysis was
right to refuse it.

What makes it true is a fact in the caller: the clause fires only when `(src i)` already satisfies
the predicate. Testing it again is redundant, so the scanner can start one byte further on:

```lisp
(numeric? (src i)) (again stk (scan-run src (go.+ i 1) numeric?) …)
```

Identical answers, one fewer predicate test, and the init becomes `i + 1` — so the corollary gives
`i' ≥ i + 1 > i`, the size-change witness. **64.5% → 90.9%, and 15 of 20 loops → 20 of 20.**

> This is the shape worth carrying. The analysis did not fail to prove a true thing; it declined to
> prove a false one, and the diagnostic named the variable. The repair was a line the program wanted
> anyway.

## 5. What is left, and it is one shape

Fifteen operations remain unbounded in the tokeniser and every one of them traces to `mx`, the
running maximum:

```lisp
(if (go.> (go.+ sp 1) mx) (go.+ sp 1) mx)
```

`mx` is bounded in truth — it only ever takes `sp + 1`, and `sp < cap` — but its update mentions
**itself**, so `stepOf` finds no step, the trip count cannot bound it, and the fixpoint widens it to
infinity before `sp` narrows.

A variable whose update is `(if c e v)` or `(if c v e)` is a **running extremum**, and its bound is
the join of its initial value with the other branch. That needs no widening and is the next small
theorem. It matters beyond neatness: one unbounded operation anywhere refuses index narrowing for a
whole method ([indexnarrow §1](indexnarrow-2026-08-27.md)), so the tokeniser still reports
`idx -inf..+inf` and Java's parity gap on it is unchanged.
