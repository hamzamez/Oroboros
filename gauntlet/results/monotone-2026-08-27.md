## 1. The theorem

For a reference variable `v` and a set `S` of names already known `≥ v`, define `e ⊒ S`:

| | |
|---|---|
| 1 | `x ⊒ S` if `x ∈ S` |
| 2 | `(+ a c) ⊒ S`, `(+ c a) ⊒ S` if `a ⊒ S` and `c` is a literal `≥ 0` |
| 3 | `(- a c) ⊒ S` if `a ⊒ S` and `c` is a literal `≤ 0` |
| 4 | `(if _ p q) ⊒ S` if `p ⊒ S` **and** `q ⊒ S` |
| 5 | `(let d (fn (x) b)) ⊒ S` if `b ⊒ S ∪ {x}` when `d ⊒ S`, else `b ⊒ S` |

**Lemma A.** If every `x ∈ S` has `⟦x⟧σ ≥ ⟦v⟧σ` and `e ⊒ S`, then `⟦e⟧σ ≥ ⟦v⟧σ`.
*Proof.* Structural induction. (1) immediate. (2) `⟦a⟧+c ≥ ⟦a⟧ ≥ ⟦v⟧` since `c ≥ 0`; symmetric case
likewise. (3) `⟦a⟧−c ≥ ⟦a⟧` since `c ≤ 0`. (4) whichever branch is evaluated satisfies it by the
hypothesis. (5) if `d ⊒ S` then `⟦x⟧ = ⟦d⟧ ≥ ⟦v⟧`, so `S ∪ {x}` meets the premise. ∎

**Theorem (loop monotonicity).** Let `L = (loop (fn (v₁…vₘ) B) z₁…zₘ)`. Position `k` is
*non-decreasing* if for every `again` in `B`, reached with let-environment `S ⊇ {vₖ}`, the argument
`aₖ ⊒ S`. Then at every iteration `⟦vₖ⟧ ≥ ⟦zₖ⟧`.
*Proof.* Induction on the iteration count. At `n = 0`, `vₖ` is `zₖ`. At `n → n+1` the next value is
`⟦aₖ⟧` for some `again`; by the induction hypothesis `⟦vₖ⟧ ≥ ⟦zₖ⟧`, so `{vₖ}` meets Lemma A's
premise and `⟦aₖ⟧ ≥ ⟦vₖ⟧ ≥ ⟦zₖ⟧`. ∎

**Corollary (exit bound).** If in addition every exit expression `e` of `L` satisfies `e ⊒ {vₖ}`,
then `⟦L⟧ ≥ ⟦zₖ⟧`.
*Proof.* An exit is evaluated at some iteration where `⟦vₖ⟧ ≥ ⟦zₖ⟧` by the theorem; Lemma A gives
`⟦e⟧ ≥ ⟦vₖ⟧`. ∎

The corollary is what is used. It turns a loop into a **lower bound on the value it produces**, which
is what a caller needs and what an interval cannot express when the bound mentions a variable.

**Caveat, stated not hidden.** Rules 2 and 3 use `a + c ≥ a`, arithmetic over ℤ. It is false under
wrapping. Our integers are exact inside [ADR 0012](../../docs/decisions/0012-portable-integer-range.md)'s
window and the target's outside it — the same caveat the rest of the interval layer carries.

## 2. The corollary needs BOTH halves, and a test for one would pass a wrong program

```lisp
(loop ((j i)) (go.>= j 10) 0 else (again (go.+ j 1)))
```

Every step increases `j`, so the theorem holds — and the loop returns **0**, which is not `≥ i`.
Checking the steps alone would accept it. `TestLoopLowerBound` carries this case for that reason,
alongside a decreasing step, a conditional with one bad branch, an opaque step, and `j + k` where
`k` is a variable rather than a literal.

`TestAtLeastIsTheRelationAndNothingMore` checks the relation directly — thirteen cases, including
that `(go.- 3 j)` is refused because subtraction is not commutative, and that a literal says nothing
about `j`.

## 3. Two places needed it, not one

`stepOf` reads a variable's per-iteration change, and `relate` builds the size-change arc. They
derive the same thing separately, and **both** had to learn the loop case — wiring only `stepOf`
moved nothing, and the diagnostic said so:

```
before   no descent on the cycle loop(stk,i,nt,sp,mx,ok): nt>nt
after    no descent on the cycle loop(...): stk>=stk i>=i nt>nt sp>=sp mx>=mx ok>=ok
```

`i` produced **no arc at all** before; it produces `i>=i` after. The arc is only sound for the
ascending measure: a lower bound says nothing about descent when the measure is `+v`, because
`v + c` with `c ≥ 0` is not smaller than `v`.

## 4. `i>=i` is the truth, and the fix was in the PROGRAM

`>=` rather than `>` is not a weakness in the derivation. `scan-run` starts at `i` and returns `i`
when the first byte fails its predicate, so `i' > i` is **false in general** — and the analysis was
right to refuse it.

What makes it true is a fact in the caller: the clause fires only when `(src i)` already satisfies
the predicate. Testing it again is redundant, so the scanner can start one byte further on:

```lisp
(numeric? (src i)) (again stk (scan-run src (go.+ i 1) numeric?) …)
```

Identical answers, one fewer predicate test, and the init becomes `i + 1` — so the corollary gives
`i' ≥ i + 1 > i`, the size-change witness. **64.5% → 90.9%, and 15 of 20 loops → 20 of 20.**

> This is the shape worth carrying. The analysis did not fail to prove a true thing; it declined to
> prove a false one, and the diagnostic named the variable. The repair was a line the program wanted
> anyway.

## 5. The running extremum, which was the whole residue

Fifteen operations remained unbounded in the tokeniser and **every one traced to `mx`**, the running
maximum:

```lisp
(if (go.> (go.+ sp 1) mx) (go.+ sp 1) mx)
```

The `else` branch is `mx` itself, so in the fixpoint `next[mx] ⊇ cur[mx]` **always**. Widening throws
the bound to infinity, and the narrowing phase — which accepts only a value *contained* in the
previous one — can never take it back. The pass-through pins it.

**Definition.** Position `k` is **self-contained** if every `again` argument `aₖ` is built from `vₖ`
and expressions not mentioning `vₖ`, using only `if` — whose **condition** may mention `vₖ`, since a
condition produces no value — and `let` whose bound value is `vₖ`-free. Its **update set** `U(aₖ)` is
the `vₖ`-free leaves.

**Theorem (reachable set).** For a self-contained position, at every iteration
`⟦vₖ⟧ ∈ {⟦zₖ⟧} ∪ ⋃U`.
*Proof.* Induction on the iteration count. At `n = 0` it is `⟦zₖ⟧`. At `n → n+1` the new value is
`⟦aₖ⟧`, which by the structure of `aₖ` is either `⟦vₖ⟧` — in the set by the induction hypothesis — or
`⟦e⟧` for some `e ∈ U`. ∎

**Corollary.** `hull({zₖ} ∪ U)` is sound, **exact in one step**, and needs no widening. Because it
no longer mentions `cur[k]`, it *narrows* as the other variables narrow — which is exactly what the
pass-through was preventing.

The recurrence is not `v' = f(v)` where `f` can grow. It is `v' ∈ {v} ∪ U`, so the reachable set is
closed after one step and a fixpoint was never needed.

| `examples/json/tokenize.oro` | ops bounded | loops | index range |
|---|---|---|---|
| before monotonicity | 64.5% | 15/20 | −inf..+inf |
| + monotonicity | 90.9% | 20/20 | −inf..+inf |
| **+ running extremum** | **100%** | **20/20** | **0..1321** |

**Every integer operation in the JSON tokeniser is now proven inside the portable window**, and the
range fits a 32-bit index — which is what index narrowing needs.

`TestSelfContained` pins the definition, including that a condition mentioning the variable is fine
and that `(if c (go.+ mx 1) mx)` is refused: that is a genuine accumulator, its reachable set is not
closed after one step, and the fixpoint is right to widen it.

## 6. And then Java, where it cascaded — and found two bugs

With `idx 0..1321`, [index narrowing](indexnarrow-2026-08-27.md) fires on the tokeniser for the
first time. It did not work immediately, and both failures were real.

**An inner loop narrowed while the outer did not.** `fitsIndexSource` refused a loop term, so the
scanner's caller kept a `long` `i` while the scanner's own `j` became an `int` — and `j`'s initial
value is `i + 1`. `int j = (i + 1)` with `i` a `long`; javac caught it and nothing else would have.
Fixed by the honest rule: **a loop's value fits when every one of its exits does.**

**The loop's RESULT variable stayed `long`.** A narrowed `i` was assigned a wide result. Narrowing is
a whole-method decision, so the result narrows with everything else — either every int local in a
method is the host's own `int` or none is.

Two more shapes `narrowIdx` did not recognise, both rule 4 again: a **conditional index**
(`(if (< sp 1) 0 (- sp 1))`, which is what a clamped stack index looks like) and an integer
**literal**.

| Java tokeniser | ns/op | `(int)` casts |
|---|---|---|
| before | 9,073 | 50 |
| **after** | **8,626** | **5** |
| hand-written `short[]`, `int` index | 7,432 | — |

**1.21× → 1.16×.** And the last stretch is the honest news: casts went 50 → 10 → 5 while the time
barely moved, so **Java's residual gap is no longer the index type or the element type** — both are
now matched to the hand-written reference. What is left is code generation and the refinement layer's
guards, which is a different question from the one indextype-2026-08-25 opened and the first time
that has been true.

## 7. What is left



**The tree, at 91.3%.** `tree.oro` did not close: its residue is not a running extremum but values
read out of the node table, which nothing bounds. That is the honest limit of a non-relational
domain and it is where octagons would be asked next.

**Java's 1.16×**, which is now a code-generation question rather than a representation one — see §6.
