# A bare type name resolves in its module

2026-09-25. hamza's question, on `(sig NumError ((err error) (func string) (num string))
go/strconv.NumError)`: why the whole path, when the declaration sits inside `go/strconv`? Spec:
[theories.md §3.4](../../docs/spec/theories.md), [target-files.md §1a](../../docs/spec/target-files.md).

## 1. What the question found

- **It was already decided.** ADR 0021, item 2: "Names resolve lexically. Type names are resolved like
  term names". theories.md §3.4 specifies it: first the current module, then each enclosing module,
  then `lang`, and "a companion therefore names its type without qualification".
- **It was never built.** A type written in a target-file signature was taken verbatim, as a key into
  the type table.
- **target-files.md contradicted the accepted spec.** It said relative names "want their own
  decision". nestmod-2026-09-20 had deferred them over one real hazard: a name that silently changes
  what it binds to when a declaration moves.
- **Constants already resolved relatively, and types did not.** A range endpoint looked up "the
  module's own first, then the bare one", in `constend.go`. Aliases had a third copy of that rule.
- **I had met it the day before.** Inside `module go`, a bare `bytestring` did not resolve, so ADR
  0030 wrote `go.bytestring` everywhere.

**Measured before building:**

| target | module-owned types | shadowing an enclosing type | absolute references | bare references that would change meaning |
|---|---:|---:|---:|---:|
| Go | 8 | 0 | 39 | 0 |
| JS, Java, windows | 0 | 0 | 0 | 0 |

So resolution could change the meaning of nothing that exists.

## 2. What is built (`emit/names.go`)

- **One rule for every name**, `resolveIn`. A qualified name is taken as written. A bare name is
  looked up in its module, then in each enclosing module **by path prefix**, then bare.

  Enclosing is read off the path, so the nested and flat spellings of one target resolve alike. Types,
  aliases and constants all use it: the constants' and aliases' two-step lookups became calls to it.
- **It runs on the glued target**, after the constants and before the aliases unfold. So a type
  declared in one file is named bare in another.
- **Shadowing is refused, naming both.** It applies to a module type named like a type in an
  enclosing module, like a root-level type, or like a language type. That is the hazard the deferral
  named, made an error instead of a silent rebinding. Siblings do not shadow.
- **The target files use it.** 29 references became bare:
  - `bytestring` in `go` and its children;
  - `NumError` in `go/strconv`;
  - `InvalidByteError` in `go/encoding/hex`;
  - `io`'s own types in `go/io`.

  A type from a sibling package stays absolute, as in `hex.oro`'s `go/io.Writer`.

hamza's line is now `(sig NumError ((err error) (func string) (num string)) NumError`.

## 3. What failed first

**The resolution went into one loader of two.** `LoadTarget` (one directory) and `LoadTargetLayers`
(a layer chain) each carried a copy of the same finishing sequence, and the pass was added to one.

The unit tests loaded by layers and passed. `TestOursIsAHostString` and the tooling check load by
directory, and failed: `bytestring` arrived unresolved.

Both loaders now call one `finish`, which takes only a function that labels errors, so neither
loader's refusal texts changed. The names test now loads through both.

## 4. Checked, and how each check fails

`emit/names_test.go` has five tests:
- a bare type in its own module;
- a companion naming its parent's type, nested and flat;
- a name declared in another file of the module;
- a constant from an enclosing module;
- shadowing refused, naming both, while siblings pass.

| planted | caught by |
|---|---|
| no resolution pass | four of the five tests |
| only the declaring module, no enclosing | the companion, constant and shadowing tests |
| shadowing allowed | the shadowing test |
| constants resolved own-then-bare only | the constant test |
| siblings treated as shadows | the shadowing test, whose sibling half is its anti-vacuity guard |

## 5. What it cost

Emission is byte-identical, and so are the proof counts. Every rewritten name resolves to the key it
used to spell, which is the measurement of §1 turned into a build.

**Compile time: a false alarm, not accepted.** Two sweeps flagged `freq` on all three targets at
about 1.6× in CPU time: Go 16.7 → 27.3 s, and Java 43.4 → 71.4 s. The change only touches target
loading, which runs once per compile. Measured serially, alternating, against a worktree at HEAD:

| `freq`, Go | CPU | wall |
|---|---|---|
| baseline | 15.0 to 16.0 s | about 6.8 s |
| this change | 13.5 to 16.8 s | about 6.8 s |

The emitted files are identical. The sweep's CPU time for `freq` rises under 16-way contention (the
second time in two days, after hoststring-2026-09-24), so the baseline was **not** moved:
`-accept` would record the inflated time and hide a real regression.

## 6. Not built

- **A relative module path in `include`.** It still takes absolute paths, because a module path is
  not a type name and nothing has asked.
- **The generator's output** still spells flat, mangled names (`hex-InvalidByteError`). It is
  regenerated, not read, and nothing is gained by respelling it.
- **`implements` at a target's root** sees no module scope, so it names `go.bytestring` in full.
