# The gauntlet on the native JavaScript target, 2026-08-20

[native-gauntlet-2026-08-20](native-gauntlet-2026-08-20.md) moved all six gauntlet programs onto
the native **Go** target and ended by saying the migration had only been done on Go, and that JS is
the most hostile host in the set. This is JS.

**All six programs, all at parity.** And the host earned its reputation: it found one real emitter
defect worth 1.31×, one attribute design that only works on targets with a rich type table, and two
benchmark-method errors that had been quietly inflating every JavaScript number in this repository.

---

## 1. Two method errors, found before any result was trusted

Both were caught by getting *contradictory* numbers rather than by reasoning, and both invalidate
existing measurements rather than language claims.

### A module property load costs 1.66×, and the harness paid it on one side only

```
hand via NAMESPACE   g.dotTyped(a, b)        49,918 ns/op
hand via NAMED       dotTyped(a, b)          30,063 ns/op
native via NAMED     nativeDot(a, b)         29,905 ns/op
native via NAMESPACE nd.nativeDot(a, b)      29,646 ns/op
```

The same function, in the same module, is **1.66× slower when reached through the module namespace
object** — the property load blocks the call from being inlined into the benchmark closure. It is
not namespace access as such: `nd.nativeDot` through a one-export module is fast.

`gauntlet/js/bench.mjs` calls every hand-written reference as `g.foo(...)`. The first draft of this
round's harness did the same, and reported emitted `dot` as **1.65× FASTER than hand-written** — a
phantom win, entirely produced by which side was imported by name.

**Both sides must be called the same way.** Numbers in earlier JS results taken through `g.` should
be read with this in mind.

### One process per comparison

Run together in one process, consecutive runs gave native `centroid` at **32,902 ns and then
236,497 ns**, and hand-written `sumMono` at **32,982 and then 135,855**. V8 carries optimization
state, inline caches and GC pressure across benchmarks. `native.mjs` now runs one case per
invocation and `native.ps1` spawns a fresh process for each, three times over.

And, unlike the Go side, **pinning made it worse**: the allocating stencil read 282k/287k/288k
pinned to core 0 and 236k/253k/233k unpinned, against a hand-written 249k. Node runs its own
threads, and pinning them all to one core adds contention a single-threaded Go benchmark does not
have. `-Pin` exists and defaults to off, which is a measurement rather than a preference.

### ADR 0013 on the host where the gap was largest

The ADR measured **2.01× on JavaScript** against a hand-written buffer-reusing form, worse than
Go's 1.79×, and named "the gap grows on a host we add" as its fourth reopening trigger.

Within this run, allocating costs **2.77× for hand-written code** (245,082 / 88,625) and **2.67×
for emitted code** (229,393 / 85,835). The same conclusion as Go: *in each shape the emitted code
matches hand-written, and the ratio belongs to the shape.* The fourth trigger has not fired — the
gap did not grow, because there was never a compiler gap to grow.

### And `Map` still loses

`Map` at 18,640,915 against `Object.create(null)` at 16,218,905. Baseline R4 measured 3.25× for
this on smaller keys; here it is 1.15×, but the direction is the same and it is still the wrong
choice. The program picks `js.object` explicitly. There is no portable `dict-empty` on this target
to make the choice on the programmer's behalf, **which is the point** — hiding the choice is how
you end up with the slow one.

## 3. What the hostile host found

### A loop in tail position was assigning a result variable — 1.31×

The emitter lowered every `loop` to a result variable plus `break`:

```js
let r1;
for (;;) {
  if (i >= a.length) { r1 = -1; break; }
  if (a[i] > k)      { r1 = i;  break; }
  i = i + 1;
}
return r1;
```

Controlled against hand-written code in *both* shapes:

| | ns/op |
|---|---|
| hand-written, early `return` | 36,973 |
| hand-written, result variable and `break` — **our shape** | 48,383 |
| emitted, before the fix | 48,813 |

So the emitted code was **1.01× against the shape it emitted** and **1.32× against the shape a
person writes**. The compiler was not losing; the *lowering* was. `emit/js.go` now returns directly
when the loop's value is the function's value, and search is at 1.00×.

**On Go the same two shapes are indistinguishable** — its compiler does this itself, which is why
five months of Go measurements never surfaced it. This is exactly the argument for building JS
second (ADR 0004), landing five months late.

Implementation note worth keeping: the first attempt recognised tail position by *pointer identity*
with the term. That silently never fires, because `Term.Body()` opens de Bruijn indices into names
and **allocates**, so two calls to it are different pointers. It is a flag threaded through `emit`
instead, consumed on entry so nothing inherits it by accident, and restored explicitly by the two
constructs that genuinely preserve tail position — a `let` continuation and the loop itself.

### `(length N)` had to be split in two

`(length N)` was introduced on the Go side meaning *argument N decides the result's length*, with
the argument's **declared type** saying how to read it: an `int` argument is a count, a container
argument passes its own length through.

**That breaks on the first target that tried it.** `targets/js/` declares every argument as `any`,
because JavaScript has one number type and untyped containers, so `new Array(n)` and a pass-through
are indistinguishable by type. A declaration that only works on targets with a rich type table is
not a declaration.

It is now two attributes and no inference: **`(length N)`** — argument N is a count; **`(length-of
N)`** — the result is as long as argument N.

### And a JavaScript array store is a map insert

`go.set-bool` carries `(length-of 0)` and `js.set` carries **nothing**, and the two are the same
operation:

| | `c[i] = x` |
|---|---|
| Go | out of range **panics**, so the length cannot change |
| JavaScript | `a[10] = x` on a three-element array **extends it to length 11**, silently |

This is the same refusal `go.set-map` makes, arriving from the opposite direction: on Go a map
insert can grow the container and an array store cannot; on JavaScript the array store *is* the map
insert. Two hosts spell the operation identically and disagree about whether it preserves a length,
which is precisely why the reading is declared by the target author rather than inferred.

`emit/length_test.go` pins both refusals, and the positive cases are checked by mutation: removing
`(length 0)` from `make-bool` fails two tests.

## 4. What JS did not need

`targets/js/` gained **one declaration** for this whole round — `(length 0)` on the four array
constructors — and no compiler change beyond the tail return. Everything else the six programs
needed was already declared:

- `js.at` indexes anything, so the Go target's `at-int`/`at-float64`/`at-string`/`at-bool` split
  collapses to one name. The suffix explosion on Go was **our type table showing through**.
- `String.fields` was already there — the Go target had no string surface at all until `wordcount`
  asked for one.
- `js.object`, `js.Map.new` and `js.Float64Array` were all declared, so the program chooses.

The delayed vector — three lines written *in the language* — moved between two hosts unchanged
except for the names it calls, on a host with no integers, no structs and no `narrow`.

## 5. Where `generic` loses half its evidence, and survives

The Go version of gauntlet program 3 argued that the two instantiations reach genuinely different
host functions — `go.at-float64` over `[]float64` and `go.at-string` over `[]string`.

**On JavaScript they reach the same one.** `js.at` indexes anything, so the element type is not
what distinguishes the instantiations here. What still does is `combine`: `js.+` is an expression
and the object update is a statement, so the two residuals have different *shapes* and neither is a
specialisation of a shared body. g3's claim — a non-recursive definition **is** a rewrite rule, so
instantiation is a side effect of matching — survives on the host that removes the easy half of the
evidence, at 0.98× and 0.89×.

## 6. What is left

Both `report` programs are built and run; every other program is measured against hand-written code
on two native targets.

**Java has not moved.** `sieve-java.oro` exists and no gauntlet program has been ported. Java is the
host with `Math.addExact` as an intrinsic and no unsigned types, and it is the one where the fused
`merge` **loses** 2.6× where Go's fused `m[k]++` wins 1.19× — so it is the target most likely to
disagree with both of the two now measured.
