# What unbounded integers cost when they do not overflow, 2026-08-19

Erlang, Common Lisp, Python, Ruby and Smalltalk all present **one** integer type that silently
becomes a bignum. The bignum path allocates and is obviously expensive. The number that decides
whether the design is affordable here is the other one: **what does every ordinary addition pay for
the possibility, when the value stays small and nothing is allocated at all?**

No argument produces that number. This is it.

## What was measured

A 4096-element sum, values small enough that no path ever overflows, in three forms:

- **plain** — machine addition, wrapping, no check. The baseline.
- **checked** — the fixnum path of a bignum representation: add, test the signed-overflow
  condition, branch away on the rare case.
- **windowed** — the check ADR 0012 already *promises* and does not perform: stay inside
  ±(2⁵³−1).

`gauntlet/go/overflow.go`, plus the JS and Java equivalents. Minimum of 9–11 runs, one variant per
process on V8 (ADR 0015's rule).

## Results, ns per 4096-element sum

| | plain | checked | | windowed | |
|---|---|---|---|---|---|
| **Go 1.26** | 1773 | 4624 | **2.61×** | 2933 | **1.65×** |
| **JavaScript (V8 26.7)** | 4118 | 15387 | **3.74×** | 7441 | **1.81×** |
| **Java 21 (long)** | 1542 | 2022 | **1.31×** | 1830 | **1.19×** |

All ratios are far outside this machine's ~15% noise floor.

## The finding

**The cost is not one number. It is 1.31× to 3.74×, and the spread is wider than the average.**

That spread has a mechanism, and it is the whole point:

- **Java is cheap because the JVM has an intrinsic.** `Math.addExact` compiles to `add` followed by
  a jump-on-overflow — which is what the hardware has provided since 1978. One instruction,
  perfectly predicted.
- **Go pays 2.61× because it has no such intrinsic.** The check becomes explicit comparisons inside
  the loop-carried dependency chain, and the branch is in the way of everything the optimiser
  wanted to do.
- **JavaScript pays 3.74× and cannot be fixed.** There is no fixnum/bignum unification to hook
  into: `Number` is a double that is exact to 2⁵³, `BigInt` is a separate heap type, and mixing
  them is a type test per operation. `Number.isSafeInteger` is the cheapest honest check and it is
  the most expensive result here.
- **x86 was not measured** and does not need to be: `add` + `jo` is one extra instruction. Java's
  1.31× *is* the hardware answer plus JIT overhead.

So the hosts that expose the hardware's overflow flag pay almost nothing, and the hosts that do not
pay 2.6–3.7×. Two of our four do not.

**The windowed check is cheaper but not free** — 1.19× to 1.81×. That matters independently of any
bignum decision, because it prices *enforcing the promise ADR 0012 already makes*.

## What this does not say

It does not say unbounded integers are wrong. It says their price differs by 3× across four hosts,
so it **cannot be hidden inside one portable name** without that name meaning something different
on each target — which is the thing [data-model.md §0](../../docs/spec/data-model.md) forbids.

It also measures only the *non-overflowing* path. The bignum path itself — allocation, and the
branch becoming unpredictable when values straddle the boundary — is strictly worse and was not
measured because it does not need to be to make the point.
