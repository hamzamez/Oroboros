# print — windows' `print_int` printed the low 20 digits of a value above the words, 2026-11-19

**A wrong answer**, found while building ADR 0138's corpus: a driver printing 20000! on windows
printed `00000000000000000000`, the last 20 of its 77,338 digits, and exited 0. 25! printed
`10043330985984000000` (it is 15511210043330985984000000), and 30! printed `91058636308480000000`.
Per assessment-2026-11-16 §3.4, a wrong answer goes ahead of the plan.

## The cause

`lib/win/print.oro`'s `print_int(n ∈ Int)` claims ℤ. Its body stores the digits of |n| backwards in
a 22-byte field and takes exactly 20 steps, since "a value of either word has at most 20 decimal
digits". On a value above the words the steps divide correctly, so no arithmetic is wrong. The
loop just stops after 20 digits and prints them. The compiler is not at fault. The library's text
claims a set its body does not compute on. Go, JavaScript and the JVM print a value above the word
by their hosts' bignums, and are right. The differential suite prints a big value through
`big_str` as a string, so it never reached this.

## Three routes, and which one held

1. **Total on ℤ**: an arm `n < −2⁶³ || n > 2⁶⁴ − 1 -> print_str(big_str(n))`. Refused in the
   kept instance: *an operand is [−2⁶³, +inf] … only a value in the signed word widens into
   arbitrary precision*. This is u128-2026-11-19's wall 2, the unsigned word with no inclusion into
   the rung above.
2. **The claim of what the body computes**, `n ∈ -2^63..2^64-1`. A set above the signed word is
   the consent to the rung above (ADR 0079), so the kept function's parameter took it: eight
   windows programs were refused, and three compiled 5× slower. The union of the two words is no
   representation. As a `where` (`-2^63 <= n && n <= 2^64-1`) it is decided by the refinement
   layer at a call, which does not read the IR's intervals. wc's counts and the sieve's n are
   proven inside the word there, but not by the fragment, so seven programs were refused.
3. **Fail-stop** (built): after the 20 digits, a quotient still non-zero means the value has more
   digits than the field holds, so the scope's start is −1 and the program abandons with *print_int:
   more than 20 digits; print a value above the word with print_str(big_str(n))*. The abandon
   stands after the scope because an exit into ∅ under a tuple pattern is refused by `CheckJoins`'
   arity rule, though ADR 0090 makes ∅ compose with any arity (owed).

Route 3 removes the wrong answer, and route 1 is the language's answer, which waits on the
inclusion U₆₄ ↪ ℤ.

## The test

`TestPrintIntStopsPastTwentyDigits` (`cmd/build/printint_test.go`), on windows and windows32,
checks two things:
- 25! stops with the reason, and its 20-digit suffix is not printed;
- the words' ends print: 2⁶⁴ − 1, −2⁶³ and 0.

The planted fault is the bug that shipped, the old library text: against it the test fails on
windows32, *got err <nil> and "10043330985984000000\n"*.
