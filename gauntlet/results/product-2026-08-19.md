# The product type, and what exact multiplication costs, 2026-08-19

Two measurements. The first prices the operation
[overflow-2026-08-19](overflow-2026-08-19.md) got wrong. The second opens the gate almost every
remaining language question waits behind.

---

## 1. Multiplication, which is the operation that actually costs

hamza's correction: *"the real price is multiplication not checking."* Right, and the earlier
result priced addition, which is the cheap case. Multiplication is worse for two reasons that
compound — **detecting** overflow needs the 128-bit product or a division, and **performing** a
big multiply is quadratic in the limb count where a big add is linear.

4096 independent multiplies of small values, summed. `gauntlet/go/bignum.go`, Go 1.26, minimum of
7 runs.

| | ns | vs plain | allocations |
|---|---|---|---|
| plain `a*b`, wrapping | 1301 | 1× | 0 |
| checked, **hardware high-multiply** (`bits.Mul64`) | 2427 | **1.87×** | 0 |
| checked, **portable** (divide back and compare) | 9632 | **7.40×** | 0 |
| `math/big`, one receiver reused | 50587 | **38.9×** | 3 |
| `math/big`, naive | 119996 | **92.2×** | 4098 |

**Three findings.**

**The check is cheap only where the hardware is reachable.** `bits.Mul64` compiles to one multiply
pair and costs 1.87×. Without it the only portable test is dividing the product back, and a
division in the loop costs **7.4×**. Of our four targets, Go and the JVM expose a high-multiply
(`math/bits.Mul64`, `Math.multiplyHigh`) and x86 has one in the instruction; **JavaScript has
none**, so it is stuck at the 7.4× shape or worse.

**`math/big` is not the best way to do it on Go, even used perfectly.** 38.9× with one reused
receiver and no allocation in the loop. The representation is the problem, not the usage: every
`big.Int` is a heap object holding a `[]Word`, and there is **no inline small-value fast path in
the value itself**. A good bignum keeps the small case in the value — a tagged word, or a struct
with an inline `int64` and a pointer — which is a *product*, which is §2.

**Naive use is 92× and allocates once per operation.** The gap between 92× and 39× is what
careless use costs on top of the representation, and it is the gap a compiler would have to close
automatically for a `bignum` type to be usable without expertise.

## 2. The product type: measured affordable

Does a two-field product returned from a hot call allocate? Almost every open item in the language
waits on this — error results, one `idiv` yielding two answers, `fold-range2`'s pair, a string as
(bytes, length), a bignum with an inline fast path — and CLAUDE.md names it as precisely where the
predecessor project died.

The shape: a `divmod` returning quotient and remainder, called in a loop, both fields consumed.
Against a baseline with no product at all.

| host | form | ns | vs no product |
|---|---|---|---|
| **Go** | no product (inline) | 3191 | 1× |
| | two return values | 3235 | 1.01×, **0 allocs** |
| | value struct | 3229 | 1.01×, **0 allocs** |
| | `*struct` — the control | 3232 | 1.01×, **0 allocs** |
| **Java** | no product (inline) | 3258 | 1× |
| | `record` returned from the call | 3118 | **0.96×**, inside noise |
| | two separate calls | 3095 | 0.95× |
| **JavaScript** | no product (inline) | 31587 | 1× |
| | object literal `{a, b}` | 35028 | **1.11×** |
| | two-element array | 41557 | **1.32×** |
| **x86** | two registers | — | free by construction |

**The product is affordable.** Go allocates nothing, *including* for the explicit pointer version —
escape analysis removes it, which is the control proving the other rows mean something. Java's C2
scalar-replaces the record completely. V8's object literal costs 1.11×, at or just under this
machine's noise floor; its **array** costs 1.32×, which is not.

**One caveat, and it is the important one.** This measures a product **created and consumed without
escaping**. One that escapes — stored in a container, returned across a boundary the host declines
to inline — will allocate on all three managed hosts. That is
[ADR 0013](../../docs/decisions/0013-accept-the-allocation-price.md)'s price arriving from a
different direction, and it means the result reads:

> **A product is free where our reducer already makes things free — when it is built and taken
> apart in the same place. It costs an allocation exactly where `materialize` costs one.**

Which is the same boundary the language already has, not a new one.

**And use an object, not an array, on JavaScript.** 1.11× against 1.32× is a target decision of
exactly the kind [ADR 0008](../../docs/decisions/0008-measurement-over-principle.md) exists for,
and it is the opposite of what the array-shaped `[q, r]` intuition suggests.
