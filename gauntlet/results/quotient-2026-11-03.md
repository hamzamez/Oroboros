# quotient-2026-11-03: −2⁶³ / −1 is decided, like `+`

Plan item 8's second defect (llvm-2026-11-02): ℤ's quotient −2⁶³ / −1 = 2⁶³ leaves the word, and
`ir.Decide` did not count `/`, so nothing decided it. Go and the JVM answered −2⁶³, MASM raised #DE,
and LLVM's `sdiv` is undefined there. Specified first in [integers.md §4a](../../docs/spec/integers.md).

## The algebra

**Theorem.** For b ≠ 0, |a / b| ≤ |a|, with equality iff |b| = 1; and |a % b| < |b|. Under truncation
|a / b| = ⌊|a| / |b|⌋, and |a| / |b| ≤ |a| with equality iff |b| = 1. The remainder has the dividend's
sign and is smaller than |b|.

So on S₆₄ a quotient leaves the word at exactly one point, and a remainder never does. On a symmetric
word, JavaScript's ±(2⁵³ − 1), neither does.

- **`/` is counted like `+`** (ADR 0019): refused unless proven inside the word, trapped under
  `-checked`. `%` is not counted.
- **The transfer is exact by monotonicity.** On a region where b keeps its sign, truncating division
  is monotone in each argument, so the extremes are at the region's corners. A divisor straddling 0
  is two regions, [lo, −1] and [1, hi]; b ≠ 0 is the zero-divisor obligation (§5). The old transfer
  gave up on any divisor that was not positive, so it was also less precise: a ∈ S₆₄ over
  b ∈ −9..−2 is now proven.
- **A target whose instruction is undefined or traps at the corner realizes `%` with −1 as its own
  arm** (a % −1 = 0). `windows-llvm`'s `lang.rem` already did. MASM's `irem` did not: it raised #DE
  at −2⁶³ % −1, a wrong answer, now fixed.

The checked forms, one per target, each trapping exactly at the corner:

| target | checked `/` |
|---|---|
| Go | `div_exact`: panics when `b == −1 && a != 0 && a == −a`; −2⁶³ is the one nonzero x with x = −x in two's complement, so no constant is named |
| JVM | `divideExact`: `Math.negateExact(a)` at −1 (JDK 18's `Math.divideExact`, written for 17) |
| x86 | `idiv` is its own checked form: it raises #DE at the corner and nowhere else in the word |
| LLVM | `lang.div_checked`: at −1, `0 − a` by `ssub.with.overflow`, a trap when it overflows; elsewhere `sdiv` |

## What was built

- `ir/interval.go` `divIV`: the transfer over the divisor's sign regions.
- `ir/decide.go`: `/` is counted, with `PlantQuotientFault` restoring the bug as it shipped.
  `ir/realize.go`: a realized `/` is counted where it stood.
- The checked forms in `targets/go/builtin.oro`, `targets/java/lang.oro`, `targets/windows/x64.oro`,
  `targets/windows-llvm/lang.oro` and its `realize` line. `emit/opnames.go` names them.
- MASM's `irem` with −1 as its own arm.
- `emit/quotient_ir_test.go`:
  - refused: a ∈ S₆₄ over b ∈ −9..9 with b ≠ 0, named by the quotient 9223372036854775808;
  - accepted: b ∈ 1..9; b ∈ −9..−2, the new corners; a ∈ −(2⁶³−1)..2⁶³−1 over b ∈ −9..9; a constant
    divisor;
  - **planted fault**: with `/` uncounted, the refused program is accepted, so the test reaches the
    rule. The refused case also catches a transfer that drops the corner b = −1: the straddling
    divisor's ends ±9 alone bound the quotient by 2⁶³/9.
- `gauntlet/differential/cases/quotient-corner.oro`: −2⁶³ % b for b ∈ −4..−1 and −2⁶³ / d for
  d ∈ −5..−2, every operation proven, its `// expect:` computed in Python's exact integers. **It
  failed first**: MASM exited 0xC0000095, Windows' integer overflow, before `irem` was fixed. Go, the
  JVM, MASM and `windows-llvm` agree. JavaScript is skipped because its word has no corner.

## What was measured

- **Refusals**: three programs, each dividing an unconstrained `a ∈ Int`, and each emitted before as
  the host's `a / b`, answering −2⁶³ at the corner:
  - `examples/native/divmod-go.oro` and `divmod-java.oro` (`divmod`);
  - `examples/sum/parse.oro` (`step`).

  Each is narrowed to the symmetric word, a ∈ −2⁶³+1..2⁶³−1, which by the theorem makes the quotient
  total whatever b is (`divmod_sum` already rested on |q| ≤ |a|). After that, all three are proven.
  No other program in the corpus was refused.
- **Counts**: 5,027 of 5,093 → **5,228 of 5,305** operations proven, the quotients now counted and the new
  case's operations with them. Loops unchanged, 557 of 580. The quotient left 11 operations
  unproven:
  - 10 are `shift-div`'s two quotients on five targets, a case built with `-checked`, whose
    dividend `0 − (n+1)` is already unproven. They trap there as the sums beside them do.
  - 1 is in `examples/int/collatz.oro`, a program meant to be refused.

  `examples/int/power.oro` gained two proven quotients.
- **Emission**:
  - On Go, the JVM and LLVM only `shift-div` changed, its checked quotients.
  - On MASM, every `%` gains its −1 arm, three instructions (`xor`, `cmp`, `je`).
  - In the benchmarked MASM sieve, that arm is in the print-out's digit loop, at most 19 iterations
    after the timed sieve, not in the timed loop.
  - The gauntlet's 26 files are byte-identical.
- **The differential suite**: every case agrees on every target. Compile time 1.09× the baseline,
  inside the gate.

## What failed first

The test's first draft used `a ∈ Int` as the dividend and expected `a / 10` accepted. It was refused,
correctly: an exported `Int` is ℤ, unbounded, and so is its tenth. The corner lives in the word, so
the dividend is S₆₄.

The corner case's first draft left `n` unconstrained. The differential harness ran it and every
target agreed, but the check's sweep refused it on every target: with n < 0, `n % 4` is negative,
so b = −1 − n % 4 may be 0. It now states its domain, n ∈ 0..2²⁰. `Nat` was not enough: unbounded
above, it put `n` on the rung above the word on Go and the JVM.

**A panic the accept found.** Bounded, the case reached JavaScript's pair pass (`ir/pairs.go`), where
−2⁶³ is above the word. That pass builds a quotient of a pair only by a constant. Its `constArg`
read the constant before checking it existed, so a divisor that was not a constant crashed the
compiler instead of being refused. The accept saw it as two sweeps disagreeing: only the panic's
addresses differed. It is fixed, and JavaScript now refuses the case with the pass's own reason, "not
a constant: not built". A probe under `-checked` (deleted afterwards) showed the pass's own guard
refusing a negative operand, so no wrong answer is reachable there.

## What was not built

- A quotient whose dividend is a trapped result is still not proven from that result's word. That
  rule is shared with `+`: a trapped operation's result is not met with the word for the next
  decision. That would prove `shift-div`'s quotients by 2 and 4. Not needed by any program today.
- The refinement layer cannot use the disjunction a ≠ −2⁶³ ∨ b ≠ −1 as a `where`; narrowing the
  dividend is the stateable form.
