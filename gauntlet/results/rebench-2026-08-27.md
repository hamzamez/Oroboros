# The parsers re-benchmarked after the fixpoint fix — 2026-08-27

[fixpoint-2026-08-27](fixpoint-2026-08-27.md) fixed a non-monotone interval fixpoint and withdrew the
interval-derived buffer narrowing that had rested on it. That changes what is emitted, so the
numbers have to be taken again. Everything here is *generated ÷ hand-written*, lower is better.

## 2. What the withdrawal cost, and it is a per-host answer

The node table was `[]uint16` and is `[]int` again — 16 KB instead of 4 KB per parse.

| | with the (unsound) narrowing | without it | cost |
|---|---|---|---|
| Go, tree | 5,524 ns | **5,483 ns** | **none** |
| Java, tree | 6,795 ns | **7,901 ns** | **1.16×** |

**On Go it bought nothing.** [elemwidth §5d](elemwidth-2026-08-27.md) recorded 6,053 → 5,524 as a
1.10× gain from narrowing the node table; the un-narrowed program measures **5,483** here, which is
the same number or better. That comparison was across sessions on a machine with a ~15% noise floor,
and it did not survive being re-taken. **Withdrawn twice over**: once for resting on an unsound
analysis, and once for not being a measurable gain on that host anyway.

**On the JVM it was worth 1.16×**, and that is consistent rather than surprising:
[json-tree-bench](json-tree-bench-2026-08-26.md) established that element width is what the JVM is
sensitive to here, because a node's size decides whether the flat form beats a `Node` object.

So the same change is worth nothing on one host and 16% on another — [ADR
0008](../../docs/decisions/0008-measurement-over-principle.md) again, and a reminder that "the node
table is a quarter the size" is not a performance claim until someone times it.

## 3. Java's tokeniser lost index narrowing, and that is the rule working

**1.16× → 1.20%.** Index narrowing requires every integer operation in the method to fit a 32-bit
index ([indexnarrow §1](indexnarrow-2026-08-27.md)), and the tokeniser's honest figure is **86.7%**,
not the 100% the broken fixpoint reported. One unbounded operation refuses the whole method, so the
`(int)` casts came back: **5 → 102**.

And the cost of 97 casts is **3.7%**. That is the third time this week the casts have turned out to
be cheap, and it keeps the earlier conclusion intact: Java's residual gap is code generation and the
refinement layer's guards, not the index type.

## 4. The narrowing is recoverable, and what it needs is structural

> **Done the same day** — [fixpoint-2026-08-27 §13](fixpoint-2026-08-27.md). The whole-function
> lookup this section proposes does **not** work: `openFresh` rebuilds a term, so there is no key
> the analysis and the backend agree on. Carrying the *assumptions* to the subterm does. With
> `(where (go.< (len src) 1024))` declared, `tree.oro` reaches 91.3% and 25 of 25 loops, its node
> table is 16-bit again, and **Java goes from 7,901 ns to 6,554 — 1.01× of hand-written.** Go is
> unmoved at 5,539, confirming §2's finding from the other direction.

`BufferRange` runs on the `build` **lambda alone**. That was presented as a soundness argument —
less context can only widen — and with a sound fixpoint it is no longer needed for soundness, only
for convenience. It is now the thing standing in the way:

```lisp
(sig measure ((src (array (int 0 255)))) int (where (go.< (len src) 1024)))
```

Declaring that takes `tree.oro` from **88.9% to 91.3%** of integer operations bounded and from
**21 of 25 loops to 25 of 25** — and the buffers still do not narrow, because the sub-pass never
sees the signature.

The fix is the one index narrowing already needed: **ask once per function, with the signature in
hand.** `Intervals` already records every buffer's store range in `IntervalReport.Stores`; what is
missing is getting that to the emitters, which is plumbing rather than a question. Measured value:
1.16× on the JVM and nothing on Go.

## 5. Method

Go: `-benchtime=2s -count=5`, median, one outlier discarded and noted. JavaScript: one `node`
process per case. Java: best-of-9 inner, median of 3 processes. Every implementation is checked
against every other on the same inputs before anything is timed — four forms on the tokeniser, three
on the tree, on each host.

Hybrid P/E-core laptop, ~15% noise floor; §2's Go comparison is exactly the case where that matters
and it is called out rather than leaned on.
