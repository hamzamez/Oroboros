# A text program folds; it does not index

2026-09-04. `examples/big/render.oro`, differential case `render`.

[overloading.md §5](../../docs/overloading.md) named one measurement as the thing
that decides how strings are represented, and named the program that could take
it. This is that program and that measurement.

> **Does a real text program INDEX a string, or only fold it?**
>
> **It folds.** Decimal rendering of an arbitrary-precision value is written in
> three operations — `concat`, `""` and η — and every one of them is derived
> from the free monoid rather than chosen. Nothing is indexed, nothing needs a
> length, and nothing compares two strings.

It also closes the arithmetic half of what windows was missing, and it is the
first program to drive the fixed-limb library end to end.

---

## 1. What the program needs, and what that rules out

`render` is 20 lines of code. Every string in it is built by prepending a
one-scalar string to what is already there:

```
(loop ((s "") (k 0) (r d))
  (>= k 8)                              s
  (and (not pad) (and (= r 0) (> k 0))) s
  else (again (concat (string-of (+ 48 (% r 10))) s) (+ k 1) (/ r 10)))
```

The operation set it uses is exactly the free monoid's presentation:

| used | what it is | derived how |
|---|---|---|
| `""` | the unit | the monoid's identity |
| `concat` | the multiplication | the monoid's operation |
| `string-of` | **η : Scalar → Scalar\*** | the generator injection |

And the operation set it does **not** use is the interesting half:

| not used | what would have needed it |
|---|---|
| `(s i)` | reading a digit back out — never done, because digits are produced |
| `length` | knowing how long the answer is — never asked |
| `=` on strings | comparing text — never done |

That matters because [string-operations.md §4](../../docs/string-operations.md)
measured indexing by scalar position at **262 ms on Go, 383 ms on V8 and 97 ms on
Java** at 16,000 scalars, and **quadratic** on all three: four times the length is
fifteen to sixteen times the work, because every host stores text variable-width.
If a text program had to index, `string` would have to become a table and pay
UTF-32, or every program would pay an `alloc`.

**One program is one data point and it is deliberately not a proof.** A tokeniser
consuming text would index; this one produces it. What it does settle is that the
first real text program in this language needed **none** of the machinery
overloading.md §3 was written to justify — no concept name, no `len` on a second
type, no `alloc`. That is a reason to *defer* those, which is what its §6
recommended, rather than a reason to refuse them.

## 2. What is built

**Two primitives per target and no compiler code.** `concat` and `string-of` are
declared in `targets/go/strings.oro`, `targets/js/builtin.oro` and
`targets/java/lang.oro`, found by SPELLING the way `findEq` finds equality — so
each host says how it does it and nothing in the compiler learns that Go spells
concatenation `+`.

| | `concat` | `string-of` |
|---|---|---|
| Go | `a + b` | `string(rune(c))` |
| JavaScript | `a + b` | `String.fromCodePoint(c)` |
| Java | `a.concat(b)` | `new String(Character.toChars((int) c))` |
| windows | — | — |

**`fromCodePoint` and not `fromCharCode`**, which takes a UTF-16 code unit and
would truncate every scalar above the BMP; **`Character.toChars`**, which yields
the surrogate PAIR above the BMP, that being UTF-16's representation of one
scalar and not two of anything. Both are
[string-literals.md](../../docs/spec/string-literals.md)'s emission rule arriving
at run time: the language's unit is the scalar, and each host's encoding form is
an implementation of it.

**windows declares neither, and is skipped for a CAPABILITY reason that is now
precise.** That host has no string type — a string there is a pointer to
NUL-terminated bytes — so it declines the two operations rather than the program.
It can do every piece of arithmetic below. What it needs is `concat` and
`string-of` written as a **library over `build`**, which is the shape
`emit/bignum.oro` already has, and that is the last capability gap left in the
integer work.

## 3. The measurement, and it is a correctness one

The case runs on **six variants** — three hosts × both storage choices for a
bounded arbitrary-precision value (`; big-repr: both`) — and all six produce
byte-identical digits:

```
ok render  15511210043330985984000000 265252859812191058636308480000000
           [go/host go/limbs js/host js/limbs java/host java/limbs]
```

Those are 25! and 30!, checked independently.

**It is the first program to drive the fixed-limb library end to end.** `x % 10^8`
is `big%-small`, `x / 10^8` is `big/` by a widened word, and `(= v 0)` and
`(> nv 0)` are the limb-wise `cmp` — all three landed the day before with only
unit tests and one hand-written case behind them. On the `limbs` variants that is
our own borrow chains and division loop producing the same digits as `math/big`,
`BigInt` and `BigInteger` do on the `host` ones, which is
[bigrepr-2026-09-03](bigrepr-2026-09-03.md)'s invariant — *selecting a
representation may not change an answer* — checked on a program that renders the
value rather than on one that returns a limb.

**The group size is 10^8 and not 10^9**, because `div-small`'s column is
`r * 2^24 + limb`, which stays inside ADR 0012's window only for a divisor under
about 2^28. Nothing in the library states that limit: bounded-by-default asks at
the call site with the caller's own range in hand, which is stronger than a
declared ceiling would be.

## 4. Three bugs, and the first one PRINTS CORRECTLY

### 4a. A rebuilt binder that never bound — and no printed form can see it

`emit/bigreuse.go`'s `let` case walked `lam.Body()`, which **OPENS** — turning
this binder's de Bruijn indices into names — and rewrapped the result with
`FnClosed`, which takes an already-closed body and **does not close**. So the
parameter's occurrences were left as free names and the binder stopped binding
them.

**What makes this shape hard is that the wrong term prints exactly like the right
one.** `Term.String` renders a lambda by opening its body, so a binder whose
occurrences are free names and one whose occurrences are indices produce the same
text — same parameter, same body. Two terms differing in *whether a variable is
bound at all* are indistinguishable by printing, so no comparison of printed
terms can find it, and neither can the differential suite: the residual is still
a legal term that still means something.

It surfaces one pass later. `intervalPass.let` freshens the binder against the
names in scope; the occurrences are free, so they are **not** renamed with it; and
the Go backend then emits `_ = …` for a binding nothing uses, beside a use of an
undefined name:

```go
_ = (… new(big.Int).Quo(v, big.NewInt(100000000)) …)   // the binding, unused
…
if ((!(nv19.Cmp(big.NewInt(0)) > 0)) && …)             // undefined: nv19
```

**Fourth time `Body()`/`openFresh` rebuilding has bitten this compiler**, after
the `FnClosed` bug in `evalR`, the shared fresh-name set, and the `Body()`-keyed
map in the Java emitter. It is the first where the wrong term was still printable,
which is why it needed a *structural* check to find and to pin.

**Two more of the same shape were found by looking**, both latent: `mapCase` and
`ruleTable` closed the rebuilt lambda on the ORIGINAL parameter names while the
body had been opened with `openFresh`'s possibly-renamed ones, so they would have
produced the identical failure the first time a map eliminator or a rule table sat
under a binder whose name collided. And `intervals`' own head did
`FnClosed(head.Params, out)` on an opened body — harmless only because nothing
encloses the head, so no later pass renames it and a free `n` beside a parameter
`n` emits correctly. **A structural invariant that holds by luck at one site is
not an invariant**, so all three are fixed.

**Pinned by `TestPipelineNeverLeavesABinderOpen`**, which states the property
directly — *a lambda's closed body never contains a free name equal to one of its
own parameters* — and checks it over the whole pipeline (`PromoteBig` plus what
`-checked` would emit) rather than over one pass. It runs on `render.oro` itself,
because the shape **cannot be hand-written down small**: it needs an
arbitrary-precision loop variable to bring `bigreuse` into the pipeline at all,
plus a `let` under the `again`, plus the `let`'s name read from inside a further
binder — and a miniature satisfying the first two declined rule R and never
reached the rebuild. All three bug shapes were reintroduced and all three fail it.

### 4b. A string literal had no type

`typeOf` had no `case core.KStr` on Go or Java, so `(if c "0" (digits x))` came
back `/*unknown*/`: the conditional asks its branches for a type and a literal had
no answer. Latent because no program had used a string literal in a typed position
until one returned text.

### 4c. Supply did not reach a loop variable

`(= v 0)` on an arbitrary-precision parameter was refused once the loop had a back
edge. Rule (S) — a name bound to a big expression is big — ran at a `let` and not
at a loop header, so `v`, whose initialiser is the big parameter, was a machine
word inside the loop and its comparison had no big form. One rule: **a loop
variable whose initialiser is big is big.**

### 4d. And a fourth, from the fix: a hoisted update naming an inner binding

`PostVars` moves a uniformly-updated loop variable into the `for` statement's post
clause, which runs at the loop HEAD — outside every binder the body opens. ADR
0015 permits `again` under a `let` precisely so a clause can compute with an
intermediate value, so the digit loop's `(again … nv …)` hoisted `nv` out of the
`let` that binds it.

The rule is now stated **positively** — hoist only what is in scope at the post
clause, meaning this loop's own variables plus the names the emitter has already
bound outside it — rather than by enumerating what to avoid. It costs the hoist
for an update mentioning an outer constant, which measured as **no emitted file
across the whole corpus**.

## 5. Cost

**No emitted file changes.** All 60 files the corpus emits across four targets are
byte-identical before and after, and nothing that emitted stops emitting; the
three new files are the new program. The differential suite is green on 27 cases
including the six `render` variants.

So the fixes in §4a and §4d are a correctness result with no speed claim attached,
which is the honest way to record them: the bug they remove could not be reached
by any program that had been written.

## 6. What this does and does not settle

**Settled.** A text program can be written with the free monoid alone. `concat`,
`""` and η are enough for rendering, they are two declarations per target and no
compiler code, and the value they produce agrees across three hosts and both
storage representations.

**Not settled, and named rather than assumed.** Whether a text-CONSUMING program
indexes — a tokeniser over text would, and
[jsontok-2026-08-26](jsontok-2026-08-26.md) already measured a string-based
tokeniser 1.89× slower than an array-based one on V8, which is the same finding
pointing the other way. `length` and `=` as concept names are still owed by
[overloading.md §6](../../docs/overloading.md) and are still unmotivated by a
program. And windows still cannot print: it now has all the arithmetic and none of
the text, which is a library over `build` rather than a language question.
