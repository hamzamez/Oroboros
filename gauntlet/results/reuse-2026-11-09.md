# reuse-2026-11-09: a dead table's storage reused by the next table of its size

6b′ step 3, R1b (hamza, 2026-11-09: "go ahead with R1b. always mathematical and algebraic").
ADR 0096 item 6, ir.md W12, llvm.md §4. R1a released each table at its death
(release-2026-11-09); this step hands the dead region to the next table of its size instead.

## The algebra

**The law.** After W11, a released region has no reference, so its address is unobservable. As
transformers of the heap,

    release(p, b) ; q ← region(b)   ≡   q ← zero(p, b)

since `region`'s contract is b fresh bytes, every one 0. That is Perceus's reuse (Reinking, Xie, de
Moura and Leijen 2021). Carried to the next allocation, it is frame-limited reuse (Lorenzen and
Leijen 2022).

**The token is linear.** A dead region of b bytes is a token, and a token is consumed exactly once,
as an owned value is:
- **locally**: a release followed in its region by an allocation of its size becomes that
  allocation's storage, and the release is gone;
- **across a loop's back edge**: a carried table dies at an iteration's end, and the next is made in
  the next iteration's arm. The body takes a token parameter, null on entry. On every path through
  the body the token is consumed once:
  - by `reuse` on the arm that allocates: the token zeroed, or a fresh region when it is null;
  - by `discard` at the start of every other arm that continues or breaks: its release, unless null.

  Every continuing arm passes the next token: a released table's storage of the size, or null. One
  token per allocation at an arm's own level, so a body that makes three tables an iteration carries
  three, each a one-element free list.

Sizes are static (a constant, or a singleton fact), so a token never meets a table it does not fit.
Zeroing is Σ_OS's fifth header, `zero(p, b)`, which windows defines as `RtlZeroMemory`. That is a
kernel32 function, so no C runtime `memset` is linked.

## What was measured first: the ceiling

A raw LLVM probe (`scratchpad/reuse/heap.ll`, 10⁷ iterations):

| | per operation |
|---|---|
| `HeapAlloc(HEAP_ZERO_MEMORY, 80)` + `HeapFree` | 26.6 ns |
| zeroing 80 bytes in place | about 1 ns |

The released limb loop took about 100 ns an iteration with three tables, so the allocator was most of
it. That ceiling is what justified building this.

## What was built

- **The pass** `ir.Reuse` (`ir/reuse.go`), after `ir.Release` and its W11, before ι.
- **The check**, W12 (`ir.CheckReuse`), re-deriving each token: null, or a dead table's storage of the
  allocation's size that nothing uses after it was taken and nothing releases; and each loop token
  consumed exactly once on every path through the body.
- **The target**:
  - kernel32's `RtlZeroMemory`;
  - Σ_OS's `zero` and windows' definition of it;
  - `lang.reuse` and `lang.discard`, with their `realize` lines.

## Witnesses

- **`TestADeadTablesStorageIsReused`**: a table of 10 carried round a loop, with a table of 20 and
  the successor of 10 made on the continuing arm. The carried region crosses the back edge as a token
  and is zeroed for the successor, and W12 accepts it.
- **`TestAReuseW12RefusesIsAFault`**, three planted faults, each refused by W12 for its own reason:
  - a token handed to a table of another size ("a token of 88 bytes is handed to an allocation of
    168", the tables of 10 and of 20 elements of 8 bytes);
  - a region both handed on and released ("released too");
  - a token the exit arm keeps ("consumed 0 times").
- **M1 again**, best of five runs on windows:

  | | release only (R1a) | with reuse | the original leak |
  |---|---|---|---|
  | 10⁶ limb additions | 102 ms | **30 ms (0.29×)** | 179 ms |
  | 10⁷ limb additions | 900 ms | **186 ms (0.21×)** | 1,672 ms (0.11×) |

  Peak memory is 3 MB throughout, and the outputs are identical.

## What failed first

- **One token for the body's first allocation fired once, on one of three tables** (687 ms). The
  tables are made in the continuing arm, not the body's own statements, since the body branches to
  its exit first. A token must therefore be consumed in the arm that allocates and given back on the
  others, which made it linear. That needed `discard`, and W12's count on every path.
- **The discards at the other arms' starts used the home arm's size operands**, which are out of scope
  there (W2). The sizes are static, so each discard got its own constants.
- **The size fault could not fail twice.** β substituted the table of 20 into its user, so it never
  stood at the arm's level. Once it was used twice and stayed bound, the fault paired it with its own
  release of 20, a valid pairing by accident. The fault was restated as the bug it stands for, taking
  the first release seen whatever its size, and W12 refused it.
- **The heredoc ate backslashes once more**, in a debugging dump; the IR text answered the question
  instead.

## What was measured

- **Emission**: 8 windows programs change, the 7 limb programs and the sieve, each where a token
  fired: 1 to 9 `RtlZeroMemory`s a program in place of release-and-allocate pairs. Counts are
  unchanged (5,120 of 5,174, 522 of 546), the gauntlet byte-identical, every step passing.
- **The windows sieve**: `main` runs the sieve repeatedly, so each repetition's table of 2²⁰ booleans
  now reuses the last one's region, zeroed, instead of `VirtualFree` and fresh pages. llvm-2026-11-02
  had measured clearing a table ourselves 10% slower than the system's zeroed pages, so this needed
  the measurement. 15 alternating runs, the same output, median 32.15 ms against R1a's 36.14 ms
  (0.89×) and the pre-release 34.72 ms (0.93×). At this size, reusing the warm region beats faulting
  in fresh zero pages.
- **Not measured**: a program whose sizes are not static. It keeps R1a's release and the heap's own
  reuse.

## Not done here

- **Sizes that are not static.** A dynamic comparison, b_token = b_new, would admit them. Measured
  first, since the heap already reuses its blocks.
- **R1c–R1e**: frame slots for static lengths, which subsumes this step's tokens for fixed limbs at no
  zeroing; the data stack; strings and containment.
