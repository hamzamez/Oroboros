# A struct passed by value (ADR 0129)

2026-11-18. hamza: "Go ahead", item 2 of the order set after mapvalue-2026-11-18. Then, asked how a
declaration says which of `const T*` and the value it means: "I agree to recommended". So the bare
set is the value and `in` marked `const T*` (ADR 0129). **The mode `in` was withdrawn the same day**
for the call's argument term `ref(x)` (ADR 0130, [ref-2026-11-18](ref-2026-11-18.md)); the by-value
half below stands.

## 1. What was measured first

The ABI's answer, from clang 23.1.4 on nine struct shapes (`-O1 -emit-llvm`, `__stdcall` imports):

| shape | x86_64 (Win64) | i686 |
|---|---|---|
| 1, 2 bytes | `i8`, `i16` | `byval` |
| 3 bytes | the copy's address | `byval` |
| 4, 8 bytes of ints | `i32`, `i64` | `i32`; `i32, i32` |
| 12, 16 bytes of ints | the copy's address | three, four `i32` |
| `{char; int}`, 8 bytes padded | `i64` | `byval` |
| `{double}` | `i64` | `double` |

So Win64 is a rule of the size alone: 1, 2, 4 or 8 bytes are the integer of the bytes, and anything
else is a copy's address. i686 is the bytes on the stack, which `byval` of the N bytes states for
every shape. `PtInRect(const RECT*, POINT)` is `(ptr, i64)` on x86_64 and `(ptr, i32, i32)` on i686
in clang, and `(ptr, ptr byval([8 x i8]) align 4)` here, the same eight bytes.

## 2. What was built

- **The spelling** (ADR 0129). J's readers take `in` as a mode after a set
  (`core/jparse.go`, `jreadtarget.go`), and `TypeName` spells it `in(T)`. The target's unfold
  (`emit/alias.go`) makes both `in T` and a bare C struct set the fresh reference, `cell T` among
  `Prim.InStructs`, and lists the bare ones in `Prim.ByValue`. `in` on a set with no layout is
  refused.
- **The call** (`ir/llvm`'s `cCall`): a by-value argument is the copy's `iN` load, or its address, on
  x86_64, and its `byval` on i686.
- **The declarations**: `RegisterClassA` respelled `wc ∈ WNDCLASSA in`, and
  `PtInRect(rc ∈ windef.RECT in, pt ∈ windef.POINT)` declared, exempt from the prototype check with
  its reason, since the survey refuses struct by value.
- **The words**: `in` listed in j.md §1.4 and §2.4, inventory.md (181 words, 148 specified),
  llvm.md §6b.

## 3. Measured

`PtInRect` with the rectangle (10, 20)–(30, 40) and four points, on windows and windows32:

| point | answer |
|---|---|
| (15, 25), inside | 1 |
| (15, 45), below | 0 |
| (5, 25), left | 0 |
| (29, 39), the last inside corner (right and bottom exclusive) | 1 |

`RegisterClassA`, now `in`, still registers and finds its class on both
(`TestACStringFieldIsLent`).

## 4. The test

**`TestAStructIsPassedByValue`** (`cmd/build/byvalue_test.go`): the four points on both triples.
The fault `llvm.PlantByValueAsPointer` passes the point by its copy's address, the `_In_` form,
which x86-64 reads as a point, and the answer must then differ.

## 5. Not built

- **A struct returned by value**: one Win32 entry point needs the hidden-pointer return
  (structval-2026-09-12).
- **The survey's struct by value**: the generator still refuses it, so a by-value declaration is
  checked by running it, not against its prototype.
