# The limb rung's cost was signed division, and the fix is a proof

2026-09-03. `emit/interval.go` (`SelectShifts`, `shiftFor`, `andI`, `shrI`),
`emit/target.go` (`ShiftWidth`, `ShiftNames`), `emit/bignum.oro`,
`gauntlet/go/limbcost_test.go`, `targets/*`.

[bigrepr-2026-09-03](bigrepr-2026-09-03.md) §6 named what should come next:
*"a target-declared limb width and carry extraction"*, citing
[bigarith-2026-08-28](bigarith-2026-08-28.md)'s **2.75x** for the limb count and
**3.9x** for a bitwise carry.

**Those are numbers about hand-written host code, and nobody had decomposed
OURS.** Doing that first changed the plan: one of the two is unreachable, the
other is not what it looked like, and the right fix turned out to need nothing
added to the language at all.

## 1. The decomposition

Our emitted fixed-limb factorial (200!, 55 base-2^24 limbs), against the same
program hand-written once per suspected cost, each variant the previous one
minus a single thing so a difference is attributable. `limbAsEmitted` is a
line-by-line transcription of `GenFactLimbs`, checked against it at run time —
comparing against a variant that is faster for two reasons at once is the
measurement error this repository has caught in itself four times.

| variant | ns/op | what it removes |
|---|---:|---|
| emitted (ours) | 13,860 | — |
| hand-written, same shape | 13,300 | (our emission is **1.04x** of it) |
| − the element mask | 12,540 | `% 2^24` on every read |
| − the index clamp | 12,951 | two never-taken compares |
| − the buffer clear | 12,881 | `clear(sp)` per iteration |
| **− `/` and `%`, using `>>` and `&`** | **5,587** | **the carry split** |
| − 24-bit limbs, using 32-bit | 4,460 | 55 limbs → 41 |

**The mask, the clamp and the clear are together inside the noise floor** — the
three variants that remove them are 12,540, 12,951 and 12,881, and removing the
clamp measures *slower* than removing the mask. All three were plausible
suspects and all three cost nothing.

**The carry split is 2.39x**, on its own, and it is the whole gap.

### 1a. Two corrections to what was expected

**64-bit limbs are not reachable, and the reason is ADR 0012.** An `int` is exact
within ±(2⁵³−1), so a limb of 2⁶⁰ is not a value this language can hold.
bigarith's 2.75x is 24-bit against 64-bit hand-written host code. The widest limb
whose product still fits without a wide multiply is 26 bits; with one it is 32,
and 1301 bits over 32 is 41 limbs against 55 — **1.20x measured, not 2.75x**.

**And the carry is not really about bitwise operators.** `x / 2^k` on a SIGNED
value is not a shift: truncation toward zero needs a rounding correction, and Go,
the JVM and x86 all emit one even though the divisor is a constant power of two.
That is what the 2.39x is, and it means the fix is available to a program that
never writes a bitwise operator.

## 2. So the fix is a proof, not a declaration

`x >> k` is FLOOR division; our `/` truncates toward zero. They agree exactly on
the non-negative numbers and differ by one everywhere else. So the rewrite is
licensed by the interval analysis:

> `(/ x C)` becomes a shift and `(% x C)` becomes a mask when C is an exact
> power of two, x is provably **non-negative**, and x fits the target's declared
> shift width.

Nothing enters the language, and integers.md §0a's reason for keeping bitwise
operators out of it stands untouched: what changed is that the COMPILER may use
a host's own shift where it has proved the rewrite changes no answer. That is
*emit at the highest layer the target natively provides* applied to an operation
a program may not write.

**What the target declares is the host fact the proof is checked against**, and
the four disagree. `(shift-width 63)` on Go, the JVM and x86; **`(shift-width 31)`
on JavaScript**, because V8 coerces both operands of `>>` and `&` to int32 — the
same divergence that keeps those operators out of the language. Declaring the
width rather than excluding the host is what lets the rewrite fire there at all,
on values that provably fit. A target declaring nothing gets nothing.

### 2a. The library had to say one thing for the proof to run

`%` takes the dividend's sign, so masking a value the analysis cannot bound gives
back `[-(2^24-1), 2^24-1]` — symmetric around zero — and every column sum built
from it is symmetric too. The measured intervals at the carry split were exactly
that, so nothing was provable and nothing fired.

`at` in `emit/bignum.oro` now returns a value that is non-negative **by
construction**, at the cost of one compare, and the whole chain follows: the
column sum, the stored limb and the outgoing carry are all provably ≥ 0.

That is a fact the program states rather than one the analysis derives, and the
honest version is still owed: a limb IS non-negative by the buffer's element
range, which is an inductive invariant over a buffer's own contents —
[frozen-2026-08-28](frozen-2026-08-28.md) says that is strictly stronger than an
octagon.

## 3. What it is worth

| | before | after | |
|---|---:|---:|---:|
| Go, limb factorial | 13,860 ns | **7,900** | **1.75x** |
| JavaScript, limb factorial | 528,137 | **272,531** | **1.94x** |
| Java, limb factorial | 15,164 | **10,553** | **1.44x** |
| windows, limb factorial | 217 lines of asm | 220 | — |

**And it changes no target's representation declaration**, which is the framework
working rather than a disappointment: the limb rung is still 3.4x behind
`math/big` (was 5.85x), 41x behind `BigInt` (was 74.9x) and 2.1x behind
`BigInteger` (was 2.82x). All three keep `(big-repr host)`. The measurement moved,
the declarations were re-examined, none of them moved.

**Outside bignums it fires on exponentiation by squaring** — `k / 2` and `k % 2`
become `k >> 1` and `k & 1` on all three hosts, which on JavaScript replaces
`Math.trunc(k / 2) + 0`. Measured on `examples/big/power.oro`: **298 ns against a
hand-written 279**, indistinguishable from the 1.00x/0.98x/1.01x
[bigrep-2026-09-02](bigrep-2026-09-02.md) recorded. A real simplification and not
a speed claim, because that loop is dominated by its multiplies.

## 4. Three bugs, and the first was silent in the way that matters

**`1 << 63` overflows an int64.** The width test was `x.hi >= int64(1)<<uint(N)`,
which at N = 63 compares against a NEGATIVE number, so every value was refused
and the rewrite fired nowhere — on the three targets that declare 63. It fired on
JavaScript, which declares 31, and that is the only reason it was visible at all:
a feature that silently did nothing on three of four hosts, while appearing to
work on the fourth.

**The rewrite outran the analysis.** `arithOp` did not know `&` or `>>`, so the
moment the carry split became one, the store's value range went to ⊤ — and the
fixed-limb factorial lost BOTH its element narrowing (`[]uint32` back to `[]int`)
and its loop-carried buffer reuse, silently, while still computing the right
answer. An optimisation that defeats two later analyses is a net loss, and only
reading the emitted code found it.

**And the shift-only pass promoted a limb table to a bignum.** `SelectShifts`
runs after a representation has been chosen, so the supply/demand solver saw a
loop it had already promoted and promoted it again, emitting
`func GenFactLimbs(n int) *big.Int` over a body that builds a `[]byte`. Gating
`bigOK` on the pass's own mode fixes it. This one at least fails loudly.

## 5. What checks it

**γ-soundness of the two new transfer functions**, directly and exhaustively over
concrete pairs, the same shape as `TestDivisionAndRemainderContain` and for the
same reason: `SelectShifts` PRODUCES `&` and `>>`, so `andI` and `shrI` decide
what the analysis believes about every carry split, and they were unfalsifiable
the day they were written. Both bug shapes were reintroduced and both fail it —
a mask claiming the dividend's bound rather than the mask's fails at
`andI([-1000000,-70000], [255,255])`, and a shift admitting a negative dividend
fails at `shrI([-inf,1],[7,7])`.

`andI` claims `[0, m]` for a non-negative constant mask **whatever the other
operand is**, including negative ones — every bit set in `x & m` is set in `m`,
which holds in two's complement — and that claim is what restores the element
narrowing `%` used to give.

**A differential case, `shift-div`**, on all four targets, with three shapes in
one program: a negative dividend that must NOT be rewritten, a value that crosses
2³¹ so JavaScript rewrites some of its divisions and declines the rest, and the
ordinary case. **Agreement alone would not catch the first** — Go, the JVM and
x86 would all shift and all be wrong together — so the expected values were
computed by hand and are in the file.

**Four unit tests on the rewrite's decisions**: a proved non-negative dividend
becomes a shift, a possibly-negative one does not, the width is the target's
(JavaScript rewrites below 2³¹ and declines above it, Go does both), and a target
declaring no width gets no rewrite.

## 6. Cost

- **8 emitted files change**, across 3 programs: `examples/big/limbs.oro` on all
  four targets, `examples/big/power.oro` on the three with a bignum, and
  `fact-limbs` on windows, which is the only target that stores it as limbs. The
  other 67 × 4 are byte-identical.
- The compiler suite, the 22-case differential suite on four targets, and the
  gauntlet's bignum correctness tests are green.

## 7. What is left

The limb rung is 3.4x behind `math/big` on Go and 2.1x behind `BigInteger`, and
what remains of the gap is **32-bit limbs** — measured at 1.20x here, needing a
wide multiply, which values.md's multiple return already passes in rax/rdx on x86
— and then ordinary tuning. Neither is worth taking until a target would change
its declaration because of it, and on today's numbers none would.

**The clamp and the element mask are still there and still cost nothing**, which
is worth recording because both look expensive and both were on the list. What
would remove the mask honestly is the analysis carrying a frozen buffer's element
range through a substitution into a lambda where the buffer is free — a real
extension, named here rather than assumed, and now known to be worth nothing on
this program.
