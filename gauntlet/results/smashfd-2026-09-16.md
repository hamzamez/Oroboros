# Array smashing: a table's contents in the interval layer, and the value clamps come out

2026-09-16/17. `emit/smash.go` (new), `emit/interval.go`, `emit/smash_test.go`, `examples/io/freq.oro`,
`examples/tally/tally.oro`, `examples/json/tree.oro`.

array-facts.md §8.3's last step: the interval layer's consumer of F-D. fdrefine-2026-09-16 taught the
refinement layer what a table holds. The operations those value clamps protected are counted by the
**interval** layer, so no clamp could come out until that layer knew too.

## 1. The domain and its transfer functions

**Array smashing** (Blanchet, Cousot, Cousot, Feret, Mauborgne, Miné, Monniaux & Rival, PLDI 2003 §6.1): a
table-valued name `c` has one abstract cell `E(c) ∈ Itv`, with the invariant `∀s. c[s] ∈ γ(E(c))`. A store is
a **weak** update. `p.elem` already held exactly this for declared and syntactic sources; what is new is a
transfer function for every term a table value can be:

| term | cell | why |
|---|---|---|
| `(build n λx.e)` | inside `e`, `E(x) = [0,0]` | the zero fill (tables.md §14.3) |
| `(set c i v)` | `E(c) ⊔ ⟦v⟧` | the new slots are a subset of the old slots plus `{v}` |
| `(if b t u)` | `E(t) ⊔ E(u)` | the value is one of the two |
| `(let v λx.e)` | `E(e)`, with `E(x) = E(v)` | a binder is its value, in `p.let` and in a clause chain's `let` |
| `(again …)` | `⊥` | a jump has no value |
| a loop | its exits' cell, at the fixpoint | the loop's value is an exit |

**A loop's table variables join the scalars' Kleene iteration**, with the same widening and narrowing. So a
read of a buffer inside its own filling loop reads the current iterate of one monotone fixpoint.
frozen-2026-08-28 refused an element range for exactly this read; that refusal was right for a *separate*
analysis consulting its own unsettled answer, and does not apply inside one fixpoint.
**Linearity (ADR 0018) is why a name's cell is never stale**: once `set` consumes `c`, only `len` may observe
it.

**Storage width is unchanged.** `BufferRange`'s sub-pass runs with smashing off, so *a buffer may not narrow on
its own contents* stays the policy its test pins. Smashing bounds values; it chooses no representation.

## 2. Two theorems, because a weak update is extensive

`E(set c i v) ⊒ E(c)`, so the back-edge transfer on a cell is **extensive**. Widening sends a growing cell to
`+inf`, and narrowing, which accepts only a value inside the current one, can never take it back. This is
monotone.go's running-extremum problem arriving at a table. It was found on freq, where iota's buffer held
`k < nw ≤ 32768` and its cell stayed `[0, +inf]`.

**Theorem (copy-closed joint invariant).** Let G be a loop's table variables and J a sound joint invariant.
Let U join, over every back edge:
- every stored value, except that a value which *is* a read of a G-table contributes ⊥;
- every table handed to a G position from outside G.

Evaluate U with reads interpreted in J. Then `J′ = ⨆ init(G) ⊔ U` is a sound joint invariant.

*Proof*, by induction on iterations. A new slot is either an old G-slot (in J′ by the induction), a copy of
one (the same), a stored value (in U), or an outside table's slot (in U). ∎

So from the widened post-fixpoint, `E ← E ⊓ J′` is sound and shrinks. The **delta** of a term is its
contribution to U, and it carries a second invariant: `content(x) ⊆ J ∪ delta(x)`. G's names have delta ⊥,
nested loops get their own delta fixpoint, and anything unrecorded falls back to its cell. This is what a
sort needs: freq's merge only copies slots between `a` and `b`.

**Theorem (bounded increments).** Let the loop run at most T iterations, which is the trip count size-change
termination already computes. Suppose every store into G is either a value in U, or a G-slot read plus a
literal `d ∈ Δ`, with at most s such increment stores along a back edge and none inside a nested loop. Then
every slot lies in `J₀ + T·s·[min(0, lo Δ), max(0, hi Δ)]`, where `J₀ = init(G) ⊔ U`.

*Proof.* A slot's value is its origin, which is in J₀, plus the increments along its provenance chain. Each
increment is a distinct store, at most s per iteration over at most T iterations. ∎

This is what bounds a count incremented in place (freq's and tally's `dt`) and a depth stored back plus one
(tree's worklist). T is known only after the size-change sweeps, so this phase runs after them. A narrowed
cell then narrows a step, so the steps are measured again and `v ∈ v₀ + T·step` is applied again. T itself is
unchanged, since the termination argument reads no cell.

Two smaller pieces:
- A name bound to a read is that read, so `(let (wl …) (fn (d) … (+ d 1)))` is an increment.
- A `build`'s value is its body's, so a scratch buffer that returns a count has the count's interval rather
  than ⊤.

## 3. Soundness, checked rather than argued

**`TestArraySmashingContains`** generates 3,000 programs and runs each one concretely. Each program:
- fills one buffer, or two swapped buffers, in a loop;
- stores literals, arithmetic, reads, copies and increments;
- sometimes stores through a table-valued `if` or `let`, a nested loop threading the buffer, or a fresh build
  handed to the buffer's position;
- sometimes binds a read in a clause-chain `let` and feeds it to an increment or an accumulator;
- sometimes uses the whole build as a number.

Every counted operation's result must lie in γ(MaxOp). **Anti-vacuity is measured**: 2,006 of the 3,000 are
bounded *only* with smashing on, found by running each program again with it off. The generator keeps to
linear programs, since a read after the store that consumed the buffer is one CheckLinear refuses.

**Plants that fail it**, each at a named seed:

| plant | caught by |
|---|---|
| strong update instead of weak | harness |
| no zero fill | harness |
| no edge join | harness |
| no widening | harness |
| a conditional's cell from one arm | harness |
| every store treated as a copy | harness |
| init(G) left out of J′ | harness |
| nested loop's delta starting at ⊥ | harness |
| nested loop's edges not joined | harness |
| no T·s·Δ extension | harness |
| half the trip count | harness |
| re-measured steps with half T | harness |
| a build's value forced to 0 | harness |
| increment count ignored (s = 1) | `TestBoundedIncrementsContain` |
| increment inside a nested loop allowed | `TestBoundedIncrementsContain` |

The last two pass the random harness. The analysis over-counts wherever it evaluates a store more than once,
and an over-count is sound, so random programs never press the count against the truth. So they are pinned by
two exact witnesses: two increments of one slot per iteration, and a nested loop of 200 iterations.

**Plants that pass, and why that is not a gap:**
- *Narrowing without the `within` test.* By monotonicity, F applied to a post-fixpoint is itself a
  post-fixpoint.
- *An outside name's delta as ⊥.* A linear program cannot hand a buffer bound outside the loop to it, because
  the initialiser consumed it.
- *Any let-bound name treated as a read.* `storedDelta` re-checks derivedness one layer down.

**Found by the harness during the build**, a real soundness bug. `elemRange` read `(set c i v)` as `c`'s range
and ignored `v`. That was harmless while no buffer being filled had a range. With cells, a `let` intersected
the correct cell with the stale one: seed 315 claimed `-80..15` for an operation producing `-231`. In a
smashing pass that function no longer answers for a store.

**And three precision bugs, found by tracing freq and tree:**
- iterate deleted a loop variable's name from `p.elem` before reading the initialiser's cell. The build binder
  and the loop variable usually share a spelling.
- A clause chain's `let` bound a value's interval and not its cell.
- The trip bound took steps measured before the increment phase narrowed a cell.

## 4. What it bought

**Proof counts: 2,307 → 2,361 of 2,413** integer operations bounded corpus-wide.

**The value clamps array-facts.md §1.2 counted are deleted:**

| program | deleted | check |
|---|---|---|
| freq | `pat`, `dword`'s cap, `dcount`, the increment's cap | 324 of 324, no `-checked`; byte-identical output to the clamped build on Go, JavaScript and Java over six files, and the three hosts agree |
| tally | `pat`, `dcount`, `dvalue`, the increment's cap | all four tooling cases pass against the hand-written Go oracle, on Go and the JVM |
| tree | none (see below) | 525 of 525 and **builds without `-checked`**; the walk is **424 of 424**, the acceptance array-facts.md set |

tree needed no relational domain: what bounds `d` is a count. Its node-index clamps (`cn`, `cw`) stay, and so
does freq's `cl sp` into the span table. Which slot is in range is a relation the refinement layer decides, not
a bound. The index clamp inside `pat` stays for the same reason.

**The limb library got faster as a consequence, not as a target.** A limb is now proven non-negative, so
shiftdiv-2026-09-03's rewrite fires on the carry split: `% 2^24` → `& 16777215` and `/ 2^24` → `>> 24`.
shiftdiv named that as *"the honest version … an inductive invariant over a buffer's own contents"*.
**Emitted `limbs.oro` on Go: 14,670 → 6,810 ns median over five runs at 20,000 fixed iterations, 2.2×, with all
64 limbs identical.** Java drops its `Math.addExact` checks in `limb-subdiv`, and windows gets `and rax` in
place of `cqo; idiv` in render, big-divmod and fact-limbs.

**Cost:**
- freq: indistinguishable at the process level, where start-up dominates (41.4/40.5/37.9 ms against
  41.2/38.7/41.0 ms); removing a clamp only removes work.
- Emission sweep: 23–30 s, within the baseline's range.
- vet, compiler, differential (every case on every target) and tooling pass.
- 30 emitted changes accepted, the rest fresh-name renumbering.

**Size:** `emit/smash.go` 140 code lines, `emit/interval.go` +489, tests +255.

## 5. What is left

- Field sensitivity. One cell for a stride-k table joins its components. It did not matter here, because
  every component was bounded, but a table mixing a small tag with an unbounded payload would need a cell per
  component. That is the currying argument array-facts.md §5.3 already makes for F-D.
- F-D₁ **declared** (`forall` in `where`/`ensures`), which is the next step of array-facts.md §8.
- Benchmarking tree with its clamps removed, which needs the node-index clamps proven first.
