# JavaScript's bit operations on its whole word, by the split; a differential case with opaque inputs

Date: 2026-11-21. hamza, 2026-11-21, on the options for JavaScript's three gaps: "I agree, go in
that order: 2, then 1, then 3". This is 2, option A: `&`, `|` and `⊕` past 32 bits and inside
JavaScript's word, realized by the split, where integers.md §0b said "refused until the split is
built".

## The law

And, or and xor are ℤ's (ADR 0082), and they act bit by bit, so they commute with any split of a
number at a bit position. On JavaScript's word W = ±(2⁵³ − 1), split at 32: x = h·2³² + l with

- l = ToUint32(x) = x mod 2³², `x >>> 0`, in U₃₂;
- h = (x − l)/2³² = ⌊x/2³²⌋, exact in doubles (x − l is a multiple of 2³² below 2⁵³ in magnitude, and
  a division by a power of two is exact), in [−2²¹, 2²¹), where ToInt32 is the identity.

Then x ∘ y = (hₓ ∘ h_y)·2³² + (lₓ ∘ l_y) for ∘ ∈ {&, |, ⊕}: the high digits' operation is
JavaScript's own int32 operator, the low digits' its operator read unsigned (`>>> 0`), and the sum
is exact where it lies in W, which the realization's result set asks the facts to prove. The result
may be −2⁵³, one past W, ((−2⁵³ + 1) & −2): the formula is exact there too, and the result set
leaves it to the facts, so that realization is not chosen for it.

## What was built

1. **`and_s53`, `or_s53`, `xor_s53`** (targets/js/builtin.oro), each a term over JavaScript's
   operations (ADR 0089), beside the S₃₂ and U₃₂ realizations. The domain rule (ir/final.go) chooses
   the narrowest realization the facts prove, so a result in S₃₂ or U₃₂ keeps its one operator, and
   the split is taken only where neither holds it.
2. **`TestTheBitOperationsOnTheWholeWordAreTheSplits`** (emit): the target's own three templates run
   in node over W's edges and every bit length, 162,867 results against BigInt's operators, each
   ℤ's; THE PLANTED FAULT, the and with its high digits or'ed, disagrees.
3. **An opaque differential case** (gauntlet/differential/run.go, `// opaque`): the driver loops
   over a counter the reducer does not unroll, `run(caseI)` for consecutive inputs and under
   `if caseI == a || …` otherwise, so each input reaches `run` unknown. `bits-edges` is opaque, and
   with the split it agrees on four targets; with the split's high digits or'ed (a one-time
   mutation of the target) JavaScript's twelve answers all differ from Go's.
4. **The book**: §7.11's sixth way (`docs/book/code/bits/wide.oro`, `mask` and `mix`), its
   summary line; integers.md §0b's table.

## What failed first

- **The test that could not fail**: `bits-edges` passed on JavaScript while its file, compiled alone,
  was refused. The driver called `run` at literals, so each operation's facts were a point, a pure
  one folded, and the rest took the narrowest realization that point proved; the realization a
  program with unknown inputs needs was never chosen. I first wrote that the case folded whole; the
  kept JavaScript shows the bit operations computed, at constants.
- **Two tests pinned the refusal**: `TestTheBitOperationsAreTheLanguagesOnEveryTarget` (emit) wanted
  exactly the S₃₂ and U₃₂ realizations, each inside V8's window, its planted fault a bare `and`
  declared over the word; it now wants three, and a realization past 32 bits must be the split, not
  the bare operator, so the planted fault still fails. `TestABitResultOutsideEveryRealizationIsRefused`
  asserted a 40-bit or refused on JavaScript; renamed `TestABitResultChoosesItsRealization`, it
  wants the split there, and still `>>> 0` (and no split) where the result is in U₃₂.
- **The opaque driver's first forms**: a table of the inputs read at the counter lost the bound
  (`edges[n]`'s 0 <= n, a literal table's element range unknown to the refinement layer); the
  counter itself keeps it. And `print(run(i))` in an `if` arm is not a statement on JavaScript and
  the JVM, whose print returns its argument.

## Found, not fixed: every case opaque

Each case whose inputs increase (83 of 89) run opaque, the other 6 not: 74 agree on four targets.
None is a JavaScript gap. Nine fail:

| cases | target | what |
|---|---|---|
| big-bits, big-nat-div, big-nat-ops, big-signed-ops, record-map, tuple-map | windows | IR_P does not verify: a table value flows into an integer comparison (W5, W6) |
| map-static | the JVM | the emitted Java does not compile: `Map.entry(1, 10)` an Integer where the map is `Map<Long, Long>` |
| quotient-corner | all four | refused: `b - 1 != 0` does not follow with the input unknown |
| sum-slots | all four | an operation proven only at the literal inputs traps under `-checked` |

None is a wrong answer: a build failure or a refusal. The first two are separate tasks; the last two
are each case's own question (is the case's claim true of every input, or only of those it names?).
The differential stays literal by default until they are settled.
