# Gauntlet program 7, write half — the first parity failure

**Result: the emitter is at parity. The *idiom* is not.** Generated code matches hand-written
functional code to within 0.6 %, and loses **1.87×** to a hand-written stencil that reuses buffers.

By the gauntlet's own standard — *parity with hand-written code in the target language* — **this is
a fail**, and it is the first one in the project.

---

## 1. What was measured

`examples/smooth.oro`, the last gauntlet program to get an Oroboros implementation. Its read half
arrived with [integer arithmetic](../../docs/spec/arithmetic.md) and its write half with
[data construction](../../docs/spec/construction.md). `vecA`, 65536 elements, minimums over seven
runs.

### One application

| | ns/op | allocs |
|---|---|---|
| `SmoothInto` — hand-written, caller owns `dst` | **66,068** | **0** |
| `SmoothAlloc` — hand-written, allocates a result | 124,188 | 1 × 512 KB |
| **`GenSmooth` — generated** | **123,485** | 1 × 512 KB |

### Eight applications, the case a stencil is actually for

| | ns/op | allocs |
|---|---|---|
| `SmoothInto` — two buffers, swapped | **544,610** | **0** |
| **`GenSmooth` — generated** | **975,568** | 8 × 512 KB |

## 2. Reading it honestly

**Against the same shape, we are at parity — marginally ahead.** 123,485 against 124,188 is 0.6 %,
well inside the noise floor. The emitter produces the best functional code available; there is
nothing left on the table in *how* we compile.

**Against the best shape, the functional idiom costs 1.87× once and 1.79× repeated.** The gap is
roughly constant per pass rather than growing, so this is not accumulating GC pressure — it is the
allocation plus writing into freshly mapped memory instead of rewriting a warm buffer.

> **The compiler is not what loses. `materialize` is.**

## 3. Why this was worth measuring

[construction.md §7](../../docs/spec/construction.md) claimed that allocating fresh makes the
destination **unique by construction**, and that this is how g7's *program* lands without g7's
*question* — aliasing — being answered.

That claim is true and the price of it is now a number: **1.8×**. Which is the useful outcome. The
oldest open question in the repository was a design worry with no cost attached; it now has one,
measured against a hand-written baseline that has sat in `gauntlet/go/aliasing.go` since before the
compiler worked.

It is also the first time a prediction in this project was made *because it might fail* and then
did. Every earlier measurement either confirmed, or refuted something that had been asserted
carelessly.

## 4. The three ways out

Not decided here. Stated so the next conversation starts from the same place.

**(a) In-place write with an ownership discipline.** `(set! a i x)` plus a proof that `a` is
uniquely held. This is g7's original question, and it is the only option that reaches the 66,068.
It costs the thing the project has avoided since the derivations: a uniqueness or linearity
property on values, which [ADR 0010](../../docs/decisions/0010-effects-as-structural-rules.md)
explicitly declined for effects.

**(b) Liveness-based reuse.** `v = GenSmooth(v)` with the old `v` dead afterwards could reuse its
storage instead of allocating — Perceus-style, explored in
[s3](../../docs/derivations/s3-cross-boundary-reuse.md). It needs no user-visible property, which
makes it the cheapest in interface terms and the hardest in analysis terms, and it is exactly the
"the compiler may not see what I did" case.

**(c) Accept 1.8× as the price of having no aliasing at all.** Defensible, and it should be said
out loud rather than assumed: the language would be one where stencils are 1.8× off hand-written
and nothing can alias. That is a real product; it is just not the one requirement 5 describes.

## 5. What did not go wrong

Worth separating, because a failure invites over-correction.

- The **emitted loop is what a person would write** on all three targets, with the window inlined
  by δ+β and no intermediate vector.
- The **delayed representation reduced away completely** — `vec.vec` and `vec.vindex` leave no
  trace, and the array exists only because `materialize` asked for one.
- `f64` **division was added and is Tier 1**: measured to agree across all three hosts on every
  case including `x/0` = ±Inf and `0/0` = NaN. [arithmetic.md §7](../../docs/spec/arithmetic.md)
  had ruled out division on grounds that apply to *integer* division only, and conflated the two.
- **Correctness is checked**, not assumed: `TestGeneratedSmoothMatchesHandWritten` compares every
  element against `SmoothInto`.
