# Gauntlet program 2 — structs, on both targets

The first program where the design has a genuine gap, found by running it rather than by
argument.

**Result: parity on both targets — Go produces byte-identical machine code to hand-written. But
getting there required a new primitive, because compile-time reduction cannot cross a runtime
loop boundary. That limit is exact, and it is the first thing the atom cannot do.**

---

## 1. There is no struct primitive

A point is Church-encoded — a function that hands its fields to a selector:

```lisp
(def point (fn (x y) (fn (sel) (sel x y))))
(def px    (fn (p)   (p (fn (x y) x))))
(def py    (fn (p)   (p (fn (x y) y))))
```

The same encoding made `vec` disappear entirely in `dot.oro`. The question was whether it
survives a point that a **loop carries**.

## 2. It does not, and the residual says so precisely

Two versions were reduced side by side.

**Scalar accumulator** — the point is built and destructured *inside* the loop body, so β has a
constructor to match against:

```lisp
(fn (ps) (fold-range 0.0 (plen ps) (fn (acc i) (add acc (xat ps i)))))
```

The point vanished completely. `(px (pat ps i))` became `(xat ps i)`.

**Compound accumulator** — the accumulator is itself a point:

```lisp
(fn (ps) (fold-range (fn (sel) (sel 0.0 0.0)) (plen ps)
           (fn (acc i) (fn (sel) (sel (add (acc (fn (x y) x)) (xat ps i))
                                      (add (acc (fn (x y) y)) (yat ps i)))))))
```

**Closures survive into the residual.** `(fn (sel) (sel 0.0 0.0))` is an allocation, and
`(acc (fn (x y) x))` is an indirect call — per iteration, on any target.

This is [q5 §4](../../docs/spec/q5-do-we-need-rules.md)'s counterexample, predicted on paper and
now produced by running code.

## 3. The limit, stated exactly

`fold-range` is primitive. Its step function becomes the loop body, so `acc` is a **loop-carried
variable** and there is no constructor for β to match. Nothing can be done about that by
reduction: the accumulator crosses an iteration boundary that exists only at runtime.

> **Compile-time reduction eliminates any abstraction that does not cross a runtime loop
> boundary. Loop-carried state is exactly what survives.**

That is not a defect — it is the same statement as the grading story. Loop-carried state is used
*n* times, so it is grade ω, and grade ω is by definition what survives to runtime
([s1](../../docs/derivations/s1-substructural.md)). The two accounts agree, which is some
evidence both are right.

The consequence is a design rule: **loop-carried state must be primitive-shaped** — something the
target can hold in locals.

## 4. The fix: an n-ary loop primitive with a finisher

```lisp
(fold-range2 x0 y0 count stepX stepY finish)
```

Two scalar accumulators, one pass, and a finisher `(fn (ax ay) result)` applied after the loop.

The finisher matters more than it looks. Without it the loop produces two values and a function
returns one, so compound state would have to cross the *loop's exit* boundary as well. With it,
**compound state never escapes the loop in any direction** — it is created, carried, and consumed
inside the primitive.

The source stays clean; the encoding still vanishes:

```lisp
(fold-range2 0.0 0.0 (alen xs)
  (fn (ax ay i) (add ax (px (pat xs ys i))))
  (fn (ax ay i) (add ay (py (pat xs ys i))))
  (fn (ax ay)   (add ax ay)))
```

reduces to a residual mentioning only `add`, `alen`, `aindex`, and `fold-range2` — no `point`,
no `px`, no `py`, no closures.

## 5. Emitted

**Go**

```go
func GenCentroid(xs []float64, ys []float64) float64 {
	ax, ay := 0.0, 0.0
	n1 := (len(xs))
	for i := 0; i < n1; i++ {
		ax, ay = (ax + (xs[i])), (ay + (ys[i]))
	}
	return (ax + ay)
}
```

**JavaScript** — note the difference, which is [g2 §6](../../docs/derivations/g2-structs.md)'s
parallel-assignment hazard arriving in the emitter. Go has tuple assignment; JS destructuring
allocates an array, so the simultaneous update needs temporaries:

```js
export function genCentroid(xs, ys) {
	let ax = 0, ay = 0;
	const n1 = (xs.length);
	for (let i = 0; i < n1; i++) {
		const u2 = (ax + (xs[i])), u3 = (ay + (ys[i]));
		ax = u2; ay = u3;
	}
	return (ax + ay);
}
```

## 7. What is still not solved

**The arity gap is real and unclosed.** [g2](../../docs/derivations/g2-structs.md) found that a
Tier 1 capability can change a function's *arity* across targets: Go wants `[]Point` (AoS,
idiomatic, and measured fine), JS needs parallel arrays (SoA, because array-of-objects loses
2.86× there).

This program sidesteps it by using SoA in the *source*, which both targets can express with
primitives they already have. Getting idiomatic AoS on Go from the same source would need the
emitter to expand one parameter into two — per target. That machinery does not exist, and it is
the honest remaining piece of g2.

**`fold-range2` is not a general answer.** A third accumulator needs `fold-range3`. The general
form is either an n-ary loop primitive or the residual→residual SROA rule that
[q5](../../docs/spec/q5-do-we-need-rules.md) predicted would be the one thing δ+β cannot do. The
measurement does not decide between them; it only shows that *something* must exist, and that a
two-accumulator special case reaches parity today.

**The library leaks the arity.** A programmer writing `centroid` must pick `fold-range2` rather
than `fold-range`. That is confined to library code — callers just use `centroid` — but it is a
leak, and it is the first place requirement 7 has been dented.
