# The limb library becomes a bignum

2026-09-03. `emit/bignum.oro`, `emit/biglimb.go` (`limbShape`, `LimbSupported`,
`widenedWord`), `emit/bigrep.go` (`remByWord`), `emit/check.go`,
`emit/target.go`, `targets/{go,js,java}/bigint.oro`.

Subtraction, division and the remainder by a machine word, and the comparisons —
in two passes, and the second is where the interesting mistake was.

[bigrepr-2026-09-03](bigrepr-2026-09-03.md) left windows as the only target that
stores a bounded arbitrary-precision value as fixed limbs, so what the built-in
library implements is exactly what arbitrary precision *means* there. It
implemented addition and multiplication.

That is ADR 0019 item 4 half delivered: **a host that could add two bignums and
not subtract them.**

## 1. What the failure looked like, which is the other half of this

```
gen: sub: in argument 1 of -: a is array int, but int is required here
```

That is `(- a b)` on two values declared `(int 0 (pow 2 200))` — a legal program,
refused with a **type error naming an internal representation**. `array int` is
how the fixed-limb rung spells a bignum and nothing in the source says it.

The honest message already existed and **nothing could reach it**.
`CheckSigs` normalises every exported definition and checks it against its
signature; it called `PromoteBig`, **dropped the error**, and then type-checked
the un-promoted body against the limb signature:

```go
if p, _, err := PromoteBig(tgt, sig, nf, all...); err == nil {
    nf = p
}
```

A refusal written to explain a capability gap, swallowed one line before it
would have been printed. Reporting it is a three-line change and it is the whole
of §3 below.

## 2. Subtraction and division by a word

**`sub` is a borrow chain**, which is addition's dual and needed nothing addition
did not have. ADR 0015 forbids `again` under an `if`, so the two outcomes are
`let`-computed arguments to ONE `again` — the shape `json/tree.oro` found when
five token classes became one clause.

**The final borrow is an underflow and TRAPS**, for the same reason the final
carry of an addition is an overflow and traps. These are non-negative
magnitudes: a program declares `(int 0 N)` to reach this rung, so `a − b` with
`a < b` is a value outside its own declaration. `guard` was already exactly the
right check and took it unchanged.

**`div-small` is `a / k` for a machine word k** — one pass, one running
remainder, the exact dual of `mul-small`. It walks DOWNWARD, most significant
limb first, because that is the direction a remainder propagates; termination is
by orientation (μ = −v), which [sct-2026-08-19](sct-2026-08-19.md) already
handles.

Two things it deliberately does not say. Its column is `r · 2^24 + a[i]`, which
stays inside the window only for k under about 2^28 — **and nothing here states
that limit**, because bounded-by-default asks at the call site with the caller's
own range for k in hand and refuses if it cannot prove it. A library stating its
own limit would be stating a weaker one than the caller can. And **division by
zero is the caller's obligation**, already discharged there before the promotion
runs (integers.md §13.4); `splice` normalises this body against the caller's
actual argument, so the same facts reach the same goal.

### 2a. Support became a question about SHAPES

`big/` is now supported when its divisor is a widened machine word and refused
when it is another bignum, which needs a quotient estimate. `LimbSupported` was
a walk over NAMES and had to become a walk over applications — the same split
`big*` already has between `mul-small` and `mul`, arriving on the operation where
it is the difference between compiling and not.

## 3. The refusal names the operation now

The old message was a fixed list — *"subtraction, division or a comparison"* —
which was wrong about subtraction from the moment subtraction existed and named
none of the three for the program in hand:

```
gen: sub: this program needs comparison on an arbitrary-precision value.
  Target windows stores one as fixed limbs (big-repr) and the built-in
  limb library does not implement that; it declares no bignum of
  its own to fall back to either. What it does have is addition,
  subtraction, multiplication, and division by a machine word
  (emit/bignum.oro).
```

Three shapes, three messages: *the remainder* (whose result is a machine word
rather than a limb table, so a change of type), *division by another
arbitrary-precision value*, and *comparison*.

## 4. What checks it, in two halves that need each other

**`big-subdiv`** — the compiler's own lowering, built BOTH ways on every target
that can render the result, so our borrow chain and our one-pass division are
checked against `math/big`, `BigInt` and `BigInteger` on the same source:

```
ok  big-subdiv  [go/host go/limbs js/host js/limbs java/host java/limbs]
```

Nine inputs, digits computed independently and pinned in the file, because
agreement is not correctness — a bug in the promotion would be shared by all six
variants. **It skips windows**, and the reason is a capability rather than a
disagreement: that host can now do this arithmetic and still cannot print the
answer, because `big-str` needs a host bignum to convert through.

**`limb-subdiv`** — the same two loops written out by hand, returning ordinary
integers, so they run on **all four targets** including the one the change is
for. Two shapes otherwise untested on windows: a conditional inside an `again`
ARGUMENT, and a loop that counts DOWN. The operands are chosen so the borrow
actually fires — limb 0 of `a` is 13,008,895 against 14,000,000, and limb 1 drops
from 9,272,996 to 9,272,995 — because a case whose borrow never fired would pass
with the whole chain deleted.

Plus unit tests: windows lowers `(- a b)`, `(/ a 4)`, `(% a 4)` and
`(if (< a b) a b)` to limbs with no host bignum in sight — and asserts which of
them allocates a limb table, since a comparison yields a bool and the remainder
yields a word. Each unsupported shape is refused by name and told what is
available.

### 4a. A pre-existing x86 ceiling, found and not fixed

`limb-subdiv` at three inputs fails to build on windows:

```
x64.movb has more spilled operands than there are scratch registers
```

**It reproduces with this work reverted**, so it is a backend limitation rather
than a regression: the harness inlines `run` at every call site, and three copies
of two `build`s and two loops exceed what the register allocator can place. The
differential README already names that ceiling and says provoking it from a
harness measures the harness, so the case uses one call whose printed number
encodes both significant limbs. Recorded here because it is now a *second*
program to hit it.

## 5. Cost

**No emitted file changes** — 70 programs × 4 targets byte-identical, across both
passes. The library additions fire only on a program that subtracts, compares or
divides a big value by a word, and nothing in the corpus does. The compiler
suite, the 25-case differential suite on four targets, and the gauntlet's bignum
tests are green.

## 6. And then comparisons and the remainder, which finished the library

Comparisons are limb-wise from the top down: the first difference decides, and
equality is reaching the bottom without one. One `cmp` returning −1, 0 or 1
serves all five, and **without them a bignum could not control a loop at all** —
no `while (x > 1)`, no gcd, no Newton iteration, no exponentiation testing its
own exponent. On a target with no host bignum to fall back to, none of that was
expressible. It is an expressiveness gap rather than a slow path, which is why
it went first.

`rem-small` is `div-small`'s other half and the two are divmod — what decimal
rendering consumes, since printing a big value is repeatedly taking the quotient
and remainder by a power of ten.

### 6a. The remainder's result is a WORD, and that had to become a type

`a % k` with `0 ≤ a` and `k` a machine word is under `k`, so the answer fits the
portable window whatever `a`'s magnitude. That is a fact about the **arithmetic**
and not about anyone's storage — so every representation has to agree with it,
and the first version did not:

```
(sig digit ((a (int 0 (pow 2 200)))) int)
(def digit (fn (a) (% a 100000000)))
```

**Accepted on the fixed-limb rung** (the loop naturally returns a word) and
**refused on the host's bignum** (`big%` yields a bignum against a declared
`int`). Selecting a representation would have changed which programs are LEGAL —
ADR 0009 at the representation boundary, the same thing `big-fit` exists to
prevent for the bound, and the invariant established two commits earlier.

So `big%-small` is its own operation with an `int` result, declared on the three
hosts that have a bignum and lowered to `rem-small` on the limb rung. **It is not
a new kind of thing**: `big<` is already a big operation with a non-big result.

### 6b. Two bugs from the same mistake, in two places

`bigTerm` decides whether an expression is arbitrary-precision, and it *decides
rather than observes* — it walks UNPROMOTED arithmetic. So `(% (/ x 10^8) 10^8)`
looked big because an operand was, the sum above it became a `big+`, and that
refused its own operand:

```
in argument 1 of big+: big%-small is int, but big is required here
```

and on the fixed-limb rung the same mistake indexed an `int` as a table
(`invalid argument: a5 (variable of type int) for built-in len`). The rule now
lives in **one** function, `remByWord`, read by both `selectBig` and `bigTerm`,
because answering differently in the two is precisely what broke. Plus a
one-word Go fix: `Int64()` is an `int64` and our `int` emits as `int`.

## 7. A limitation found on the way, and it is the one rendering will hit

**A big value declared on a HELPER's signature is not promoted once reduction
inlines that helper.** Written as

```
(sig scaled ((n (int 0 50))) (int 0 (pow 2 200)))
(def scaled (fn (n) (loop ((acc (+ n 7)) (i 0)) (>= i 6) acc else (again (* acc 999983) (+ i 1)))))
(sig run ((n (int 0 50))) int)
(def run (fn (n) … (scaled n) …))
```

the program is **refused**: four integer operations cannot be proven in-window,
because after inlining nothing tells the solver the accumulator is meant to be
arbitrary-precision. The declaration is a BOUNDARY and inlining removes it —
refinements.md §6b's limit, arriving on the representation solver for the fifth
time.

It is not a silent wrong answer (bounded-by-default refuses), and a big LITERAL
seeds the promotion without any signature, which is how `big-divmod` is written.
But **it is the exact shape decimal rendering has**: the big value is internal
and every result is a word. Recorded rather than worked around, because it is a
design question — what survives inlining — and not a bug to patch.

## 8. What windows still cannot do

**Print.** `big-str` is *"not bound … not a primitive on this target"*, so a
program there can compute an arbitrary-precision value and never observe it.
Decimal conversion from limbs is repeated division by a power of ten —
`div-small` is exactly that operation, so the arithmetic half is now in place and
what remains is a string surface (docs/spec/strings.md).

Still absent, and now it is exactly the two operations that need a **quotient
estimate**: division and remainder by another arbitrary-precision value (Knuth
D). Nothing has asked for them.

**And the binding constraint on windows is no longer the library, it is the x86
register allocator.** `big-divmod` cannot be built there at any size that also
exercises what it tests — it fails at ONE input with two comparisons, and with
the big value built by a loop rather than a literal, so it is program SIZE and
not any construct. That is the third case to hit the ceiling. If arbitrary
precision on windows is to be used for real, that is the next thing to fix, and
it is a backend question rather than an integer one.
