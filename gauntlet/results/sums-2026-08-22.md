# Sums on four targets, 2026-08-22

The sum, built after [the product](multiresult-2026-08-22.md) and [`match`](../../docs/spec/match.md),
in the order [type-algebra §8](../../docs/type-algebra.md) argued for. Spec:
[sums.md](../../docs/spec/sums.md).

Three things were genuinely unknown. Two are now measured and one turned out to be a
benchmark-method problem rather than a result.

---

## 1. Parity

`examples/sum/parse.oro` — a function returning `(sum result (ok int) (err int))`, consumed by a
hand-written Go caller. Medians of five, `-benchtime=2s`.

| | ns/op | allocs/op | |
|---|---|---|---|
| hand-written, tag and payload | 118.4 | 0 | |
| **emitted** | **118.3** | **0** | **1.00×** |

```go
func SumStep(a int, b int) (int, int) {
	if (b == 0) {
		return 1, 1
	}
	if ((a % b) > 0) {
		return 1, 2
	}
	return 0, (a / b)
}
```

That is *literally* what a Go programmer writes, which is the point: a sum is Σ, so its value is a
tag and a payload, and Go's `(T, error)` idiom is already that shape. Go is the host with **no sum
type** and it needed nothing.

## 2. The measurement that did not work, recorded rather than dropped

The interesting comparison was meant to be against Go's own answer — the `error` interface.

| | ns/op | allocs/op |
|---|---|---|
| emitted sum | 118.3 | 0 |
| `(int, error)` with **sentinel** errors | 126.6 | 0 |
| `(int, error)` with a **constructed** `&stepErr{}` | 118.3 | **0** |

**Neither row supports a claim.** The sentinel difference is 7%, and this machine has a ~15% noise
floor, so it is not a result. And the constructed-error row reports **zero allocations**, which is
not what that code says — `go build -gcflags=-m` shows `&stepErr{...} escapes to heap` inside
`handErrAllocStep`, but the benchmark **inlined** the function into the loop, after which escape
analysis at the call site removed the allocation.

So the microbenchmark measured a version of the program that does not allocate, and the question
"what does a constructed Go error cost" is still open. The obvious fix — `//go:noinline` — is
exactly the one-sided error already recorded in
[native-js-2026-08-20](native-js-2026-08-20.md) and in the Go harness before it, because **the
generated function cannot be marked** and marking only the hand-written side reports a difference
that is not there.

The honest summary: **the emitted sum reaches hand-written parity, and this build says nothing
about the `error` interface.**

## 3. Case-of-case perturbs nothing

[type-algebra §8](../../docs/type-algebra.md) put case-of-case last and conditioned it on measuring
whether it changes any existing residual. It was measured before the rule shipped.

**184 residuals** — every program in `examples/` reduced against all four targets — with the rule
on and with it off. `diff -rq`: **no differences.**

The rule fires only where an eliminator meets a constructor across a branch, and no existing
program has a sum. It is purely additive.

## 4. What the build taught that the argument had not

**The static sum needed `=` to fold.** The Church-encoded sum reduced away exactly as
[sums-research §0](../../docs/sums-research.md) said — and then left `(if (= 0 0) … …)` behind. The
tag became a literal; the *comparison* did not. One narrow rule fixed it, and its narrowness is the
interesting part: integers only, `=` only, because ADR 0009 permits folding only where compile time
and run time provably agree, and float arithmetic is where they famously do not.

**Case-of-case needs a `let` companion, and only a nested test finds this.** A two-level sum reduced
completely; the three-level test stopped at `((let v (fn (#p) …)) K)`. β itself puts the `let`
there — a shared subterm that is not duplicable gets bound (ADR 0010) — so the eliminator ends up
outside a *binder* rather than outside an `if`. The general statement is better than the specific
one: **push an eliminator through anything β can leave in operator position**, which here is
exactly `if` and `let`.

**A function returning a sum returns from several places.** `multiValue` recognised one product at
the top of a body, which is all `values` ever needed. A sum's body is a *tree* of returns, so each
backend gained `multiTail`, walking `if` and `let` to the leaves and returning at each. The same
two forms again — and on V8 this is also the 1.31× that
[native-js-2026-08-20](native-js-2026-08-20.md) measured for a tail `return` over a result
variable, arriving a second time from a different direction.

**Exhaustiveness removes a branch rather than adding one.** Because a sum is closed and finite, the
last clause needs no test. That was not the argument for checking exhaustiveness, and it is a
better one.

**And the refinement layer had to be taught the language's `=`.** An error check is
`(if (= b 0) (err …) (ok …))`, so the fact the ok-branch needs — `b != 0` — comes from negating the
language's own equality and nothing else. Without it the division inside the ok-branch could not be
discharged even though the guard directly above it says exactly what is required.
[sums-research §5.3](../../docs/sums-research.md) predicted refinements would need nothing new; it
was one line in a table, but it was not nothing.
