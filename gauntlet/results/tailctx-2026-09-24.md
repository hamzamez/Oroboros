# A host call's continuation is a tail position

2026-09-24. The build of [ADR 0027](../../docs/decisions/0027-a-host-calls-continuation-is-a-tail.md),
which hamza chose as option A after [u128-2026-09-23](u128-2026-09-23.md) §4 met the same wall three
times. The spec came first: the ADR, iteration.md "Where `again` may appear", binding.md §7 and
values.md §4b.

## 1. What it is

The positions a jump may occupy are the tail contexts

```
E ::= []  |  let x = e in E  |  if c E E  |  (p a…) (λx̄. E)
```

The fourth line is new. `p` is a primitive with n ≥ 2 declared results, and `λx̄` is its
continuation, the n-ary let. It holds because that continuation is **second-class**: it runs once,
immediately after the call, and never escapes. Every backend emits it as the call followed by the
body's statements in the same block. This is the known-continuation case of CPS compilation (Appel
1992; Kennedy 2007), where a jump needs no closure.

In source, `(let (tuple b err) (r.ReadByte) (again …))` is now a binding that may wrap an `again`,
as a one-name `let` always could. A lambda handed to one of the program's own functions,
`(f (fn (a b) (again …)))`, desugars to the same shape and stays refused, because it may run twice,
never, or later. The reader tells the two apart by a mark it puts on the tuple pattern it desugars,
and erases the mark before any form leaves it.

## 2. What was built

| layer | change |
|---|---|
| reader | the tuple-pattern mark, checked by the clause rule and erased at every entry point (`core/let.go`, `core/read.go`) |
| type checker | `loopBody` walks a host call's continuation, **and a one-name `let`**, and checks the `again` inside |
| interval analysis | `collectAgain` walks the continuation as a back edge, binding each parameter from the call's declared results (`bindMulti`, now shared with `multiPrim`) |
| monotonicity | all three walks take the continuation; its parameters are never assumed `⊒ S` |
| `soleExit` | walks into the continuation |
| Go, JS, Java | `emitMultiPrim` split into a head (the call and its receiving statements) and the rest; the loop body and the several-results return call the head and go on inside |
| Go, Java | a several-results signature spells each result in its value type |

windows declares no host call with several results, so it has nothing to emit.

## 3. What failed first, and it was the point of the spec

The ADR said that every walker enumerating back edges must see the new form, or be unsound. I built
the reader and the Go emitter first to see a loop run, and the first program showed why the ADR says
that. With only those two in place, cmd/gen accepted and emitted

```lisp
(let r (loop ((x 0)) (= x n) x
        else (let (tuple s c) (b.Add64 5 6 0) (again (+ x 1))))
  (* r 3037000500))
```

reporting **"2 of 2 integer operations bounded; 1 of 1 loop(s) proven terminating"**. The interval
pass never saw `x` grow: `collectAgain` walked only `if` and a one-name `let`, and read the
continuation as an exit. So `x` stayed [0, 0], the product was "proven", and a loop that diverges for
any negative `n` was "proven" to terminate. The same loop with a bare `again` gives 0 of 2 and 0 of 1.

The second false proof was in `monotoneStep`, whose comment stated ADR 0015's rule as an assumption:
*"An `again` is only ever a clause body or under a `let`, so the branches of the clause chain are the
only other places to look."* A counter falling inside the continuation was certified
non-decreasing, and an index `(t v)` was accepted with `v` possibly negative. The same loop with the
`again` bare refuses on `(<= 0 v)`.

Both are fixed, and each has a witness that compares against the bare form.

## 4. Two faults the new paths reached

1. **`again` under a one-name `let` was never type-checked.** `loopBody` sent a `let` to the general
   walk, where `again` is no primitive, so its arguments went unchecked: a string handed to an `int`
   loop variable passed the checker, leaving it to the host compiler, and on JavaScript nothing
   checks it (types.md). No program in the corpus relied on it, and all emission is byte-identical
   under the check.
2. **A several-results return with a small range did not compile, on Go or on Java.** The result's
   type was spelled with its narrowest storage type, so `(tuple (int 0 1) int)` gave a Go signature
   `(byte, int)` and a Java record `(byte f0, long f1)`, each receiving an `int` / `long`. javac:
   *"possible lossy conversion from int to byte"*. It predates ADR 0027: no export in the corpus had
   such a result until `num/u128`'s `add` became compilable. Each result is now spelled in the type
   that holds its value.

## 5. Checked, and how each check can fail

Every test below was run against the fault it pins, with that case removed, and failed:

| test | pins |
|---|---|
| `TestAgainReachesThroughAChainOfBindings` (core) | the reader accepts `again` under a tuple pattern, still refuses it in a program's own lambda and under `if`, and the mark does not leak |
| `TestABackEdgeInAHostContinuationIsSeen` | `collectAgain`; the answer must equal the bare loop's |
| `TestMonotonicityChecksAnEdgeInAHostContinuation` | `monotoneStep`, with a rising control that must still be proven |
| `TestAgainIsCheckedUnderEveryBinding` | `loopBody`, for the continuation and the one-name `let` (the witness keeps the `let` alive by using its name twice) |
| `TestASeveralResultsReturnUsesTheValueType` | the Go signature |
| differential `read-loop` (Go, JS, Java) | each emitter's loop body: removing any one fails the case |

`read-loop` alternates a file that exists with one that does not, so on JS and Java, whose `ReadFile`
templates assign from a `try`/`catch`, both arms run: `0 1 1 4 5` on every host.

## 6. What it bought

- **u128's step emits one `mulw`**: 2 `Mul64` and 1 `Add64`, where the per-component workaround emitted
  6 and 3. `factorials` still prints the 36 lines Python gives.
- **`lib/num/u128.oro` compiles on its own**, all four exports, and `go vet` passes on the output.
- **A read loop can be written**, which `bufio` needs.
- No existing program's emission moved: the accepted changes are `factorials`, `u128.oro` and the new
  case. Proof counts: 2,368 of 2,419 operations, 349 of 387 loops (+2 from `u128.oro`'s own loops;
  `digits18` is proven and `decimal` is not, for the reason its comment gives).

## 7. What was not built, and what was found in passing

- `decimal` keeps `Rem64` for its digit group. `divw`'s remainder would do the same job now that the
  loop can bind all three results, but its bound r < y is a law of Div64's tuple, which cannot be
  stated.
- **An internal definition's declared parameter range is not checked at the calls it is inlined
  into.** `(sig g ((x (int 0 9))) int)` called with `n ∈ [0, 1000]` is accepted. The `decimal`
  experiment exposed it: a `divw` remainder, only known to be ≤ 2⁶⁴−2, was accepted by `digits18`,
  which declares ≤ 10¹⁸−1. It predates this work and is raised as a separate task.
- `soleExit` and `loopExitsFit` treated the new form as an exit they could not vouch for, which is
  safe. Each now walks into it anyway, for uniformity.
