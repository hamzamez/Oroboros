# One application on two hosts, and the five compiler bugs it found

2026-09-11. `examples/tally/` — `tally.oro`, `tally-go.oro`, `tally-java.oro`, `access.log` — with
fixes to `core/reduce.go`, `core/hygiene.go` (new), `emit/check.go`, `emit/interval.go`,
`emit/golang.go` and `emit/java.go`, and four application cases in `gauntlet/stdlib/tooling_test.go`.
[assessment-2026-09-11](../../docs/assessment-2026-09-11.md) item 3: *one real program reaching a host
API by generated declarations on two hosts, which tests all three layers at once.*

> **`tally PATTERN FILE` RUNS ON GO AND THE JVM AND AGREES WITH A HAND-WRITTEN REFERENCE.** For every
> line the pattern matches it takes capture group 1, and prints each distinct value with its count,
> most frequent first — `grep -o | sort | uniq -c | sort -rn`, with **the host's own regex engine**,
> RE2 on one host and `java.util.regex` on the other. **One 97-line core, bound by 15 lines on Go and
> 19 on the JVM**, every host call a declaration `survey.go` or `jvm.go` generated. On the sample log
> and on `CLAUDE.md` (61 distinct values) the two hosts are byte-identical to each other and to
> `grep | sort | uniq -c`; usage, a missing file and no match agree too.
>
> **IT NEEDED NO NEW MECHANISM.** The six host operations are a static-level ARGUMENT — a negative
> product `(values compile hit? capture cmp lines show)` — and reduction erases it, so the residual is
> one first-order function per host with the host's calls written straight in. An ML functor applied
> at compile time, and the reason the core can hold a regex it has no type for: the residual is typed
> after reduction, when it is a `*regexp.Regexp` on one host and a `Pattern` on the other.
>
> **AND WRITING IT FOUND FIVE COMPILER BUGS, TWO OF THEM EXPONENTIAL.** Every construct it uses was
> already in the differential suite, which passed; what was new was the program's SIZE and a string
> table read handed to an impure host call. Each is pinned by a test that fails against HEAD.
>
> | | where | what it did |
> |---|---|---|
> | 1 | reducer | a λ that reads a table was never substituted into an impure body, so the interface reached the emitter as an "escaping closure" |
> | 2 | reducer → every consumer | a let-bound argument took a hint that CAPTURES once the residual is opened by name — Go refused `cannot use i5 (variable of type byte) as int value` |
> | 3 | checker | a binder's type outlived its body, so a sibling with the same hint was checked against a stranger's type |
> | 4 | interval pass | five evaluations of every comparison operand per `if`: **exponential in nested conditions** |
> | 5 | Go and Java emitters | every λ walked twice, each walk running an interval analysis per `build`: **exponential in nested lets** |
>
> **The build went from not finishing in 500 seconds to 3 s on Go and 12 s on the JVM.**
>
> **AND A PUBLISHED NUMBER WAS COUNTING THE WRONG THING.** "N of N integer operations bounded"
> counted EVALUATIONS: `freq.oro`'s **872 of 872 is 324 of 324**, and its 33 of 37 loops are **27 of
> 31** — the same four unproven. Every ratio stands; every magnitude with a comparison over a
> computed operand was inflated.
>
> **Cost: 178 emitted files swept, 175 byte-identical**; the three that moved are `limbs.oro` on
> three hosts, one variable renamed by bug 2's fix and nothing else. Differential suite green on four
> targets, tooling suite green.

## 1. The shape

```
tally.oro        97 lines of code   the tool; names no host
tally-go.oro     15                 regexp.MustCompile, Regexp.MatchString, Regexp.FindStringSubmatch,
                                    strings.Compare, strings.Split, strconv.Itoa
tally-java.oro   19                 Pattern.compile, Pattern.matcher, Matcher.find, groupCount,
                                    start(int), group(int), group(), String.compareTo,
                                    String.split(String,int), Long.toString
```

The core is `freq.oro`'s structure over the host's strings rather than byte spans: count the matching
lines, build a table of captures, merge-sort a permutation of it with the host's comparison, count
runs, sort the runs by count, render. The report is built by `concat`, render.oro's free monoid.

Each binding is eleven-odd lines of a `(values …)` and `(def main (fn () (tally.run host)))`. Nothing
under `targets/` was edited: the generated files go in a project layer, as the acceptance programs'
do.

**target-system.md §6.2 specifies the mechanism that would delete the two bindings** — `D_T`, a
target's own library, so `(use tally)` picks each host's operations through the capability graph and
there is one `main`. It is not built, and this is its price, measured: two files of 15 and 19 lines.

## 2. The two hosts are not the same host

Four places the hosts differ, each found by running the program and not by reading about it.

**A matcher is state.** Go matches with one call; the JVM builds a `Matcher` and asks it, and `find`
advances it — so each question gets its own, and the generated `find` is correctly impure.

**`split` is a regex and drops trailing empties.** `"a\n".split("\n")` is one string on the JVM and
Go's `Split` gives two. The binding uses `split(String, int)` with a limit of −1, which keeps them —
a different overload, which the generator names `split2`.

**A group that takes no part is `null`.** `(a)?b` on the line `b` matches with group 1 absent: Go's
`FindStringSubmatch` gives `""`, the JVM's `group(1)` gives `null`, and the merge sort's `compareTo`
threw a `NullPointerException`. **The generated declaration types `group2` as `string`, and Java's
`String` is nullable** — so every reference-typed result the JVM survey counts is a claim the host
does not keep. The binding asks `start(1)` first, which is −1 exactly when the group took no part, and
both hosts answer `""`. That input is one of the four suite cases.

**A bad pattern ends the program on both, differently.** `MustCompile` panics; `Pattern.compile`
throws `PatternSyntaxException`. Symmetric, and a partial call the program cannot test on either host:
Go has `Compile` returning `(re, err)`, which would totalise, and **a generated JVM declaration cannot
catch** — the template that catches is written by hand (portableio-2026-09-09) — so the Go binding
takes the partial form too, to agree.

## 3. The five bugs

**Bug 1 — a λ that reads a table was refused substitution.** effects.md §7c: a term that reads a table
through a bound variable is not substituted into an impure body, which is what stops a buffer read
moving across a store. But a λ performs no read until it is APPLIED, and its applications are already
in the body where the programmer wrote them, so substituting it moves no evaluation. The comparator
`(fn (u v) (< (cmp (cs u) (cs v)) 0))` was let-bound as a bare λ, and so was the continuation handed
to the host dictionary — which reached the emitter as *"a bare abstraction … an escaping closure"*.
**`freq.oro` escaped only because its comparator hides the read behind a call to `wcmp`.** Fixed by
exempting a λ, pureTerm's own reason.

**Bug 2 — a residual's names did not say what its indices say.** Reduction never opens a body, so
inside it a hint is only a hint. Every consumer — checker, refiner, interval pass, backends — opens
with `Body()`, turning each index into its binder's hint. β let-bound a comparator's arguments under
hints `a` and `b` inside a sort whose buffers are hinted `a` and `b`:

```
(let (cs (pat a n j)) (fn (a) (let (cs (pat a n i)) (fn (b) …))))
```

correct by index, and the second value's `a` — the BUFFER — opens as the first value's STRING.
`core/hygiene.go` renames exactly the binders whose hint equals a name their body refers to past them,
and nothing else. **The witness is not argued**: with the pass disabled, `tally` fails in **Go's own
compiler** — `cannot use i5 (variable of type byte) as int value in assignment` — so a backend really
did emit the capture. It is the `Body()`/`openFresh` family a fifth time, arriving from the reducer.
It also fired on `limbs.oro`, which is the one file the sweep saw move: a variable renamed, since that
backend had been freshening its names and so was already right.

**Bug 3 — the checker's binder types outlived their bodies.** `types` is one map keyed by name. A
`let` wrote its binder's type and never removed it, and when a value's type was unknown — a table
read — it wrote nothing, so the older entry stayed: `dists`'s `(fn (s) …)` binds an int, the host's
`(fn (r s) …)` let-binds a string read under the same hint, and the checker said *"s is int, but
string is required"*. **Every program before read bytes, so every leaked type was `int` and happened
to be right.** One helper, `bind`, now scopes all six binding sites — and `iterate` had a seventh leak
of the same kind: it bound each loop variable before walking the next variable's initialiser, which is
outside the loop's scope.

**Bug 4 — the interval pass was exponential in nested conditions.** `cond` evaluates the condition,
then `refine` runs once per branch and evaluated BOTH operands of the comparison each time: five
evaluations of every operand per `if`, and an operand containing an `if` pays five again. A clamped
table read is two nested `if`s, and `new?` puts two of them under a comparison under a clause.
`narrow` can only act on a variable, a `len` or a square, so an operand is now evaluated only when the
other side is one of those — which loses no fact, since narrowing anything else was always a no-op.
The test is forty nested conditions: 5^40 under the old rule.

**Bug 5 — the Go and Java emitters walked every λ twice.** `inferLet` recursed into a λ's CLOSED body
through its children and then into the OPENED one, doubling at every level, and each `let` of a
`build` met on the way asks `typeOf`, which runs a whole interval analysis of the build. The profile
put 34% of a 295-second build there. The closed walk contributed nothing — the opened walk used the
same hints and ran after it at every level — so it is gone, and **all 178 emitted files are
byte-identical across that change**.

| build of tally | Go | JVM |
|---|---:|---:|
| bugs 1–3 fixed | killed at 500 s | killed at 500 s |
| and bug 4 | 151 s | 218 s |
| and bug 5 | **3 s** | **12 s** |

## 4. What "N of N operations bounded" was counting

Bug 4's fix moved `tally`'s note from 73 operations to 59, which is how this was found. The interval
report counts an operation each time the pass EVALUATES it, and `refine` re-evaluated comparison
operands — including loops sitting inside conditions, which is why the loop count moved too.

| | HEAD | now |
|---|---|---|
| `freq.oro` | 872 of 872, 33 of 37 loops | **324 of 324, 27 of 31 loops** |
| `jsonfmt.oro` | 99 of 99, 13 of 13 | 99 of 99, 13 of 13 |
| `wc.oro` | 2 of 2, 1 of 1 | 2 of 2, 1 of 1 |

**No ratio moves and no emitted code depends on the count** — narrowing reads the JOIN of the
intervals, which a repeat does not change. What was wrong is the magnitude of every figure over a
program that compares computed operands, and product-2026-09-09, freq-2026-09-08, portableio and
products.md are annotated. The four loops `freq` cannot prove are the same four, the merge sort's.

## 5. What it leaves

**`D_T`** — the target library target-system.md specifies — would make this one `main`. Measured
price of not having it: two binding files, 34 lines.

**Generated JVM declarations make two claims the host does not keep**: a reference result may be
`null`, and a call may throw. The first is now priced by an input where it bites; the second by a
program that crashes on a bad pattern on both hosts.

**The balance, since that is what item 3 was for**: 131 lines of Oroboros and an 82-line sample,
against 190 changed lines in five compiler files and a new 129-line one — most of both being the
explanations of five bugs that every smaller program had walked past.
