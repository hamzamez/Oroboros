# A value in [0, 2⁶⁴) on the JVM and V8

2026-09-22. `gauntlet/js/u64repr.mjs`, `gauntlet/java/U64ReprBench.java`. The measurement
[ADR 0026](../../docs/decisions/0026-an-int-is-an-integer.md) (10) defers to, and §9 of
[what-an-int-is.md](../../docs/what-an-int-is.md) named before anything was built: a value proven in
[0, 2⁶⁴−1] is native on Go (`uint64`) and windows (unsigned qword). The JVM has no unsigned type and
JavaScript has no 64-bit integer. What should hold it there?

## 1. What is being chosen, and the theorem that licenses the candidates

The quotient map `q : ℤ → ℤ/2⁶⁴` is a ring homomorphism, and a 64-bit machine word (signed or
unsigned) is a set of representatives of ℤ/2⁶⁴. So for `⋆ ∈ {+, −, ·}`:

```
q(a ⋆ b) = q(a) ⋆ q(b)
```

If the result is **proven** to lie in a realization R (a set of representatives), then its residue
names exactly one member of R, which is the result. So `+`, `−` and `·` may be computed with
wrapping in *any* 64-bit type and read back in R. The quotient does **not** preserve order, so `<`,
`/` and `%` need a realization containing both operands, or unsigned operations.

Every candidate below is correct on every input by that argument, and the harness checks each
against the host's bignum on the same data.

## 2. The kernels

What a `uint64` does in the next two packages:

- **decode** — `binary.BigEndian.Uint64`: `v = Σ bᵢ·256^(7−i)`, and a running maximum under unsigned
  order. Multiply by a small constant, add, compare.
- **digits** — `strconv.FormatUint`'s loop: `r = v % 10`, `v = v / 10` until zero. Division, which the
  homomorphism does not license, over the whole 64-bit range.

1,024 pseudo-random 8-byte records, whose values are spread over [0, 2⁶⁴), so most exceed 2⁶³ and
all exceed 2⁵³. Nanoseconds per value; best of five reps in each of three processes, one variant per
process; the three processes are listed. The laptop drifted ~1.3× during the first JS pass and those
numbers were discarded.

## 4. What it says

- **The JVM: `long` holding the residue, by 60× on decode and 8× on division.** On multiply-add it is
  within 1.25× of a signed `long` — the homomorphism makes it the same instructions — and within
  1.15× of Go's `uint64`. Division costs 2.8× a signed `long`, because JDK 17's
  `Long.divideUnsigned` is a library call; it is still 8× ahead of `BigInteger`.
- **V8: the split pair, by 4.8× on decode and 4.3× on division.** Its division is within 1.3× of a
  plain Number's (which is wrong on this data), because long division by a small constant is two
  exact float divisions.
- **`asUintN` is a trap worth recording.** V8 lowers `BigInt.asUintN(64, a·b + c)` to machine words,
  and on multiply-add it ties the split pair. On division it is **1.27× worse than plain `BigInt`**.
  A representation chosen from one kernel would have picked it.
- **One rejected variant**, for the method record: computing the split carry with `(t / 2³²) >>> 0`
  instead of `Math.floor(t / 2³²)` was **1.6× slower** (62 vs 39 ns, same session), though it looks
  like the cheaper operation.

## 5. What this decides, and what it does not

- **The JVM's realization of [0, 2⁶⁴−1] is `long`, with unsigned comparison, division and
  printing.** It is a representation, like Java's `int` for a counter bounded by a length
  (indextype-2026-08-25): the integer is the same, the host type is the fastest one that holds it.
- **V8's is the split pair**, and it is a new representation class for the JS emitter: one value in
  two locals, which is how products are already flattened (products.md) but for a scalar. **It is
  not built.** Until it is, a value above 2⁵³ on JS is `big` — `BigInt` — by ADR 0026 (5), which is
  correct and 4–5× slower, and says so because someone declared the range.
- **Nothing here measures signed 64-bit on V8.** A signed split pair has the same operation count
  plus a sign; it should be measured when the rung is built, not inferred from this.
- **Parity with hand-written code** is not the question here: these are hand-written candidates,
  and the question is which representation to emit. Parity is measured when one is emitted.
