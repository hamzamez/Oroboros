# wc-2026-10-24: a word count over files, program first, and `unicode`

The 10-21 plan's item 3: the Go library, program first, written by hand in J, what the reader catches
counted. The program is `examples/os/wc.oro`, `wc [FILE]…`: the lines, words, characters and bytes of
each file, read in chunks, then their total.

## 1. What it is

A file is x ∈ B*, and d : B* → Σ′* is the decoding Go's `utf8.DecodeRune` defines (each byte that begins
no codeword is one error rune).

| count | algebra |
|---|---|
| bytes C = \|x\| | the length homomorphism (B*, ·) → (ℕ, +) |
| lines L = \|x\|₁₀ | a letter count; LF is never inside a codeword, so also the runes `\n` of d(x) |
| characters M = \|d(x)\| | not a homomorphism over reads, since a codeword may be cut; d is a sequential transducer with **look-ahead 4**, so decoding at k only while 4 bytes remain, or at the end, decodes each chunk as the whole input decodes, and the carry is the tail of fewer than 4 bytes |
| words W | the maximal runs of runes outside S = White_Space, the fold of a two-state machine over d(x) |

So the output is a function of each file's bytes, whatever the reads were.

## 3. What writing it by hand caught

In the order met. None was a fault of J's lexer or parser. Each was a rule of the language or a gap in
an analysis, and each is fixed, written around, or put as a question:

| # | caught by | what | what was done |
|---|---|---|---|
| 1 | the reader | **"a case arm is no tail"**: `case gos.Open(name) { 'err(e) -> again(…); 'ok(f) -> again(…) }` in a loop. abstract.md §2.5 and ADR 0057 let one arm continue a loop, `try`'s success arm, and every other arm leave it | written around: `open(name)` gives `(File, Bool)`, 1 + File held as its tag and slot by hand, standard input the filler. **A question for hamza (§6)** |
| 2 | the compiler | "an `again` sits inside the body of a tuple pattern whose value comes from a loop": a loop copying the tail inside the read arm hands the buffer back as a tuple (tables.md §2.5, not built) | three guarded stores, t ≤ 3 |
| 3 | the refinement layer | `os.Exit(status)`, status a loop variable in {0, 1}: Exit's `where` was decided only by the refinement layer, which does not see a loop's exit value | **built**: a `where`'s constant bounds on one parameter are its range obligation, decided by a literal, the IR's intervals, then the refinement layer (`emit/wherebounds.go`, ADR 0062's bounds in binder sets). The plan's deliberately-not-next "a host `where` on the IR's intervals", now named by a program |
| 4 | the refinement layer | the window's end n ≤ len b after a read, through the read's law | stated as a binder's claim, `end ∈ 0..size_buf = t + got`, proven, as `shape` does |
| 5 | the refinement layer | a guarded store, `if t > 0 { b[0] := b[k] }`, made the read's buffer argument `(if (> t 0) (set b 0 …) b)`, and its length an unknown apart from len b | **built**: a length is keyed by what it denotes (refinements.md §5b, `lengthSubject`): len ∘ set = len ∘ π₁, and len commutes with a conditional whose arms agree |
| 6 | the refinement layer | the name index av[i + 1] under a boolean flag `stdin`: a fact is read off a comparison, and a failed disjunction inside a guard resolved nothing | the inputs as a word of names, ⟨""⟩ or av's FILEs, so the guard i ≥ len(names) bounds the read |
| 7 | the IR's decision | the file counter i + 1 in the arms that finish a file, bounded only by a path-sensitive invariant | counted where the next file is opened, under the failed guard |

Building 3 found that `TestAStatusIsBoundedByItsExits` pinned a **false refusal**. Its "an exit of 3i, up
to 300" exits only while i < 50, since the arm `i == 50` exits first, so 3i ≤ 150. The IR's intervals
prove it, and 5i (≤ 250) is accepted and 6i (≤ 300) refused, as computed by hand. The case is now 6i, and
3i is a control that must be accepted.

A first attempt at 3, narrowing `Exit`'s parameter to `code ∈ 0..255`, broke two of the hand check's
planted mistakes (`Len64` given a 32-bit argument, `IsSpace` over a byte). A narrowed parameter is,
mechanically, a transposed function. It was reverted, and the route was changed instead of the
relation (CLAUDE.md: a relation relaxed for one check weakens every check that reads it).

## 4. The corpus, and the speed

`cmd/check`, every step: pass, with 4 changes, all `examples/os/wc.oro`'s (a new source on four targets;
it is a Go program, refused on the others). No other program's emission, outcome or refusal text
changed under the `where`-bounds normalisation (ADR 0075) or the length key. Counts: 2,100 of 2,145
operations (`wc`'s 36, all proven) and 353 of 376 loops (`wc`'s 2, a loop that reads a file, unproven as
`shape`'s is).

**Speed**, on a 100,000,002-byte file of mixed ASCII and multibyte words, all four programs giving the
same four counts. Medians of 7 alternating runs, each run alone:

| | ms | ratio |
|---|---|---|
| generated `wc` | 607 | |
| hand-written Go, the SAME shape (one loop over a cursor, saturating counts) | 601 | generated / it = **1.01** |
| hand-written Go, nested loops (a rune loop inside the read loop), saturating counts | 519 | flat / nested = **1.16** |
| hand-written Go, nested, plain `++` | 513–516 | saturation = 1.03 |

So the printer is at parity, and the 1.18× against idiomatic Go is the program's SHAPE, 1.16, and its
counts' semantics, 1.03. The shape is the language's: a loop per file, or a rune loop per chunk, hands
back a tuple, and an `again` after a loop's join point is not built (tables.md §2.5). So the counts and
the cursor ride in one loop with 16 variables, where Go's register allocator keeps a nested loop's 5 in
registers. That cost has a number now, and it belongs beside §6's question.

## 6. A question for hamza: may a `case` arm continue a loop?

`wc` must report a file that will not open and go on to the next. Today only `try`'s success arm continues
a loop (ADR 0041, 0057), and a `case` arm is no tail, so the program held 1 + File as a product by hand.
The algebra offers two answers, each consistent with what is decided:

- **(a) The tail sort closed under the eliminator.** case(e; pᵢ → tᵢ) is a Tail when each tᵢ is, the
  commuting conversion of the loop's step with the sum's eliminator. Each arm runs once, now, as a host
  call's continuation does (ADR 0027), and the core already lowers a `try`'s success arm this way. It
  relaxes ADR 0057's "exactly one arm continues" to "every arm is a tail or leaves".
- **(b) abstract.md §2.4's loop-arm patterns**, decided in the abstract syntax and not built in J. A
  loop's arm is a pattern over its state variables, so a sum is held in a state variable and its tag
  chosen among the loop's own arms. That is `match`, a loop whose arms have patterns. It needs a sum as a
  loop variable, which ADR 0042's representation has at a loop's exit but not across its back edge.

(a) is the smaller and changes no existing program. (b) is the decided abstract syntax and the more
uniform, since one arm grammar makes `case` and `loop` the same choice. **Recommended: (a) now, as the
tail rule's closure, and (b) when J takes loop-arm patterns.** Either would delete `open`'s junk slot.

**The measured cost is a neighbour of this question.** §4's 16% is the join point: an `again` after a
nested loop's value is taken apart (tables.md §2.5, ADR 0031's "not built"). With it `wc` would nest its
rune loop in its read loop, as Go does. That is the bigger of the two, and it is a candidate for the next
plan with a number attached.

## 7. Not built

- `wc`'s body is emitted twice (436 lines of Go), once for standard input and once for files, because
  `main` calls it in each branch with a different table. That is code size, not speed.
- GNU wc's options (`-l`, `-w`, `-m`, `-c`), its column width, and its POSIX locale behaviour.
- The other `unicode` predicates and mappings, each work and none a wall.
