# Can we declare the whole Windows API?

2026-09-06. `gauntlet/stdlib/win32.go`, run against the installed Windows SDK
10.0.26100.0 — 1,753 headers in `um/` and `shared/`.

The companion to [gostdlib-2026-09-06](gostdlib-2026-09-06.md), and it is
deliberately the same three questions asked of a different ecosystem, because
**the interesting result is where the two disagree.** Go's standard library is
values and objects. Win32 is words and handles, and this language has no objects
and nothing but words.

> **FOLLOWED UP 2026-09-08** — [win32-2026-09-08](win32-2026-09-08.md). Two of
> the three ceilings named below were a constant and a hole syntax and are gone;
> a `void` result with an argument was declarable all along, which this document
> refused for 409 functions; and the 665 reachable-only-by-NULL below was a claim
> about a capability nobody had, because the language could not write NULL until
> `(x64.null)`. **72.6% → 76.1% declarable, 33.5% → 34.8% callable, 7,813 →
> 8,809 primitives generated.**


> **72.6% of the flat C API is DECLARABLE and 33.5% is CALLABLE — against Go's
> 70.0% and 19.0%.** Nearly the same declarability, and **1.8× the usability**,
> on the host with no type system, no garbage collector and no expressions.
>
> And it is not a paper result: **the generated declarations build and run.**
> `MulDiv(7, 6, 2)` prints 21 through a mechanically generated template, and a
> program calling `GetCurrentProcessId` and `GetTickCount` assembles under MASM
> and executes.

## 1. The result

```
WINDOWS SDK 10.0.26100.0
  1753 headers, 11575 distinct flat entry points
  (163597 COM/callback method slots counted separately)

FLAT C API: 11575
  declarable as a (prim …):   8400   72.6%
  callable by a program:      3878   33.5%
  and the call says it all:   3591   31.0%

  of the callable, 665 reach it only by passing NULL where SAL says _opt_/_Reserved_
```

**7,813 primitives across 384 headers were generated, and they load as one
target.** Merged with the real `targets/windows/`, a program using them builds
through MASM and runs — which is what makes 72.6% a measurement.

## 2. Why Win32 does better than Go's standard library on the harder question

Declarability is a wash (72.6% against 70.0%). **Usability is not: 33.5% against
19.0%**, and the reason is one sentence.

> **On x86-64 every handle, pointer and integer is one register, so there is
> nothing to be opaque ABOUT.**

The Go survey's dominant gap was *cannot build the argument* — 54.8% of
declarable names — because a `*bytes.Buffer` is a thing the program must obtain
before it can call anything on it. A `HANDLE` is a qword. We can hold it, pass it
back, compare it to 0 and to −1, and store it in a table. `windows-target.md`
already says a table is one register because a fat pointer needs two; **the same
convention is why the API's own currency costs nothing to carry.**

That is the parasite model working at its best, and it is worth stating plainly
because it runs against the intuition that the poorest host is the hardest one.

**And there is no COM here.** 163,597 `STDMETHODCALLTYPE` slots are counted and
excluded: a COM method is a vtable index, which is dynamic dispatch through a
pointer, which is `callbacks.md` tier 3. The flat C API is the whole of what this
measures, and it is what `kernel32`, `user32`, `advapi32` and `ntdll` are.

## 3. SAL, and it is a source of facts we do not read

Win32 is annotated for `/analyze`, and general-purpose.md argues that most of SAL
is buffers and sizes, which our refinements already decide. Counted across 34,140
annotations:

| what it says | count | share |
|---|---:|---:|
| direction: in | 20,528 | 60.1% |
| **nullable** (`_opt_`) | 5,169 | 15.1% |
| direction: out | 3,756 | 11.0% |
| **buffer + size** | 2,886 | 8.5% |
| other | 1,343 | 3.9% |
| **must be zero** (`_Reserved_`) | 407 | 1.2% |
| **value range** (`_In_range_`) | 51 | 0.1% |

**Nullability is the load-bearing one and nobody predicted it.** general-purpose.md
named buffers-and-sizes as the part our refinements already do, and that is 8.5%.
`_opt_` is **nearly twice as much**, and it is what makes this survey's third
number possible:

> **665 of the 3,878 callable functions — 17% — are reachable ONLY because SAL
> says a pointer we cannot build may be NULL.**

`CreateFileW` takes a `LPSECURITY_ATTRIBUTES` we have no way to construct, and
`_In_opt_` says 0 is a legal value. Without reading the annotation the honest
verdict is *unreachable*; with it, the call is a literal 0 away. **That has no
analogue in the Go survey at all** — a Go manifest does not say which pointers
accept nil — and it is the clearest evidence for general-purpose.md's claim that
the type system should be able to reason about the target.

`_In_range_` is only 51 occurrences, so the annotation that maps most exactly
onto our range language is the rarest. **The refinement layer's best fit is the
one Win32 barely uses**, which is worth knowing before designing around it.

## 4. Roadblocks

### 4a. Structs by value — 13.9%, the largest, and the FORMAT's

`POINT`, `RECT`, `LARGE_INTEGER`, `GUID` passed or returned by value do not fit
one register, and there is no product type at the dynamic level to hold one.
This is the single biggest refusal and it is bigger here than anywhere in the Go
survey, because Win32's small-struct idiom is pervasive in the graphics and shell
headers.

`values.md`'s negative product is the near-miss: a two-word struct returned by
value is `rax`/`rdx`, which is **exactly** what multiple return already emits on
this target. So `POINT` returned by value is reachable and `POINT` *passed* by
value is not.

### 4b. ARITY IS A CEILING, and only a host with no expressions has one

Not visible in the Go survey at all, because a Go call is an expression and the
compiler places the arguments.

```
ARITY, of the declarable (widest is 14 arguments)
  more than 4 — some arguments go on the stack:   1770   21.1%
  more than 6 — past the reserved 48-byte home:    587    7.0%
  more than 9 — past the %1…%9 template holes:      86    1.0%
```

Three different limits, and each is a decision written down somewhere:

- **four** is the Win64 ABI's register quota, and the generator handles the rest
  by writing into the home space, as `targets/windows/kernel32.oro` already does
  for `WriteFile`'s fifth argument;
- **six** is `emit/asm.go` reserving 48 bytes at the bottom of every frame, which
  was chosen so a template could write stack arguments without knowing anything
  about the frame it is expanded into. **7.0% of the declarable API is past it**;
- **nine** is `%1…%9`, the template hole syntax itself — 1.0%, and the widest
  entry point in the SDK takes 14 arguments.

The 48 bytes are a constant in the emitter and the holes are a lexer rule. Both
are cheap to raise, and neither is a language question — but they are real
ceilings that only appeared once something tried to declare the whole API.

### 4c. Void results — 3.9%, and it is the `stmt` contract

A `stmt` primitive's value is argument 0 ([target-files.md §3](../../docs/spec/target-files.md)),
and a `void` function has no argument 0 to be. `CloseHandle` returns `BOOL` and is
fine; `Sleep` returns nothing and is not. The fix is a `stmt` whose value is *the
unit*, which the language does not have — the nearest thing is `seq`, which is a
β-redex with an unused binder.

### 4d. Function pointers — 2.7%

`EnumWindows`, `SetWindowsHookEx`, `CreateThread`. And
[callbacks.md](../../docs/spec/callbacks.md) already made the argument that **the
Win32 API is designed for a language without closures** — the environment is
passed explicitly as an `LPARAM` or an `lpParameter` — so these are tier 2, a
function pointer with no free variables, which all four hosts have and which we
refuse today with the wrong message. 2.7% is the price of that refusal, measured.

### 4e. Unresolved typedefs — 6.9%, and it is THIS TOOL, not the language

Named as the tool's residue rather than a finding. It began at **23.5%** and came
down in two steps that are worth recording, because both were the survey
flattering itself in the wrong direction:

- **the legacy `IN`/`OUT`/`OPTIONAL` macros**, which predate SAL and are still
  everywhere, were being read as part of the *type*;
- **typedef chains were not followed** — `MSIHANDLE` is `unsigned long`, and
  `typedef DWORD DEVNODE, DEVINST;` names two aliases in one declaration.

What remains is a genuine long tail: 370 distinct types, mostly Hyper-V, RPC,
smart-card and Direct3D, each appearing a handful of times. A tool that reported
23.5% as *"the language cannot express these"* would have attributed its own
vocabulary to the language.

## 5. And the same roadblock as Go, on a second ecosystem

The first program written against generated declarations was **refused**:

```
(fmt.print-int (pt.GetCurrentProcessId))
```

`emit/interval.go` returns ⊤ for an application of any primitive it does not
structurally recognise, so the process id is unbounded, so `print-int`'s
arithmetic on it cannot be proven in-window, so ADR 0019 refuses the program.
`-checked` is the only way through.

**This is [gostdlib §4b](gostdlib-2026-09-06.md) reproducing on a completely
different ecosystem**, and reproduction is what turns it from an observation into
a finding: *there is no way for a target to say what range a host call's result
lies in*, and until there is, **arithmetic on any host result in any ecosystem is
refused.** A `DWORD` result is `0..4294967295` and the header says so.

## 6. THE BUG: the backend is chosen by the flag string

Found by building, and it is the clearest possible demonstration of the gap
[target-system.md §1](../../docs/spec/target-system.md) names — that a target is
a pair `(B, Δ)` and the pair is implicit.

```go
switch target {          // ← the -target FLAG, not the target's declared name
case "js":      …
case "java":    …
case "windows": …
default:        code, err = emit.Func(…)   // the GO backend
}
```

A target directory named anything but `go`, `js`, `java` or `windows` **silently
falls through to the Go backend.** The declarations load, `tg.Name` is `windows`,
and `cmd/build` emits Go control flow with x86 templates spliced into it:

```
(string=1)sub %!r(MISSING), %!
(MISSING)jno Lok%!u(MISSING)
ud2
Lok%!u(MISSING):) {
                if (mov %!r(string=m2), %!
```

No error and no warning — MASM eventually refuses it, and the message is
`invalid character in file`. The identical target directory renamed to `windows`
builds and runs.

**This makes question 3 worse than "you cannot have both."** A user can point
`-targets` at their own directory, and if they name it anything but one of the
four blessed strings they get silent garbage. The fix is one line — switch on
`tg.Name`, or better, make the pair explicit and have the target *declare* its
backend — and it is a prerequisite for anything in target-system.md §5 or §7.

## 7. What this changes in the specification

Four things turned up that [target-system.md](../../docs/spec/target-system.md)
did not have, and it has been updated:

1. **The backend must be part of the target, not of the invocation** (§6 above).
   §1 said the pair was implicit; it is now recorded as a *bug* with a
   reproduction, and it moves to the top of the build order.
2. **Arity is a target-dependent ceiling.** A backend with no expressions has
   limits a template format has to state, and they are three separate numbers.
3. **SAL is a source of facts, and nullability is the valuable one** — 15.1% of
   annotations, 17% of the callable surface reachable only through it. That is a
   stronger case for reading host annotations than buffers-and-sizes, which was
   the part general-purpose.md predicted.
4. **Opacity is target-relative.** A type that is opaque on Go is a word on
   windows. The Go survey's `obtainable` fixpoint has no work to do here, and
   the same declaration is worth more on the poorer host.

## 8. Reproducing

```bash
go run gauntlet/stdlib/win32.go                # the table above
go run gauntlet/stdlib/win32.go -emit DIR      # 7,813 primitives, 384 headers
```

so a generated module is `win/WinBase`. A real generator should case-fold.
