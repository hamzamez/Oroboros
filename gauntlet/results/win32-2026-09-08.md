# The Win32 ceilings were a constant, a syntax and a missing line

2026-09-08. `emit/asm.go`, `gauntlet/stdlib/win32.go`, `targets/windows/x64.oro`.
The follow-up to [win32-2026-09-06](win32-2026-09-06.md), which measured the
Windows API and named what stopped us reaching the rest.

> **72.6% declarable → 76.1%. 33.5% callable → 34.8%. 7,813 generated
> primitives → 8,809**, across 384 headers → 392.
>
> **And two of the three ceilings it named were not about the host at all.** Six
> arguments was a constant in the emitter. Nine was a hole syntax. Neither was a
> language question, which that survey said in as many words and nobody acted on.
>
> **The largest single correction is one line of target data.** 681 entry points
> — 17% of the callable number — were counted reachable because SAL says a
> pointer may be NULL, and **the language could not write NULL**. `(x64.null)` is
> one `prim`.
>
> **And 409 of the 447 `void`-returning functions were declarable all along**:
> a statement's value IS its first argument, which is how `Sleep` and
> `WriteFile` have been declared by hand since the target was written. That is
> the survey talking about itself for the third time.
>
> **Cost: all 70 emitted files byte-identical.**

## 1. What moved

| | 2026-09-06 | 2026-09-08 |
|---|---:|---:|
| declarable as a `(prim …)` | 72.6% | **76.1%** |
| callable by a program | 33.5% | **34.8%** |
| and the call says it all | 31.0% | **32.3%** |
| primitives actually generated | 7,813 | **8,809** |
| headers covered | 384 | **392** |

The generated count is the number that matters, because it is the one that has
to be true: a name counted declarable and never emitted is a claim.

## 2. A `void` RESULT WITH AN ARGUMENT WAS NEVER A LIMIT

`(prim Sleep (int) int stmt "mov rcx, %1\ncall Sleep" (import "Sleep"))` is in
`targets/windows/kernel32.oro` and always was. `Sleep` returns `void`. **A
statement's value is its first argument, on every target** — that is what `stmt`
means — so a void entry point is declared `stmt` and typed by the argument it
hands back.

The survey refused all 447 of them with the note *"a stmt's value is argument 0;
there is none"*, which is true only when there is no argument either. Split:

```
void result WITH arguments    409   3.5%   <- declarable all along
void result and no argument    38   0.3%   <- genuinely refused
```

**That is the third time a survey's first number was the tool talking about
itself**, after the Go survey scoring methods at 0% by defining an opaque
receiver as unusable, and this survey's own unresolved-typedef residue starting
at 23.5%. The pattern is worth more than any of the three: *when a measurement of
what a language can do is written by the same hands as the language, the first
number is a description of the measurer.*

**Checked rather than assumed**: `gauntlet/stdlib/acceptance/void-stmt.oro`
calls the generated `SetLastError(4242)` and reads it back through
`GetLastError`, which was already declarable. It prints 1.

## 3. THE ARITY CEILINGS WERE A CONSTANT AND A SYNTAX

win32-2026-09-06 named three, and said *"all cheap to raise, none a language
question"*:

| ceiling | what it was | share of declarable |
|---|---|---|
| **4** | the Win64 register quota — the rest go on the stack | 20.2% past it |
| **6** | `emit/asm.go` reserved 48 bytes of home space | 6.7% |
| **9** | the `%1…%9` template holes | 1.0% |

Four is the ABI and is not a ceiling: the generator already wrote
`mov rax, %5 / mov [rsp+32], rax` and always could. Six and nine were ours.

### 3.1 The reservation is per procedure, and that is not tidiness

The obvious fix is to raise the constant to 112 — 32 bytes of home space plus ten
stack arguments, which covers the widest entry point in the SDK. It works, and it
**changed all nine emitted windows programs**: every value slot moves 64 bytes
further from rsp, and x86 encodes a displacement up to 127 in one byte and
everything above it in four. A hot loop that spills would pay, in code size, for
a call it does not make.

So `asmShadowFor` computes it per procedure from the widest prim that procedure
calls, with 48 as a floor. **All 70 emitted files are byte-identical**, and a
procedure that calls `CreateFileA` reserves 64.

**The floor is load-bearing and the reason is that a declared arity is a LOWER
BOUND on what a template writes.** `kernel32.ReadFile` declares three arguments
and its template writes a fourth and a fifth itself. So the floor stays at the
six every hand-written template was authored against, and only a *wider declared*
call raises it.

### 3.2 `%{10}` rather than `%10`

The bare form cannot be extended. `%12` would have to mean operand 12 in a
template with twelve operands and operand 1 followed by the character `2` in one
with fewer — **a template's meaning would depend on its arity**, which is the
kind of context-dependent parse this project refuses elsewhere. So the wide form
is spelled differently: `%{10}`, with `%b{10}` and `%e{10}` for the byte and
dword forms. Pinned by a test asserting that `%12` still means `%1` then `2`
whatever the arity, which is the property that makes it safe to add.

87 generated primitives use it. The widest is `BCryptDecrypt`, at ten.

## 4. AND THE BIGGEST ONE WAS A LINE THAT WAS NEVER WRITTEN

win32-2026-09-06 recorded this as a finding:

> *665 of 3,878 callable functions — 17% — are reachable ONLY because `_In_opt_`
> says a pointer we cannot construct may be 0.*

**We could not write 0.** The language has no null; an integer literal is an
`int`, and the checker refuses it where `ptr` is required —

```
build: main: in argument 4 of win/fileapi.CreateFileA:
       an integer literal is int, but ptr is required here
```

— and the windows target declared nothing. So 17% of the callable number was a
claim about a capability nobody had, and the survey has been counting it since
the day it was written.

```lisp
(prim null (none) ptr expr "xor %er, %er" pure)
```

One line of data, which is the parasite model working: a host capability the
target says how to perform. The count is now real rather than aspirational.

**Found by trying to write the acceptance test**, not by reading the survey —
which is the argument for making a percentage build and run every time.

## 5. The acceptance test

`gauntlet/stdlib/acceptance/wide-call.oro`, and it is one program covering both
halves:

```lisp
(f.CreateFileA "no-such-file-here.txt" 2147483648 0 (x.null) 3 128 0)
```

Seven arguments — three of them at `[rsp+32]`, `[rsp+40]`, `[rsp+48]` — and a
NULL for `lpSecurityAttributes`. It assembles under MASM and prints **2**,
ERROR_FILE_NOT_FOUND.

It was wrong twice on the way, and both are worth keeping. Passing
`(k.GetProcessHeap)` for the security attributes gave **998**, ERROR_NOACCESS —
which is the callee dereferencing argument four, so the wide call was already
working and the argument was simply a lie. Then the literal `0` was refused by
the type checker, which is §4.

## 6. Cost

| | |
|---|---|
| emitted files | **70 of 70 byte-identical** |
| differential suite | 29 cases, four targets, green |
| unit tests, `go vet` | green |
| generated Win32 primitives | 7,813 → **8,809** |

Four tests, three of them verified to fail against their bug: the braced hole,
the bare hole's unchanged meaning, and the per-procedure reservation. The fourth
— that a reservation covers a call under a binder — is a policy test, because the
generic walk reaches it either way.

## 7. What is left, and it is now one thing

**Struct by value: 1,610 names, 13.9%, marked `[format]`.** It is the largest
refusal remaining and the only large one that is not the tool's own residue
(unresolved typedef, 6.9%) or an argued refusal (function pointer, 2.7%, which is
callbacks.md tier 3).

And values.md is the near-miss it has always been: **a two-word struct returned
by value is `rax`/`rdx`, which is exactly what multiple return already emits on
this target.** That is not a plan, but it is the reason this row keeps being the
one at the top.
