## 1. The misreading, and why the number had to be measured

```go
reStruct = regexp.MustCompile(`\}\s*([A-Za-z_][A-Za-z0-9_]*)\s*(?:,[^;]*)?;`)
```

It reads the identifier after any `}` that ends a `typedef` — which is right for a struct and a
union, and wrong for an enum, and the SDK declares **5,178 `typedef enum`s**. So an enum name sat in
the struct table, `classify1` found it there, and every function taking or returning one was refused
as *struct by value*, which the survey blames on the FORMAT.

assessment-2026-09-09 put the enum share at **675**, and products.md and CLAUDE.md repeated it. No
survey output had ever printed that number and no result document recorded it: it was the right
mechanism with an unmeasured count. Measured, it is **665**. Close, and not equal — and *close to a
number nobody measured* is still not a measurement.

## 2. The fix

**An enum becomes its base type.** Two expressions collect every enum name the headers declare — a
`typedef enum [tag] [: base] { … } NAME [, *PNAME…];` and a bare `enum TAG [: base] {` — and record
the C type each is stored as: `int`, unless the declaration names another. Five `typedef enum`s do,
three as `BYTE` and two as `DWORD`, plus 29 C++ `enum class`. A comma-listed `*PNAME` is a pointer.

**It is decided before the naming heuristics, and the order is load-bearing.** `classify1` guesses
shapes from names when nothing else knows: `LP…`/`P…` in capitals is a pointer, `H…` in capitals a
handle. `PROCESS_DPI_AWARENESS` is an enum that starts with P and is all capitals, so the pointer rule
would have claimed it one step after the struct table let go.

**The struct table no longer receives enum names at all**, and the ones it would have are counted —
that is where the 5,831 comes from.

## 3. The signed result

Under Win64 an integer result narrower than 64 bits is in `EAX`, `AX` or `AL`, and the rest of `RAX`
is not part of it. On x86-64 a write to a 32-bit register zero-extends, so an unsigned `DWORD` read as
`RAX` happens to be right and a signed `INT` never is when negative. A `BOOLEAN` is written to `AL`
alone and the upper bits are simply whatever was there.

So the result is now read by its C type, after the alias chain and after an enum becomes its base:

| C type | read as |
|---|---|
| `INT`, `LONG`, `BOOL`, `HRESULT`, `NTSTATUS`, an enum, `int`, `long` | `movsxd %r, eax` |
| `UINT`, `ULONG`, `DWORD`, `COLORREF`, `ACCESS_MASK`, `unsigned` | `mov %er, eax` |
| `SHORT` / `USHORT`, `WORD`, `WCHAR`, `LANGID` | `movsx %r, ax` / `movzx %er, ax` |
| `CHAR` / `BYTE`, `UCHAR`, `BOOLEAN` | `movsx %r, al` / `movzx %er, al` |
| pointers, handles, `SIZE_T`, `LONGLONG`, `LRESULT`, every 64-bit word | `mov %r, rax` |

**Windows is LLP64, not LP64**: `long` is 32 bits here, and so is `LONG`, `HRESULT` and `clock_t`,
which is the whole reason the table exists. `unsigned` is a qualifier the shape classifier strips,
and here it is the whole answer, so it is read before stripping.

**It is safe for a spilled destination, checked rather than assumed.** `movsxd` needs a register
destination and `mov %er, eax` into a stack slot would write four bytes of eight. emit/asm.go hands a
template `rax` as `%r` whenever the real destination is a slot, and stores the full register after —
so both forms always have a register to write.

**The witness can fail, which the old one could not.** `wide-call.oro` called `MulDiv(7, 6, 2)` and
printed 21, and a positive result cannot show this bug. `signed-result.oro` calls `MulDiv(-7, 6, 2)`
and prints whether the result is negative, then the result plus 100:

| | prints |
|---|---|
| before | `0`, `4294967375` |
| after | **`1`, `79`** |

It does not print the negative itself: `win/fmt.print-int` prints a blank line for one, and is within
its rights (refinements.md §6b).

## 4. The same bug, hand-written

`targets/windows/msvcrt.oro` read `rax` after `puts`, `putchar`, five `printf` variants, `atoi`, `rand`
and `clock`, every one of which returns a C `int` or `long`. All ten now sign-extend. `atoi("-5")` was
4,294,967,291; `puts` and `putchar` return `EOF`, −1, on failure, and `printf` a negative count. The
`kernel32` templates were checked and are right as they are: every result there is a pointer, a
handle, a 64-bit value or an unsigned `DWORD`.

**No emitted example changes** — all 9 windows examples are byte-identical before and after, because
none of them calls these ten; the differential suite's windows driver does, and it is green.

## 5. Floating point was declared through integer registers

`FLOAT`, `DOUBLE`, `float` and `double` were in the word table, so the generator moved such an
argument into `RCX` and read such a result from `RAX`. Win64 passes the first four floating-point
arguments in `XMM0`–`XMM3` and returns one in `XMM0`, so **36 declarations would have passed and read
the wrong register**. They are refused now as *floating point*, a format refusal — the template has
to say which `XMM` register, which is exactly what `msvcrt.oro`'s hand-written `printf` does with
`movsd xmm1`. A generator does not make a claim it cannot justify.

## 6. The arity ceiling had gone stale

With enums declarable the widest entry point became **17 arguments**, and the template builder
refused anything past 14 — *"the widest entry point in the SDK"*, true when written. So **six names
were counted declarable and never emitted**, and the discipline this survey was held to on
2026-09-08 — *a name counted declarable and never emitted is a claim* — caught it. The limit was
already stale: `asmShadowFor` sizes each procedure's reserved home from the widest prim it calls, with
no cap, and the `%{10}` hole names any operand. Removed, and **9,427 = 9,427**.

## 7. The enum witness, and the prediction that was wrong

`enum-param.oro` calls `GetFileInformationByHandleEx`, which takes `FILE_INFO_BY_HANDLE_CLASS`:

| class | predicted | the host said |
|---|---|---|
| 0, `FileBasicInfo`, no buffer | `0`, then **6** `ERROR_INVALID_HANDLE` | `0`, then **24** `ERROR_BAD_LENGTH` |
| 9999, not a class | — | `0`, then **87** `ERROR_INVALID_PARAMETER` |

**The prediction was wrong, and the way it was wrong is the evidence.** The function validates the
buffer length *for the class* before it looks at the handle, so 24 already says the class arrived. The
second call makes it a comparison rather than a reading: two enum values, two different errors, so the
callee dispatched on the enum we passed. The program's comment records both, and records the
expectations as observed.

## 8. What it leaves

**A DLL the build does not link.** `build.bat` links `kernel32`, `msvcrt`, `ucrt` and `vcruntime`, and
nothing else — so a generated declaration for `user32`, `gdi32` or `advapi32` is declarable, counted
callable, and cannot link. The first choice of enum witness, `GetAwarenessFromDpiAwarenessContext`,
lives in `user32` and is how this was found. **Unmeasured and named**: the survey cannot map a header
to its DLL without reading the SDK's import libraries, and the link line is hard-coded in the emitter
rather than declared by the target — which is itself the kind of fact this project keeps in data.

**Struct by value is 945 names, 8.2%**, and is now what it was always said to be: aggregates. That is
the research the assessment puts after the tooling tests. *(It is **140** and 1.2% —
structval-2026-09-12 did that research and found 805 of these are pointer parameters this tool
misread. "What it was always said to be" was still wrong.)*

**And the tooling still has no tests.** Every correction here was found by reading and running by
hand. assessment-2026-09-11 item 2.
