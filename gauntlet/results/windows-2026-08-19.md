# windows target vs hand-written x86-64, 2026-08-19

The fourth target emits assembly. The bar is assembly a person wrote.

## What was measured

100 rounds of a 200000-element sieve of Eratosthenes, summed and printed in decimal. Both
programs allocate with `VirtualAlloc`, mark with byte stores, count with byte loads, and print
through `WriteFile`. Both print `1798400`.

- generated: `examples/native/sieve-win-bench.oro` → `build -target=windows`
- hand-written: `gauntlet/windows/sieve.asm` → `ml64` + `link`

The hand-written reference is written **the way a person writes it**, not in the shape the emitter
produces. Specifically it does two things the emitted version does not:

- `i*i` is computed once per outer iteration and kept in `rdi`, serving both the guard and the
  inner loop's starting value. The emitted version computes it twice — there is no
  common-subexpression elimination anywhere in the pipeline.
- The decimal conversion divides **once** per digit. The emitted one divides twice, because one
  `idiv` yields quotient and remainder together and the language has no product type to receive
  them with.

## Wall clock, 9 runs each, interleaved (ms)

```
hand  263 269 270 270 273 276 281 281 282
gen   260 261 262 264 265 268 268 273 312
```

| | hand | generated | ratio |
|---|---|---|---|
| minimum | 263 | 260 | **0.99×** |
| median | 273 | 265 | **0.97×** |

**Parity.** The measured difference is 3%, against a documented ~15% noise floor on this machine
(CLAUDE.md). Nothing may be concluded from the sign of it, and in particular the generated code is
*not* faster; it is not distinguishable.

Process startup is included in both and is the same for both.

## Artifact size

| program | generated | hand-written |
|---|---|---|
| hello | **2560** | 2560 |
| sieve benchmark | 3072 | 2560 |

`hello` is byte-identical in size. The sieve's 512 bytes are the target's 256-byte `__buf`
crossing a section boundary; `__buf` is a target declaration, not a compiler cost, and the
hand-written reference declares a 32-byte one.

Target storage is emitted only when the code names it. Before that check, a 4096-byte buffer put
`hello` at 6656 bytes for a buffer it never touches.

## The inner loops

Crossing loop, **emitted**:

```asm
Ltop9:
        cmp r12, 20000
        jge Lnext10
        mov byte ptr [rbx+r12], 1
        add r12, rsi
        jmp Ltop9
```

Crossing loop, **hand-written**:

```asm
inner:
        cmp     r12, N
        jge     nexti
        mov     byte ptr [rbx+r12], 1
        add     r12, rsi
        jmp     inner
```

Instruction for instruction, including the register choices. The counting loop matches likewise.

Four things were needed to get there, and each was a measurable gap before it existed — they are
listed in [windows-target.md §5](../../docs/spec/windows-target.md). The two that mattered most:

- **`(jump …)`**, which lets a target declare the condition code for a predicate so a guard
  becomes `cmp` + `jcc` instead of `cmp` + `setcc` + `cmp` + `jcc`. Its optional second form
  fuses the sieve's byte test into a single `cmp byte ptr [c+i], 0`.
- **Ordered back-edge assignment**, which turns `(again (add i 1) (add acc i))` from three moves
  plus two adds into two adds, by assigning `acc` before `i` rather than staging both.

## What this does not measure

Floats. The target declares the SSE2 scalar set and `f64` values live in xmm6-xmm13, but no
benchmark exercises them, and `msvcrt.printf1f` — which has to put a double in *both* xmm1 and rdx,
per the Win64 variadic convention — is declared and untested.
