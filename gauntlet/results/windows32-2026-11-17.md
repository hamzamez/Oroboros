# The second triple as a target: `windows32`, the address space on bytes, and a NUL nobody wrote

2026-11-17. Item 4 of [assessment-2026-11-16](../../docs/assessment-2026-11-16.md) §5, step 2 of
[ADR 0122](../../docs/decisions/0122-the-windows-family-is-a-fibration-and-a-triple-is-a-model.md),
after step 1 (commit `2588d6a`, the family as a fibration: `targets/win32/` the base, `windows` its
x86_64 member). hamza, on [triple-research.md](../../docs/triple-research.md) §6: "Go with your
recommendations on D1–D7".

**`windows32` is a target**, i686-pc-windows-msvc. Of the differential suite's 74 cases, 66 pass on
it, against 63 through the research's scratch copy. The other 8 are D2's (4), D6's (2) and the
harness's (2). Built on the way:
- D3, the address space as a bound on bytes;
- D1's data-model sets for kernel32's `SIZE_T`;
- the sentinel compared at pointer width.

Two defects were found and fixed:
- **a `where` could not read an imported name**;
- **a wrong answer on both triples**: a raw region's zero byte was written at a layout the table did
  not end up with, so a C string ran into the heap.

## 1. The algebra

- **A member is a model of what the base leaves open** (ADR 0122 item 1). Each member's directory
  states its four parameters, and nothing else differs:

  | | `windows` | `windows32` |
  |---|---|---|
  | triple, toolchain (`windows.oro`, `windows32.oro`) | x86_64-pc-windows-msvc, `vcvars64` | i686-pc-windows-msvc, `vcvars32` |
  | data model (`model.oro`) | `SIZE_T = 0..2^63-1` (LLP64, the word's naturals) | `SIZE_T = 0..2^32-1` (ILP32) |
  | address space (`space.oro`) | `max_bytes = 2^47`, `max_len = 2^47 - 9` | `2^31`, `2^31 - 9` |
  | the ISA's operations | `x64.oro` | none yet (D4's `x86.oro` waits for D2) |

  The build line is `{{VCVARS}}` and `--target={{TRIPLE}}`, both the member's (`emit.buildScript`).
- **D3: the address space bounds bytes.** A region of a table of n elements of w bytes is
  b(n, w) = n·w + 9 bytes (`lang.bytes`), and the OS serves b only if b ≤ A_t. So the bound is a
  precondition of Σ_OS's operations, `region`, `region_raw` and `zero`: `where b <= max_bytes()`.
  `allocate` binds b once and tests it, so the guard and the obligation are one atom of the
  decision:

  `allocate(n, w) = let b = bytes(n, w) in if b ≤ max_bytes() then region(b) else trap`

  On i686 this is what makes the byte count passed to kernel32's 32-bit `SIZE_T` a theorem: from the
  guard, b ≤ 2³¹ < 2³². Before, `max_len` bounded *elements*, and a word table's bytes could reach
  8·(2³¹ − 9) + 9 > 2³².
- **The sentinel at pointer width.** `ptrtoint` of an ILP32 pointer to i64 zero-extends, so
  `(HANDLE)−1` read as 2³² − 1, and `open`'s `llvm.address(h) == -1` was false on a failed
  `CreateFileA`. A pointer's all-ones is a property of the pointer, not of an integer of fixed
  width: `llvm.is_all_ones(p)`, `icmp eq ptr p, inttoptr (i64 -1 to ptr)`. The constant truncates
  to the pointer's width, so the test is the same on both triples.
- **A header's formula is resolved as its body is** (`core.qualifySig`). `alias.f` through
  `use M as alias` is M's f. Before, `readall`'s `where sz <= los.max_len()` kept `los.max-len`, a
  name nothing defines, so the obligation could be neither proven nor refused. This rule is not the
  triple's, and it held on x86_64 too.
- **A raw region's zero byte at both layouts** (W15). A table born full takes a region with no zero
  fill (ADR 0097), and the allocator writes the one byte past the elements, a string's NUL
  (ADR 0117). The width w it is asked at is the table's type at the storage pass. Its final layout
  b, ElemBytes of its IR_P type, is fixed only after every round of ι and the decision, and facts
  only refine a range, so b can only narrow: **b ∈ {1, w}**. Writing the zero at n·w + 8 is
  therefore right only when b = w. The allocator now writes it at n·w + 8 and at n + 8:
  - laid out at w, n + 8 lies among the elements, all of which are written after (born full);
  - laid out at 1, n + 8 is the NUL.

  `reuse_raw` writes the second zero again, since its predecessor's elements overwrote it, and
  `reuse_fit_raw` writes both. W15, `ir.CheckStorageLayout`, refuses a final layout outside {1, w}.
  It runs in ToP after Finalize and reads the width from the statement (`Stmt.RawW`), since value
  numbering is not stable across the passes.

## 2. The witnesses

- **`TestARawRegionsZeroByteIsAtItsLayout`** (cmd/build, new):
  - **the property**: `crc32` of one file, reached by paths of six lengths (both parities), on
    `windows` and `windows32`, must equal Go's IEEE CRC of that file;
  - **the planted fault**: `PlantW15Strict` asks b = w exactly, without the second zero, and the
    corpus's narrowed byte tables are reported. So the second zero is load-bearing.
- **`TestAWhereReadsAnImportedName`** (cmd/build, new):
  - **the property**: `take(n ∈ 0..2^47-9) where n <= los.max_len()` builds and runs at 5, and at
    2⁴⁷ − 8 is refused as false at the call;
  - **the planted fault**: `PlantSigAliasUnresolved` leaves the name as written, and the false call
    is no longer decided false.
- **The suite on the triple** (`experiments/i686/run32.go`, which now builds a named target through
  `$I686_TARGET`, run on the real `targets/`), 74 cases:
  - **66 pass**, each printing its `// expect:` line on 32-bit Windows, exit 0. Three are new since
    the research:
    - `read-loop`: D3, since `readfile`'s bound is now `max_len`, not the literal 2⁴⁰;
    - `big-kara` and `big-sqr`: the step-1 split already keeps `x64.oro`'s `llvm.x86.addcarry.64`
      from windows32, so `nat.add` takes the generic full adder, which i686's backend expands.
  - **4 are D2's**: `big-fib`, `big-nat-div`, `big-nat-ops` and `big-render` are refused, not
    crashed: K(ℕ\*)'s digit division is a 128-by-64 `udiv` whose double word no realization on
    i686 holds. They wait for the digit base per triple.
  - **2 are D6's**: `bits-edges` and `word-wide` link against `__allrem` and `__alldiv`, the 64-bit
    division helpers.
  - **2 are the harness's**: `u128-fact` and `u128-ops` skip windows on x86_64 too, because Go's
    `math/bits` is not bound.
- **The research's "found in passing" items 1 and 2 are closed**: the sentinel (item 1), and
  `crc32` and `fnv` answering *cannot read that file* (item 2), which is the NUL below and not the
  sentinel.

## 3. What failed first

0. **A wrong answer on both triples, older than this step.** On i686, `crc32` could read some paths
   and not others; the failing ones had an even total path length. The same happened on x86_64 once
   looked for.
   - **The cause**: text_v's copy of the path, a table made by a realized term in a later round, was
     asked at w = 8 and laid out at 1. Its zero was at 8n + 8, and the byte after the path was the
     heap's, so `CreateFileA` read a path that ran on.
   - **Why it slipped**: the corpus's file programs are run on paths whose next heap byte happened to
     be zero.

   Four fixes failed before the one built:
   - removing `finalTableTypes`' numbering guard: the copy is numbered otherwise;
   - pairing tables in lockstep: this under-allocated `fib`'s `nat.add` digit buffer, an overflow,
     and was reverted;
   - a claim in text_v: ascriptions are erased before lowering;
   - a zeroed region wherever the types were not yet final: W15 still fired on round-0 tables, whose
     layouts later rounds also narrow.

   The derivation, b ∈ {1, w}, is what settled it: since the layout can only narrow and only to 1,
   one more byte covers every case.
1. **The roundtrip step limit** after the `where`s were added. Each `bytes(n, w)` written twice was
   two atoms, and the decision could not tie the guard to the obligation. Fixed by binding b once in
   `allocate`, guarding `zero` the same way in `reuse` and `reuse_fit`, and resolving the alias
   (`los.max-len` was the unresolved name).
2. **numberedHoles and WriteProgram tested the name `windows`**; they now accept the family's names
   (step 1's commit).
3. **A `git checkout` of `lang.oro`** reverted this step's guards with the experiment's edits; they
   were restored by hand and re-checked by the full suite.
4. **W15 keyed by value** answered about renumbered values. The width moved onto the statement.

## What was not built

- **D2** (the digit base per triple, amending ADR 0106) and with it D4's `x86.oro`: the four
  K(ℕ\*) cases.
- **D6**, `/` and `%` on i686 as a realization over `divl` (Knuth's D in the language): the two
  link failures.
- **D1 by header** (W1): only kernel32's four `SIZE_T` functions take the data model's set; the
  `windows/basetsd` module and the rest of the type names come with TinyRetroPad's surface.
- **D5**, i32 scalars.
- **windows32 in `cmd/check`'s differential step**: it runs through the experiment's runner, not
  the suite's four targets.
- **The second zero only where b may narrow**: an element whose sort is ℤ and w = 8. Elsewhere
  b = w is a theorem of the sort, and one store would do.
- **The guard proven at the site** where a fact bounds a word table's length by (A − 9)/w rather
  than by `max_len`: `fact max_len` is uniform in w, so 8·max_len + 9 > A and every word table's
  guard is printed.
- **The reuse token's size fact** (`reuse`'s guard on `zero`), owed as a missing proof.
